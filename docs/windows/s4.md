## 三、菜单系统（S4-A）

### 3.0 先撤销一个裁决

`design.md` §1.7 第五项写过：

> **主菜单栏本身**：同上，不做。那 103 条命令通过命令面板（S3 块 E）和右键菜单到达。

**用户 2026-09-01 当面推翻了它。** 原话：「缺少重要的菜单栏……
windows 下没有 head bar 和菜单栏，可以在最左侧加一个菜单按钮，
点击后可以展开多级菜单」。

**原裁决错在哪，要说准。** 它的推理是「Windows 终端没有菜单栏」——这句话本身是对的，
Windows Terminal 确实没有。**但它回答的是「要不要一条横贯窗口顶部的 menu bar」，
而用户问的是「那 96 条命令，一个没被人告诉过的人怎么找到」。**
这正是 §1.7 自己量出来的那个维度——可发现性——**而当时那一节的结论是
「模型里没有这一栏」，紧接着下一段就用「不做」把它填平了。**
同一份文档里，隔了三十行。

### 3.1 主菜单按钮：放哪，长什么样

**放在标签条最左端，x = 0。** 用户指定的位置，而且有两条它自己的理由：

1. **它不动。** 放在最后一个标签右边（Windows Terminal 的 `⌄` 那个位置）
   会随标签增减而移动，标签溢出时还会被挤走。一个每次都在别处的入口，
   等于每次都要重新找。
2. **右端是标题栏按钮的地盘。** 我们用的是标题栏内嵌标签条
   （`shell.rs` 的非客户区自绘），右端 138px 归最小化/最大化/关闭。
   Windows Terminal 的 `⌄` 不在右端，正是因为这个。

**尺寸与画法**（都用 `strip.rs` 已有的 token，不要新造一套）：

| | 值 |
| --- | --- |
| 宽 | `46 * scale`，高 `strip_h(scale)` |
| 图标 | Polter 的 `≡`（三横），线宽 `1.0 * scale`，居中 |
| 常态 | 不画底 |
| 悬停 | 与标签悬停同一个填充色，圆角 `4 * scale` |
| 按下/菜单展开中 | 与选中标签同一个填充色 |
| 键盘 | `Alt` 单击或 `F10` 打开（Win32 惯例），方向键导航由 `TrackPopupMenu` 白送 |

**标签的第一个槽位要整体右移这个宽度。** `strip.rs:84` 的 `layout()` 目前从 0 起算，
新增一个左内缩参数；`is_interactive` 和 `Hit` 都要跟着改，
**`Hit` 要加第六个成员 `Menu`**——像块 B 当初加 `New` 那样。

### 3.2 菜单树：结构照抄 macOS，动作全部来自核心

> **订正（2026-09-02，W1 报的，我逐条核过）**：本节初稿写错了四个动作名——
> `next_search_result` / `previous_search_result` / `toggle_surface_read_only` /
> `poltergeist_conversations`，`src/input/Binding.zig` 的 93 个 Action 成员里
> 一个都没有。照原文写会得到四条静默失效的菜单项，**正是本节下一段警告的那种**。
> 下面的表已改成核心的真名。**这份文档不是动作名的依据，`Binding.zig` 才是。**

**这是本块唯一的硬约束：菜单里的每一条都必须是核心已经发布的命令。**
和 `ctxmenu.rs` 一样，标题可以是人话，动作字符串必须能被
`ghostty_surface_binding_action` 认出来。一条认不出来的动作**不会报错，只会静默什么都不做**——
所以要有编译期的 `assert_actions_exist` 测试**和**运行期的计数日志，两道都要。

根菜单（六个分组 + 尾部两条）：

### 3.3 三处右键菜单

| 位置 | 现状 | 要做什么 |
| --- | --- | --- |
| **surface 上** | `ctxmenu.rs` 已有 13 条，走 `WM_CONTEXTMENU` | 对着 `SurfaceView_AppKit.swift:1585` 补齐；加只读/改标题 |
| **标签上** | **没有。用户报的缺陷。** | 见下 |
| **标签条空白处** | 没有 | 新建标签 / 重开关闭的标签 / 命令面板，三条 |

**标签右键菜单**，照 macOS 的 `configureTabContextMenuIfNeeded`
（`TerminalWindow.swift:717`）逐条搬，**它是这个仓自己写的，不是 AppKit 白送的**：

```
关闭标签              close_tab:this
关闭其他标签          close_tab:other
关闭右侧的标签        close_tab:right
移到新窗口            move_tab_to_new_window
---
重命名标签…           （复用 strip.rs 已有的就地改名，double_click 那条路）
标签颜色 ►            （八色，当前色打勾）
---
设为总管              poltergeist_supervisor      ☑ 当此终端已是总管
监督此终端            poltergeist_toggle_watch    ☑ 当已被监督
禁止 agent 进入       poltergeist_toggle_shielded ☑ 当已护盾
```

**三条 agent 项必须带勾选态**，理由 macOS 侧的注释已经写了，照抄：
一个点过的项要和没点过的长得不一样，否则唯一确认上次点中没有的办法是再点一次。

**关键的一条：菜单作用于「被右键的那个标签」，不是当前焦点标签。**
macOS 那份代码专门为这件事绕了一圈去拿 `targetController`。Windows 侧同理：
`WM_CONTEXTMENU` 的坐标先过 `strip.rs` 的命中测试拿到 tab index，
**这个 index 要一路传到动作执行处**，不能中途退化成 "current"。
**这是本块最容易写错、而且错了看起来完全正常的一处**——你右键第三个标签选「关闭」，
关掉的是第一个，而你多半会以为是自己点错了。

### 3.4 可发现性：三件不写代码就不存在的事

1. **每条菜单项要显示快捷键**（`\t` 后面那半，`ctxmenu.rs` 已经这么做了），
   **而且必须从核心的绑定表取，不能手写常量**。手写的会和用户改过的配置不符，
   且不会有任何东西报错。
2. **同义词。** `windows/host/src/synonyms.txt` 已有 24 行。菜单用的是人话
   （「查找…」），核心叫 `start_search`——菜单这边是对的，**要保证的是反过来
   在命令面板里搜「查找」也能搜到**，这是 §1.7 量出来的那个 20 条改名问题。
3. **不可用的项灰掉，不要隐藏。** 一个消失的菜单项和一个从来不存在的菜单项，
   用户分不出来；一个灰掉的项告诉他「有这个功能，现在不能用」。

### 3.5 验收判据（可观察，且带地板）

> **订正（2026-09-02，W1 实测）**：「约 41 条」是我数漏了三个子菜单的内容
> （查找 4 / 选择分屏 4 / 调整分屏 5，共 13 条）。**叶子项实测 55 条**（先测得 54，后来「改标签标题…/改终端标题…」补成两条），
> 其中动作串 55 个、`unresolved=0`。根菜单上一眼看见的是 **8 项**
> （6 分组 + 设置… + 关于），和 `items=8` 那行对得上。**M3 要逐条点的是 55 条。**

> **订正二（2026-09-02，真机跑 M3 时暴露）**：M3 原写「每条都有 `ok=1`」，
> **这条判据在构造上不可能通过，而且是我写的。** `ghostty_surface_binding_action`
> 返回 false 有两种含义——**解析不了**，和**认得但此刻没什么可做**。
> M1 已经读到 `0 unresolved`，54 个名字核心全认得，**所以 ok=0 只可能是后者**：
> 没有选区时复制、没开查找条时 `end_search`、没关过标签时 `undo`。
> 实测 40 ok / 11 failed / 3 skipped，11 条里至少 7 条是这一类。
> **一个数把「动作被派发」和「动作做成了事」压成了一件事。**
> 判据已改成四个数，并加了一条翻转地板——**否则「状态依赖」是一句不可证伪的借口。**

**判据行一律用 `logf!` 打，不许用 `println!`。** `main.rs:506` 的 `log_line`
对 stdout 和日志文件各 flush 一次，所以用它打的行是即时可见的；
`println!` 在 stdout 被重定向到文件时是块缓冲（约 8KB），
**读到空文件既可能是没打、也可能是没 flush、还可能是进程根本没起来**，三者分不开。
（`main.rs:246` 那条注释是唯一的例外，看守狗不能走 `log_line`，因为它会阻在自己的
`println!` 的全局锁上。）

宿主要打这四行日志，**每行自足**（`[palette]` 那三行的形状）：

```
[menu] built 6 groups, 41 items, 0 unresolved
[menu] root shown at 0,30 items=8
[menu] pick "复制" -> copy_to_clipboard ok=1        ← 前提：此刻有选区
[tabmenu] shown for tab 3 of 5 at 412,18 items=10
```

判据，逐条：

> **M0（W4 于 2026-09-02 加，排在全部判据之前）**：每个今晚新增或改动的文件，
> 先注入一行**语法错误**看构建变红、再注入一个**类型错误**看它走到类型检查
> （语法错误只证明文件被 parse 到了）；撤销后 `touch` 再编，确认回绿。
> **改动过测试的，`cargo build` 绿不算数，要 `cargo test --no-run` 绿**——
> `cargo build` 不编译 `#[cfg(test)]` 代码，而测试编不过时目录里那个同名
> 测试 exe 照样在。**测试 exe 的体积变化本身是一个读数**：它不涨，多半是
> 你的测试根本没进去（实测 10,090,367 → 23,792,825，多出来的一倍就是那批）。

| # | 判据 | 地板（不满足就说明判据本身瞎了） |
| --- | --- | --- |
| M1 | 启动日志有 `[menu] built …, 0 unresolved` | **故意写一条不存在的动作，`unresolved` 必须变成 1** |
| M2 | 点最左端按钮，出现根菜单，日志有 `[menu] root shown` | 点标签条别处不出现 |
| M3 | 55 项逐条派发，汇总行四个数：`N ok, N nothing-to-do, N failed, N skipped`。**`failed` 必须是 0**——那一档只留给「不依赖当前状态却仍返回 false」的 | **挑一条 `nothing-to-do` 的，把它的前提造出来再跑一次，必须变成 `ok`**（最省的是复制：先选中一段文字）。一条都翻不过来，「状态依赖」就还是借口不是读数 |
| M4 | 右键第 3 个标签，日志 `for tab 3 of 5` | **右键第 1 个必须是 `tab 1 of 5`**——这一条是 3.3 那个陷阱的唯一探针 |
| M5 | 右键第 3 个标签选「关闭标签」，剩下的是 1/2/4/5 | 缺了这条 M4 只证明日志对，不证明动作对 |
| M6 | 「监督此终端」在已被监督的终端上带勾 | 在没被监督的终端上**不带勾** |
| M7 | 未实现的「检查更新…」是灰的，不是没有 | — |

**M1/M3/M4 的地板必须真的注入一次再撤掉**，不是想一想觉得会过。
这是 `status.md` 第七节第 4 条：「如果被测的那个东西是错的，这条判据会看见吗」。

## 四、今晚做什么，不做什么

### 5.1c ⭐ **cmd 不需要集成脚本：`PROMPT` 环境变量就是注入点**（2026-09-02 实测）

`PROMPT` 支持 `$E`(ESC) 和 `$P`(当前盘符与路径),所以
```
set PROMPT=$E]7;kitty-shell-cwd://localhost/$P$E\W4-$P$G
```
**每画一次提示符就发一条 OSC 7**。真机读数:`cd` 两次 → 两条 `[action] pwd … attached=1`,
路径跟着走。**一个变量、零文件、零 profile**,而「往子进程环境里塞变量」正是
`shell_integration.zig` 本来就在做的事。

三条实测出来的形状,写脚本前必须知道:
· **`file:///C:/…` 会被拒**（`host` 为 null,`stream_handler.zig:1069`）。
  **必须带主机名**,用 `kitty-shell-cwd://<host>/…`——和我们自己 bash/zsh 那两份一致。
· **`localhost` 会短路 `isLocal`**（`hostname.zig:15`),真机器名走逐字节比较。
  **探针先用 `localhost`**,机器名对不对是另一个问题、另一步。（实测真机器名也过。）
· **收尾只能用 `$E\`(ST),不能用 BEL**——cmd 的 `PROMPT` 转义表里没有 BEL,
  和 bash/zsh 用 `\a` 不一样**是被迫的,不是笔误**。

### 5.1b ⭐ **Windows 上没有任何一个原生 shell 有集成——这一条比它挡住的功能大**

`src/shell-integration/` 出厂带五份:**bash / zsh / fish / elvish / nushell**。
**没有 PowerShell,没有 cmd。**

后果不是「少一个可选功能」,是 **`GHOSTTY_ACTION_PWD` 在 Windows 的默认 shell 下
永远不会到达**。2026-09-02 真机实测:在 cmd 里 `cd` 两次,屏幕上目录确实变了,
整场会话 PWD 动作**零条**。

已知被它挡住的:

| | 症状 |
| --- | --- |
| 「重开关闭的标签」 | 关掉的标签**根本不进栈**(`no cwd known`),菜单项永远是灰的 |
| 新标签继承当前目录 | 未验,但走同一个来源,多半同样不工作 |

> ⚠️ **而「没有目录就不记」这个行为是对的,不要改。**
> `ClosedTabs.swift:47` 的 macOS 版逐字是同一条
> (`guard let directory, !directory.isEmpty else { return }`)。
> **在 macOS 上它不咬人,只是因为那五份集成覆盖了 macOS 用户实际用的 shell。**

> ⚠️ **同一个用户可见现象,两个完全不同的原因**:菜单项永远灰着,
> 可能是「关闭栈写了但没接上」,也可能是「接上了,而它如实拒绝记一个不知道目录的标签」。
> **界面上分不出来**——分出来的是 `[reopen] not remembering … no cwd known` 那一行。

**要做什么**:给 PowerShell 写一份集成(cmd 几乎没有可注入的点,
现实的做法是 PowerShell + 记录 git-bash/WSL 是可用的真实路径)。
这不属于 S4-A,是一条独立的账。

#### B1-e 的反方向：**它治好了「过早退出」，留下了「该退不退」**

**这一条今天是红的，写在这里是因为它此前只活在一次对话里。**

判据 E1–E7 全部是围绕「关最后一个标签**不要**退进程」写的，而实现也确实做到了。
真机复现出来的是它的另一头：**关最后一个窗口的最后一个标签，进程不退**——窗口
全没了，进程还在。当时机器上留下过一个无窗口的残留进程；那台机器随后被收拾干净，
所以下面要老实标清楚哪些是读到的、哪些是没读到的。

| | |
| --- | --- |
| **读到了** | 现象在最新版复现；现场是一个「没有窗口但还活着」的进程 |
| **没读到** | 走的是四条关闭路里的哪一条；日志三行的原文；残留进程卡在哪 |

**为什么那三行是先决条件、而不是补充材料。** `winid::window_finished(frame)` 是
全树唯一的 `PostQuitMessage` 落点，设计是只有窗口数减到 0 才发。于是
`destroyed; N window(s) left`、`-> quitting`、`[main] exiting` 三行把这条红劈成
两个**完全不同**的缺陷：

- **没数到 0** —— 登记表里还挂着一个已经销毁的窗口。缺陷在记账。
- **数到 0 了却没退** —— 该发的发了，消息循环没走掉。缺陷在退出路径。

两者的修法互不相干，而**猜错方向的那个修法，看起来也会像修好了**：随手在别处补一
次退出，能让现象消失而记账依然错，下一个多窗口场景再把它翻出来。所以在拿到那三行
之前不要动手。

**这一格的教训与 B1 其余五格是同一条**：判据写在实现之前是对的，但 E1–E7 全部朝
一个方向问。**一个只朝一个方向问的判据集，会把它的反面留在暗处，而且全绿。**

### 5.1e `ghostty.ps1` 两条分支的验证状态：**5.1 真机已验，6+ 引擎侧已验、Windows 侧仍是空的**

那个二选一的守卫，两支现在都被执行过，但**执行它们的不是同一种机器**，
所以两支能证明的事情不一样。

| 分支 | 条件 | 状态 | 在哪验的 |
| --- | --- | --- | --- |
| 5.1 回落（包 `prompt`） | 属性不存在 | ✅ 含守卫取反地板 | Windows 真机，Windows PowerShell 5.1 |
| 6+ （`LocationChangedAction`） | 属性存在 | ⚠️ **引擎侧已验、Windows 侧未验** | macOS 上的 pwsh 7.6.5 |

**6+ 那一轮拿到的读数**（`-File` 非交互跑法，仓库文件全程只读，
取反的副本生成在 scratchpad）：

```
HOOK=event                      走了这一支
LOCATION_ACTION_SET=True        钩子真的挂上了,不只是标记写对了
OSC 7 = 3 条 / 3 个不同目录      读字节,不读日志;第三次回到同一目录没有第四条(去重成立)
PROMPT_BEFORE == PROMPT_AFTER   逐字相同(-ceq),len=211
```

**`LOCATION_ACTION_SET` 是必要的第二个读数**：`HOOK=event` 只说明
**代码走了那条分支**，不说明**那一行赋值成功了**——而 115 的整个缺陷
正是「走进了分支、赋值炸了」。

**地板里真正的本体是那个没变的信道**：

| | 原样 | 取反 |
| --- | --- | --- |
| `HOOK` | `event` | `prompt` |
| `LOCATION_ACTION_SET` | `True` | `False` |
| `PROMPT_IDENTICAL` | `True` | `False` |
| **`HAS_EVENT_PROPERTY`** | **`True`** | **`True`** ← **不变** |

属性在两次里都确实存在，**变的只有守卫**——所以这组读数排除的不是
「两次环境不同」，**而正是「守卫在挑」**。

**模块注释里那句 `on 6+ this file never touches the user's prompt`，
至此从一句断言变成一条读数**，而且取反那次 `PROMPT_IDENTICAL=False`
证明这个探针有分辨力，不是一个恒真的断言。

#### ⚠️ 两处会被读宽的，先挡住

1. **取反那一轮 OSC 7 只有 1 条，不是 3——那不是 `prompt` 支坏了。**
   `-File` 是非交互的，`prompt` 函数根本不会被调用，所以那一支在这种跑法下
   只有启动那一条。**`prompt` 支的 `cd` 追踪是在 Windows 真机 5.1 上验的
   （三次 `cd` 三条 pwd）**——两条证据来自两台机器、两种跑法。

2. **这是 macOS 上的 pwsh。** 能力检测、事件挂载、`cd` 触发、OSC 字节生成
   都是 PowerShell **引擎**行为，与操作系统无关，所以是真验;
   **但「Windows 上的 pwsh 7 会不会有别的行为」这一格仍然是空的**，
   它和 ConPTY 那一格是**两件不同的未验**，不要合并成一句「Windows 未验」。

### 5.1f ⚠️ Windows 上没有任何写法能给 `command` 传一个带空格的参数

真机验 111 的 P7 时撞到的,**而挡住半轮的不是这个限制,是一句指错路的注释。**

| 写法 | 怎么切的 | 能不能表达 `"a b"` |
| --- | --- | --- |
| `command = x -a "a b"`（默认 shell 形） | Windows 上 `tokenizeAny(v, " \t")` | ❌ |
| `command = direct:x -a "a b"` | `splitScalar(str, ' ')` | ❌ |

**两条路都不行,而 `Exec.zig` 原来的注释把用户指向第二条**,说它
`takes an argv array as-is`——那句话对**程序里构造**的 `Command` 成立,
对**配置文件里写**的不成立(`config/command.zig` 的 `parseCLI` 同样朴素按空格切)。

**代价是可测量的**:真机上那一轮的读数是「参数没生效 ＋ `shell could not be
detected`」两件事同时发生,而验证者**判不了是自己写法错还是缺陷**——
因为仓库里唯一一句谈这件事的话告诉他那样写是支持的。
**一句指错路的注释,比没有注释贵**,贵在它把「不知道」变成了「知道了一件错的」。

已做的两件:注释改成说出实情(并写明它原来说了什么);
`config/command.zig` 里加一条**断言这个限制**的测试——
`direct:cmd "a b"` 切出 **3** 个参数,引号是普通字符。
**写成测试而不是只写注释**,是因为原来那句就是注释,而**错的散文安静地一直错着**;
哪天有人给这个解析器加上引号支持,这条测试会红,**那正是该被发现的时刻**。

**没做的**:让它真的支持引号。那是核心行为、影响所有平台,不在这一档里。
所以这条今天是一个**已知且已写下的能力缺口**,不是缺陷单。
