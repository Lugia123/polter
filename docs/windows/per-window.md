# 什么是「每个窗口一份」的，什么不是

**这一篇写给下一个在 Windows 宿主里加状态的人。** B1 那六格把一个单窗口的宿主
拆成了多窗口，过程里反复用到同一条判断，而那条判断只活在过程消息里，没有落到
任何文件。它比 B1 本身有用，因为它对**还没写的代码**也成立。

> 最后更新：2026-09-02。相关：`s4.md` §B1（那六格的台账）、
> `windows/host/src/tabs.rs`（`WindowState` 与 `State` 的字段各自写了自己的理由）。

---

## 一、那条判断，一句话

给一个字段找位置时，问的**不是**「拆开会不会更干净」，也不是「哪个改起来省事」：

> **一个同时开着两个窗口的用户，这个事实对他是一个，还是两个？**

答两个就进 `WindowState`，答一个就进 `State`（进程级）。

**这条问句之所以有用，是因为它在单窗口下永远问不出来。** 只有一个窗口时，
每个字段都既是一个又是两个，怎么放都对——所以「今天能跑」不构成证据，
而这正是这些缺陷能活到多窗口落地那天的原因。

几个用它判出来、值得记住的答案：

- **`scale`**——两个。两块不同 DPI 的屏各有各的。单屏上两个值必然相同，
  所以「两个窗口各打一行 `scale=` 然后对比」是一条**永远绿**的判据，不能用。
- **`paints`**（标签条重绘计数）——两个。它曾经是一个进程级 `AtomicU32`，
  于是在窗口 2 上滚动会改到窗口 1 的状态行，让「窗口 1 逐字节不变」这条判据
  **红在一个跟它无关的地方**。
- **`editing`**（重命名框的 `HWND`）——两个，而且这个共享起来会**丢句柄**：
  在窗口 2 开重命名会覆盖窗口 1 的 `Some`，那个 EDIT 控件再没人销毁。
- **`next_id`**——**一个，而且必须是一个**。拆了，两个窗口各有一个 `Tab(1)`，
  而日志闸「一行提到 `TabId` 就算无歧义」那条豁免的前提正是 id 全进程唯一；
  它失效的样子是**闸照常报绿**。
- **`pending_cwd`**——一个。写它的那一刻（`ghostty_surface_new` 内部）
  还没有窗口可归属，这正是它存在的原因。

## 二、B1 之后仍然是「一份」的东西

**都不是缺陷，但都是「还没有人问过」，下一个人会撞上。** 列在这里，是为了让撞上
的时候能立刻知道这是已知的，而不是重新调查一遍：

| 事实 | 现在的行为 | 撞上时的样子 |
| --- | --- | --- |
| 会话几何（`session.json`） | 只记**第一个**窗口的矩形；其余窗口的移动不写盘 | 第二个窗口下次启动不回到原位 |
| 快速终端 | 整个进程一个，**不是**注册的 frame | `winid` 不给它编号；`frame_of_window` 对它答 `None` |
| HUD 覆盖层 | 整个进程一个，量的是 `overlay_frame()` 那个窗口 | 尺寸提示可能描述的不是你正在拖的那个窗口 |
| `binding(name)` | 打到 `overlay_frame()` 的活动 surface | 加速键在哪个窗口按的，宿主这一层不知道 |
| 菜单勾选状态（`state_for`） | 同上 | 勾的是「前面那个窗口」的状态 |

`overlay_frame()` 现在答的是**最后被激活的那个 frame**（`WM_ACTIVATE` 里记的），
所以上面这几条在多数情况下是对的；它们的共同缺口是**动作本身不带窗口**，
宿主只能问「人在看哪个」，不能问「这个动作是在哪个窗口上发出的」。

## 三、有三个按窗口的登记表，更新顺序是有要求的

一个窗口在三个地方各有一份记录，**没有任何东西强制它们同步**：

| 登记表 | 在哪 | 装什么 |
| --- | --- | --- |
| `winid::FRAMES` | `winid.rs` | 窗口**编号**，以及 `count()`——「最后一个窗口关了所以退出」读的就是它 |
| `tabs::Registry.windows` | `tabs.rs` | 窗口**状态**（tabs / active / ops / scale / …） |
| `strip::UI` | `strip.rs` | 标签条的**交互状态**（滚动、拖动、悬停、重命名框、重绘计数） |

**创建**：`create_frame` 调用 `winid::created`，**它一次写两个表**（先 `FRAMES`
发号，再 `tabs::add_window`——后者用 `wlogf!` 记日志，要先有号）；**再** `ShowWindow`。
两次登记必须在 `ShowWindow` 之前——显示窗口会同步派发 `WM_SIZE`/`WM_PAINT`，
而那些处理函数会来问这个窗口的标签。

**它们写成一个函数，是为了让「两个表暂时不一致」这个瞬间在创建侧不存在。**
从前它们是 `create_frame` 里的两条语句，分居 `ShowWindow` 两侧——那段时间里
窗口过程真的在跑，而两个表的说法不一样。收进一个函数之后，中间没有地方可以站人。
`tabs::add_window` 仍然是 `pub(crate)`、全 crate 可达（Rust 没有更窄的词），
所以「只有 `winid::created` 调它」是一句写下来的话，不是编译器守着的规则。

**销毁**（`WM_DESTROY`）：`winid::window_finished` → `tabs::remove_window` →
`strip::forget`。**顺序不能反**：`window_finished` 要的是**还把这个窗口算在内**
的那个计数，它据此决定进程退不退；先摘掉记录，那个计数就已经少了一个。

`strip::UI` 的条目必须删，理由和另外两个不同：**Windows 会回收 `HWND`**，
留在死句柄下的条目会被下一个拿到同一句柄的窗口捡到，那个窗口会带着别人的滚动
位置、以及一个指向已销毁控件的 `editing` 开场。

**这三个表是三个不同的事实，不是同一个事实的三份。**「窗口的编号」「窗口的状态」
「标签条的交互状态」各归一个表所有，这是对的，也是它们不能合并的原因之一
（`wlogf!` 会取 `winid` 的锁，而本文件的规则是不许持锁调用会取锁的东西，合并会造出锁环）。

出事的从来不是「有三个表」，而是**同一个事实被第二个地方持有**。这条规则在本仓
已经有一处最好的表述，写在 `menu.rs::default_state` 的文档头上，因为菜单勾选是
最容易长出第二份的地方：

> **每个 arm 读的都是别人已经在维护的值，绝不是它的副本**：只读那个勾读的是角落
> 徽章画的同一个 `AtomicBool`，三个 agent 勾读的是标签自己的右键菜单打勾用的
> 同一批每标签字段。**两个菜单从两个源打勾，迟早会不一致，而且不一致是无声的。**

**把它抄到这里，是因为它此前只在一个文件里生效。** 一条只写在一处的规则，不是
一条规则，是那一处的实现细节——下一个在别的文件里加缓存的人不会读到它。

它今天还缺的下半句，由 B1-e 那条红补上：**两个数字并排印在一起，在有东西规定它们
必须相等之前，都不是互相印证。** 读者会把一致当成印证、把不一致当成噪音——真机上
`1 window(s) remain` 和 `0 window(s) tracked` 就是紧挨着的两行，当场不一致，
而那个不一致就是答案。`winid::empty_agrees` 是给这一条补的那个「有东西规定」。

### 三个表之间必然不一致的两个瞬间

**它们不是缺陷，是设计的一部分，写在这里是因为任何检查它们的东西都必须避开：**

| 瞬间 | `winid::FRAMES` | `tabs::Registry` | 谁看着 |
| --- | --- | --- | --- |
| `CreateWindowExW` 内部（`WM_NCCALCSIZE` / `WM_GETMINMAXINFO` 同步到达） | 否 | 否 | **判据 E10**：这里的日志行会印 `w?` |
| `winid::window_finished` 之后、`tabs::remove_window` 之前 | 否 | **是** | **判据 E10**：同上，且这是 `w?` **预期出现**的地方 |

**创建侧曾经有第三个瞬间，现在没有了。** 两次登记从前是 `create_frame` 里分居
`ShowWindow` 两侧的两条语句，那段时间里窗口过程真的在跑；收进 `winid::created`
一个函数之后，中间没有地方可以站人。

**这一步值得记下的不是它修好了什么，是它替掉了什么。** 中间那个瞬间一度只是被
「缩到没有观测者」，而「没有观测者」是一句关于今天的话，不是关于代码的话：谁在
那两行之间加一句会派发消息的调用，它就回来了——**而且不会有任何东西红**。
那里的 `wlogf!` 会拿到一个漂亮的窗口号（`FRAMES` 已经说是了），所以 E10 看不见；
`hlogf!` 会退化成无标签行，但 `window-tagged-logs.py` 把 `hlogf!` 无条件算作已
分类（该文件第 307 行），所以棘轮也不动。**一个既没有判据也没有棘轮看着的瞬间，
唯一可靠的处置是让它不存在。**

## 四、`windows/tools/` 那些闸能看见什么，看不见什么

**它们全部断言源码文本的形状，没有一道断言运行中的程序。**

- 这一行有没有说是哪个窗口（`window-tagged-logs.py`）
- 这个访问器收不收窗口（`state-names-a-window.py`）
- 这个入队调用有没有指名目标（`post-op-has-a-target.py`）
- 这个字段有没有进状态行（`WindowState::state_fields` 的穷尽解构，编译期）

**后果是精确的：它们挡得住「有东西写错了」，挡不住「有东西根本没来」。**

实测过一次：把「Poltergeist 标记通知不带 surface」那个缺陷原样放回去，
**九道闸全绿，而且编得过**——因为不存在一行需要被判「说没说是哪个窗口」。
基线数字动了一下，那只是修复的影子，不是对它的检测。

今晚真正被抓出来的缺陷几乎全是「没有来」那一类——`new_window` 在
`cb_action` 里没有分支、18 个 arm 无条件返回 `true`、关闭请求发给不存在那个
pane 的窗口、四条关闭路里三条从不销毁窗口、`pane_of` 在注册前恒返回 `None`。
**没有一个是闸抓到的**，全部来自读代码时问第一节那句话。

所以：**闸的作用在发现之后**——把答案钉住，让它不会被下一个人无声地退回去。
把它们当保险，是把「回归防护」误读成「正确性证明」。凡是「这个东西到底有没有
发生」的判据，写成真机读数，并在提交信息里写明**本地全绿不构成对它的证据**。
