# 判据：分屏动作作用在**指名的**那一格

**这份文件覆盖 382 那一族四条动作**：`new_split` / `goto_split` / `resize_split` /
`toggle_split_zoom`。它们从前一律作用在**当前有焦点**的那一格，所以一个指名了 pane 的
工具调用会改到别的 pane 上，**而日志说它成功了**。

## 自核：这份判据还适用吗

⚠️ **不要用提交范围判断**（这份文件的第一版就是那么写的：「`git log <提交>..HEAD --
tabs.rs` 为空即可用」）。**那条前提在同族另外三条落地的当天就失效了**，而失效之后它会
把一棵健康的树判成「判据不可用」。**改成按内容核**：

    grep -c 'acting_pane' windows/host/src/tabs.rs        # ≥ 5：一个定义 + 四处调用
    grep -c 'unwrap_or(tab.focused)' windows/host/src/tabs.rs   # 必须是 1

**第二条是这一族的全部要害**：回落到焦点的规则只许有一处。出现第二处，就是这个缺陷
开始重新长回来。

## 键位

⚠️ **以 `Config.zig` 里 `Keybinds.init` 的非 darwin 分支为准，不是 macOS 的拼法。**
判据写错键位的表现和功能真坏了一样：**按下去没反应。**

| 动作 | Windows 上的键 |
|---|---|
| `new_split:right` | `Ctrl+Shift+O` |
| `new_split:down` | `Ctrl+Shift+E` |
| `goto_split:上/下/左/右` | `Ctrl+Alt+↑ / ↓ / ← / →` |
| `resize_split` | `Win+Ctrl+Shift+↑ / ↓ / ← / →` |
| `toggle_split_zoom` | `Ctrl+Shift+Enter` |

## 布置：焦点和 target 必须是两格不同的

1. 开一个终端，记它在 `terminal_list` 里的 id 为 **A**。
2. 在 A 上按 `Ctrl+Shift+E` 分出 **B**。**点一下 B，让焦点落在 B 上。**
3. 从**别处**（另一个终端或总管）对 **A** 发动作。

⚠️ **第 2 步是这四格的全部。** 焦点和 target 是同一格时，**修好和没修长得一模一样**。

| 动作 | 发什么 | ✅ 修好 | 🔴 旧行为 |
|---|---|---|---|
| new_split | `terminal_action(id=A, "new_split:down")` | 新 pane 在 **A** 下方 | 在 **B** 下方 |
| goto_split | `terminal_action(id=A, "goto_split:down")` | 从 **A** 出发往下找 | 从 **B** 出发 |
| resize_split | `terminal_action(id=A, "resize_split:down,10")` | **A** 那条边动了 | **B** 那条边动了 |
| toggle_split_zoom | `terminal_action(id=A, "toggle_split_zoom")` | **A** 铺满 | **B** 铺满 |

## 日志：`None` 是有意义的

四条都把落点打了出来（`from=Some(P)` / `pane=Some(P)` / `cwd=…`）。
⚠️ **`Some`/`None` 的读法**：`None` 表示这次动作没有指名 surface，或者指名的那格已经
不在这棵树里，于是回落到焦点。**用键位触发时 `None` 不是缺陷；用 `terminal_action(id=…)`
触发时，`None` 就是缺陷。**

## 回归：键位那条老路不许变

在 **A** 上直接按上表里的键（不是工具调用），效果应当仍在 **A** 上。
⚠️ **四条共用同一段落点解析，所以键位是这次改动最可能弄坏的东西。** 四条各测一次。

# 407：同一句话的另一半 —— 被指名的那格**不在活动标签里**

上面四格管的是「哪一格」，这一节管的是「哪个标签」。⚠️ **两半是同一条规则**，
`acting_tab` 的文档注释逐字写着：

> **The other half of the rule `acting_pane` is one half of.** Task 362 fixed "the tool
> names a pane and the effect lands on whichever pane has focus" -- and fixed it *within
> a tab*, because every caller had already picked `win.active` before asking. So the same
> defect survived one level up: name a pane in one tab, open another, and the action lands
> on the new tab's focused pane with nothing saying so.

⇒ **所以 407 的判据放在这里，而不是另开一份。** 一族判据劈成两处，下一个人只会读到
其中一处。

## 布置：让活动标签**不是**目标所在的那个

1. 在第 1 个标签里记下一格的 id 为 **A**。
2. `terminal_action(new_tab)` —— **活动标签现在是新开的那个**。
3. 从别处对 **A** 发调用。⚠️ **第 2 步是这三格的全部**：活动标签恰好就是 A 所在的
   标签时，**修好和没修长得一模一样**。

## 三格

| 格 | 发什么 | ✅ 修好 | 🔴 旧行为 |
|---|---|---|---|
| **(a)** | `terminal_layout`，叶子指名旧标签里的 **A** | **ok**，形状落在**旧标签**上 | `Refused: leaves out pane …`（它拿新标签的 pane 集合去校验旧标签的布局） |
| **(b)** | `terminal_action(id=A, "new_split:down")` | 新 pane 在**旧标签**的 A 正下方 | 落在**新标签**的焦点格上 |
| **(c)** | **不指名任何 pane** 时仍落在活动标签 | 落在活动标签 | —— |

### ⚠️ `[layout #N]` 的缺席意味着什么——先确认你手上的包属于哪一边

**这一整份判据有两格靠 `[layout #N]` 定胜负，而那行是有门控的**：`tabs.rs` 里
`layout()` 用一个**进程级、从不复位**的计数器给这些行封顶（见那里的 `verbose`）。
开标签、分屏、缩放、拖分隔条、改窗口大小，每一次都花掉一格。

**曾经的后果**：封顶用完之后每一次布局都沉默，而「切回去什么都没有」和
「布局根本没发生」逐字同形 ⇒ **这份判据在第 41 次布局之后无法失败**。下面 (b)
那条读数取到的是 `[layout #35]`，**离用完只剩 5 次** —— 那一格当时绿，一部分
原因是它跑得早。

**现在那个封顶有了逃逸**：`verbose = n <= 40 || 形状变了`。形状取自这次要应用的
那两张表（可见 pane 的矩形 + 隐藏的 pane），所以分屏、关闭、缩放、切标签、改尺寸
**永远出声**，只有「把同一个窗口重新摆回它已经在的位置」才安静。
⇒ **带这条逃逸的包不再要求新进程**，随便一个跑了多久的实例都能跑这份判据。

#### 怎么判断你手上的包有没有它（只看日志，不看源码）

写一次那个转储哨兵文件，然后看下一条 `[strip] dump | …` 行：

- **行里有 `lastlayout=`** ⇒ **有逃逸**。`[layout #N]` 缺席 = 这次布局的形状和上次
  一样；**形状变了却没有行，是缺陷，可以照常判红。**
- **行里没有 `lastlayout=`** ⇒ **没有逃逸，是旧行为**。⚠️ **这份判据必须在一个新
  进程的前 40 次布局之内跑完**；起 Polter、开第二个标签、发一次布局、切回来看，
  这条路径大约花掉十几格，够用，但**不能在一个已经被别人测了半小时的实例上接着跑**。
- **一条 `[strip] dump` 都没有** ⇒ **哨兵没写成或位置不对**，这一步没做成，
  ⚠️ **不要读成「没有 `lastlayout=`」** —— 那条 dump 行本身也是有门控的。

### (c) 为什么够不到——这条要读完，不要当成「大概也没问题」

`acting_tab` 的回落分支要 `at == None`，而**每一条门都指名了 surface**：

- 键位触发时，那一格命名的就是它自己；
- `terminal_layout` 的 `id` 是**必填**；
- 指名一个**不存在**的终端，会在**核心侧**被 `UnknownPane` 拦下，**根本到不了**
  `acting_tab`。

⇒ **今天没有一条路能把 `None` 送进那个分支。** 能说的只有：被指名的 pane 就在活动
标签里时一切正常。⚠️ **未检验，不是已排除。**

⚠️ **哪天有人打算测 (c)**：先找出一条**合法地不指名 surface** 的调用路径；如果找不到，
就把这一格继续记成够不到，**不要用「指名了一个恰好在活动标签里的 pane」冒充它**——那
是 (a)(b) 已经覆盖的形状，会得到一个绿而证明不了回落分支。

### 这三格读不到时长什么样

- **(a)** 回 `Refused: leaves out pane …` ⇒ 旧行为原样复发（校验用错了标签的 pane 集合）。
- **(a)** 回 `ok` **但形状落在新标签上** ⇒ 更坏的一种：拒绝没了，落点还是错的。**必须
  切回旧标签用 `[layout #N]` 核实，只看回执看不出来。**
  ⚠️ **包里没有 `lastlayout=` 时，前提是这个进程还没跑满 40 次布局**；跑满之后这一格
  无法判读，不是通过（见上）。
- **(b)** 新 pane 出现在**新标签**里 ⇒ 旧行为。⚠️ 判据是切回去看 `[layout #N]` 的矩形，
  不是看回执，也不是看当前屏幕（当前屏幕是新标签）。
  ⚠️ **同样只在没有 `lastlayout=` 的包上要求「进程还没跑满 40 次布局」**（见上）。
- **(c)** 无论看到什么都先问一句：**我这次调用真的没指名 surface 吗？** 指名了就不是
  这一格。
