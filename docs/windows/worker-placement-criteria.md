# 判据：总管开出来的 worker 落在哪

**覆盖 362 前半段**：`terminal_open` 不再一律新开 tab，而是按一份住在核心里的预算
把 worker 摆进总管自己的 tab。预算是 `App.zig` 里的 `WorkerPlacement.decide`，
**两个 apprt 里没有它的任何一个数字**——它们只回答一个事实：这个 tab 里有几格。

## ⚠️ 最要紧的一条，以及它今天为什么应该是红的

> **主管说 1+1+2+2，得到的就是 1+1+2+2，且那个 2+2 是田字。**

**这一版达不到它，而且是设计上达不到，不是坏了。** 今天能摆出来的只有
**主管在左 + 右边一列最多三个 worker**，第 4 个起一律新开 tab。

⇒ **拿这条判据去测这一版，正确的结果是「不符合，且日志说明了为什么」，不是绿。**

**留着它的理由就是这个**：今天没有任何别的判据能抓住「形状对不上」——
「开了 4 个 worker」绿的时候，形状可以是错的。**一条判据在它保护的能力还没做出来
之前，答案应该是红，而不是把判据改软。** 缺的那一半是「切子树」，归 346。

## 1. 主线：连开 5 个 worker

从一个只有总管的窗口开始，让总管连开 5 个 worker（`terminal_open`，各带不同 `cwd`）。

| 第几个 | 期望 | 日志里应有 |
|---|---|---|
| 1 | 在总管**右边**；总管仍在最左、占满高 | `[split] Right -> pane N (cwd …)` |
| 2 | 在**第 1 个的下方** | `[split] Down -> pane N (cwd …)` |
| 3 | 在**第 2 个的下方**（右列三格） | 同上 |
| 4 | **新开一个 tab** | `falling back to a tab -- 3 workers already here, and a fourth would need a second column, which means splitting a subtree (not possible today)` |
| 5 | 也在新 tab 里 | 同上 |

⚠️ **每个 worker 的 shell 必须真的在它自己的 `cwd` 里**——在每一格里 `pwd` 看一眼。
这是那条硬约束：**要么在请求的目录里，要么根本没被分屏。**

## 2. `place` 三档

| 发什么 | 期望 |
|---|---|
| `terminal_open(cwd=…)`（不给 `place`） | 走 `auto`。⚠️ **不是 tab**——这个默认值在 362 里变过 |
| `terminal_open(cwd=…, place="tab")` | **一定是新 tab**，永远不会变成分屏。这是保证不是偏好 |
| `terminal_open(cwd=…, place="here")` | 在总管的 tab 里分屏；没位置时回落 tab，**并且多打一行说明「你明确要的东西没拿到」** |

## 3. 四处回落，各自要有那一行

| 怎么造 | 日志里那句 |
|---|---|
| 在 Linux/GTK 上开 worker | `this apprt would not split into …`（GTK 给不了目录 ⇒ 不分屏） |
| apprt 答不出「几格」 | `this apprt does not say how full a tab is` |
| 先手动 `Ctrl+Shift+E` 分一屏，再让总管开 worker | `this tab has N terminals that were not opened as workers…` |
| 开 2 个 worker、**关掉第 2 个**、再开一个 | `the last worker is gone; falling back to a tab rather than guessing which pane replaced it` |

⚠️ **最后一条是「有洞」那一格，它的行为是刻意的**：不填洞、不猜，退到新 tab。
**右列会留一个空位**——**这是这一版的已知形状，不是缺陷。** 填洞需要「洞在哪」的概念，
而那取决于用户在它关掉之后做了什么；不填洞才使「同一串操作永远得到同一个形状」成立，
**而上面每一格判据都建立在这一点上**。

## 4. 一格只有人能答

**总管自己那一格的进程有没有被重建。** 开工前在总管里 `echo $$` 记下 pid，
连开 5 个之后再 `echo $$`。
⚠️ **pid 变了 = 杀掉了总管自己**，比形状错严重得多，**撞到就停下别继续测。**
（这一版不重排，所以理论上不会——**但理论不是读数。**）

## 这份判据不覆盖什么

- ⚠️ **设计里那条「开 12 个 worker 得 2 个 tab」现在不能用**：这一版一个 tab 只放 3 个
  worker，12 个会得到 **1 + 4 个 tab**。**拿它去量只会量到一个已知的数**，并且会让人
  报一个不存在的缺陷。它要等切子树落地才有意义。
- ⚠️ **mac**：mac 侧照做了、构建过了，**没有人按过**。
- **没有人跑过这份判据。**

# 这两份判据背后的欠账

**都不在任何补丁里，写在这里是为了它们不跟着会话消失。**

1. ~~**第 4 个 worker 起要「切子树」。**~~ ⚠️ **这一条的成因是错的，2026-09-09 更正。**
   两棵树各缺哪一半属实（核心的 `SplitTree.split` 收任意节点、Windows 的 `insert`
   只接叶子），**但由此推出的「所以摆不出 1+1+2+2」不成立**：任何二叉布局都能**只切
   叶子**按顺序搭出来 —— 田字就是「切 A 右得 B、切 A 下得 C、切 B 下得 D」。
   ⇒ **真正的成因是下面第 2 条**：切完不知道新出来的是谁，于是只能对着已知那格继续切。
   **原文留在这里而不是删掉**，因为它已经被引用过，而且它正是「读数对、推论错」的样本：
   谁核了「两棵树各缺哪一半」都会核成属实，然后连着那半句推论一起签收。
2. **`terminal_action` 的成功回执是裸 `ok`，不带新 pane 的 id。** ⇒ 手工摆布局必然
   退化成一行或一列，因为调用方只能一直对着它已知的那一格分。归 346；
   `supervising` skill 里已经写了今天可用的三步配方（分屏前后各 `terminal_list` 取差集）。
3. ⚠️ **mac 上 `new_split` 那一族是不是同样拿焦点当 target —— 未查。不是「没问题」。**
4. **`windows/host/src/ffi.rs` 的 `payload` 是 24 字节**，`new_split` 的新结构
   （一个 i32 加两个指针）**正好填满**。**下一个带三个字段的动作会溢出**，而溢出的表现
   是读到别的字节，不是编译错误。
5. **这两份判据都没有人跑过。** 每一格都是预期。

# 2026-09-09：`terminal_layout` 落地之后的两条真缺陷（406 / 407）

**机制在真机上成立**：田字出来了、负对照确实是一条链、不许减少和原子性都按写的答。
下面两条是 WT 在那之后验出来的，**同一族：工具指的东西和它说的不是同一个**。

## 406：`pane` 用的不是 agent 手里的 id

**现象**：照工具描述给终端 id（`terminal_list` / `terminal_read` / `terminal_send`
用的那一种）⇒ 被拒，原文 `the layout leaves out pane 1, which is in this tab.` ——
**而 pane 1 就在给出的布局里**。

⭐ **复现的关键是「只改一个变量」**：同一份布局、同一个调用，**只把 `pane` 的值从终端 id
换成宿主内部的 `PaneId`（`0x1`/`0x5`/`0x6`/`0x7`）⇒ ok**。⚠️ **这一格是这条缺陷的全部
证据**：两个命名空间的数字长得一模一样（都是 `0x…`），**换掉别的任何变量都分不开它们**。

⚠️ **而 agent 无从得知 `PaneId`** —— 没有任何 MCP 工具暴露它。WT 是从日志
`[pane] N hwnd=` 里读出来的，agent 没有这条路。⇒ **这不是「文档没说清」，是这条工具在
它自己的描述下无法被使用。**

**修法**：进出两侧都用终端 id，翻译在核心（`App.zig`）—— 宿主从来没见过终端 id，
`findSurfaceByID` 是唯一的映射。宿主内部继续用 `PaneId`，边界上换成 surface 句柄。

### 判据：**三格一起发**，而第三格是用来钉住第二格的读法的

1. **叶子全用终端 id** ⇒ **通**，且**回执里每格的 `pane` 也是终端 id**。
   ⭐ 拿回执里**新建**那格的 id 直接 `terminal_read` ⇒ 读得到。**这一格才是这条工具存在
   的理由**：回执里的 id 喂不回去，等于「告诉你新 pane 是谁」那半没做。
2. **叶子全用宿主 `PaneId`**（`0x1`/`0x5`/`0x6`/`0x7`）⇒ **被拒**，而且拒绝话是
   **「找不到这个终端」一类**，不是「格式不对」。
   ⚠️ **修之前这一组是通过的** —— 没有这一格，「改成收终端 id」和「两种都收」分不开，
   而后者会让这条缺陷**看起来已经修好了**。
3. ⭐ **叶子给一个语法合法但不存在的终端 id**（把某个真 id 末位改一下）⇒ **也被拒，
   而且和第 2 格是同一句话**。
   ⚠️ **这一格钉住的是拒绝的理由，不是拒绝这件事**：如果 2 和 3 给出不同的拒绝理由，
   说明宿主仍然在按「像不像 PaneId」分流，两种 id 就还没真正统一 —— **而那时第 2 格
   单独看是绿的**。

**落到修法上就是一句**：解析之后**只有一次查找**，查不到就是查不到，**不许对「看起来像
PaneId 的字符串」走另一条路**。

> ⚠️ **为什么这个坑是真的**：宿主 `PaneId` 是小序数（1、5、6、7），而终端 id 是
> **随机 64 位**（`Surface` 用 `rng.int(u64)` 抽，只排除 0 和 `not_a_terminal`）。
> 两者**在语法上无法区分** —— `0x1` 是一个完全合法的终端 id 写法，只是没有终端叫这个。
> 所以拒绝**只能**建立在「查得到 / 查不到」上。

## 407：按 `win.active` 定标签，不是按 `id` 指名那格所在的标签

**现象**：`new_tab` 之后紧接着调布局、`id` 仍是旧标签里的 pane ⇒ `the layout leaves out
pane 8`，**而 pane 8 在新标签里**。

⚠️ **`split_pane` 是同族**，上一轮标的「未检验」这一轮被检验为真。**两处一起修，用同一处
规则**（`acting_tab`）：**动作落在它指名那格所在的标签上，只有它没指名时才落在活动标签上。**
⭐ 362 修的是同一句话的**另一半**（「指名一格、效果落在焦点那格」），**但它只修到标签
之内** —— 每个调用方在问之前就已经挑好了 `win.active`。**一句规则被拆在两个地方，修了一半
的那半看起来像修好了。**

### 判据
1. **正对照**：开一个新标签 ⇒ 立刻用**旧标签里**某个 pane 的 id 调布局 ⇒ **旧标签变成
   那个形状，新标签一点没动**。
2. **同一格对 `split_pane`**：新标签之后 `terminal_action(旧标签的 id, "new_split:right")`
   ⇒ **分的是旧标签**。
3. **不指名时仍落在活动标签**（这条是防我把规则改反）。
