# 判「卡没卡」的仪器，和它们各自答得了的那一句

这份文件的存在理由，是 2026-09-03 夜里量到的一格：

| 状态 | `SendMessageTimeout(WM_NULL)` | `IsHungAppWindow` |
| --- | --- | --- |
| 健康 | ok=true 14ms | false |
| **模态框挡住 152 秒** | **ok=true 0ms** | **false** ← 假绿 |
| 真挂起 | ok=false 2999ms | true |

（原始记录在 `docs/windows/status.md`「任务 177 之二」一节。数字抄在这里而不是只留一个
指针，是因为**这份文件是给坐在机器前的人用的**，而那个人不会去点指针。）

**中间那一行是全部**：窗口 152 秒不响应用户，而两件仪器都答「没卡」。成因是嵌套模态
循环——`MessageBoxW` / 菜单 / 窗口移动改尺寸——**它照样在派发消息**，而这两个 API 问的
恰恰就是「消息还派不派得动」。

---

## 一、按问题分，不按 API 分

**一刀切成「这两个 API 不能用」是错的。** `IsHungAppWindow` 回答的是一个真问题，只是
不是大多数人以为的那个。所以下表按**你实际想知道的那一句**组织：

| 你想知道的那一句 | 能回答它的 | **不能**回答它的 |
| --- | --- | --- |
| **这个窗口最近 5 秒有没有处理过消息？** | `IsHungAppWindow`（这就是它的字面契约，答案是真的）；`SendMessageTimeout(WM_NULL)` 同族 | — |
| **这个进程的主线程是不是卡住了？** | 宿主自己的看门狗：`[wd] … ping X UNANSWERED`（见下） | `IsHungAppWindow` / `SendMessageTimeout` / `Process.Responding` —— 模态循环下三者全答「没卡」 |
| **人现在能不能用这个应用？** | **只有人能答**，或者一次「必须产生可见效果」的按键 | 上面**每一件**，包括看门狗的 `PUMP BUSY … Not a fault.` |

第三行不是凑数。看门狗在模态那一格打的是：

```
[wd] pid=N PUMP BUSY 152.0s: ticks frozen at M, ping S ANSWERED -- a nested modal loop
     (menu, window move/size) is dispatching. Not a fault.
```

**技术上一个字没错，而读日志的人会照着 `Not a fault.` 这四个字跳过去**——用户那一侧
看到的是「窗口未响应 152 秒」。所以：**「不是缺陷」是关于代码的判断，不是关于人的**。

## 二、宿主自己的那件仪器，为什么它答得了第二问

`main.rs::start_watchdog` 每 2 秒 `PostMessageW(WM_WD_PING)`，主线程的 wndproc 回填
`WD_PONG`，然后按 `pong == seq` 分叉。**分界是代码划的，不是从两行日志里读出来的**：

| 读数 | 意思 |
| --- | --- |
| `MAIN THREAD BLOCKED …s: ticks frozen at N, ping X UNANSWERED` | **连一条投递来的消息都没被派发**。真阻塞。 |
| `PUMP BUSY …s: ticks frozen at N, ping X ANSWERED … Not a fault.` | 嵌套模态循环在派发。**不是阻塞**，但**人可能正被挡着**。 |
| `resumed after Ts, ticks=…` | 结束，`T` 是持续时长 |

外部 API 拿不到这个分叉，因为它们**只能从外面敲门**，而模态循环会开门。看门狗是从
**里面**问的：它问的不是「有没有人开门」，是「主循环那一圈还转不转」（`ticks`）。

## 三、哪些结论作废，哪些不受影响

**失明是单向的**，这决定了重看的范围：

- ❌ **用这一族判过「没卡」的，作废**——只要当时可能有菜单、模态框、或窗口移动改尺寸。
  「可能有」就够，不需要证明当时有：仪器在那一格给不出区分。
- ✅ **用这一族判过「卡了」的，不受影响。** 它们没有假红：模态循环会让它们答「没卡」，
  不会让它们答「卡了」。
- ⚠️ **把 `Process.Responding` 和 `IsHungAppWindow` 当成两条独立读数用过的，先做第
  五节那一格再说。** 它们**可能**共用同一个实现，**没有人验过**，所以这里不写成结论，
  写成一个一步能定案的判据。

  已知的一个具体例子：任务 292 那次真机判定，当时记的是「`[wd] ticks frozen` +
  `Responding=False` + 20 个采样，三条独立读数」。**如果第五节那一格答「两个都答没卡」，
  那次就是两条读数不是三条**，而承重的是 `[wd] ticks frozen`——它是宿主自己的心跳
  计数器，和这一族没有共同实现。**那次的结论不变，但它站在比记录的更薄的基础上**，而
  这个差别正是这一节要防的。

## 四、标定：一分钟摆出「已知失明」的现场

**这一节的价值不是「这里有个 bug」，是「仪器可以被标定」。** 这是我们**唯一一个能主动
制造的、已知会骗过某些仪器的现场**——所以以后每加一件新仪器（新的探针、新的判据、新的
自动化检查），都可以**先拿它试一遍**，看它在这一格是答对还是答错。一件从没在已知失明的
现场上试过的仪器，它的「绿」是没有量纲的。

**这个现场是可按需复现的，不必等意外。** `main.rs::cb_confirm_read_clipboard` 用
`MessageBoxW(..., MB_YESNO | MB_ICONWARNING)` 在主线程上弹确认框——那就是嵌套模态循环。

> **触发条件不只是「多行」，还取决于接收方。** 同一个 `Ctrl+V`，接收窗格是 `cmd.exe`
> 时弹框（实测 149 字符 / 8 行），是 TUI 程序时**不弹**（658 / 667 字符也不弹），很可能
> 是 bracketed paste。所以摆现场要用 `cmd.exe` 那种窗格。

### 步骤（每一步都带着它的前提检查）

0. **先确认前提，并记下来。** 一次「什么都没量到」的运行和一次「量到了没事」的运行，
   在结果里长得一模一样。所以：
   - 记下 pid、frame 的 HWND、以及构建号；
   - 摆好现场后，**先在日志里找到**
     `[clip] paste confirmation requested: pane=… N chars, M lines`。
     **没有这一行就是框根本没弹出来，这一轮什么都没量到**，重摆，别往下走。
1. 一个跑 `cmd.exe` 的窗格，剪贴板里放 ≥2 行文本，`Ctrl+V`。**框弹出来之后不要回答它。**
2. **从另一个进程**，在框还开着的时候读三件仪器：
   - `IsHungAppWindow(frame)`
   - `SendMessageTimeout(frame, WM_NULL, 0, 0, SMTO_ABORTIFHUNG, 5000, …)` 的返回与耗时
   - `(Get-Process -Id <pid>).Responding`

   **预期：三个都答「没事」。** 这一步不是在找 bug，是在**这一份构建上**把仪器的失明
   演示出来——「上次在别的构建上失明过」不能替代这一步。
3. 同时读宿主自己的日志，应当有
   `[wd] pid=… PUMP BUSY …s: ticks frozen at …, ping … ANSWERED … Not a fault.`
   **这就是能把两者分开的那件仪器。**
4. 回答那个框。日志应出现 `[wd] pid=… resumed after Ts, ticks=…`。
5. **另一半标定：已知可检出的现场。** 只做第 2 步，「三个都答没事」和「应用本来就没事」
   分不开。所以还要从外部 `SuspendThread` 挂起 UI 线程（`status.md` 记录 2026-09-03 做过：
   `MAIN THREAD BLOCKED` 如期出现，30 秒后 `resumed after 32.0s`），此时：
   - 三件外部仪器**必须**答「卡了」；
   - 日志**必须**是 `UNANSWERED` 那一支。

   **两半都做完，第 2 步的「都答没事」才是「仪器失明」而不是「当时没事」。**

## 五、`Responding` 和 `IsHungAppWindow` 是不是同一件仪器

在第 2 步那个**已知失明**的现场里同时读两者。**能得出的结论写多强就写多强，别多写一格：**

- 两个都答「没事」→ **只证明它们在这一格上不独立。** 一份同时引用这两个读数、而现场
  可能有模态循环的证据，在那一格实际上只有一条腿。**这还不足以说「它们是同一件仪器」**
  ——那需要反证，见下。
- 一个答「没事」另一个答「卡了」→ 它们**确实是两件仪器**。记下哪一件在这一格更灵，并把
  这一节改掉。
- **要说「它们是同一件仪器」，需要至少一个它们答案分歧的现场来反证，而找不到分歧本身
  也是有用的读数**——它把「不独立」的适用范围一格一格扩大，即使永远到不了「同一件」。

⚠️ **这一格没有人跑之前，谁都不要把这两个当成两条独立读数。** 包括把它写进这份文件的我。

### 为什么这一条特别难发现

本仓已经记过这条经验的两种形态，这是第三种：

1. **同法复核不算数**——换个人用同一个方法，盲区原样复制。
2. **「独立」指的是读法独立，不是执行者独立**——同一个函数调两次不算两个读法。
3. **两个不同名字的 API 可能共用同一个实现，于是「两件仪器」其实是一件。**

第三种比前两种难发现，因为**名字不一样，看起来就是独立的**。

## 六、写新判据时的一句话规则

> **不要问「它响应吗」，要问「我要的那件事发生了没有」。**

一次必须产生可见效果的操作（按键出字、点击换标签、命令改字号），加上宿主日志里
**它自己写下的那一行**，回答的是第三问；而第三问才是人遇到的那件事。外部 API 只回答
第一问，看门狗回答第二问，**三问不能互相替代**。

## 七、把 292 造出来：一次点击不够，两次紧邻才够

**这一节和第四节是同一种东西**：一个**可按需制造**的现场。区别是第四节那个是「已知会
骗过仪器的现场」，这个是**缺陷本身**——`ShellExecuteW` 在拥有窗口的那条线程上不返回。

**它以前看着像随机，是因为触发它要两个条件同时成立，而以前只找了一个。**

    两次紧邻的 open_url  +  第一次是「冷」调用（进程内第一次，~155ms）   -> 卡
    两次紧邻的 open_url  +  第一次是「热」调用（Chrome 已在跑，~14ms）    -> 不卡
    一次 open_url        +  冷调用                                        -> 不卡

**三格都在同一台机器、同一条 URL、同一个默认处理程序上量的**，读数在下面。

> **为什么以前抓不到规律。** 曾经有一个缺陷让**一次** ctrl+点击派发**两次**
> `open_url`（`ReleaseCapture()` 自己发的 `WM_CAPTURECHANGED` 与「捕获被抢走」是同一
> 条消息）。那个缺陷保证了「两次紧邻」这一半**总是**成立，于是能不能卡就只取决于另一
> 半——点的是不是这个进程里的第一条链接。修掉重复派发之后，一次点击只派发一次，
> **今天唯一的触发者没了，但缺陷本身还在**：手快点两下两条链接同样满足这两个条件。

### 读数（三格，各一次点击动作）

    冷 + 一次      [link] handing … -> true in 155ms          主线程照常
    热 + 两次紧邻  两条 handing，各 14ms 返回                  主线程照常
    冷 + 两次紧邻  只有一条 handing，**之后再无任何行**        4 秒后 MAIN THREAD BLOCKED

卡住那一格的日志逐字就是那行前置日志自己写的那句：

    [link] handing "…" to ShellExecuteW on the thread that owns the windows;
    IF THIS IS THE LAST LINE IN THE LOG, the call did not return

**判据不是「少了一行」，是主线程停了**：点击前 `[loop] … main-thread alive` 的 ticks
还在涨，点击后冻住不动，`[wd]` 随后把它报出来。两条一起看才是读数。

**两次卡死的 RIP 逐位相同**（同一个 `ntdll.dll` 偏移），一次是自然发生的、一次是构造
出来的——**是同一个卡点，不是两个长得像的东西**。栈上 `Windows.Storage.dll`
（`ShellExecuteW` 的实现所在）的地址带在 RSP 之上约 8KB 处，内层是消息泵回到本进程
自己的代码。⚠️ **这是按栈槽扫描得到的，不是真 unwind**：RIP 是权威的，模块带是提示。
测试机上没有能符号化的调试器，所以「卡在哪一帧」这件事目前没有定论。

### 步骤（每一步都带着它的前提检查）

0. **记下前提**：包的提交号、pid、frame 与 pane 的 HWND（都从**被测进程自己写下的**
   `[win] wN = frame 0x…` / `[pane] N hwnd = 0x…` 取，不要从截图认），以及 URL 原文和
   当时的默认处理程序（`HKCU\SOFTWARE\Microsoft\Windows\Shell\Associations\UrlAssociations\https\UserChoice`）。
   **三格必须用同一条 URL 和同一个处理程序**——`ShellExecuteW` 的行为由处理程序决定。
1. **先跑「前提格」：单击一次。** 日志里 `[link] handing` **必须只出现一次**。
   出现两次说明重复派发那个缺陷还在，**这一轮不可读**，先修那个。
   这一步同时给出这台机器上「冷调用」的耗时，后面要用它对齐条件。
2. **正对照必须用新进程的第一次链接点击。** 已经点过链接的进程里，`ShellExecuteW`
   十几毫秒就返回，条件不成立。**重启宿主，第一次就打两下。**
3. 两次点击间隔 **40ms**。理由：此时第一次的调用还没返回，第二次点击的消息排队、在第一
   次返回后紧接着派发——这正是自然发生那次的时序。⚠️ 间隔取 160ms 会失败，但不是因为
   缺陷不复现，而是**浏览器窗口已经盖住了那个点**，第二次点击根本发不出去。
4. **每次点击之前，在同一个进程里回读 `WindowFromPoint`，不等于目标 pane 的句柄就一个
   事件都不发。** 两次点击各查一次——第二次尤其重要，浏览器就是在这几十毫秒里抢前台的。
   闸不过要记 SKIPPED 且**不计入分母**。
5. **ctrl 必须在指针移动时按着**，否则终端不会进链接模式：顺序是 ctrl 按下 → 挪 1px →
   挪回 → 停一下 → 再过一遍闸 → 点。前提成立的证据是日志里
   `[action] mouse_shape 3 (pointer) -> IDC_HAND`；**没有这一行就是链接压根没被认出来，
   这一轮什么都没量到。**

### 这套构造是 324 的验收判据，也是它唯一能证伪自己的东西

把 `ShellExecuteW` 挪出拥有窗口的那条线程之后，**同样的构造应当不再让主线程停住**。
验收时三格都要跑，而且**判据不许改**：不能因为修法让某一行日志换了位置就换一把尺。

**它覆盖不到的**（写在这里，免得绿被读成「这一族没了」）：

  * **只覆盖 `open_url` 这一条路。** 同一族的其它主线程阻塞调用不在里面——
    `blocking-call-says-so-first.py` 的主体集今天只有 `ShellExecuteW` 一个名字。
  * **只覆盖两次紧邻这一种时序。** 三次、或者间隔不同的两次，没有量过。
  * **不回答「卡在哪一帧」**，见上面关于 unwind 的那一段。
  * **不覆盖处理程序换掉之后的行为。** 换一个浏览器就是换一个被测对象。
