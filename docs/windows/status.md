## 二、关停死锁：已修，两种时序下都验过【实测】

**结论**：命名管道传输层在 Windows 上跑通整个 server 套件。

| 版本 | 时序 | 结果 |
| --- | --- | --- |
| 修复前（`pD`） | 带插桩 | **3/3 挂**在 `stop.failInflight.post` |
| 顺序修复（`pE`） | 带插桩 | **3/3 挂**在同一行（sha 已核，修复确实在里面） |
| 改异步（`pF`） | 带插桩 | **3/3 panic**（shutdown 首次通过） |
| 删掉 `CancelIoEx`（`pG`） | 带插桩 | **3/3 过** |
| **同上，交付版（`pI`）** | **不带插桩** | **5/5 过**，`92 passed; 5 skipped; 0 failed` |

**为什么两种时序都要验**：插桩会改变时序，而原始故障是竞态——「确定性复现下修好了」
不蕴含「竞态版也修好了」，而交付的正是不带插桩那个。

**为什么是 5 次不是 3 次**：原始形态是 2 挂 1 过。三次全过是碰巧的概率，
按**观察值**（通过率 1/3）算是 3.7%，按**保守假设**（通过率 2/3）算是 **约 30%**；
五次分别是 0.4% 和 13%。**「保守估计约 30%」这个限定词不能省——去掉它就成了
一个听起来像测出来的数。**

**这个结论的边界**：5/5 过**不等于**没有竞态，只等于在这个基率下没观察到。
准确的说法是：**若仍有竞态，其发生率显著低于原来的 2/3。**

## 二之三、M3 中文输入：已在真终端里打出汉字【实测】

全链路通过，两张验收截图为证：

| 环节 | 证据 |
| --- | --- |
| TSF 激活 | `ActivateEx ok, clientId=32` → `context pushed, editCookie=1` |
| 按键进入 IME | 第一个真实虚拟键就出 `OnStartComposition`（**不能用合成文本，它绕过 IME**） |
| 组合串 | `SetText 0..0 <- "n"` → `SetText 0..2 <- "你"` |
| **候选窗定位** | 截图：候选窗**紧贴 preedit 正下方**，不是屏幕角落 |
| **preedit 渲染** | 截图：终端里 `>ni` **带下划线**，核心自己画的 |
| **上屏** | `OnEndComposition commit="你"`，截图里 `C:\Users\bestf>你` |

**`SetText 0..2 <- "你"` 这个范围本身是一次验证**：「你」是 **1 个 UTF-16 码元但占 2 格**，
是这条路上最容易算错的地方。用核心的 `ghostty_unicode_grapheme_width` 算的，不是手写表。

### 实现上的一个判断，不是从探针照搬来的

探针里文档是一行自己画的文本、在自己编的网格上。接进终端时形状变了：
**文档只装组合串**——终端不是可编辑文档，`ITextStoreACP` 不假装持有一个；
`GetText` 只答 preedit，上屏的字通过 `ghostty_surface_text` 离开后就不再属于这里。

### ⚠️ `ghostty_surface_ime_point` 的四个出参不在同一个单位里

读 `Surface.zig:2277-2340` 发现的，**96dpi 上看不出来，缩放显示器上会**：

| 出参 | 实际是什么 |
| --- | --- |
| `x` | 光标格的**水平中点**，不是左边缘（`x += cell_width / 2`） |
| `y` | 光标格的**底边**，不是顶边（`y += cell_height`） |
| `height` | 格高 **÷ content_scale** |
| `width` | preedit 宽度，**故意没有除以 content_scale** |

最后一条是源码里作者自己的话：*"we don't apply content scale here because it looks
like for some reason in macOS its already scaled. I'm not sure why that is"*。

**当前的处理是不用 `width`**——列数由宿主按宽度表自己量，x/y/height 乘回 scale。
**接 DPI 缩放的人要先看这一条。**

### 已知未解（原样记下，不是失败）

- **滚动**：核心自己在 `imePoint()` 里的 TODO 还在——组合中滚屏可能让候选窗跑偏。
- ~~**没有 VK → keycode 表**~~ → **已解，而且是用「不需要这张表」的方式解的（#73）。**
  `ghostty_input_key_s.keycode` 不是 `GHOSTTY_KEY_*`——核心拿它去查
  `src/input/keycodes.zig` 的**原生列**，Windows 构建下那是第 3 列，即 IBM PC set-1
  扫描码。而 `WM_KEYDOWN` 的 lParam 位 16–23 正是扫描码、位 24 是扩展标志。
  **转换六行，核心自带的 673 行表干掉剩下的活**（`windows/host/src/keys.rs`）。
  写一张 VK→key 的表也能工作，但那会是第二张要和 `keycodes.zig` 保持一致的表，
  而不一致的表现是「某个布局下某个键什么都不做」——不报错，没人会发现。

两份分叉的原型（标签/action 一份、TSF/键盘一份）合成一份（行数以第一节的增补为准，

**位置**：`windows/host/`，和 `macos/` 同性质（平台应用壳，不归 `zig build` 管）。
交叉编译的一个环境坑记在 `windows/AGENTS.md`：**target 目录路径不能带空格**，
否则 `dlltool` 在编依赖时就挂，报错和本仓代码无关。

### 真机上暴露的两处，都不报错

| 症状 | 根因 | 是什么定位的 |
| --- | --- | --- |
| 窗口「未响应」、全黑，日志停在 `[tab] surface` | `layout()` **持 `STATE` 锁**调 `SetWindowPos`，子窗口的 `WM_SIZE` 同步派回同一线程再取锁；`std` 的 `Mutex` 不可重入 | **缺的那一行**：`[tab] created` 没打，而它和上一行之间只有 `layout()` |
| 死锁修好后仍然全黑 | GL 上下文建在一个**还是 100×100** 的占位子窗口上（见 `development.md` 5.2 第四条）；**事后 `set_size` 补救不回来** | 像素格式探针 = 5（绑定成功 → 故障在下游）＋ 四版本对照；**首次归因「必须先显示」被 `--hide-first` 对照推翻，真正起作用的是尺寸** |

第一条现在有哨兵：`windows/host` 的 `state()` 先 `try_lock`，再犯会打
`[state] lock contended`，而不是像这次一样一行都不留。

### 一条读数陷阱，代价是一整轮误判

旧版 `polter-host-m3.exe` 还开着，而新版日志**同名**（都是 `C:\app\polter-host.log`），
一个文件里混着两个进程。「主线程 ticks 在涨」被读成「循环没死、卡在某条消息里」，
**那串心跳其实是旧进程打的**，新版死在进消息泵之前。判据是：日志里同时出现只有新版
会打的行和只有旧版会打的行。现在日志是 `polter-host-<pid>.log`，首行打 pid 和路径。

### 2. QuickTerminal 在不在 v1 射程内？

877 macOS 代码行，目前**默认算在射程内**（`design.md` §4.3 的 S4 档）。
没有任何一份文档写过它是否要做——M1–M6 六个里程碑一次都没提到它。

- **不在**：区间下移约 750 总行

## 七、方法论（每条都带触发条件，今天真踩出来的）

0. **拿到一个支持结论的读数就停手——这是下面几条的母形状。**
   今天被推翻的九条判断里，多数不是因为没有证据，而是**证据就在手里，
   而人停在了让结论成立的那一步**：
   - 令牌下发那条：链的**下游**读了（env 怎么被消费），**上游**没读（env 怎么被构造）
   - 目录逃逸那条：失败消息读了（`expected 2, found 0`），**那个断言在数什么**没读
   - 控制台归属那条：看到测试转绿就归因给它，**没注意同一轮还有第二个变量在变**
   - action 计数那条：拿到一个数，**因为它和文档一致就不再追**（而文件里有两个同名 enum）

   **触发条件很具体：当一个读数刚好支持你正想成立的那个结论时，那就是要多走一步的时刻。**
   相关的一条：**升级一个结论（从「疑似」到「阻塞项」）比提出它需要更多证据**，
   而升级往往发生在最想收工的时候。

1. **编译挡着链接，链接挡着运行，运行挡着绘制。** 今天穿了五层，最后一层是上游显式挡的。
2. **「那个假设没被检验过，不是被排除。」** 未经检验的假设被当成已排除，比已知未解更危险——没人会再回去看它。
3. **用错的探针得到的阴性，和没做过实验是一回事。** `GetConsoleWindow` 对「无控制台」和
   「有控制台无窗口」都返回 null。
4. **负对照必须在过滤之前取。** `Where-Object` 之后再数，数的是过滤后的世界。
   同理适用于「查产物里有没有某个字符串」：**「0 处命中」和「这个搜索根本找不到东西」
   长得一模一样**。核对交付版不含调试插桩时，要同时搜一个必然存在的符号作地板——
   `插桩串: 15 → 0，而 DisconnectNamedPipe: 1 → 1`，后半句才让前半句成立。
5. **当一个阴性结果让你少干活时，那就是必须量基率的时刻。**
6. **当一条二手前提能决定下一步做什么时，先花两分钟核它。** 核它一次 `grep`，不核一个完整往返。
7. **预先声明判据，是为了在结果出来之前锁住解释权。**
8. **一直在调整一个不该存在的东西的参数。** `CancelIoEx` 三轮错了三种方式，正确动作是删掉它。
   每一步都对，方向整体是错的。
9. **规则的适用条件比规则本身更难记住。**「别在锁里做系统调用」是对的，但那把锁正是防
   use-after-close 的机制。
10. **绕开一条路，不等于绕开它底下的那一族问题。**
