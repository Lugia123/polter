## 二、关停死锁：已修，两种时序下都验过【实测】

**结论**：命名管道传输层在 Windows 上跑通整个 server 套件。

| 版本 | 时序 | 结果 |
| --- | --- | --- |
| 修复前（`pD`） | 带插桩 | **3/3 挂**在 `stop.failInflight.post` |
| 顺序修复（`pE`） | 带插桩 | **3/3 挂**在同一行（sha 已核，修复确实在里面） |
| 改异步（`pF`） | 带插桩 | **3/3 panic**（shutdown 首次通过） |
| 删掉 `CancelIoEx`（`pG`） | 带插桩 | **3/3 过** |
| **同上，交付版（`pI`）** | **不带插桩** | **5/5 过**，`92 passed; 5 skipped; 0 failed` |

**为什么两种时序都要验**：插桩会改变时序，而原始故障是竞态——「确定性复现下修好了」
不蕴含「竞态版也修好了」，而交付的正是不带插桩那个。

**为什么是 5 次不是 3 次**：原始形态是 2 挂 1 过。三次全过是碰巧的概率，
按**观察值**（通过率 1/3）算是 3.7%，按**保守假设**（通过率 2/3）算是 **约 30%**；
五次分别是 0.4% 和 13%。**「保守估计约 30%」这个限定词不能省——去掉它就成了
一个听起来像测出来的数。**

**这个结论的边界**：5/5 过**不等于**没有竞态，只等于在这个基率下没观察到。
准确的说法是：**若仍有竞态，其发生率显著低于原来的 2/3。**

## 二之三、M3 中文输入：已在真终端里打出汉字【实测】

全链路通过，两张验收截图为证：

| 环节 | 证据 |
| --- | --- |
| TSF 激活 | `ActivateEx ok, clientId=32` → `context pushed, editCookie=1` |
| 按键进入 IME | 第一个真实虚拟键就出 `OnStartComposition`（**不能用合成文本，它绕过 IME**） |
| 组合串 | `SetText 0..0 <- "n"` → `SetText 0..2 <- "你"` |
| **候选窗定位** | 截图：候选窗**紧贴 preedit 正下方**，不是屏幕角落 |
| **preedit 渲染** | 截图：终端里 `>ni` **带下划线**，核心自己画的 |
| **上屏** | `OnEndComposition commit="你"`，截图里 `C:\Users\bestf>你` |

**`SetText 0..2 <- "你"` 这个范围本身是一次验证**：「你」是 **1 个 UTF-16 码元但占 2 格**，
是这条路上最容易算错的地方。用核心的 `ghostty_unicode_grapheme_width` 算的，不是手写表。

### 实现上的一个判断，不是从探针照搬来的

探针里文档是一行自己画的文本、在自己编的网格上。接进终端时形状变了：
**文档只装组合串**——终端不是可编辑文档，`ITextStoreACP` 不假装持有一个；
`GetText` 只答 preedit，上屏的字通过 `ghostty_surface_text` 离开后就不再属于这里。

### ⚠️ `ghostty_surface_ime_point` 的四个出参不在同一个单位里

读 `Surface.zig:2277-2340` 发现的，**96dpi 上看不出来，缩放显示器上会**：

| 出参 | 实际是什么 |
| --- | --- |
| `x` | 光标格的**水平中点**，不是左边缘（`x += cell_width / 2`） |
| `y` | 光标格的**底边**，不是顶边（`y += cell_height`） |
| `height` | 格高 **÷ content_scale** |
| `width` | preedit 宽度，**故意没有除以 content_scale** |

最后一条是源码里作者自己的话：*"we don't apply content scale here because it looks
like for some reason in macOS its already scaled. I'm not sure why that is"*。

**当前的处理是不用 `width`**——列数由宿主按宽度表自己量，x/y/height 乘回 scale。
**接 DPI 缩放的人要先看这一条。**

### 已知未解（原样记下，不是失败）

- **滚动**：核心自己在 `imePoint()` 里的 TODO 还在——组合中滚屏可能让候选窗跑偏。
- ~~**没有 VK → keycode 表**~~ → **已解，而且是用「不需要这张表」的方式解的（#73）。**
  `ghostty_input_key_s.keycode` 不是 `GHOSTTY_KEY_*`——核心拿它去查
  `src/input/keycodes.zig` 的**原生列**，Windows 构建下那是第 3 列，即 IBM PC set-1
  扫描码。而 `WM_KEYDOWN` 的 lParam 位 16–23 正是扫描码、位 24 是扩展标志。
  **转换六行，核心自带的 673 行表干掉剩下的活**（`windows/host/src/keys.rs`）。
  写一张 VK→key 的表也能工作，但那会是第二张要和 `keycodes.zig` 保持一致的表，
  而不一致的表现是「某个布局下某个键什么都不做」——不报错，没人会发现。

### 真机上暴露的两处，都不报错

| 症状 | 根因 | 是什么定位的 |
| --- | --- | --- |
| 窗口「未响应」、全黑，日志停在 `[tab] surface` | `layout()` **持 `STATE` 锁**调 `SetWindowPos`，子窗口的 `WM_SIZE` 同步派回同一线程再取锁；`std` 的 `Mutex` 不可重入 | **缺的那一行**：`[tab] created` 没打，而它和上一行之间只有 `layout()` |
| 死锁修好后仍然全黑 | GL 上下文建在一个**还是 100×100** 的占位子窗口上（见 `development.md` 5.2 第四条）；**事后 `set_size` 补救不回来** | 像素格式探针 = 5（绑定成功 → 故障在下游）＋ 四版本对照；**首次归因「必须先显示」被 `--hide-first` 对照推翻，真正起作用的是尺寸** |

第一条现在有哨兵：`windows/host` 的 `state()` 先 `try_lock`，再犯会打
`[state] lock contended`，而不是像这次一样一行都不留。

### 一条读数陷阱，代价是一整轮误判

旧版 `polter-host-m3.exe` 还开着，而新版日志**同名**（都是 `C:\app\polter-host.log`），
一个文件里混着两个进程。「主线程 ticks 在涨」被读成「循环没死、卡在某条消息里」，
**那串心跳其实是旧进程打的**，新版死在进消息泵之前。判据是：日志里同时出现只有新版
会打的行和只有旧版会打的行。现在日志是 `polter-host-<pid>.log`，首行打 pid 和路径。

8. **⚠️ `ctrl+shift+c` 会静默变成「复制标题」——这条还没发生，但触发条件已经在了。**

   **两条腿不一样，这是关键**：`ctrl+c` 靠 **keycode** 走 `ctrlSeq`；
   `ctrl+shift+c` 的默认绑定是 `.{ .key = .{ .unicode = 'c' } }`（`Config.zig:6782`），
   而 `Binding.getEvent` 的三级匹配是 物理键 → `utf8` 单码点 → **`unshifted_codepoint`**
   （`Binding.zig:2787`）。ctrl+shift+c 的 `WM_CHAR` 也是 `0x03`，text 为空，
   **所以它只能靠 `unshifted_codepoint` 匹配上**，而那个值来自 `keys.rs` 的
   `MapVirtualKeyW(vk, MAPVK_VK_TO_CHAR)`。

   - **触发条件**：`MapVirtualKeyW` 在某个键盘布局下对 `VK_C` 返回 0。
   - **症状**：核心的绑定匹配不上 → `surface_key` 返回 false →
     落到 `keys.rs` 的 `accelerator` 表，那里 `(ctrl, shift, VK_C)` 指向
     **`copy_title_to_clipboard`**。于是**复制选区静默变成复制标题**。
   - **为什么难发现**：「什么都不做」会被立刻注意到，「做了另一件事」不会——
     用户会以为自己没选中。
   - **两条腿不会一起坏，也不能互相当对照**：ctrl+c 好不代表 ctrl+shift+c 好，反之亦然。

### 9. 三条只有开了核心日志才看得见的事（2026-09-01）

**背景**：`libghostty` 的 `std.log` 在真机上「看不见」这笔账，**根本不是欠账**——
`src/global.zig` 读环境变量 `GHOSTTY_LOG`，而 `Logging{ stderr, macos }` 里
`stderr` 对 lib 构建默认 `false`、`macos` 在 Windows 上恒为 `false`，
**两个 sink 相加等于没有出口**。`GHOSTTY_LOG=stderr` 就够了，宿主现在在
`ghostty_init` 之前自己设它。

> `main_c.zig` 的注释本来就写着 "On Windows that leaves no sink at all"。
> **前半句写清楚了，后半句要读的人自己接**：既然两个 sink 都关着，那总得有东西能打开它们。
> 那句注释被读过不止一次，没有人往回推那一步。

**打开之后立刻暴露的三条**，它们都不是新出现的问题，是**在此之前无法被看见**：

1. **`warning(config): no default shell found, will default to using cmd`**
   Windows 上没有 shell 探测，**永远回落到 `cmd`**。用户装了 PowerShell 7 也不会被用上。
2. **`warning(io_exec): no resources dir set, shell integration disabled`**
   shell 集成（提示符标记、当前目录跟踪、`cd` 同步那一类）在 Windows 上**整个是关的**。
3. **`warning(stream): unimplemented mode: 9001`** 和 `ignoring CSI t`
   `cmd` 会发这些，目前忽略。无害，但它们标出了终端能力的边界。

**这一条真正的价值不是上面三件**，是从今往后真机故障能读到根因：
缺陷「关闭标签挂死主线程」正是靠它从「卡在 `ghostty_surface_free` 某处」
缩到「第一个 join 过了、`threadEnter` 执行了、卡在 io 线程那个 join」。

### 10. `160x0`：出现过一次，未复现，原因未查清（2026-09-01）

**现象**：`--striptest` 开 18 个标签的过程中，**第 6 到第 15 次布局连续把新 pane 摆成 `160x0`**
（宽 160、**高 0**），第 16 次自己恢复 `1000x670` 并一直正常到结束。约七秒。

**已排除的三条**（都是读代码，不是猜）：`--selftest` 混跑（日志里零命中）、
别的窗口共用框架 wndproc（`hud`/`keyseq`/`search`/`palette` 各有自己的窗口类和 wndproc）、
UI-C 改小了框架窗口（那四个模块拿到 `frame_hwnd()` 之后只 `GetWindowRect` 读，无任何写）。
`st.frame` 全程只被写过一次。**所以那七秒里框架客户区是真的 160×≤30，为什么没有证据。**

**下一版（加了 `client=` 探针和 `refusing` 拒绝分支）上未复现**，18 次布局 `client=1000x700` 一次没抖。
**但这不能记成「修好了」**：三处改动没有一处能解释它——**`refusing` 分支一次都没触发**
（它只在坏情况发生时才有作用），`client=` 是纯日志，`selftest` 收口和这条路径无关。
**「被顺带改掉」这个可能性因此很弱，剩下基本只有间歇性**——而「十次全是 160、一次没抖」
和间歇性同样别扭。**两种都没有证据。**

**危害已经拿掉**：`content_bounds` 现在在高度为 0 时返回 `None`、整个 layout 不执行，
**保住上一次的好几何**，而不是把 pane 摆成零高度（原来 `SetWindowPos` 会报告成功——
把窗口移成零高度是合法请求）。

**再发生时怎么判**：`[layout] refusing: client WxH (strip N), window WxH zoomed= iconic=`
**同时打客户区和窗口矩形**，那两个数正好分开两种世界——窗口矩形也小 → 窗口真的变小了；
窗口矩形正常而客户区小 → **`WM_NCCALCSIZE`（UI-A）算错了**。

> **⚠️ 这条链上有三个「看起来像独立证据」的东西，全都在它下游**：
> `warning(surface): very small terminal grid detected with padding set`（核心对我们喂进去的
> 尺寸的正确抱怨，客户区正常时不出现）、`[hud] size 16x0 from client 160x1`、
> 以及 `[win] surface WM_SIZE 160x1`。**三个都不是独立观察，是同一个原因的三个回声。**

### 11. 批次二那四个缺陷，各自的下场（2026-09-01）

`--striptest` 和真机手动那两轮共暴露四条，**此前它们只活在群聊里**：

| # | 缺陷 | 状态 |
| --- | --- | --- |
| 1 | **关闭标签挂死主线程** | **已修**（`dbbad4314`）：管子有两个写者、都是我们的，而关它的 `CloseHandle` 排在等它的 `join` 之后。现在 `surface_free` 15 毫秒返回，两条入口（合成点击、`binding_action`）都验过 |
| 2 | `new_split` 后**原 pane 没收到 `WM_SIZE`**（字符横向拉伸两倍） | **已修**：`Placement` 契约（`ef3147208`）让返回值覆盖每个 pane，调用方不再只摆新增那一个 |
| 3 | `zoom` 后**未被 zoom 的 pane 没被隐藏** | **已修**：同上——`Hidden` 现在是返回值的一部分，不必求补集 |
| 4 | **鼠标点击激活后整条标签条消失** | **未复现，未解释**。合成点击（`synth_click`，走 `hit()` → `on_button_down/up`）行为与模型路径完全一致，`paints` 都是下一拍涨。**真实点击多出的是 `WM_ACTIVATE` / `WM_NCACTIVATE` / `WM_SETFOCUS`，而那一层至今没有被任何自动化覆盖**——`--striptest` 明确不假装覆盖它 |

**第 4 条要说清楚它的位置**：它不是「查过了没问题」，是**唯一一个还没有工具能碰到的现象**。
覆盖它要让宿主自己合成真实的窗口激活消息，那是另一件事。

- 被否决的另一边是「出厂绕、第三方按机器当前策略走，被拦住就报一条清楚的错」，

**这条不是机械结论，是被看过之后的决定**（`docs/poltergeist/provisioning.md` 9.6 第②条）。

## 五之三、Ctrl-C：判据在跑之前先写死

**缺陷已确证存在**（Polter 终端里 Ctrl-C 不中断 `ping -t`），
**位置未定**：宿主/核心 **或** 探针，二选一。下面这张表就是用来二选一的。

### 为什么位置退回了「未定」

原先的结论是「缺陷在我们这边」，依据是一个负对照：同一个 argus 组合发给原生 cmd
窗口能立刻中断。**那个对照不成立**——`cmd` 读的是控制台输入缓冲区，拿到的是虚拟键码
和字符，**它从头到尾不看扫描码**。所以那次对照证明的是「按键到达了 OS、并且能让一个
控制台程序收到 Ctrl+C 事件」，**它没有证明 `WM_KEYDOWN` 的 lParam 里扫描码非零**——
而后者是我们这条路唯一依赖的东西。教训记在第七节第 14 条。

### 静态复核已经确定的三件事

**1. 在 Windows 上，Ctrl-C 完全押在物理键查表上，没有第二条路。**
`key_encode.zig:682` 的 `ctrlSeq` 取字符只有两个来源：

```zig
if (utf8.len == 1) break :char utf8[0];      // 第一来源：文本
if (logical_key.codepoint()) |cp| { ... }    // 第二来源：物理键
return null;                                  // 没有第三个
```

**`unshifted_codepoint` 不是 `char` 的来源**，它只在 `char` 已取到且是大写字母时用来
转小写。而 `keys.rs` 对控制字符**故意不送 text**（`c >= 0x20` 才填）。
所以 Ctrl-C 走的必然是第二条：`keycode → .key_c → 'c' → 3`。
**在会送 text 的平台上 keycode 错了会被文本掩盖，Windows 上不会**——
「映射这一段是对的」不是旁证，是唯一的承重墙。

**2. `keycode == 0` 会静默命中垃圾条目。**
`keycodes.zig` 里 Win 列为 `0x0000` 的有 **85 条**，线性扫描第一个撞上的是第 184 行
`.{ 0x000000, 0x0000, 0x0000, 0x0000, 0xffff, "" }`，code 是空串，
`code_to_key.get("")` 查不到 → `key = .unidentified` → `codepoint()` 返回 null →
`ctrlSeq` 返回 null → **什么都不编码**。

| | 扫描码正常 | **扫描码 = 0** |
| --- | --- | --- |
| 打字母 `a` | text=`"a"` → 正常 | `.unidentified`，但 **text 仍在** → 命中第一来源 → **照常工作** |
| **Ctrl-C** | `.key_c` → `'c'` → `0x03` | **`.ignored`，静默失效** |

**字母正常、Ctrl-C 静默失效——和症状逐字吻合。** 什么时候扫描码会是 0：物理键盘不会，
RDP 通常会合成，**但 `SendInput` 只填 `wVk`、不带 `KEYEVENTF_SCANCODE` 时会**。

**3. TSF 吃不吃这个键，读我们的代码得不到答案。**
宿主没有注册自己的 `ITfKeyEventSink`（`tsf.rs` 只实现了 `ITextStoreACP` 和
`ITfContextOwnerCompositionSink`），**吃不吃 100% 是当前文字服务的决定**。
而且文档管理器只要 surface 有焦点就是 focused（`ime_init` 的
`AssociateFocus` + `SetFocus`），**与是否在组合中无关**——所以 Ctrl-C 一定会被问到。

### 判据表：`keys.rs` 那行日志，一行定案

```
[key] msg=0x100 vk=0x43 keycode=0x… mods=0x… text=… -> surface_key=…
```

| 看到什么 | 结论 | 下一步 |
| --- | --- | --- |
| **压根没有这行**，只有 `[key] TSF ate … vk=0x43` | **看输入法当时的状态，见下** | 组合中：正常；空闲时：问题在 IME 交互 |
| `keycode=0x0` … `surface_key=false` | **扫描码为 0** | 换物理键盘、或给注入补 `KEYEVENTF_SCANCODE` 复测；**这时缺陷在探针不在产品** |
| `keycode=0x2e mods=0x2 text=none → surface_key=false` | 送进去的是对的，核心仍拒了 | **上面的静态复核有错**，回去重读 `ctrlSeq` |
| `keycode=0x2e … → surface_key=true` | 核心编码并入队了 | **缺陷在 key 路径下游**：pty 写入 / ConPTY / 子进程 |

> ⚠️ **第 1 行是状态相关的，不是一个静态结论。** 2026-09-02（**日期未能确认**，可能跨午夜——测试机 +08:00）做了组合中/无组合的对照：
>
> | 输入法状态 | `WM_KEYDOWN` 到达 wndproc？ |
> | --- | --- |
> | **有活动组合**（屏上 `a'b`、候选窗开着） | ❌ `TSF ate msg=0x100 vk=0x11 (not dispatched)` |
> | **按 Esc 清掉组合之后** | ✅ 到达，但 `keycode=0x0` |
>
> **微软拼音只在组合中吃 Ctrl 组合，空闲时不吃。** 所以同一台机器、同一个按键，
> **两种状态会走进这张表的不同行**，而两种状态在用户那里都是常态。
> **在组合中看到 `TSF ate` 是正常的，在空闲时看到才是异常**——
> 原来的写法把它写成了静态结论，会让人把正常读成故障。

**`mods` 出现 `0x22` 是正常的**（`0x2` ctrl + `0x20` numlock）：
`Mods.binding()` 只保留 shift/ctrl/alt/super，锁定位和侧位都会被剥掉。

⚠️ **`surface_key=true` 有一个例外，别过度解读**：`Surface.zig:2894` 在
`terminal.modes.get(.disable_keyboard)` 时**直接返回 `.consumed` 而不编码任何东西**。
概率很低，但它是「返回 true ⟺ 已写入 pty」这条等价关系唯一的漏洞。

### 顺手排除掉的两条（附为什么它们本来是好候选）

- **`CREATE_NEW_PROCESS_GROUP` —— 排除。** 微软文档写明该标志会为新进程组的所有进程
  **禁用 Ctrl+C**，与症状完美吻合。但 `Command.zig:418` 的 flags 只有
  `CREATE_UNICODE_ENVIRONMENT`（有 attribute list 时加 `EXTENDED_STARTUPINFO_PRESENT`），
  全仓 `grep` 不到这个标志。
- **Windows 上 ctrl+c 被绑成复制 —— 排除。** `Config.zig:6775` 的分支是
  `isDarwin → super，否则 → ctrl+shift`，源码注释自己写着
  *"Linux ctrl+shift since ctrl+c is to kill the process"*。**ctrl+c 上没有任何默认绑定。**

## 五之四、M5 的验收判据（2026-09-01 改写）

**原判据把三件阻塞方不同的事捆成了一句**：插件自己做完、那家 CLI 接受、以及对端存在。
**捆在一起时，只要最后一件没到，前两件的成果就无法表述。** 拆成三级：

**必须（与环境无关）— 已达成。**
插件在真 Windows 上按真协议跑完：握手、批次、应答、三态、失败时 tell 排在 `ok:false`

## 七、方法论（每条都带触发条件，都是真踩出来的）

0. **拿到一个支持结论的读数就停手——这是下面几条的母形状。**
   今天被推翻的九条判断里，多数不是因为没有证据，而是**证据就在手里，
   而人停在了让结论成立的那一步**：
   - 令牌下发那条：链的**下游**读了（env 怎么被消费），**上游**没读（env 怎么被构造）
   - 目录逃逸那条：失败消息读了（`expected 2, found 0`），**那个断言在数什么**没读
   - 控制台归属那条：看到测试转绿就归因给它，**没注意同一轮还有第二个变量在变**
   - action 计数那条：拿到一个数，**因为它和文档一致就不再追**（而文件里有两个同名 enum）

   **触发条件很具体：当一个读数刚好支持你正想成立的那个结论时，那就是要多走一步的时刻。**
   相关的一条：**升级一个结论（从「疑似」到「阻塞项」）比提出它需要更多证据**，
   而升级往往发生在最想收工的时候。

1. **编译挡着链接，链接挡着运行，运行挡着绘制。** 今天穿了五层，最后一层是上游显式挡的。
2. **「那个假设没被检验过，不是被排除。」** 未经检验的假设被当成已排除，比已知未解更危险——没人会再回去看它。
3. **同一个「什么都没有」背后有几个互不相同的世界，而读数不区分它们。**
   一天之内三次差点把「日志里没有那行」当成结论，三次的分母完全不同：
   **探针根本没发出那个键**（argus 报 `success: true`，日志显示它只发了 Ctrl，主键一个没发）、
   **代码没有走到打印那行的地方**、**进程已经不在了**。
   **三种情况的补救毫无共同之处，而三种情况在日志里长得一模一样。**
   所以看到一个阴性时，先问「有几种世界能产生它」，再为每一种找一个能把它排掉的读数——
   往记事本发一个不带修饰键的单键，分的就是第一种。
   这是第 2 条的加强版：那条说未检验不等于已排除，这条说**同一个缺席有好几个成因**。

4. **⭐ 在拿到读数之前先问:「如果被测的那个东西是错的,这条判据会看见吗?」**
   ——不是「这条判据通过了吗」。
   **这把「判据够不到被判的东西」从一个只能事后发现的意外,变成一个可以事先问出来的性质。**

   2026-09-01 一天里这件事发生了**六次**,六次「够不到」的维度各不相同,
   而**症状全都是「测试是绿的」**:

   | 判据 | 够不到的东西 |
   | --- | --- |
   | 启动表读 `builtin.os.tag` | **另一个操作系统**的表项,在构建机上不可达 |
   | `--selfresize` 看中心像素 | 贴在左下角的旧画布**永远盖住中心** |
   | 全局热键自测 | 脚本跑在 Polter 里**就意味着 Polter 是前台** |
   | 手写 JSON 的单元测试 | **另一个实现**——它只证明「我和我同意」 |
   | `mutate.ps1` 的注入目标写死 | **另一个文件**,于是那组断言从来没有地板 |
   | 那次注入的离线预检 | 够到了文件,**没够到产生那个字符串的那一层**(PowerShell 转义) |

   **六次里没有一次能通过上面那个问句**,而六次全是事后才发现的——
   其中一次(`--selfresize`)还先以「**通过**」的形式活了一整天,
   期间它该发现的那个缺陷又长出两处症状。

   **这条和第 3 条是一对**:第 3 条讲怎么读一个阴性,这条讲**在拿到阴性之前
   就判断这条判据配不配产生阴性**。前者救的是结论,后者救的是实验。

   ⚠️ **补救几乎总是同一招:把那个够不到的维度变成参数。**
   目标系统当参数收、判据点从前后尺寸算出来、预检从产生字符串的那一层取锚点——
   **三处不同的工作,同一个动作。**

   ### 这一族里最常见的一种形式:**自检闭合在自己身上**

   一个「还原之后校验」的步骤,如果比的是**它自己启动时取的那份快照**,
   那么当那个文件在脚本启动**之前**就已经是错的,它会忠实地把它还原成那份错的,
   然后报告成功。**「和我启动时看到的一样」不等于「对」。**
   要用运行之外的东西比——仓库里的字节、别处取的哈希。

   **同一天里这个形状出现了三次,而三次的「自己」各不相同:**

   | 校验 | 闭合在什么上 | 打开它的外部基准 |
   | --- | --- | --- |
   | 变异脚本的 `matches the original` | 脚本启动那一刻的快照 | 仓库里的字节数 + sha |
   | 手写解析器的单元测试 | 同一个人写的那份实现 | 另一个实现真的去读一遍 |
   | **主控说「我已经放 X 上机」** | **主控自己写下的那句话** | **对方那边有没有收到** |

   **第三行是人的版本,而它当天发生了两次**,两次都造成了七八分钟的空转:
   一句描述被当成了一个动作,**而唯一的证据是写下那句话的人自己。**

   ⚠️ 还有一个更小的形态,值得单记,因为它连「跑」都不用就会错:
   **位置指代**。一份清单末尾写「最后那条是这个陷阱的缩影」,
   清单增加一行之后,那句话开始指向另一条——**不报错、不难读、只是指错了**。
   **它的正确性依赖于一个它自己不检查的条件(清单长度)。** 指名,不要指位置。

   ### 用在调试上:**不问「这个值对不对」,问「这个东西是不是我以为的那种东西」**

   同一个问句挪到调试里,形状变了:不问「这次改动会让它过吗」,
   问「**如果我猜错了,这次输出会告诉我吗**」。

   一次真实的追查:某条注入始终打不进去,五个诊断窗口,**四次在猜**。
   打印过锚点长度、锚点字节、键名清单、`.Contains` 和下标两种取法——**全部正常**。
   最后由一条只打**类型和计数**的探针定案:

   ```
   M7:  object type : System.Object[]                 ← 数组
   M8:  object type : System.Collections.Hashtable    ← 对照
   ```

   一处结尾的逗号被后来的插入挤到了行首,而在 PowerShell 里换行结束语句,
   **行首的逗号是一元数组构造运算符**——那个条目被包成了一个只含它自己的数组。

   **五个诊断全被骗过,而骗法很干净**:数组会把成员访问穿透给它唯一的元素,
   所以 `.Name`、`.Keys`、`.Pairs` 全部「正常」,**只有按字符串下标取值返回 null**。
   **它们问的全是「值对不对」,而那个东西在「值」这一层上确实都对。**

   > **「锚点找不到」和「这个条目不是我以为的那种东西」,症状完全相同。**

   追查的人自己的账,比机制更值得留:

   > **我每次都在问「这个值对不对」,没有一次问「这个东西是不是我以为的那种东西」——
   > 类型是我从头到尾假设的,所以从头到尾没打印它。**
   > **打印的是我怀疑的东西,不是我假设的东西。**

   **「怀疑的」和「假设的」是两个不相交的集合,而人只会去打印前者。**
   后者是没在被怀疑、因而也没人看过的那些——**而它们恰恰最可能出错,因为没人看过。**

   ⚠️ **一条没有对策的**:同一轮里,那个人先写了一句错的根因注释
   (「注释块放在 hashtable 里导致键丢失」),查清后改掉了。
   **一条写错的根因注释比没有注释更贵,因为下一个人会照着它排除掉正确的方向**
   ——它不是浪费时间,是把人推向反方向。
   而「注释要么带可 grep 的符号名、要么不写」那条对策**对因果断言无效**:
   **因果恰恰是最不可能带符号名的那种断言。这个洞今天没有对策,记着。**

5. **判据不适用的时候,要说自己不适用。**
   一条算不出结果的判据如果静默,那么「日志里没有那行」同时意味着
   「它适用而且没发现问题」和「它这次根本没被应用」——**而这两件事的下一步完全相反。**
   `newly_exposed_point` 在没有任何一边变大时返回 `None`,并打印
   「nothing grew; the new-region criterion does not apply」,就是为了不制造第四个分母。

6. **用错的探针得到的阴性，和没做过实验是一回事。** `GetConsoleWindow` 对「无控制台」和
   「有控制台无窗口」都返回 null。
7. **负对照必须在过滤之前取。** `Where-Object` 之后再数，数的是过滤后的世界。
   同理适用于「查产物里有没有某个字符串」：**「0 处命中」和「这个搜索根本找不到东西」
   长得一模一样**。核对交付版不含调试插桩时，要同时搜一个必然存在的符号作地板——
   `插桩串: 15 → 0，而 DisconnectNamedPipe: 1 → 1`，后半句才让前半句成立。
8. **当一个阴性结果让你少干活时，那就是必须量基率的时刻。**
9. **当一条二手前提能决定下一步做什么时，先花两分钟核它。** 核它一次 `grep`，不核一个完整往返。
10. **预先声明判据，是为了在结果出来之前锁住解释权。**
   **这一条在 2026-09-01 有四次独立到达，来自三个不同的人和三种不同的工作**，
   所以它不再是一条建议：变异测试里「修完之后它应该变红」被事先写下来
   （而不是事后解释「它当时为什么绿」）；`--qttest` 的每一行判据带着输入量
   先于代码写出；分屏的六条真机判据写在上机之前；插件页的 29 条范围清单
   在写第一行代码之前发出，**并且作者在里面自己揪出一条写错的判据**
   （引了个不存在的行号——`ghostty_diagnostic_s` 只有 `message`）。
   **最后那次最能说明问题：一条判据在被使用之前就被作废，代价是零；
   它如果活到验收那天，会以「这项没法验」的形式出现，而那时它看起来像是产品的问题。**
11. **一直在调整一个不该存在的东西的参数。** `CancelIoEx` 三轮错了三种方式，正确动作是删掉**对读的**取消（对 *connect* 的取消是必须的，见 `transport_windows.zig:153`）。
   每一步都对，方向整体是错的。
12. **规则的适用条件比规则本身更难记住。**「别在锁里做系统调用」是对的，但那把锁正是防
   use-after-close 的机制。
13. **绕开一条路，不等于绕开它底下的那一族问题。**
14. **负对照检验的那一层，必须就是被测路径依赖的那一层。**
    这条不是「要做负对照」的重复——**对照做了，也通过了，然后主控停在了那里。**

    Ctrl-C 不生效，主控的负对照是「同一个 argus 组合发给原生 cmd 窗口能立刻中断」，
    据此结论「探针是好的，缺陷在我们这边」。**但 `cmd` 读的是控制台输入缓冲区，
    拿到的是虚拟键码和字符，它从头到尾不看扫描码**——而扫描码是我们这条路唯一依赖的
    东西（见第五之三节）。那个对照证明了「按键到达了 OS」，**没有证明我们要的那一层**。

    **和第 3 条的区别**：第 3 条是探针用错了、阴性等于没做实验；
    这一条是**探针是对的、实验做成了、阳性也是真的，但它测的是隔壁那一层**。
    第 3 条给的是「没有信息」，这一条给的是「有信息，且指向错的方向」——**更贵**。

    **触发条件**：当你写下「我做过负对照了」这句话时。
    **下一句必须是**：「它对照的是哪一层？被测路径依赖的是哪一层？两者是同一层吗？」
    这次两者差了一层，而差的那一层正好是唯一相关的那层。


15. **一个读数如果对「对的行为」和「错的行为」给同样的值，它就不是判据。**
    **触发条件**：当你要检查的性质是「某件事**不该**发生」时。
    - **删除计数**：「删了 1 个」对「只删了该删的」和「删了该删的 + 漏了一个」是同一个数——**连方向都不给**。
    - **两次跑完文件逐字节相同**：一个「每次都重写、但写同样的值」的插件产生的正是同样的字节。
    - **配置文件的 sha 变了**：不区分是谁改的（真凶是另外两个活着的 CLI 会话）。
    **解法都是换一个能分辨方向的问题**：「它还在吗」「SDK 自己报了 provisioned 吗」「我写的那个特征串在不在里面」。

16. **「没报错」不等于「做成了」。**
    **触发条件**：当你用「某条错误日志没出现」当证据时。
    `log.warn` 只在 errno 不是 SUCCESS 时打，所以「没有那行 warn」只证明**调用返回了 ≥ 0**，
    **不证明那个字节进了那根管子**——后来的隔离实验证明它确实没进去。
    同族：「配置文件写出来了」≠「对面读得懂」（`opencode` 那轮才第一次由对面回答）。

17. **一个读数能不能外推，取决于「测量时的条件和目标条件有没有差别」。**
    同一次运行、同一份日志里的两个读数，一个能外推一个不能：
    - **写 quit 管道返回成功** → 能外推（不依赖写端是否已关）
    - **`CancelIoEx` 返回 SUCCESS** → **不能**（成败取决于此刻读是否 pending，而修复恰好改了这一点）
    **所以第一轮那个 SUCCESS 什么都没证明**，要专门把 `closeConsole` 挪到取消之后再跑一次才有效。

18. **一条判据的证据如果被别处限流，它会悄悄地不再可检验——而且失败的样子和「功能没跑」一模一样。**
    `[hud]` 的缩放判据原本要和 `tabs.rs` 的 `[win] … WM_SIZE` 相比，
    **而那行只打前 10 次，`--selfresize` 在 5 秒才触发，启动期布局早把配额用光了**。
    **解法是让判据自足**：`[hud] size 124x37 from client 1240x790 cell 10x21`，一行之内的除法，
    不依赖任何别人的日志。**判据不该跨文件依赖别人的可观测性预算。**

19. **一个碰巧成立的判据，和一个被设计成立的判据，在它们都通过的那天看起来一模一样。**
    「把第 1 个标签拖到第 3 位，检查内容跟着走」——七个标签标题全是 `cmd.exe` 时，
    **平行数组错位也长这样**。是「移动前先改名成 `MOVED-ME`」那一步让它真的可判。
    **一个只在标题各不相同时才有效的检查，不该依赖标题恰好不同。**

20. **找到一个真的根因就停手，而根因可以有两个。**（第 0 条的变体）
    ConPTY 挂死：两次独立诊断各找到**一个真的写者**（控制台主机那份、我们自己那份），
    **两个都对，两个都不够**——关掉任一个，管子仍有写者。
    > **两个人独立复核得出一致结论，在这里恰恰不是收敛的信号。**

21. **探针查的是输出，被查的是源。**
    自检脚本 grep「日志行是否存在」时搜的是**渲染后的字符串**，而源码里是格式串 → 两条假的「0 命中」。
    同族四例：`.cmd` 把 `=` 当分隔符拆掉 argv、Zig 多行字符串把 `\n` 写成两个字符、
    在缩放 0.6 的截图上目测像素、以及上面这条。
    **四次的第一反应都是去查产品**，而四次都是工具在篡改它要观测的东西。

22. **结论对、机制错，比两者都错更难发现。**
    「退出字节没送到」这个结论是对的，而给出的机制（mingw `_write` 按 int 截断 HANDLE → EBADF）是错的。
    **结论对的时候，没有人会回头查机制。**
    > 那一格不是靠谁更谨慎发现的，**是靠一次被证伪**——如果那条推理侥幸对了，
    > 我们会带着一个正确的结论和一个错误的机制往下走。
