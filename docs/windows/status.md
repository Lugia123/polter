### 这一夜真正的收获是一个形状，它出现了七次

> **报告的那一句，和它要报告的那件事，之间没有连线。**

七种形式各不相同：无条件的 `echo 全绿`；被命令替换重置的 `$?`；被管道吞掉的 `$?`；
把提交放进一条不检查结果的 `&&` 链；`cmd` 在解析整行时就展开 `%ERRORLEVEL%`；
一道闸在扫一个**已经不存在的形状**（全树零匹配、永远报干净）；一道闸的**名字比它
查的范围宽**。

**七次里有五次发生在核验环节本身**——也就是我们用来发现别的东西坏掉的那个装置上。
而它们的共同后果是同一句：**输出和真的通过长得一模一样。**

从这七次里长出来的东西，都写在别处而不是这里：三种假绿各自的防法（`s4.md`
判据一节开头）、行号引用闸、PowerShell 解析闸、摘要式的本机标识闸、以及五处
「以陈述句写的假话」被改掉。

### 一条给下一个人的规矩

**任何要报告某件事结果的 shell 循环，必须先 `rc=$?` 取值再用那个变量**，绝不让
命令替换或管道站在取值之前。这条不是风格，是这一夜里唯一一条**同时在三个人身上
各发作过一次**的错。

## 二、关停死锁：已修，两种时序下都验过【实测】

**结论**：命名管道传输层在 Windows 上跑通整个 server 套件。

| 版本 | 时序 | 结果 |
| --- | --- | --- |
| 修复前（`pD`） | 带插桩 | **3/3 挂**在 `stop.failInflight.post` |
| 顺序修复（`pE`） | 带插桩 | **3/3 挂**在同一行（sha 已核，修复确实在里面） |
| 改异步（`pF`） | 带插桩 | **3/3 panic**（shutdown 首次通过） |
| 删掉 `CancelIoEx`（`pG`） | 带插桩 | **3/3 过** |
| **同上，交付版（`pI`）** | **不带插桩** | **5/5 过**，`92 passed; 5 skipped; 0 failed` |

**为什么两种时序都要验**：插桩会改变时序，而原始故障是竞态——「确定性复现下修好了」
不蕴含「竞态版也修好了」，而交付的正是不带插桩那个。

**为什么是 5 次不是 3 次**：原始形态是 2 挂 1 过。三次全过是碰巧的概率，
按**观察值**（通过率 1/3）算是 3.7%，按**保守假设**（通过率 2/3）算是 **约 30%**；
五次分别是 0.4% 和 13%。**「保守估计约 30%」这个限定词不能省——去掉它就成了
一个听起来像测出来的数。**

**这个结论的边界**：5/5 过**不等于**没有竞态，只等于在这个基率下没观察到。
准确的说法是：**若仍有竞态，其发生率显著低于原来的 2/3。**

### 实现上的一个判断，不是从探针照搬来的

探针里文档是一行自己画的文本、在自己编的网格上。接进终端时形状变了：
**文档只装组合串**——终端不是可编辑文档，`ITextStoreACP` 不假装持有一个；
`GetText` 只答 preedit，上屏的字通过 `ghostty_surface_text` 离开后就不再属于这里。

### ⚠️ `ghostty_surface_ime_point` 的四个出参不在同一个单位里

读 `Surface.zig:2277-2340` 发现的，**96dpi 上看不出来，缩放显示器上会**：

| 出参 | 实际是什么 |
| --- | --- |
| `x` | 光标格的**水平中点**，不是左边缘（`x += cell_width / 2`） |
| `y` | 光标格的**底边**，不是顶边（`y += cell_height`） |
| `height` | 格高 **÷ content_scale** |
| `width` | preedit 宽度，**故意没有除以 content_scale** |

最后一条是源码里作者自己的话：*"we don't apply content scale here because it looks

     用户会以为自己没选中。

   `ACTION_MOUSE_SHAPE` / `ACTION_MOUSE_VISIBILITY` 已实现：形状按 surface 记下，
   由 pane 的 `WM_SETCURSOR` 应用——**后者才是让它持续生效的那一半**，因为 pane 的
   窗口类带 `IDC_ARROW`，`DefWindowProc` 会在鼠标一动时把它换回去。可见性另走一条
   投递（`mouse::WM_POLTER_MOUSE_VISIBILITY`），因为核心是在**用户打字时**要求隐藏的，
   而那正是不会有 `WM_SETCURSOR` 的时刻。

   - **形状对快速终端是好的**：`tabs::surface_of` 查不到 pane 时会兜到
     `quick::surface_of`，而快速终端用的是同一个窗口过程和同一个窗口类。
   - **够不着的只有「立刻隐藏」**：那条投递要一个 pane 的窗口句柄，而
     `tabs::pane_hwnd_of_surface` 走的是「窗口 → 标签 → pane」这张表，
     **快速终端的 surface 不在这张表里**（它不是 pane，也不属于任何标签）。
     所以它答 `None`，动作里记一行 `posted=0` 就过去了。
   - **后果**：在快速终端里打字，光标不会隐藏；移动鼠标时形状照常跟随。
   - 要修的话，得让那条投递能问到「这个 surface 的窗口是谁」而不是「它的 pane 是谁」——
     `quick.rs` 自己知道答案，缺的是把它接进同一个查询。

### 10. `160x0`：出现过一次，未复现，原因未查清（2026-09-01）

**现象**：`--striptest` 开 18 个标签的过程中，**第 6 到第 15 次布局连续把新 pane 摆成 `160x0`**
（宽 160、**高 0**），第 16 次自己恢复 `1000x670` 并一直正常到结束。约七秒。

**已排除的三条**（都是读代码，不是猜）：`--selftest` 混跑（日志里零命中）、
别的窗口共用框架 wndproc（`hud`/`keyseq`/`search`/`palette` 各有自己的窗口类和 wndproc）、
UI-C 改小了框架窗口（那四个模块拿到 `frame_hwnd()` 之后只 `GetWindowRect` 读，无任何写）。
`st.frame` 全程只被写过一次。**所以那七秒里框架客户区是真的 160×≤30，为什么没有证据。**

**下一版（加了 `client=` 探针和 `refusing` 拒绝分支）上未复现**，18 次布局 `client=1000x700` 一次没抖。
**但这不能记成「修好了」**：三处改动没有一处能解释它——**`refusing` 分支一次都没触发**
（它只在坏情况发生时才有作用），`client=` 是纯日志，`selftest` 收口和这条路径无关。
**「被顺带改掉」这个可能性因此很弱，剩下基本只有间歇性**——而「十次全是 160、一次没抖」
和间歇性同样别扭。**两种都没有证据。**

**危害已经拿掉**：`content_bounds` 现在在高度为 0 时返回 `None`、整个 layout 不执行，
**保住上一次的好几何**，而不是把 pane 摆成零高度（原来 `SetWindowPos` 会报告成功——
把窗口移成零高度是合法请求）。

**再发生时怎么判**：`[layout] refusing: client WxH (strip N), window WxH zoomed= iconic=`
**同时打客户区和窗口矩形**，那两个数正好分开两种世界——窗口矩形也小 → 窗口真的变小了；
窗口矩形正常而客户区小 → **`WM_NCCALCSIZE`（UI-A）算错了**。

> **⚠️ 这条链上有三个「看起来像独立证据」的东西，全都在它下游**：
> `warning(surface): very small terminal grid detected with padding set`（核心对我们喂进去的
> 尺寸的正确抱怨，客户区正常时不出现）、`[hud] size 16x0 from client 160x1`、
> 以及 `[win] surface WM_SIZE 160x1`。**三个都不是独立观察，是同一个原因的三个回声。**

### （二）任务 142：组合框的创建高度 `s(200)` 在原则上是错的

**状态**：不可观测（出货构建带 v6 清单，主题化 comctl32 **忽略**这个高度，所以改它在
屏幕上没有任何差别）· **销案**：**没有真机判据，而且不该为它造一个** —— 唯一能让它显形
的做法是拿掉清单重编，那会把这个进程里每个控件都换成 1995 年的外观，**是一次为了验证
而更换被测系统的实验**。它的销案条件是**别人的**：哪天真的要发一个不带清单的构建，那一次
就是它的判据。

组合框传给 `CreateWindowExW` 的高度，按定义是**含下拉列表的整体高度**。`s(200)` 既不对应我们想要的行数，也不对应任何东西。

**它今天无害，只因为 comctl32 v6 忽略它**（上面（一）那两组读数就是证据）。

**而让它无害的那个条件，是一个别人可能出于别的理由去动的文件**：`windows/host/polter.manifest`。那个文件顶部本身就在警告「没有 v6 依赖，这个进程里每个标准控件都会被 comctl32 v5 画成 1995 年的样子」。**拿掉它，这条就从「无害」变成「下拉封顶 8~9 行」**，而症状会看起来像一个全新的缺陷。

> **一个「今天无害」的缺陷，它的危险程度等于「让它无害的那个条件有多容易消失」。**

### （三）任务 129：两半的状态不同，而面板上它是一格

**状态**：半验（锁序那半已验；投递那半在那台机器上验不了）· **销案**：在一台**会投递
UIA 事件**的机器上跑 `-Mode events`，四个动作各自收到预期的事件类型。

| 半 | 状态 | 依据 |
| --- | --- | --- |
| **锁序**（发事件时会不会自锁） | **已验证** | 全份日志里 `[uia] ... not announced` **一次都没出现**，所以每次都走「宣告」那一支（`clients_listening=true`、`window_live=true`）；四个动作的 `raising` / `raised` **每一对都在同一毫秒闭合**，没有一次停在 `raising`；全程进程存活、日志继续长 |
| **投递**（客户端收不收得到） | **在那台机器上验不了** | 一个 20 行、不经过我们任何代码的独立探针：STA、交互式控制台、`DoEvents` 泵 20 秒、真实点击两次 → **收到 0 个焦点变更**。UIA 的「拉」在那台机器上一直是好的（四个 dump 模式、读 Document 的 Value 全都拿到数据），**坏的只有「推」** |

### （四）任务 164：标签条空白处右键 —— 拒绝路径从前是静默的

**状态**：未验 · **销案**：WT 跑完下面六格，**尤其第 4 格出现 `-> window buttons`**。

判据写在这里而不是 `docs/windows/keys.md`：那一份是键盘。

#### 任务标题里那句话是错的，而它花掉了两轮

面板上写的是「那个右键菜单不写任何日志行」。**三个菜单都有自己的行**（`[ctx]`、
`[tabmenu]`、`[stripmenu]`），`show_strip_menu` 的成功和失败路径都写。

**静默的是拒绝路径** —— 右键根本没走到 `show_strip_menu` 的那三条。

> 这个区别不是措辞：**按那句描述去找，会去看 `show_strip_menu`，而那里没有问题。**

**这句错在从观察转写成断言的那一步**：观察是「日志里没有这个菜单的行」，
写下来变成了「这个函数不打日志」。**观察对，断言错，而断言把人送进了错的文件。**

#### 改了什么

`strip::on_nc_right_click` 的三个 `return false`（越界 / 拿不到客户区 / 点在窗口按钮
那一片）从前都是静默的，各自都以系统菜单收场。屏幕上「空白处右键没菜单」同时是四件事
的样子，**而只有其中一件有日志**。

现在**一次消息一行，无论结果**：

```
w1 [strip] nc right-click client=(420,12)  strip_h=30 reserved_right=138 -> handed on
w1 [strip] nc right-click client=(1740,12) strip_h=30 reserved_right=138 -> window buttons
w1 [strip] nc right-click client=(420,52)  strip_h=30 reserved_right=138 -> outside the strip
w1 [strip] nc right-click client=(600,20)  strip_h=45 reserved_right=207 -> handed on   ← 150%
```

**一行在入口，不是三个出口各一行**：三个日志点会各自漂，而读的人分不出措辞改动和
行为改动。**带上的那两个数是做出这个决定的那两个** —— 决定错了，这一行直接说出是哪个数
错的。`strip_h` 尤其：它是 `strip_h(scale_of(frame))`，**缩放错了整条标签条都会拒绝，
而那看起来就是「这个菜单坏了」。**

#### 判据

**第 0 步**：`docs/windows/keys.md` §2.0.2 的「第 0 步（通则）」，**正文在那里，不抄**。
这条判据的正对照具体是：**在标签条空白正中右键一次，确认 `[strip] nc right-click …
-> handed on` 和 `[stripmenu] shown` 两行都出得来。两行都没有，本轮作废。**

| # | 点哪里 | 期望 |
| --- | --- | --- |
| 1 | 标签条空白正中 | 菜单出现；`-> handed on` |
| 2 | 一个标签上 | `[tabmenu] shown`；**不出现** `[stripmenu]` |
| 3 | `≡` 按钮上 | `ignored by design`，无菜单 |
| **4** | **最小化 / 关闭那一片** | **`-> window buttons`，无菜单，而这是通过** |
| 5 | 标签条**下方**的终端区 | **一条 `[strip] nc right-click` 都没有**（负对照） |
| **6** | **150% 下重做第 1 格** | 仍 `handed on`，且 **`strip_h=45`、`reserved_right=207`** |

**第 4 格是最容易被记成失败的一格** —— 没有菜单，而它是对的。**在那一行存在之前，
它和第 1 格失败长得一样**，这就是这次改动买到的东西。

**第 6 格验的是那两个数，不是「高 DPI 下菜单能用」。** 同一天有一条 DPI 疑案花了两轮，
**收掉它的正是一个印出来的数**；在那之前两轮都在猜。

**坐标从窗口矩形算**（`GetWindowRect` + 客户区偏移），不要从截图量 —— 截图报的 scale
是假的（`keys.md` §2.0）。

## 五之二、五条裁决（2026-09-01 已定）

**这一节和第五节不同。** 第五节是技术账——有确切位置、有人能查下去。
这三条**查不出答案**，因为它们不是事实问题：没有一次测量能告诉你该选哪边。

### 1. Windows 版的 UI 要做到多精细？ — **裁决：做到接近 macOS 的精细度（0.6 端）**

S3 档按 **约 2,617 Rust 行**计，不是 654。

> 保留它是为了让日后翻案的人知道当初的另一边长什么样，不是为了留个口子。

| | 行数 |
| --- | --- |
| macOS 的 titlebar tabs | 约 1,050 行，且是 Ventura / Tahoe **两套** |

Splits 的三个视图、`SurfaceView.swift` 的 SwiftUI 包装、插件页、关于/设置），

- **选 0.6**（向 macOS 的精细度看齐）：约 **2,617** 行

**差 2,000 行，约占总区间 6,600 行宽度的 30%。** 定了这一条，区间立刻收窄三成。

### 2. QuickTerminal 在不在 v1 射程内？ — **裁决：在**

**连带确定的**：全局热键（`RegisterHotKey`，80–150 Rust 行）从「要做但不是移植」
那一档里**升格成 v1 必做**——QuickTerminal 没有热键就没有意义。

877 macOS 代码行，目前**默认算在射程内**（`design.md` §1.3 的 S4 档）。
没有任何一份文档写过它是否要做——M1–M6 六个里程碑一次都没提到它。

- **在射程内**：按 S4 的系数，约 **610 – 877** Rust 行
- **不在**：区间下移约 750 总行

它不像 AppleScript 那样「Windows 上没有这个概念」——下拉式终端在 Windows 上完全成立
（Windows Terminal 自己就有）。所以这是**排期问题，不是可行性问题**。

### 3. 出厂插件里那 7 个 `.sh` — **裁决：系统字段暂不加**

**理由是「现在加等于 8 个插件都填同一个值」**：字段不携带任何信息，却要从现在起
一直维护。等第一个真正只支持某个系统的插件出现时再加，那时需求是具体的。
**这不改变 M5 的做法**（各补一份 `.ps1`，见 `development.md` 5.3），只是不动插件模型。

方向已定（各补一份 `.ps1`/`.cmd`，见 `development.md` 5.3），但连带那个
**机制缺口**没定：插件清单里没有「支持哪些系统」这个字段，
所以平台专属插件只能在启动失败时暴露。**改插件模型要人拍板，不在 M5 范围内。**

### 4. 无障碍（屏幕阅读器）在 v1 做到什么程度 — **裁决：v1 不做**

| Windows 要写的 | **450 – 900**（UIA 五个接口、36 个方法，`ITextRangeProvider` 一个就 18 个） |

**预算 41–58，实际 450–900，8–16 倍**，是全份估算里比例最悬殊的一格（`design.md` §1.7）。

**裁决：v1 不做，0 行。** 代价按当时列出的原样记在这里：

- **屏幕阅读器用户完全无法使用 Windows 版**
- **政府和大企业采购场景可能直接出局**——无障碍在那类采购里常是硬性验收项
- 后补时不会比现在贵（它是独立的一组接口，不和别的模块纠缠）

**没有把这 450–900 加进规模区间**，因为它现在不是需求。将来若翻案，
`design.md` §1.7 里那三档（不做 0 / 最小可读 450 / 做全 900）和它们各自的后果都还在。

### 5. 第三方插件的 PowerShell 执行策略 — **裁决：全部绕过**

宿主启动 `.ps1` 用 `-ExecutionPolicy Bypass`。**出厂 7 个插件是我们自己的，
这只是让它们能跑；但同一段代码会同样对待用户装进 `<config>/polter/plugins/` 的
第三方 `.ps1`。**

**裁决：全部绕过，不区分出厂与第三方。** 代价原样记下：

- **用户或公司 IT 特意设的 PowerShell 执行策略，会被 Polter 替任意第三方脚本绕过去。**
  这是一道别人设的闸，我们主动跳过它。
- 被否决的另一边是「出厂绕、第三方按机器当前策略走，被拦住就报一条清楚的错」，
  代价是第三方插件作者要处理签名或让用户改策略。

**这条不是机械结论，是被看过之后的决定**（`docs/poltergeist/provisioning.md` 9.6 第②条）。

## 五之三、Ctrl-C：判据在跑之前先写死

**缺陷已确证存在**（Polter 终端里 Ctrl-C 不中断 `ping -t`），
**位置未定**：宿主/核心 **或** 探针，二选一。下面这张表就是用来二选一的。

### 为什么位置退回了「未定」

原先的结论是「缺陷在我们这边」，依据是一个负对照：同一个 argus 组合发给原生 cmd
窗口能立刻中断。**那个对照不成立**——`cmd` 读的是控制台输入缓冲区，拿到的是虚拟键码
和字符，**它从头到尾不看扫描码**。所以那次对照证明的是「按键到达了 OS、并且能让一个
控制台程序收到 Ctrl+C 事件」，**它没有证明 `WM_KEYDOWN` 的 lParam 里扫描码非零**——
而后者是我们这条路唯一依赖的东西。教训记在第七节第 14 条。

### 静态复核已经确定的三件事

**1. 在 Windows 上，Ctrl-C 完全押在物理键查表上，没有第二条路。**
`key_encode.zig:682` 的 `ctrlSeq` 取字符只有两个来源：

```zig
if (utf8.len == 1) break :char utf8[0];      // 第一来源：文本
if (logical_key.codepoint()) |cp| { ... }    // 第二来源：物理键
return null;                                  // 没有第三个
```

**`unshifted_codepoint` 不是 `char` 的来源**，它只在 `char` 已取到且是大写字母时用来
转小写。而 `keys.rs` 对控制字符**故意不送 text**（`c >= 0x20` 才填）。
所以 Ctrl-C 走的必然是第二条：`keycode → .key_c → 'c' → 3`。
**在会送 text 的平台上 keycode 错了会被文本掩盖，Windows 上不会**——
「映射这一段是对的」不是旁证，是唯一的承重墙。

**2. `keycode == 0` 会静默命中垃圾条目。**
`keycodes.zig` 里 Win 列为 `0x0000` 的有 **85 条**，线性扫描第一个撞上的是第 184 行
`.{ 0x000000, 0x0000, 0x0000, 0x0000, 0xffff, "" }`，code 是空串，
`code_to_key.get("")` 查不到 → `key = .unidentified` → `codepoint()` 返回 null →
`ctrlSeq` 返回 null → **什么都不编码**。

| | 扫描码正常 | **扫描码 = 0** |
| --- | --- | --- |
| 打字母 `a` | text=`"a"` → 正常 | `.unidentified`，但 **text 仍在** → 命中第一来源 → **照常工作** |
| **Ctrl-C** | `.key_c` → `'c'` → `0x03` | **`.ignored`，静默失效** |

**字母正常、Ctrl-C 静默失效——和症状逐字吻合。** 什么时候扫描码会是 0：物理键盘不会，
RDP 通常会合成，**但 `SendInput` 只填 `wVk`、不带 `KEYEVENTF_SCANCODE` 时会**。

**3. TSF 吃不吃这个键，读我们的代码得不到答案。**
宿主没有注册自己的 `ITfKeyEventSink`（`tsf.rs` 只实现了 `ITextStoreACP` 和
`ITfContextOwnerCompositionSink`），**吃不吃 100% 是当前文字服务的决定**。
而且文档管理器只要 surface 有焦点就是 focused（`ime_init` 的
`AssociateFocus` + `SetFocus`），**与是否在组合中无关**——所以 Ctrl-C 一定会被问到。

### 判据表：`keys.rs` 那行日志，一行定案

```
[key] msg=0x100 vk=0x43 keycode=0x… mods=0x… text=… -> surface_key=…
```

| 看到什么 | 结论 | 下一步 |
| --- | --- | --- |
| **压根没有这行**，只有 `[key] TSF ate … vk=0x43` | **看输入法当时的状态，见下** | 组合中：正常；空闲时：问题在 IME 交互 |
| `keycode=0x0` … `surface_key=false` | **扫描码为 0** | 换物理键盘、或给注入补 `KEYEVENTF_SCANCODE` 复测；**这时缺陷在探针不在产品** |
| `keycode=0x2e mods=0x2 text=none → surface_key=false` | 送进去的是对的，核心仍拒了 | **上面的静态复核有错**，回去重读 `ctrlSeq` |
| `keycode=0x2e … → surface_key=true` | 核心编码并入队了 | **缺陷在 key 路径下游**：pty 写入 / ConPTY / 子进程 |

> ⚠️ **第 1 行是状态相关的，不是一个静态结论。** 2026-09-01做了组合中/无组合的对照：
>
> | 输入法状态 | `WM_KEYDOWN` 到达 wndproc？ |
> | --- | --- |
> | **有活动组合**（屏上 `a'b`、候选窗开着） | ❌ `TSF ate msg=0x100 vk=0x11 (not dispatched)` |
> | **按 Esc 清掉组合之后** | ✅ 到达，但 `keycode=0x0` |
>
> **微软拼音只在组合中吃 Ctrl 组合，空闲时不吃。** 所以同一台机器、同一个按键，
> **两种状态会走进这张表的不同行**，而两种状态在用户那里都是常态。
> **在组合中看到 `TSF ate` 是正常的，在空闲时看到才是异常**——
> 原来的写法把它写成了静态结论，会让人把正常读成故障。

**`mods` 出现 `0x22` 是正常的**（`0x2` ctrl + `0x20` numlock）：
`Mods.binding()` 只保留 shift/ctrl/alt/super，锁定位和侧位都会被剥掉。

⚠️ **`surface_key=true` 有一个例外，别过度解读**：`Surface.zig:2894` 在
`terminal.modes.get(.disable_keyboard)` 时**直接返回 `.consumed` 而不编码任何东西**。
概率很低，但它是「返回 true ⟺ 已写入 pty」这条等价关系唯一的漏洞。

### 顺手排除掉的两条（附为什么它们本来是好候选）

- **`CREATE_NEW_PROCESS_GROUP` —— 排除。** 微软文档写明该标志会为新进程组的所有进程
  **禁用 Ctrl+C**，与症状完美吻合。但 `Command.zig:418` 的 flags 只有
  `CREATE_UNICODE_ENVIRONMENT`（有 attribute list 时加 `EXTENDED_STARTUPINFO_PRESENT`），
  全仓 `grep` 不到这个标志。
- **Windows 上 ctrl+c 被绑成复制 —— 排除。** `Config.zig:6775` 的分支是
  `isDarwin → super，否则 → ctrl+shift`，源码注释自己写着
  *"Linux ctrl+shift since ctrl+c is to kill the process"*。**ctrl+c 上没有任何默认绑定。**

## 五之六、「静默死亡」不是不明原因，是不可观测

**任务 93 记的是「进程 85 秒后静默死亡：无 panic、无 stderr、无 exiting 行」，
判定为不明原因，出现过两次。** 记在这里是因为它此前只活在任务面板上——一条只活在
面板上的观测，下一个人读到的是结论而不是它的来路。

**那三条读数没有一条是关于缺陷的。它们对这个 exe 的每一次 panic 都成立。**

| 读数 | 为什么它对每一次 panic 都成立 |
| --- | --- |
| 无 `[main] exiting` | 那行印在**消息循环之后**（`main.rs`），任何非正常终止都走不到它——panic、访问违例、`abort()` 一视同仁 |
| 无 stderr | panic 消息由默认 hook 写 **stderr**，而进程是被 detach 拉起来的，**它自己的控制台没有被任何人捕获**。消息写出来了，写进了没人看的地方 |
| 无 panic | 我们唯一收集的物证是**日志文件**，而 `log_line` 只写 stdout 和文件，**没有任何东西把 stderr 引进文件**。panic 消息从来不会进那个文件 |

**所以「不明原因」当时就没有被确立过；它是不可观测，不是不明。** 这两者的下一步动作
完全相反：前者要去猜机制，后者只要装一个仪器然后等它自己说话。

另外三件量出来的、会改变现象形状的事：

- **`panic = "abort"` 只设在 `[profile.release]`**（`windows/Cargo.toml`，且那里已有注释
  说明 profile 必须写在 workspace 根）。**debug 构建是 unwind 的**：主线程 panic 会退出
  进程（码 101），**非主线程 panic 只死那一条线程、进程继续跑**。两次观测分别是什么
  构建，会改变该期待什么现象。
- **子系统是 `WINDOWS_CUI`**（`Subsystem = 3`，读 PE 可选头 offset 68 量的），不是
  `WINDOWS_GUI`。全仓也搜不到 `windows_subsystem` 属性。
- **85 秒不对应任何常量**：看守狗是 2 / 4 / 60 秒，`tabs.rs` 有个 5 秒 deadline，
  UIA 是 500 毫秒。没有定时器在那个时刻。

### 装了 hook 之后，哪一种阴性才开始有意义

`install_panic_hook`（`main.rs`）把 panic 写进日志文件，**并且不碰程序里任何一把锁**
（路径在装的时候就解析好；文件每次现开；stderr 走 `WriteFile` 而不是
`std::io::Stderr`；**绝不调用 `wlogf!`**——那会去要 `winid::FRAMES`，而一个正持有
`FRAMES` 的线程在 panic 时会就地挂死而不是报告）。理由是 panic hook **跑在 unwind
之前，panicking 线程手上的锁全都还握着**。

**它只抓 Rust panic**：访问违例、栈溢出、C 侧 `abort()`、OOM 都不经过它，一个字都不会写。
**这不是缺点，这是它买来的读数**——装上之后，下一次静默死亡如果日志里仍然一行都没有，
**那就排除了 panic**，而这是今天拿不到的一条结论。

### 判据 P0–P3：证明这个 hook 不是哑巴

**这些判据此前只活在一次对话里。** 写在这里的理由和 E1–E7 是同一条：一组只能被
转述的判据，没有人能整组读一遍，于是它们共同的缺口不会有任何时刻是可见的。

> **P0（前提，必须最先跑，而且它不在 hook 的代码里）**
>
> 确认 `--panic-test` 这个参数还能被解析出来。
>
> **这条判据的前提在别人手里，而且那批改动已经落地。** `--panic-test` 和所有
> `--foo` 参数都从同一条命令行来，而命令行的取得（`GetCommandLineW`）和切分
> （认引号的切分器）在 `c9a3f90cf` 里换掉了——**从此每一个 `--foo` 都要先经过
> 那条切分器**。它若对某种形状的参数处理不同，**P1 会红，而那个红会被读成
> 「hook 坏了」**；它实际说的是「参数没进来」。两者的下一步动作完全相反。
>
> 那批自带四条切分器单元测试（全量 4026/4044、0 failed）。**但单元测试证明的是
> 切分器按它自己的规则工作，不是 `--panic-test` 这个具体串还进得来**——那是两个
> 不同的问题，P0 问的是后一个。
>
> 读数：跑 `polter-host.exe --panic-test`，日志里必须先出现
> `--panic-test=plain: panicking on purpose to prove the hook speaks`。
> **这一行是参数解析说的话，不是 hook 说的话**；它不出现就先停下，P1–P3 全部无效。

> **P1（最容易的情形）**：`--panic-test`，读日志文件。
> 必须有 `[panic] thread "main" panicked at <file>:<line>:<col>: ...`。
> **地板**：同一份日志里必须也有启动横幅 `=== Polter host (Windows) === pid=...`，
> 否则那行 `[panic]` 可能来自别处的日志。

> **P2（最重要的一条）**：`--panic-test=locked`——**在握着窗口状态锁时 panic**。
> 同样必须出现 `[panic]` 行，**而且进程必须真的结束**。
>
> **失败形态是「挂住」，不是「没那行」**：`tasklist` 里进程还在、日志停止增长，
> 就说明 hook 在要一把锁。请把日志最后三行原文报回来。
> **P1 过而 P2 挂，是最可能的结果**——P1 只证明了「在最容易的情形下会说话」，
> 而静默死亡从来不发生在最容易的情形下。

> **P3（负对照，缺了它 P1/P2 不算数）**：不带任何 `--panic-test` 正常跑一次并正常
> 退出。日志里**不许**有 `[panic]` 行，且必须有 `[main] exiting`。
> 没有这条，一个无条件打印 `[panic]` 的 hook 也能通过 P1 和 P2。

> **P4（顺带，只在 debug 构建下有意义）**：`--panic-test=thread`。
> 期望 `[panic] thread "polter-panic-test" panicked ...` 出现，**而进程继续活着**，
> 并打出 `--panic-test=thread: the thread has ended (joined_ok=false)`。
> 这条同时验证「非主线程 panic 不杀进程」——那是从 `[profile.release]` 只设了
> `panic = "abort"` 读出来的推论，没验过。

## 五之七、exe 和 DLL 可以来自不同构建，而症状是「这个功能没做」

真机上 `ghostty-internal.dll` 建于 09-02 06:26，**比修它的那个提交（`c9a3f90cf`，
09-03 03:43）早 21 小时**。于是命令行动作那条路在那块 DLL 上是死的——**而它看起来
不像「版本不齐」，看起来像「这个功能没有人写」**，因为核心不认识的 action 是被静默
拒绝的，**而一个被拒绝的 action 和一个不存在的 action，从外面看是同一件事**。

### 缺的从来不是数据，是判决

**这条要单独说，因为它推翻了「加个检查」的直觉。**

`[build]` 那行**当时已经在打三个二进制的 sha / size / mtime**。数据齐全，摆在同一份
日志里，**而没有人比对**。所以再多打两个哈希不会改变任何事——**缺的是一个由机器做出
的、说出口的判断**。

同一晚还有一个同族的：`empty_agrees` 那条不变量存在之前，`1 window(s) remain` 和
`0 window(s) tracked` 是紧挨着的两行，**当场就不一致，而那个不一致就是答案**——但没有
任何东西规定这两个数必须相等，所以没人把它读成失败。

**两个并排的数字，在有东西规定它们必须相等之前，都不是互相印证。**

### sha 和 mtime 回答不了「配套」这个问题

| | 它回答的 | 它答不了的 |
| --- | --- | --- |
| **sha** | 「这个文件是那一份」 | 「它和另一份是同一次构建出来的」——两个各自正确的哈希，可以来自隔了 21 小时的两次构建 |
| **mtime** | 几乎什么都不答 | 拷贝就会变；而且 release 构建不可复现（同源码两个 sha，本文另有记录），所以「源码相同」推不出「哈希相同」 |

**能回答的只有构建期编进去的出处。** 核心一直有：`src/build/GitVersion.zig` 在构建时
跑 `git log --pretty=format:%h -n 1`，短哈希经 `build_config` 进 `ghostty_info()`，
就是关于框里 `1.3.2-HEAD-+1fe09f51b` 的那一段。**宿主一直没有**——`build.rs` 只嵌
manifest，全仓 `env!` / `option_env!` / `GIT_` 零命中。

所以这件事的主体是**给宿主也加上**，不是写个检查器；一旦两边都有，比对就是一句话。

### 三个分支，而「未知」两头都不许像

宿主的 commit 是**直接编进去的**，核心那一侧要**解析别人的版本串**。解析是唯一脆弱的
一步，于是有两条对称的规矩：

- **未知不许长得像「一致」。** 核心 git 不可用时的兜底是 `0000000`；宿主若也用一个
  兜底常量，两边都拿不到时会比出相等——**一个由兜底制造出来的假匹配**。宿主的未知值
  是空串，且 `0000000` 被按名字拒绝。
- **未知也不许长得像「不一致」。** 解析失败时取不到东西，它不会等于宿主那个值，
  于是天然落进 MISMATCH——**那是假警报**。而假警报同样致命，只是死法不同：它会让人在
  两边其实配套时看到告警，**然后学会忽略这一行，而这一行的全部价值在于它被读一次**。
  所以解析不出来一律落进第三支。

（同一条在别处的样子：**一个五次里错四次的闸会被关掉，而关掉它的人不会回来。**）

### 两个已知的洞，写出来而不是留给读者猜

- **脏树。** 同一个 commit、不同的未提交改动，短哈希相同。这棵树上经常有三四个人同时
  在改，所以这不是假想。宿主的戳带 `dirty` 标记，**但它只说「有未提交的改动」，不说是
  哪些**；而且核心的版本串里根本没有这个标记（`GitVersion` 有 `changes` 字段，没进
  版本串），**所以核心那一侧的干净与否，无从得知**。`dirty` 只降低「同一个 commit」的
  含金量，从不把一致变成不一致。
- **两边都旧。** 一致但都过时，检查是绿的。它答的是「配不配套」，不是「新不新」。

### 它说在什么时候，以及为什么是两个地方

**启动时打一行判决**（`log_pairing`）：每次运行都看，**包括「机器上那份 DLL 是别人手
放的」这种情况——而这次正是这种**，构建期的闸对它一无所知。

**关于框里同时显示宿主的 commit**：日志是**事后**给追查的人看的，关于框是**当下**给
困惑的人看的。**这次困惑的人是测试者，而它去看的正是关于框。**

**并且这两个都不替代第三种**：`keys.rs` 在解析不到 `ghostty_config_trigger` 时会打
`[keys] ghostty_config_trigger not exported; menus will show no shortcuts`——**符号级
探测在使用点精确回答「这份 DLL 没有我要的入口」**。启动那行覆盖面宽但笼统，符号那行
精确但只覆盖被显式解析的符号。**两个都要，不是二选一。**

## 五之八、组字被打断这条上还欠一笔：**守卫是靠宽度成立的，不是靠精确**

组字期间按一个快捷键，半截音节会被提交进终端。修法是在宿主重排自己窗口时把
「组字结束」当成丢弃而不是提交（`main.rs::with_host_shuffle`，罩住 `tabs.rs` 布局里的
隐藏循环）。**判据 H 五格全绿**，包括两个方向的地板（H5 正常上屏仍然正常、H3 真切到别的
应用仍然提交）。

**但触发条件没有查清，而我们一度以为查清了。**

第一次读数里，同一次布局中两个 pane 被隐藏，只有 `was visible: true` 的那个之后紧跟着
`OnEndComposition`——**这看起来是一条规律，而且它被当成结论写进了代码注释**。
**H4（组字中按 `Ctrl+Shift+O` 分屏）否掉了它**：那一次两个被隐藏的 pane **都是
`was visible: false`**，组字照样结束。

| | |
| --- | --- |
| **已知** | 组字结束发生在那个隐藏循环内部（两次独立读数） |
| **未知** | 是哪一次 `ShowWindow` 做的，条件是什么。「隐藏可见的 pane」是第一个假说，**已被证伪** |

**所以 H 全绿的原因是守卫罩得比触发条件宽**，不是因为我们判对了触发条件。

### 这一条的后果，写下来是因为它不明显

**一个靠宽度成立的守卫，它的地板绑在被罩住的代码上，不绑在守卫上。**

也就是说：**H5 那一格，以后每次动那段布局代码都要重跑**，而不是只在改守卫时重跑。
守卫不会告诉你它不再罩住某样东西——把一个 `ShowWindow` 挪出那个循环、或者加一条绕过它
的路径，守卫仍然编得过、H1 仍然可能绿，而 H5 会红。

**这是欠账不是阻塞**：宽守卫是安全的（H5 证明它没有一直开着，H3 证明它没有把该提交的也
丢掉）。查清真正的触发条件可以晚做。

### 一句方法上的，因为这次是我们自己往仓里放的

那句被证伪的注释**自信、有真机原文支撑、写给下一个人看**，而它会让那个人**在正确的地方
停止搜索**。今晚追了一整夜的正是这个形状——**这一次是我们自己制造的**。

**一个只出现过一次的相关，写进注释时要带上它是一次读数还是一条规律。** 那三行读数是真的，
从它们推出的那句话不是。

## 五之九、鼠标上报（判据 M）：**「vim 里鼠标不好使」是三件事，不是一件**

`157` 把点击和移动接进了核心（`ghostty_surface_mouse_button` / `_mouse_pos`）。**上报本身
是核心做的**——它按终端当前的模式自己发转义序列，宿主没有第二条路要接。所以这一条的
第一步是**读数，不是修改**：如果它已经好了，产出是一行记录。

### 但滚轮那一半压在别处，判据必须先把它们分开

读 `Surface.zig::scrollCallback`：**滚轮也是上报的一部分**，而且是从这个入口发出去的——

```zig
if (self.isMouseReporting()) {
    for (0..@abs(y.delta)) |_| {
        self.mouseReport(switch (y.direction()) { .up_right => .four, .down_left => .five }, …);
```

**而 `ghostty_surface_mouse_scroll` 这个入口宿主还没接（那是 159）。**

同一段里还有第三条路：**alt screen + 未开上报 + `mouse_alternate_scroll`** 时，滚轮被转成
**方向键**——`less`、`man`、`vim` 的滚动靠的正是它。**它也走 `scrollCallback`。**

**所以「在 vim 里滚不动」有三个成因，而三个都经过同一个还没接的入口**：

| 现象 | 走哪条路 | 今天的状态 |
| --- | --- | --- |
| 点击定位、拖选、点列头排序 | `mouse_button` / `mouse_pos` | **已接**（157） |
| 上报模式下滚轮发转义序列 | `scrollCallback` → `mouseReport` | **未接**（159） |
| alt screen 下滚轮转方向键 | `scrollCallback` → 方向键 | **未接**（159） |

**判据不分开的话，「vim 鼠标不好使」会被当成一个失败报回来**，而它是「一个已接的和两个未接的」——
**处置完全不同：前者要查，后者只要等 159。**

### 判据 M

- **M1（点击类，今天就该绿）**：`vim` 里 `:set mouse=a`，点一下 → 光标跳到点击处；
  `htop` 里点列头 → 排序变化。
- **M2（地板，必须做）**：同一轮里在终端里**拖选一段文字** → 选中正常。
  **没有它，「vim 里点了没反应」可能只是鼠标压根没进来**，而那和上报无关。
- **M3**：`printf '\033[?1000h'` 打开上报后点击 → 屏幕上/日志里有转义序列进来。
- **M4（预期红，写下来是为了它别被算成缺陷）**：`vim` 里**滚滚轮** → 今天不会动。
  **这是 159 未接的直接后果，不是上报的问题。** 159 落地后这一格才该转绿。

**M1+M2+M3 绿而 M4 红 = 160 已经好了**，产出是这一节的记录，不是补丁。

## 五之十、滚轮（判据 N）：**接一次，三件事一起活；判据要分开写**

`ghostty_surface_mouse_scroll` 接上了（`tabs.rs::mouse_wheel`）。**同一个入口后面挂着三个
功能**，所以「滚轮好了」这句话会替三件事说话：

1. 滚回滚缓冲；
2. **上报模式**下把每一格变成 button-4/5 报告（全屏程序看见的滚轮）；
3. **alt screen 交替滚动**：未开上报时把格数转成方向键——`less`/`man`/`vim` 靠它。

### 换算

`wDelta / 120` = 格数（高分辨率滚轮给分数，直接传）。**乘 `SPI_GETWHEELSCROLLLINES`**
（默认 3，用户自己设的），**不乘 cell 高度、不乘 `mouse-scroll-multiplier`——那两个核心
自己乘**。符号直通：Win32 的「远离用户为正」和核心的「正为上」是同一个方向。

**这是一处对其它平台的有意分叉**，理由和本 fork 那八条快捷键偏离同类：Windows 上的终端
是个 Windows 程序，滚轮快慢的预期由系统给。不乘的话它比这台机器上每个别的窗口慢三倍，
而用户改的那个设置什么都不做。**分叉不是问题，悄悄分叉才是**，所以它写在代码里、也写在
这里，并且前五格滚轮会把 `lines_per_notch` 打进日志。

`WHEEL_PAGESCROLL`（`0xFFFF_FFFF`，「一格一屏」，控制面板里点得到）走单独一支并**每次**
打日志——当行数直接乘会得到四十亿行。

### 判据 N

| # | 做什么 | 期望 |
| --- | --- | --- |
| **N1** | 输出几屏内容，向**下**滚 | **内容往下走：看到的是更新的内容** |
| **N2** | 向**上**滚 | 看到更早的内容 |
| **N3** | `vim`（alt screen）里滚 | 视图跟着动（第 3 条路） |
| **N4** | `vim` `:set mouse=a` 后滚 | 同样跟着动（第 2 条路） |
| **N5** | 滚到缓冲最底之后**继续滚** | 不崩、不越界、不倒着走 |
| **N6（地板）** | 同一轮里拖选一段文字 | 正常——证明鼠标那条路当时是活的 |
| **N7** | 抄回前五行 `[mouse] wheel …` | 确认 `lines_per_notch` 是这台机器的系统设置值，不是写死的 3 |

> **N1 和 N2 是这组里最容易被漏掉的两格，而它们是同一件事的两半。**
> **一个符号写反的实现，和一个正确的实现，在「画面动了没有」这个判据上完全一样。**
> 方向错是用户第一秒就会发现的，却最容易在判据里缺席——**因为写判据的人脑子里已经知道
> 该往哪边走，于是不会把它写下来。**

> **N7 是「分叉有没有真的发生」的读数。** 没有它，「滚轮手感对了」可能只是默认值 3 恰好
> 等于这台机器的设置——**那样这段代码里读系统设置的那一半从来没被证明跑过。**
>
> **【已验证，但这一格差点没有区分力，而缺口在判据里，不在执行里】**
> 真机上 `WheelScrollLines` **恰好就是 3**，和写死的默认值相等。**那种情况下读到
> `per_notch=3` 什么都不证明**：读了系统设置和完全没读，输出一模一样。
> 执行的人把系统设置临时改成 **5**、重滚、读到 `per_notch=5`、再改回 3——**这一格
> 才有意义**。
>
> **这一句是判据里原本缺的。** 上面那段写清了「没有 N7 会怎样」，**却没写「N7 自己
> 在默认值撞上时会怎样」**。凡是判据依赖一个默认值（配置的、系统的），**那个默认值
> 要写进判据**，并说明相等时这一格没有区分力、以及要把它改成什么。
> 同族的完整讨论见 `docs/windows/s4.md`「观测手段的作用域，和被观测对象的实际形状，
> 不是同一个集合」。

| **N8** | 横向滚轮（触控板双指横滑 / 倾斜滚轮） | **本机大概率无法验证** ——见下 |

> **N8 写成「无法验证」而不是省略。**
>
> 横向滚轮**已经接上了**（`WM_MOUSEHWHEEL` 走同一条路，读 `SPI_GETWHEELSCROLLCHARS`）。
> 它一开始被判为「不实现」，理由是「几乎没有鼠标能产生它，实现了就是永远不会运行的代码」
> ——**那句话没有量过，而且是错的**：Windows 精密触控板的双指横滑就发这条消息，倾斜滚轮
> 也发，**笔记本上这是常规输入**。
>
> 更该记的是那个理由**误用了哪一条教训**：「写了但从不运行」要求的是**去确认它会不会
> 运行**，而它被用来**假设它不会**。**一个听起来足够充分的理由，正是让核查停下来的东西。**
>
> 测试机是台式机 + 外接鼠标，所以这一格这一轮多半跑不出来。**一个标着「本机无法验证」的
> 条目，和一个根本不在清单上的条目，在纸面上长得不一样——而后者会被读成做完了。**
>
> **【结果：宿主侧已验，真实硬件仍未验】** 注入 `MOUSEEVENTF_HWHEEL` 后读到
> `axis=horizontal` 并走同一条换算——**证明的是宿主这一段代码会跑**。
> **没有证明的是**：真实的精密触控板 / 倾斜滚轮发出来的消息长什么样、
> `SPI_GETWHEELSCROLLCHARS` 在有那种硬件的机器上取到什么。**这一格仍然空着，不是绿的。**

**异常值的处理（两个轴同样对待）**：`WHEEL_PAGESCROLL` 按名字单独一支；**其余大于 100 的
值当成错误而不是偏好**，退回 3 并打日志；`SystemParametersInfoW` 失败也退回 3 并打日志。
**三支都不静默**——一个手感不对的滚轮，应该能追到它被给了哪个数。

## 七、方法论（每条都带触发条件，都是真踩出来的）

0. **拿到一个支持结论的读数就停手——这是下面几条的母形状。**
   今天被推翻的九条判断里，多数不是因为没有证据，而是**证据就在手里，
   而人停在了让结论成立的那一步**：
   - 令牌下发那条：链的**下游**读了（env 怎么被消费），**上游**没读（env 怎么被构造）
   - 目录逃逸那条：失败消息读了（`expected 2, found 0`），**那个断言在数什么**没读
   - 控制台归属那条：看到测试转绿就归因给它，**没注意同一轮还有第二个变量在变**
   - action 计数那条：拿到一个数，**因为它和文档一致就不再追**（而文件里有两个同名 enum）

   **触发条件很具体：当一个读数刚好支持你正想成立的那个结论时，那就是要多走一步的时刻。**
   相关的一条：**升级一个结论（从「疑似」到「阻塞项」）比提出它需要更多证据**，
   而升级往往发生在最想收工的时候。

1. **编译挡着链接，链接挡着运行，运行挡着绘制。** 今天穿了五层，最后一层是上游显式挡的。
2. **「那个假设没被检验过，不是被排除。」** 未经检验的假设被当成已排除，比已知未解更危险——没人会再回去看它。
3. **同一个「什么都没有」背后有几个互不相同的世界，而读数不区分它们。**
   一天之内三次差点把「日志里没有那行」当成结论，三次的分母完全不同：
   **探针根本没发出那个键**（argus 报 `success: true`，日志显示它只发了 Ctrl，主键一个没发）、
   **代码没有走到打印那行的地方**、**进程已经不在了**。
   **三种情况的补救毫无共同之处，而三种情况在日志里长得一模一样。**
   所以看到一个阴性时，先问「有几种世界能产生它」，再为每一种找一个能把它排掉的读数——
   往记事本发一个不带修饰键的单键，分的就是第一种。
   这是第 2 条的加强版：那条说未检验不等于已排除，这条说**同一个缺席有好几个成因**。

4. **⭐ 在拿到读数之前先问:「如果被测的那个东西是错的,这条判据会看见吗?」**
   ——不是「这条判据通过了吗」。
   **这把「判据够不到被判的东西」从一个只能事后发现的意外,变成一个可以事先问出来的性质。**

   2026-09-01 一天里这件事发生了**六次**,六次「够不到」的维度各不相同,
   而**症状全都是「测试是绿的」**:

   | 判据 | 够不到的东西 |
   | --- | --- |
   | 启动表读 `builtin.os.tag` | **另一个操作系统**的表项,在构建机上不可达 |
   | `--selfresize` 看中心像素 | 贴在左下角的旧画布**永远盖住中心** |
   | 全局热键自测 | 脚本跑在 Polter 里**就意味着 Polter 是前台** |
   | 手写 JSON 的单元测试 | **另一个实现**——它只证明「我和我同意」 |
   | `mutate.ps1` 的注入目标写死 | **另一个文件**,于是那组断言从来没有地板 |
   | 那次注入的离线预检 | 够到了文件,**没够到产生那个字符串的那一层**(PowerShell 转义) |

   **六次里没有一次能通过上面那个问句**,而六次全是事后才发现的——
   其中一次(`--selfresize`)还先以「**通过**」的形式活了一整天,
   期间它该发现的那个缺陷又长出两处症状。

   **这条和第 3 条是一对**:第 3 条讲怎么读一个阴性,这条讲**在拿到阴性之前
   就判断这条判据配不配产生阴性**。前者救的是结论,后者救的是实验。

   ⚠️ **补救几乎总是同一招:把那个够不到的维度变成参数。**
   目标系统当参数收、判据点从前后尺寸算出来、预检从产生字符串的那一层取锚点——
   **三处不同的工作,同一个动作。**

   ### 这一族里最常见的一种形式:**自检闭合在自己身上**

   一个「还原之后校验」的步骤,如果比的是**它自己启动时取的那份快照**,
   那么当那个文件在脚本启动**之前**就已经是错的,它会忠实地把它还原成那份错的,
   然后报告成功。**「和我启动时看到的一样」不等于「对」。**
   要用运行之外的东西比——仓库里的字节、别处取的哈希。

   **同一天里这个形状出现了三次,而三次的「自己」各不相同:**

   | 校验 | 闭合在什么上 | 打开它的外部基准 |
   | --- | --- | --- |
   | 变异脚本的 `matches the original` | 脚本启动那一刻的快照 | 仓库里的字节数 + sha |
   | 手写解析器的单元测试 | 同一个人写的那份实现 | 另一个实现真的去读一遍 |
   | **主控说「我已经放 X 上机」** | **主控自己写下的那句话** | **对方那边有没有收到** |

   **第三行是人的版本,而它当天发生了两次**,两次都造成了七八分钟的空转:
   一句描述被当成了一个动作,**而唯一的证据是写下那句话的人自己。**

   ⚠️ 还有一个更小的形态,值得单记,因为它连「跑」都不用就会错:
   **位置指代**。一份清单末尾写「最后那条是这个陷阱的缩影」,
   清单增加一行之后,那句话开始指向另一条——**不报错、不难读、只是指错了**。
   **它的正确性依赖于一个它自己不检查的条件(清单长度)。** 指名,不要指位置。

   ### 用在调试上:**不问「这个值对不对」,问「这个东西是不是我以为的那种东西」**

   同一个问句挪到调试里,形状变了:不问「这次改动会让它过吗」,
   问「**如果我猜错了,这次输出会告诉我吗**」。

   一次真实的追查:某条注入始终打不进去,五个诊断窗口,**四次在猜**。
   打印过锚点长度、锚点字节、键名清单、`.Contains` 和下标两种取法——**全部正常**。
   最后由一条只打**类型和计数**的探针定案:

   ```
   M7:  object type : System.Object[]                 ← 数组
   M8:  object type : System.Collections.Hashtable    ← 对照
   ```

   一处结尾的逗号被后来的插入挤到了行首,而在 PowerShell 里换行结束语句,
   **行首的逗号是一元数组构造运算符**——那个条目被包成了一个只含它自己的数组。

   **五个诊断全被骗过,而骗法很干净**:数组会把成员访问穿透给它唯一的元素,
   所以 `.Name`、`.Keys`、`.Pairs` 全部「正常」,**只有按字符串下标取值返回 null**。
   **它们问的全是「值对不对」,而那个东西在「值」这一层上确实都对。**

   > **「锚点找不到」和「这个条目不是我以为的那种东西」,症状完全相同。**

   追查的人自己的账,比机制更值得留:

   > **我每次都在问「这个值对不对」,没有一次问「这个东西是不是我以为的那种东西」——
   > 类型是我从头到尾假设的,所以从头到尾没打印它。**
   > **打印的是我怀疑的东西,不是我假设的东西。**

   **「怀疑的」和「假设的」是两个不相交的集合,而人只会去打印前者。**
   后者是没在被怀疑、因而也没人看过的那些——**而它们恰恰最可能出错,因为没人看过。**

   ⚠️ **一条没有对策的**:同一轮里,那个人先写了一句错的根因注释
   (「注释块放在 hashtable 里导致键丢失」),查清后改掉了。
   **一条写错的根因注释比没有注释更贵,因为下一个人会照着它排除掉正确的方向**
   ——它不是浪费时间,是把人推向反方向。
   而「注释要么带可 grep 的符号名、要么不写」那条对策**对因果断言无效**:
   **因果恰恰是最不可能带符号名的那种断言。这一种今天仍然没有对策。**

   ### 同一族的第三个形态,以及它一半的对策

   **文档断言「代码现在是什么样」。** 它比前两个更容易被当成没问题——
   **因为文档本来就是描述代码的**,所以没人觉得那是一句需要被检验的话。

   一次真实的例子:一份文件写着「命中枚举是这四项,穷举」「一条右键消息都没有」
   「没有第三条通向命令面板的路」,并据此推出三条「必然不通过」。
   **四十分钟后有人把这三件都实现了,三条结论同时翻转。**
   实现者在代码里留了一句注释指名那份文档的小节,**而它自己不够**:

   > **代码里指向文档的注释,只有改代码的人会看见;
   > 文档里那句「代码现在是这样」,没有任何东西会为它变红**
   > ——不参与编译、不参与测试、`grep` 也查不出它过期了。

   **但这一种有一半对策,而且它今天就能用,不需要任何工具**:

   | 文档里的写法 | 能不能被重跑 |
   | --- | --- |
   | 引**代码原文**(`pub enum Hit { … }`) | ✅ 和源文件比对即可 |
   | 引**一个统计数**(`WM_LBUTTONDOWN ×9`、「一条右键消息都没有」) | ✅ 重跑那次统计即可 |
   | **转述结论**(「右键在任何位置都不产生任何东西」) | ❌ **没有任何东西能为它变红** |

   > **要么带上可以被重跑的东西,要么不写**——和注释那条是同一条规矩的另一半。

   ⚠️ **这只是「过期时能被发现」,不是「过期会被自动发现」。**
   后者要一个把文档里的代码块和源文件比对的脚本,**那个脚本不存在**,
   记成一件没做的事,**不要因为写下了这条规矩就以为它被覆盖了。**

5. **判据不适用的时候,要说自己不适用。**
   一条算不出结果的判据如果静默,那么「日志里没有那行」同时意味着
   「它适用而且没发现问题」和「它这次根本没被应用」——**而这两件事的下一步完全相反。**
   `newly_exposed_point` 在没有任何一边变大时返回 `None`,并打印
   「nothing grew; the new-region criterion does not apply」,就是为了不制造第四个分母。

6. **用错的探针得到的阴性，和没做过实验是一回事。** `GetConsoleWindow` 对「无控制台」和
   「有控制台无窗口」都返回 null。
7. **负对照必须在过滤之前取。** `Where-Object` 之后再数，数的是过滤后的世界。
   同理适用于「查产物里有没有某个字符串」：**「0 处命中」和「这个搜索根本找不到东西」
   长得一模一样**。核对交付版不含调试插桩时，要同时搜一个必然存在的符号作地板——
   `插桩串: 15 → 0，而 DisconnectNamedPipe: 1 → 1`，后半句才让前半句成立。
8. **当一个阴性结果让你少干活时，那就是必须量基率的时刻。**
9. **当一条二手前提能决定下一步做什么时，先花两分钟核它。** 核它一次 `grep`，不核一个完整往返。
10. **预先声明判据，是为了在结果出来之前锁住解释权。**
   **这一条在 2026-09-01 有四次独立到达，来自三个不同的人和三种不同的工作**，
   所以它不再是一条建议：变异测试里「修完之后它应该变红」被事先写下来
   （而不是事后解释「它当时为什么绿」）；`--qttest` 的每一行判据带着输入量
   先于代码写出；分屏的六条真机判据写在上机之前；插件页的 29 条范围清单
   在写第一行代码之前发出，**并且作者在里面自己揪出一条写错的判据**
   （引了个不存在的行号——`ghostty_diagnostic_s` 只有 `message`）。
   **最后那次最能说明问题：一条判据在被使用之前就被作废，代价是零；
   它如果活到验收那天，会以「这项没法验」的形式出现，而那时它看起来像是产品的问题。**
11. **一直在调整一个不该存在的东西的参数。** `CancelIoEx` 三轮错了三种方式，正确动作是删掉**对读的**取消（对 *connect* 的取消是必须的，见 `transport_windows.zig:153`）。
   每一步都对，方向整体是错的。
12. **规则的适用条件比规则本身更难记住。**「别在锁里做系统调用」是对的，但那把锁正是防
   use-after-close 的机制。
13. **绕开一条路，不等于绕开它底下的那一族问题。**
14. **负对照检验的那一层，必须就是被测路径依赖的那一层。**
    这条不是「要做负对照」的重复——**对照做了，也通过了，然后主控停在了那里。**

    Ctrl-C 不生效，主控的负对照是「同一个 argus 组合发给原生 cmd 窗口能立刻中断」，
    据此结论「探针是好的，缺陷在我们这边」。**但 `cmd` 读的是控制台输入缓冲区，
    拿到的是虚拟键码和字符，它从头到尾不看扫描码**——而扫描码是我们这条路唯一依赖的
    东西（见第五之三节）。那个对照证明了「按键到达了 OS」，**没有证明我们要的那一层**。

    **和第 3 条的区别**：第 3 条是探针用错了、阴性等于没做实验；
    这一条是**探针是对的、实验做成了、阳性也是真的，但它测的是隔壁那一层**。
    第 3 条给的是「没有信息」，这一条给的是「有信息，且指向错的方向」——**更贵**。

    **触发条件**：当你写下「我做过负对照了」这句话时。
    **下一句必须是**：「它对照的是哪一层？被测路径依赖的是哪一层？两者是同一层吗？」
    这次两者差了一层，而差的那一层正好是唯一相关的那层。


15. **一个读数如果对「对的行为」和「错的行为」给同样的值，它就不是判据。**
    **触发条件**：当你要检查的性质是「某件事**不该**发生」时。
    - **删除计数**：「删了 1 个」对「只删了该删的」和「删了该删的 + 漏了一个」是同一个数——**连方向都不给**。
    - **两次跑完文件逐字节相同**：一个「每次都重写、但写同样的值」的插件产生的正是同样的字节。
    - **配置文件的 sha 变了**：不区分是谁改的（真凶是另外两个活着的 CLI 会话）。
    **解法都是换一个能分辨方向的问题**：「它还在吗」「SDK 自己报了 provisioned 吗」「我写的那个特征串在不在里面」。

16. **「没报错」不等于「做成了」。**
    **触发条件**：当你用「某条错误日志没出现」当证据时。
    `log.warn` 只在 errno 不是 SUCCESS 时打，所以「没有那行 warn」只证明**调用返回了 ≥ 0**，
    **不证明那个字节进了那根管子**——后来的隔离实验证明它确实没进去。
    同族：「配置文件写出来了」≠「对面读得懂」（`opencode` 那轮才第一次由对面回答）。

17. **一个读数能不能外推，取决于「测量时的条件和目标条件有没有差别」。**
    同一次运行、同一份日志里的两个读数，一个能外推一个不能：
    - **写 quit 管道返回成功** → 能外推（不依赖写端是否已关）
    - **`CancelIoEx` 返回 SUCCESS** → **不能**（成败取决于此刻读是否 pending，而修复恰好改了这一点）
    **所以第一轮那个 SUCCESS 什么都没证明**，要专门把 `closeConsole` 挪到取消之后再跑一次才有效。

18. **一条判据的证据如果被别处限流，它会悄悄地不再可检验——而且失败的样子和「功能没跑」一模一样。**
    `[hud]` 的缩放判据原本要和 `tabs.rs` 的 `[win] … WM_SIZE` 相比，
    **而那行只打前 10 次，`--selfresize` 在 5 秒才触发，启动期布局早把配额用光了**。
    **解法是让判据自足**：`[hud] size 124x37 from client 1240x790 cell 10x21`，一行之内的除法，
    不依赖任何别人的日志。**判据不该跨文件依赖别人的可观测性预算。**

19. **一个碰巧成立的判据，和一个被设计成立的判据，在它们都通过的那天看起来一模一样。**
    「把第 1 个标签拖到第 3 位，检查内容跟着走」——七个标签标题全是 `cmd.exe` 时，
    **平行数组错位也长这样**。是「移动前先改名成 `MOVED-ME`」那一步让它真的可判。
    **一个只在标题各不相同时才有效的检查，不该依赖标题恰好不同。**

20. **找到一个真的根因就停手，而根因可以有两个。**（第 0 条的变体）
    ConPTY 挂死：两次独立诊断各找到**一个真的写者**（控制台主机那份、我们自己那份），
    **两个都对，两个都不够**——关掉任一个，管子仍有写者。
    > **两个人独立复核得出一致结论，在这里恰恰不是收敛的信号。**

21. **探针查的是输出，被查的是源。**
    自检脚本 grep「日志行是否存在」时搜的是**渲染后的字符串**，而源码里是格式串 → 两条假的「0 命中」。
    同族四例：`.cmd` 把 `=` 当分隔符拆掉 argv、Zig 多行字符串把 `\n` 写成两个字符、
    在缩放 0.6 的截图上目测像素、以及上面这条。
    **四次的第一反应都是去查产品**，而四次都是工具在篡改它要观测的东西。

22. **结论对、机制错，比两者都错更难发现。**
    「退出字节没送到」这个结论是对的，而给出的机制（mingw `_write` 按 int 截断 HANDLE → EBADF）是错的。
    **结论对的时候，没有人会回头查机制。**
    > 那一格不是靠谁更谨慎发现的，**是靠一次被证伪**——如果那条推理侥幸对了，
    > 我们会带着一个正确的结论和一个错误的机制往下走。

23. **⭐ 我们只有一种判据，而且不知道自己只有一种。**
    2026-09-01 把全部判据分了类（一条判据 = 一个带独立通过条件的条目；
    自动化套件的断言按「一组」计一条，否则测试断言会把比例冲平）：

    ```
    今天之前   37 条 →  功能 24 / 外观·行为 13 / 可发现性 0
    今天之后   42 条 →  功能 24 / 外观·行为 13 / 可发现性 5
    ```

    **可发现性那一列今天从零开始，而它是在用户用了十分钟、
    撞上三个我们内部判据一条都没发现的缺失之后才有的。**

    ⚠️ **而「不知道」这件事有证据，比那个 0 更硬**：那 37 条的作者，
    **没有任何一条在写它的时候说过「这一类之外还有别的类」**。
    **不是漏了，是那个类别当时不存在于我们的词汇里**——
    **漏了会漏掉几条，不会漏掉一整类。**

    ### 中间那一类最难发现，因为它既通过检查也通过直觉

    分类的检查是「通过条件里有没有只有内部人知道的名词」。
    **它是「功能判据」的检测器，不是「可发现性判据」的检测器**——
    而写下它的人以为那是个二分。扫完之后「没有内部名词」的那一堆里有两种东西：

    | | 例子 | 问的是 |
    | --- | --- | --- |
    | 功能 | 「命中数与 `ghostty_surface_search_*` 返回一致」 | 它对不对 |
    | **外观·行为** | 「Win10 与 Win11 都不出现白色标题栏 + 深色终端的撕裂」 | **它看起来对不对** |
    | 可发现性 | 「不看文档的人 30 秒内能不能用鼠标开出第二个标签」 | **他找不找得到** |

    **中间那一类不含内部名词、人能判、看起来「很像用户视角」——
    而它们全都预设了用户已经知道那个东西在哪。**
    「双击标签进入改名」测的是改名对不对，**不是他会不会想到双击。**

    > **只用那条检查会给出一个偏乐观的答案**：它会说「我们有 13 条不是功能判据」，
    > 而那 13 条**一条都不解决**用户当天撞上的问题。
    > **一条会给出偏乐观答案的检测器，比一条不工作的检测器危险。**

    **所以那条检查要配一条**：通过条件里没有内部名词，只说明它不是功能判据；
    要判它是不是可发现性判据，**还得问它的主语是不是一个不知道答案的人。**

24. **⭐ 只在出错时才走的那条路径,自己也只在出错时才发作。**
    2026-09-01 一天里出现三次,**三次的机制各不相同,而失败形态完全一样:什么都没有。**

    | 报警路径 | 它自己带的缺陷 |
    | --- | --- |
    | `content_bounds` 里「客户区退化就拒绝布局并说明原因」那一支 | 那句日志调 `frame_hwnd()`,**而它要拿 `layout()` 正持着的那把锁**——报警本身会挂死主线程 |
    | 看门狗第一版 | 和被监视的主线程共享 `println!` 的全局 stdout 锁——**主线程卡在一次写上时,看门狗在自己那行日志上阻塞,永久沉默** |
    | 看门狗第二版 | 报警那一支要 `format!`,**而 `format!` 要堆锁**;从外部冻结主线程会连带冻住堆,**于是造出的正对照可能什么都不打** |

    **共同点**:那条路径**任何常规运行都碰不到**,所以它不在任何一次「跑通了」里;
    而它失败时的症状是**缺席**,和「一切正常」在日志里长得一模一样。

    ⚠️ **第三个实例还多一层,值得单记**:那是**探针自己**的报警路径,
    而**它的失败形态(沉默)和它要排除的东西(看门狗坏了)同形**——
    **地板的失败形态如果和它要排除的东西同形,建在它上面的判据全部悬空。**

    ### 可执行的那条:报警路径不许分配,也不许和被监视的东西共享任何锁

    修的时候发现 **`format!` 不是唯一的分配点**:取时间戳的函数返回 `String`、
    按路径开文件要把路径转成宽字符串,**两个都要堆**。
    落地的形状是:**句柄在健康时预开并留着、数字写进固定栈缓冲、时间戳手工拼**。

    **而「已经排除了」这句话本身要分三段写,不能合成一句**:

    | | |
    | --- | --- |
    | **已量到** | 线程内零 stdout、报警支零分配调用——一条带正负 canary 的检查器每次都能重跑 |
    | **结构性、未量** | 没有一个**具名**调用碰堆,**但两跳之外的 helper 仍然可能;名字是检查器能看见的全部** |
    | **未检验** | 主线程真卡在 stdout 写上或持着堆锁时,看门狗还出不出声——**从没演示过** |

    > **它停在未检验,直到有人量它,不是直到有人觉得论证够有说服力。**

    **中间那一段最容易被吞掉**:第一次写这句话的人把三段合成了「改动在代码层面消除了共享锁」,
    **而那句两边都不属于——机制那半今天就能变成读数,结果那半必须一直标未检验,
    中间那句只是错的。**

    | --- | --- |

68. **⭐ 参考实现把变量名叫 `FakeCode`,而它 ship 了。**（2026-09-02）

    调查 PowerShell 能不能发 OSC 133 D(命令结束 + 退出码)时,
    读微软在 shipping 的 `shellIntegration.ps1`,原文是:

    ```powershell
    $FakeCode = [int]!$global:?
    ```

    **它用的是 `$?`(成功/失败的布尔),不是 `$LASTEXITCODE`。**
    `[int]!` 把它变成 0 或 1——**所以「退出码 3」和「退出码 127」一律报成 1。**

    > **一个不够区分的数,被当成一个精确的数用。**
    > 而写它的人知道,变量名就叫 `FakeCode`。

    调查者的建议是**不要跟着做**:要么只发 D 不带退出码(微软自己在
    「没有历史项」时就是这么做的),要么用 `$LASTEXITCODE`——
    **但它只对原生 exe 有意义,对 cmdlet 失败是 stale 的,那是另一种近似值不是改进**。
    **不要发 0/1 冒充退出码**:终端拿到「1」会显示「命令失败,退出码 1」,
    而真值可能是 127(命令不存在)。

    **三个精确的标记加一个诚实的「命令结束了」,胜过四个里混一个假数。**

    ⚠️ 连带一条量化证据:微软那份脚本必须维护一个状态机
    (`LastHistoryId` / `IsInExecution`)才能判断「这次回车到底跑没跑过命令」——
    Ctrl+C 和空回车都会触发 prompt 但没有命令。
    **不带状态机的实现会给每一次空回车发一个 D,
    终端那边看到一串没有 C 与之配对的 D。**

73. **⭐ `ok:true` 是「文本打进去了」,不是「它收到了」;而被打断的指令在历史里不留痕迹。**（2026-09-02）

    > **判据只有一个:历史里有没有那条 `❯ 那句话`。没有就是从未执行。**

    另外两条实测(同一晚):
    · **`terminal_key(enter)` 不提交**——两个终端、三次按键,屏幕纹丝不动。
    · **框里有残留时,`terminal_send` 一会儿追加、一会儿吞掉**,两种都吃到过:
      一次拼成了两个人都没写过的一句话,一次把原话整条吃掉、只发出了解释用的括号。
      **所以核的是历史里那条 `❯` 的全文,不是「有没有新行」。**

74. **⭐ 一条判据能证伪自己,比它能发现缺陷更值钱。**（2026-09-02）

    主控给的验收判据是「断言 `Config.ShellIntegration` 的每个成员在
    `Shell` 里都存在」。实现者照着写完,**跑地板——全绿,86 pass。**

    **方向反了**:那条断言是 `Config ⊆ Shell`,而缺陷是 `Shell ⊄ Config`。
    把 `powershell` 从 `Config` 删掉只是让那张表变短,**剩下每一条仍然在
    `Shell` 里,断言成立**——缺陷正好是它的反面。
    第一版里还专门写了一段注释,说另一个方向「是个小得多的缺口,故意不断言」:
    **给「不测那个真缺陷」写了一段理由。**

    > **一条断言的方向写错时,它不报错、不变红,它就是通过。
    > 而「通过」这个字,长得和真的通过一模一样。**

    落地:两个方向都断言,并且**把两种失败各自意味着什么写进错误名**——
    `InjectableShellIsNotConfigurable`(能注入、写不出来:功能照常工作,
    用户以为文档错了)、`ConfigurableShellHasNoIntegration`(写得出、没人注入:
    功能静默缺席)。**是地板抓住了判据,不是判据抓住了缺陷。**

    **同一轮里还有一条更硬的判读**:验这个修复时,**地板比正向硬**。
    正向的「没有错误框」只说明这一行没报错;
    **地板(写一个不存在的值)的错误消息把整张合法值表打了出来,
    `powershell` 在里面。**
    一个「把这一行特判掉不报错、但表里还是没有」的假修复能过正向,过不了地板。

75. **⭐ 前提没造出来的那一次,长得正像「地板抓到了缺陷」。**（2026-09-02）

    判据是「焦点停在 alpha 的标签上开新标签,新标签必须开在 alpha」。读数是:

    ```
    标签条:1: C:\work\alpha   2: C:\work\beta
    点了标签 1,然后 ctrl+shift+t
    新标签里 shell 自己报:C:\work\beta
    ```

    **无懈可击地像那条地板要抓的缺陷本身**(继承的是别的标签的目录)。
    真相是那一下**点空了**:`grep 'activate'` **零命中**,
    按 `ctrl+shift+t` 时焦点还在 beta 上——**新标签继承 beta 是对的行为。**

    > **前提没造出来的运行,不是「地板失败」,是这次运行作废。
    > 而这两者在读数上完全一样。**

    这是同一个家族里最贵的一种。前两种今晚都出现过:
    **阴性**(什么也没发生,以为排除了)、**假阳性**(探针对没测过的东西报 ok)。
    这一种是**假缺陷**——**它不会让人漏掉一个坏东西,它会让人去修一个没坏的东西**,
    而修完之后原来对的行为就真的坏了。

    落地:**凡是「先把焦点/状态摆成 X,再做动作」的判据,摆完必须有一条独立的确认**,
    确认那个前提真的成立(这次是现成的 `[strip] click -> activate TabId(2)`,
    代价是一次 `grep`)。**没有它,一次点空会伪装成一个缺陷。**

    **同一轮里还有一条值得抄的地板设计**:重跑那次,另外两个标签都停在 beta,
    所以「继承最后创建的标签」「继承任意别的标签」都会给出 beta,
    **只有「继承焦点标签」给 alpha**——**一条读数同时排掉两种错误实现。**

76. **⭐ 两个人各改了同一个数的一半,闸不会红——它会对。**（2026-09-02）

    一个棘轮的基线要跟着分类进度往下走。**两个人同时在往下改它**:
    一个在写脚本里的那个数,另一个在另一处按自己算出的差额改同一行。

    **它被抓住的两次,一次靠判据,一次靠运气。**

    · **靠判据那次**:分类了 11 条,基线掉了 12。规矩是「降幅必须等于自己
      分类的条数」,于是停下来查那多出来的 1——**是另一个人未提交的改动**。
      如果读成「12,比 11 多,大概是我数错了」,**别人的工作就被记成了自己的进度**。
    · **靠运气那次**:主控的 `sed` 去改 `= 237`,而那个数已经被推到 225,
      **没匹配上,所以什么也没改。**

    > **要是它匹配上了,闸会变绿——而绿的理由是两个人各自把同一个数改了一半。
    > 那一刻没有任何东西会喊,因为它不会红,它会对。**

    这一族里最危险的不是「红成了绿」,是**「对成了对,而理由是错的」**:
    一个凑巧正确的结果不留任何痕迹,而下一次同样的操作会给出一个凑巧错误的结果。

    落地两条:
    · **一个数只能有一个人在一段时间里改**;要动之前先看它现在是多少,
      **而不是看自己上次记得的是多少**。
    · 判据写成**「变化量 == 我做的量」**,不是「变化量 == 预期值」。
      预期值是别人给的,而**别人不知道你手上有几笔**。

77. **⭐ 地板里最要紧的那个信道,是没有变的那个。**（2026-09-02）

    验一个二选一的守卫,取反之后三个读数都翻了面:
    `HOOK` 从 `event` 变 `prompt`、钩子从装上变没装上、
    `prompt` 从逐字未动变被改写。**三条都翻了,看起来足够了。**

    **但这三条同时翻,还有另一个解释:两次的环境不一样。**
    真正排除掉它的是第四条——**那条没有变的**:

    ```
    HAS_EVENT_PROPERTY   原样 True    取反 True   ← 不变
    ```

    > **属性在两次里都确实存在,变的只有守卫。
    > 一个「什么都翻了」的地板,证明的是「两次不同」;
    > 要证明「是我改的那一处造成的」,得有一样东西明确没变。**

    同一轮里还有一条同族的:`HOOK=event` 只说明**代码走了那条分支**,
    不说明**那一行赋值成功了**——而它要验的那个缺陷正是
    「走进了分支、赋值炸了」。所以加了第二个读数 `LOCATION_ACTION_SET`。
    **一个「分支选对了」的读数,和一个「分支里的事做成了」的读数,是两句话。**

    做法上还有一处省了整个出错面:**被测文件全程只读**,
    取反的副本生成在别处。没有「改了再还原」,就没有「还原漏了」——
    今晚已经有人在 `cp` 带回旧 mtime 上栽过一次。

78. **⭐ 一次改动里,最要紧的那一半可能没有任何闸守着——而「做完了」的样子把这件事盖住。**（2026-09-02）

    三行日志本来只打 `tab 3`,两个窗口一开就不可判读。改成同时打
    **窗口**和 **`TabId`** 之后,按规矩做地板:把其中一行的窗口拿掉。

    **闸没响。** 不是地板没接上——那一行仍然打着 `TabId`,
    而「打了 id 的行」是被豁免的,**而且豁免得对**:id 全进程唯一。
    只有把两样一起拿掉,计数才动。

    > **所以窗口那一半,谁哪天删掉,四道闸全绿,
    > 而「哪个窗口的条上第 3 个」从此没有答案。**

    **没有为它造规则。**「打了 index 的行必须同时打 frame」贴身到
    误伤会比它挡住的多——**一条会被人加豁免绕开的规则,最后只剩下豁免。**

    要点在后半句:**这件事被写下来了,而不是以「我做完了」的形状留在那里。**
    这一批的正确性靠的是签名上那段文档注释和提交信息,**不靠闸门**——
    和「收口只覆盖代码、不覆盖已验证」是同一种坦白。

    **同一轮里还有两次「只在预期的那种失败下才出声的读法」**:
    · 地板的 `grep` 写死了 `^FAIL: 1 more`,而当时检查器打的是
      `FAIL, and it is good news`——**什么都没匹配到,读起来像「地板没响」**。
      **这一条它上一批刚记过,隔了一批又犯。**
    · 改基线的脚本在第二处断言上抛了,整段没写入,
      于是「基线没变」看起来像别的问题——**又是那条「部分成功不存在」。**

79. **⭐ 滤条名写错和滤条名写对,读数相同。**（2026-09-02）

    这个仓的 `zig build -Dtest-filter=X` **是加法不是过滤**:
    有一批测试无论如何都会跑(本仓当时是 **85** 条),`X` 每命中一条就 +1。
    **`X` 拼错时,它照样 85 pass、exit=0。**

    > **所以「跑 `-Dtest-filter=X`,全绿」这句话,
    > 在 `X` 拼错的时候同样成立——而那时候一条都没跑。**

    可靠的形式是两步,缺一步都不够:
    1. **基线 + 差值**:先用一个不存在的名字量基线(85),再看这条是不是 86。
       差值证明的是「**有东西**进去了」。
    2. **我写的每一条各自跑过**:差值 +1 说明进去了一条,
       **不说明进去的是哪一条**。同一轮加两条测试时,
       如果其中一条的名字不含滤条那个词,**它一次都不会执行,
       而计数从 91 涨到 92 看起来像两条都进去了。**

    实测过的那次:同一轮加了「powershell 集成」和「三句话互不相同」两条,
    后者名字里没有 `powershell`。**分开跑两个滤条**才拿到两个各自的
    85→86,否则那条测试从写出来到提交一次都没运行过。

    同一族的一般形式:**一个「什么都没匹配到」的检查,
    和一个「匹配到了并且都通过」的检查,输出相同。**
    今晚它出现过四次(这条、`grep '^FAIL: 1 more'` 那次、
    正则认不出 `next_id2` 那次、被窄化的白名单那三次)。

80. **⭐ 一条正确的方法用了一半,读起来和用完了一样。**（2026-09-02）

    同一晚上,三个人各自撞了一次,形状一模一样:

    · **验证者**发现「命令面板关窗不打 destroyed」,**做了正确的对照**
      (在另一条路上看到它存在),还写下了「两轮对照才分得开『没实现』和
      『这条路没走到』」——**然后停在两条**。真实情况是四条路里三条都不打。
      它另外两条那轮**跑过**,但当时窗口里还有别的标签,
      **从没走到「最后一个」那一支**。
      > **同一个手势,在「还剩别的标签」和「这是最后一个」下是两条不同的路。
      > 我验的是前者,报的却像是关于后者的结论。**
    · **集成作者**在同一份调查里写下了「『每台 Windows 都有』严格说只对
      5.1 成立」,**却没把这个认识用在自己正在用的那个 6+ API 上**。
    · **主控**要求「两个方向都断言」,自己写判据时**只写了一个方向**,
      而缺陷正好在没写的那一边。

    **共同点不是粗心,是三次都已经拿到了那把钥匙,然后没有把它插进自己那把锁。**
    这比「不知道」难查得多:**不知道的人会去查,用了一半的人以为自己查过了。**

    可执行的形式:**每次写下一条一般性的话,当场问一句
    「我手上这件事,是不是它的一个实例」**——今晚三次,
    三次那句话都是当事人自己刚写下的。

81. **⭐ 判据本身不会过期,判据里对「当前状态」的描述会。**（2026-09-02）

    一份验收判据写在实现之前——这是对的,今晚一直这么做。
    但那份文本里同时有两种句子:

    · **「必须成立什么」** —— 这是判据,它不随时间变。
    · **「今天是什么样」** —— 这是**写作那一刻的快照**,它会。

    实例:判据的前置一节写着「四条关闭路径今天终点相同,所以现在分不出
    谁走的哪条」,并要求把痕迹补上。**等接手的人读到时,那件事已经做完并验过了**
    ——四条各有各的 `via`,`PostQuitMessage` 全树只剩一处。
    照着那段描述去做的人,会**把一件已经完成的事从零重做一遍**,
    而且做完发现「果然可以」,**读起来像是自己修好的**。

    > **凡是判据里以「今天…」「现在…」开头的句子,都是写作时的快照。
    > 到手先核一次,而不是照着做。**

    **写的那一侧也有对应的落地**(同一个人在同一份台账上第二次撞到之后给的):
    **要么写上取数时间,要么把句子从「现在是什么」改写成「我验的是什么」。**
    后者不会过期——「我在 X 时刻点它没有反应」永远为真,
    而「它点了没有反应」半小时后就可能是假的。

    **这条第一次咬到的是立规矩的人自己。** 主控向机器上的人反复强调
    「凡是『今天…』开头的句子要核不要照做」,然后在同一天把一条自己笔记里的
    「M6 卡在 provider 没装」当成现状转述出去——**那句话写在 provider 装上之前**,
    而验证者当场纠了回来:「和你让我守的那条规则同一个形状,这次落在了你自己的笔记上。」
    **一条规矩最后一个被应用到的地方,通常是写它的人自己的笔记。**

    **过期时的改法是标住,不是改掉。** 那次的处理值得抄:
    原话按当时的样子留着、加一句「这是我取那份读数时的状态」、
    后面补上现在的状态,**并明写「那是静态读数,没有人在真机上点过它」**——
    因为 `cb_action` 里有分支只说明**有人接**,不说明**点下去出来一个窗口**。
    **要么自己点一次,要么别把它当已修。**

    这条被捕到不是因为流程,是因为**上一个持有仪器的人在交回之前又读了一遍那份判据**,
    发现其中一段描述的世界已经不存在了。**交接的价值有一半在这里:
    交出去的人是唯一知道「那句话现在还对不对」的人。**

82. **⭐ 负对照挑中的那一项,自己也得是好的——而弱判据不会暴露它坏了。**（2026-09-02）

    取一条读数时用了负对照:「菜单不是一律置灰」——**同一子菜单里
    另外三项不灰**。结论成立,量的是**灰态**。

    **但挑中的那三项里,有一项既不灰、又什么都不做**(「新建窗口」:
    菜单行存在、不灰,而宿主根本没有处理那个动作的分支)。
    **不是验过它能用然后它坏了,是从来没问过这一问。**

    > **「不灰」和「能用」是两个量。
    > 拿「不灰」当负对照,挑的是你验过真的能用的那一项。**

    这条的阴险处在最后半句:**负对照只要「能证伪」就够用,所以弱判据下它不暴露**。
    换一个稍微严一点的判据(「不灰即可点出效果」),
    同一次取样就会**拿一个坏项当基准**——
    **而那种错法读起来和做对了一样。**

    (那条缺陷本身也因此被找到:一个用户看得见、点得动、毫无反应、
    也没有任何提示的菜单项。它不是被判据抓到的,
    是另一个人为了别的事去读代码时掉出来的。)

83. **⭐ 把人「停下来」和让人「收不到」是两件事——撤掉看守反而让群消息叫得醒他。**（2026-09-02）

    两位工作者上下文用尽、交接写完,主控撤掉了他们的看守以止住静默通知。
    **然后往群里发了一份交接记录。**

    在这套工具里,**被看守的终端不会被群消息唤醒,没被看守的会**。
    所以那一帖精确地叫醒了刚被请下场的两个人,
    **让他们用仅剩的上下文读了一份写给别人看的总结。**

    > **「我让他停下来了」和「他现在收不到我说话」是两件事。
    > 撤掉看守只做了前一半,而且把后一半推向了反面。**

    落地:**人一旦请下场,关于他的话就不要再进群**;
    要留档就写进文档或提交信息——那些他不会被动读到。

84. **⭐ 正对照通过了,答案仍然可以是错的——它只覆盖你想到的那几类。**（2026-09-02）

    要量一个数:宿主的 `cb_action` 到底处理了多少个核心动作,
    差集就是「点了没反应」的完整名单。**量了四次,前三次都给出一份
    看起来很像真的名单**,而三次的错法各不相同:

    | 次 | 模式 | 结果 | 错在哪 |
    | --- | --- | --- | --- |
    | 1 | `ffi::ACTION_\w+` | 缺 33 | 有一半调用点不带 `ffi::` 前缀 |
    | 2 | `^\s+ACTION_\w+ =>` | 缺 23 | 另一半带前缀,这次轮到它们落空 |
    | 3 | 两种并集 | 缺 5 | **or 模式** `A \| B =>` 里的第一个分支看不见 |
    | 4 | 三种并集 | 缺 2 ✅ | —— |

    **第三次那一轮我加了正对照**:`ACTION_PWD` / `ACTION_NEW_TAB` /
    `ACTION_READONLY` 必须出现在「已处理」里——**三条全过,而答案仍然是错的。**

    > **正对照证明的是「我这条路能走通」,
    > 不是「所有路我都走过」。它只覆盖你想得到的那几类,
    > 而漏掉的那一类正是你没想到的那一类——否则你早就把它加进对照了。**

    **认出错的不是对照,是一条与它矛盾的既有事实**:
    `ACTION_CLOSE_WINDOW` 出现在「未处理」名单上,
    而真机上明明量到过 `via core close_window` 生效。
    **一条外部读数和一份内部名单打架,那一次名单认输。**

    (最终结果:48 个动作 46 个有分支;
    剩下两个一个是**灰的且写明了理由**、一个**没有任何界面入口**。
    所以「不灰却什么都不做」的行全树只有一个——正是那次顺手挖出来的。)

85. **⭐ 一份写着「这里没有 X」的文档,对每一次搜索都回答「有 X」。**（2026-09-02）

    给可执行文件嵌一份清单,里面**刻意不声明 DPI**(声明它会让另一处代码
    安静地失效)。为了让下一个人别来补,清单注释里写了一句:
    「如果你是来加 `<dpiAware>` 元素的,请在同一次编辑里删掉那行代码。」

    **那句话把元素名写进了产物。** 而任何人问「这个 exe 的清单声明 DPI 了吗」,
    最自然的检查就是去二进制里搜那个名字——**于是答案是「有」。**

    > **注释对加载器是惰性的,对人和脚本不是。
    > 一份声明「此处没有 X」的文档,如果对每一次搜索都回答「有 X」,
    > 比没有那份文档更糟。**

    改法不是删掉那句话(那句话是对的、也是必要的),
    是**把它写成不含那个词的形式**,并加一句
    「这份文件里刻意不拼出那个元素名,搜它应当什么都搜不到」。

    **它是怎么被发现的,比它本身重要**:这份清单**上一轮已经验过一次**
    (`.rsrc` 段在、清单原文在),读数三行、全绿。
    这一次只是因为一条新定的规矩——**要单独落地的一批,读数必须取自
    「HEAD + 我的改动」那棵树,而不是工作区**——而被重新量了一遍,
    量的时候顺手多问了一句「那 DPI 呢」。
    > **规矩定的是「重编一次」,实际买到的是「再看一眼」。**

86. **⭐ 「将要提交的内容」住进了两个地方,于是一次普通提交撤掉了两个修复。**（2026-09-02）

    工作区里有别人未写完的改动,而要落地的这一批和它在同一个文件里。
    为了一个字都不碰工作区,**用临时索引直接写树提交**
    (`GIT_INDEX_FILE` + `read-tree` + `write-tree` + `commit-tree` + `update-ref`)。
    **那一步是对的,它保住了别人的活。**

    **但它移动了分支而没有更新主索引。** 之后一次再普通不过的提交
    ——`git add` 一个文档、`git commit`——提交的是**整个主索引**,
    而主索引还停在那两批之前。

    > **两个修复连同一条方法论一起被撤掉,而没有任何东西说这件事。
    > 提交还在历史里,文件回去了。**

    这一族的形状和这一晚其它十几次一样,**只是这次的载体是 git 自己**:
    **同一个事实(「将要提交的是什么」)有了两个住处,它们会漂移,而漂移是无声的。**
    临时索引每用一次,主索引就旧一次;而主索引旧掉的**症状为零**,
    直到某一次不带路径的 `commit` 把它整个写下去。

    **落地的两条**:
    · **临时索引提交之后,立刻 `git reset`(不带 `--hard`)把主索引对回 HEAD**——
      它不碰工作区,只是让那两个住处重新一致。
    · **每次提交后核一眼「这次到底动了哪些文件」**(`git show --stat`)。
      这次那条 `settings_ui.rs -157` 就印在屏幕上,而当时没人看。

    **它是怎么被发现的**:一个正在读树的人注意到
    「暂存区里压着一份别人提交前的旧快照,现在直接 commit 会把它撤掉」,
    **并且说了出来,而不是假设负责提交的人知道自己在干什么。**
    它自己那一轮什么也没提交,这句话是顺带报的。

87. **⭐ 检查那些闸的那行命令,自己没有被检查过——它一整晚印的都是 `basename` 的退出码。**（2026-09-02）

    每次提交前跑一遍全部的闸,用的是这一行:

    ```sh
    for f in windows/tools/*.py; do
        python3 "$f" >/dev/null 2>&1
        printf "%-28s exit=%s\n" "$(basename $f)" "$?"   # ← 坏在这里
    done
    ```

    **`$(basename $f)` 在 `printf` 之前执行,而它把 `$?` 重置成 0。**
    所以那一列 `exit=` 报的是 `basename` 的退出码,**恒为 0**。
    「九道闸全绿」这句话,在一晚上里说了十几次,**一次都没有被验证过。**

    > **一个永远说「通过」的检查,和一个真的在检查的检查,输出一模一样。**
    > 这条规矩这一晚给别人立过七次;**立它的人自己那一行,从没被自己跑过一次。**

    **补验的结果**:HEAD 上八道真绿,唯一红的那道是工作区里一个过期的基线,
    而 HEAD 里那个数是对的——**所以没有一次提交落在真红的闸上。
    但那是运气,不是那个检查。**

    **它是怎么暴露的**:一道闸单独跑时报 `exit=1`,而同一棵树上循环里报 `exit=0`。
    **两个读数打架,而其中一个必须是错的**——这和今晚那条
    「一条外部读数和一份内部名单打架,那一次名单认输」是同一条,
    只是这次输的是我的检查。

    **落地**:退出码要在**下一条命令之前**取下来(`rc=$?`),
    而任何「一行里既取退出码又做别的事」的写法都要假定它已经坏了。
    更一般的一条:**每一个用来判断别人的工具,自己也要有一次被判断的时刻**——
    今晚每道闸都被要求带 canary、带地板,**唯独跑这些闸的那一行没有。**

88. **⭐ 那个数是影子,不是那件事——把缺陷原样放回去,九道闸全绿。**（2026-09-02）

    一整晚建了九道闸,烧掉两百多条日志的窗口标识,那个数从 **274 走到 38**。
    最后一批修的是一个真缺陷:标记某个终端时,通知**从来没有带上那个 surface**,
    所以菜单说不出标记落在哪个终端、两个窗口时也说不出落在哪个窗口。

    修完之后,做了两条负对照,**而它们说的是这一整套东西的边界**:

    · **把标签改成「当前那个窗口」**(那个诱人的写法)→ **闸全绿**。
      这道闸问的是「有没有指名一个窗口」,**不是「指的对不对」**。
    · **把缺陷原样放回去**(通知重新什么都不带)→ **闸还是全绿,而且编得过。**

    > **这次真正修的那个东西,所有的闸都看不见。
    > 41 → 38 那个数字,只是它的影子。**

    这不是说那些闸没用——它们今晚抓到过十几件真东西。
    **是说它们抓的是「说得出说不出」,而不是「说的对不对」**;
    而一个能被静态检查的性质,和一个只能被运行出来的性质,中间永远隔着一台机器。

    落地:**凡是「修好了但闸看不见」的改动,判据必须写成一条真机上的读数,
    并且在提交信息里写明「本地全绿不构成对这一条的证据」。**
    那一批的判据是:开两个窗口、焦点留在窗口 1,
    去标记窗口 2 里的一个后台 pane——**两行都必须带 `w2`**;
    印成 `w1` 就是查表退回成了「当前窗口」,
    **而那个形状,负对照已经证明没有任何一道闸会拦。**

## 七之二、这一晚的全部方法论,其实是一句话

第 25–88 条各自带触发条件,但把它们摆在一起之后,**大半是同一句话的不同穿法**:
（这句原本写的是「四十条里有三十条」。**那个比例是在第 64 条那一版上数出来的**,
后加的 65–88 条没有重数,所以这里不再报比例——
**一个不重数、却跟着范围一起扩大的比例,正是这份文档自己反复在抓的那种数。**）

> **一个在「被测的东西是坏的」时候也会出现的观察,不是证据。**

同一晚上,它以这些形状出现过:

| 观察 | 坏的时候也长这样 |
| --- | --- |
| `0 mismatches` | 四个标签的探针点在窗口外,`contains` 照样匹配 |
| `85 pass, exit=0` | `-Dtest-filter` 匹配不到任何东西时的读数 |
| 测试 exe 还在目录里 | 编译失败时上一次那个也还在 |
| `cargo build` 绿 | 它不编译 `#[cfg(test)]` |
| 三个绿(build / test --no-run / 97 个单测) | **没有一道闸运行过代码** |
| `[reopen] opener installed` 在第 16 行 | 死锁那次也在第 16 行 |
| 菜单项不带勾 | 「状态是关的」和「没人告诉过我状态」 |
| 提示符看起来正常 | `$P$G` 渲染出来正好是 cmd 的默认提示符 |
| `shortcut_for` 返回 `None` | 测试二进制里没加载核心,任何查询都返回 `None` |
| grep 0 命中 | 探针够不到目标(**四次**:调用点 / `since` 范围 / 读错文件 / 正则漏一行) |
| exe 的 sha 对上了 | **dll 的 sha 在同一行的隔壁,三个半小时没变过** |

**对策也只有一句**:在拿这个观察当结论之前,**先让被测的东西坏一次,看这个观察变不变**。
那就是「地板」。今晚每一条真正站住的结论,后面都跟着一次真的注入;
每一条没站住的,都是因为那次注入没做、或者做的是另一条路径。

⚠️ **而地板本身也会瞎**,今晚三次:定位串不唯一所以注入没发生却报 exit=0;
`| head -5` 让编译器 SIGPIPE 死在写产物之前,跑的是旧二进制;
以及一条**造不出地板的分支**——留着它不是覆盖,是覆盖的样子。
**所以还有一句**:**地板不响的第一嫌疑,永远是地板本身。**
