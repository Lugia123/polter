# 任务面板：存的是「谁在做哪件事」，不是那件事本身

> 校验方式：`git log -1 --format='%H %h %ad %s'`
> 状态：**已实现。** 本章推翻了核心原则 P7 的一半，理由在第一节，
> 那一节比后面的形状更重要。

## 这一章要解决的是什么

> **worker 的工作注意力。不被其他 worker 打断，能集中在自己的工作内容上。**

面板是这件事的一半——给 worker 一个「我该做什么」的地方，那个地方不会随上下文
被冲掉。另一半在机制里，见第六节：**被监管的终端不因群消息被叫醒。**

两半解决的是同一件事，所以写在同一章。

## 本章覆盖什么

- 为什么 P7「不管理任务」要被改写，以及改写成什么。
- 面板存什么、不存什么，以及那条防止它长大的红线。
- 群聊、直接指令、面板三者各自的分工。
- 取消一个任务为什么必须先说话再消失。
- 界面：群聊 TUI 里的第二个 tab。

## 本章不覆盖什么

- 群聊模型本身（成员、`seq`、compact）—— 见 [chatui.md](chatui.md) 与 [mcp.md](mcp.md)。
- 可达性规则、`terminal_send` 怎么注入 —— 见 [mcp.md](mcp.md)。
- 核心存储与插件存储的分界 —— 见 [boundary.md](boundary.md)。

## 一、P7 被改写了，这一节是理由

`README.md` 的 P7 写着：

> **Poltergeist 本身不管理任务。** 任务由其他系统 / 载体承载。不干涉任务内容、
> 不存任务、不排任务。理由：一旦开始存任务，就要处理任务状态、依赖、冲突、
> 持久化，**能力层会长成一个任务系统**，而市面上已有的任务载体比我们做得好。

**那句怕的事是对的，怕错了对象。** P7 防的是「长成一个任务系统」，而这里要解决的
不是项目管理，是**一条派下去的命令活不过它自己那一屏**。

### 这和 P5 推翻工作模式用的是同一个论证

P5 当年否掉工作模式，理由是：

> **一个只在设定那一刻存在的状态，等于没有状态。** 切模式会往终端注入一句提示，
> 之后这句话就随上下文被挤走了——挂机过夜恰恰是上下文最容易被冲掉的场景。

**一条 `terminal_send` 派下去的命令正是这样的状态。** 它滚出屏幕、被 compact 掉，
半夜醒来的 worker 不知道自己该干什么。tab 上那个常驻的环就是为这个加的
（[supervisor.md](supervisor.md)），面板是同一个论证用在「派了什么活」上。

### 所以界线重画，而不是取消

> **存的是「谁在做哪件事、做完没有」，不是「那件事是什么」。**

| 面板**存** | 面板**不存** |
| --- | --- |
| 一行标题 | 需求描述、验收细节 |
| 负责的终端 | 依赖、优先级、截止日期 |
| 开 / 关 / 取消 | 子任务、附件、评论 |
| 进度状态 | 历史流水 |

**红线：一行标题放不下的东西，属于别的载体。** 要那些的人有 Kanban、有 issue
系统，而它们做得比我们好——这正是 P7 原话里成立的那半句。**这条红线是可执行的闸**，
不是自觉：字段就那几个，加字段要先回来改这一章。

## 二、三条路各管什么

面板不是第四种沟通方式，它是**把已有三条路上会消失的那部分固定下来**。

| | 走哪 | 受众 | 为什么 |
| --- | --- | --- | --- |
| **命令** | `terminal_send` 直接进对方输入框 | 那一个终端 | 在群里 @ 某人会把群变成指挥频道，其余成员每条都被打断一次 |
| **汇报** | 群 | 总管 + 明天早上那份记录 | 大家能看见彼此在什么进度，总管能回溯 |
| **规划** | 群 | 所有人 | 一份带署名的清单，谁做哪件一目了然 |
| **状态** | **面板** | 总管随时查，worker 只看自己的 | 命令会滚走，状态不该跟着滚走 |

**汇报里要写明是哪几个任务的**，这样总管核对时不必靠读散文猜进度。

## 三、生命周期，以及取消为什么必须先说话

- 总管**建**任务、**派**给某个终端。
- worker **更新进度**，并在群里汇报（注明任务号）。
- 总管核对之后**关闭**。
- 总管也可以**提前取消**。
- 关闭 / 取消的任务**从 worker 的视野里消失**。

**取消必须先告诉 worker，再消失。**

一个正在干活的 worker，如果它的任务只是从面板上悄悄没了，它**不会知道该停**——
它会继续干一件已经被取消的事。这是「静默的状态变化」，而这套东西**已经栽过三次**：
删掉的 skill 继续在用户机器上指挥 agent、`set_watch` 丢掉参数还回 ok、
供给插件找不到 `claude` 就静默退出 0。

所以：**取消 = 一条 `terminal_send`（「任务 X 取消了，停下」）+ 从面板移除**。
关闭不需要——关闭是 worker 自己报完、总管核过的，它已经知道了。

## 四、面板是核心功能，不是插件

判据用 [boundary.md](boundary.md) 第一节那条：**缺了它 Polter 就不成立的是功能。**

如果派活的状态只在某个插件开着时才存在，那和「只在设定那一刻存在」是同一个毛病，
只是把消失的时机从「上下文被冲掉」换成了「插件没开」。

还有一条现实的：**插件今天加不了工具**。插件能调 MCP 工具面，但不能给总管**提供**
一个 `task_create`。要做成插件，得先给插件框架加「插件可以声明工具」一整块能力，
而那是比面板本身大得多的改动。

**跨重启必须存在。** 挂机过夜是这整套东西存在的理由，而第二天早上一块空面板等于
没有面板。落盘复用已有的形状（[storage.md](storage.md) 的记录那一半），
不发明第三种。

## 五、界面：群聊 TUI 里的第二个 tab

群聊界面是终端内的 TUI（`src/cli/chat.zig`，1322 行，左栏群列表 + 右栏消息，
带鼠标点击与滚动）。**原生窗口那条路当年做出来被否掉了**，见
[chatui.md](chatui.md)「决策变更」——不要重新提。

右栏顶部加一个 tab：**群聊 / 任务**。左栏（群列表）不动，因为任务是**按群**的，
切 tab 不该改变「现在看的是哪个群」。

任务视图一行一个任务：状态、标题、负责的终端。**用户看的是全部**（包括已关闭的，
那是它回顾昨晚的方式）；**worker 通过工具只看到自己的、且未关闭的**——
两者是不同的问题，不要用同一个过滤器。

## 取舍记录

| 方案 | 成本 | 为什么没选 / 为什么选 |
| --- | --- | --- |
| 不做，继续只靠群里的清单 | 零 | **没选。** 清单是一条会滚走的消息，正是 P5 判过死刑的那种状态 |
| 做成插件 | 要先给插件加「声明工具」的能力 | **没选。** 状态不能取决于某个插件开没开；而且那块能力比面板本身大 |
| 完整任务系统（依赖、优先级、子任务） | 大 | **没选。** 那正是 P7 怕的东西，而且 Kanban 做得更好 |
| **一行标题 + 归属 + 状态** | 小，且红线可执行 | **选了。** 解决「命令会消失」，不解决项目管理 |
| 取消时静默移除 | 零 | **没选。** worker 会继续干一件已取消的活，本仓栽过三次同形状的静默变化 |
| 面板另开一个窗口 | 又一个界面 | **没选。** 群聊 TUI 已经在那儿，任务是按群的，切 tab 不该改变看的是哪个群 |

## 六、通知按角色分，不按发言人分

面板只解决一半。另一半是：`App.tellTerminalsAboutMessages` 原来对群里**每一个**
成员检查未读，有未读就往那个终端打字一条提醒，只有一道 30 秒限流，
**完全不看收件人是谁**。三个 worker 各自汇报，每个 worker 都被打断一次，
而它们互相之间根本不需要知道对方的进度。

### 规则

> **被监管的终端（`role == .watched`）不因群消息被叫醒，无论那条消息是谁发的。
> 它的注意力归它的总管。** 其余成员照常通知。

判据是 `Bus.roleOf(收件人)` 一个，不需要新概念，而且**三种角色的答案都从
「谁在指挥它」推出来**：

| 角色 | 通知吗 | 因为 |
| --- | --- | --- |
| `watched` | **否** | 它的注意力归它的总管，总管会直接送到它的输入框 |
| `supervisor` | 是 | 它要靠这个知道谁报了什么 |
| `none`（无标记、用户） | 是 | **没有人在指挥它**，群是它唯一的渠道 |

「按收件人精确通知」没有做：那等于把 `@` 变成机制，而 `@` 正是这条要废掉的用法。

### 两条不变的

1. **未读计数不跟着改。** `Chat.unread` 一个字没动，`waking` 是另一个函数。
   worker 下次自己 `group_read` 仍然读得到全部——总管的既要、同伴的汇报，
   一条不少。**「不打断」不等于「看不见」。**
2. **界面照旧显示全部。** 那是界面，不是打断。

### 这条让一件事从「不推荐」变成「不会发生」

**总管只在群里发，活就永远派不出去。** 这是个会静默失败的坑：总管在群里派了活，
看起来说了，而没有任何 worker 会动。所以 skill 里写成后果而不是禁令
（`supervising.md`「Posting in a group does not make anybody move」）。

用户定的流程：

1. 总管 `task_create` 建任务。
2. 群里 `group_post` 一份既要——**主要给自己和记录看**，顺带给屏幕前的人。
   它不需要叫醒任何人，这正是它的定位。
3. **逐个** `terminal_send` 把任务指令直接送进每个 worker 的输入框，
   带上任务号和验收标准。
4. `task_assign` 让面板记上谁在做。

## 七、当初的未决问题，现在的答案

1. **进度是枚举，不是自由文本。** `queued / working / blocked / done`。
   自由文本是第二个描述字段，而第二个描述字段正是红线要挡的东西；
   枚举还让「有没有人卡住」能一眼扫出来，不必读散文。散文仍然存在——
   它去群里，汇报时注明任务号。
2. **一个任务只能派给一个终端。** 两个负责人等于没有负责人，拆成两条的成本是一行。
   `owner` 是一个 `Bus.Id`，`0` 表示还没派。

   **负责的终端关掉时，任务留着，`owner` 退回 0**（`Tasks.forget`，由
   `Surface.deinit` 调）。任务本身不删：一个负责人已经没了的任务，正是第二天早上
   要看见的那一条——它需要有人接，而这只有在它还在面板上时才看得见。
   把它改成未分配是记账，不是判断：**谁来接是总管的判断**，面板不替它做。

3. **群没了，群里的任务跟着没**（`App.chatDestroy` 调 `Tasks.forgetGroup`）——
   面板是按群画的，群不在了这些任务就没有地方可画。
   这条以前有点危险：一个还在干活的群被删掉，worker 的任务会在它脚下消失。
   现在删不掉了——**群里还有开着的终端就不许销毁**（`GroupActive`，
   见 [chatui.md](chatui.md)「群列表：顺序与 `d`」）。
4. **面板自己恢复，`session_recall` 不碰它。** 两份真相的问题是这样避开的：
   `session_recall` 交的是**材料**（群、简介、每个终端的 cwd 和 title），
   总管读了自己判断；面板交的是**事实**（第 7 号任务是谁的、什么状态），
   没有需要判断的地方。前者要判断是因为「屏幕上这个终端是不是昨晚那个」是个判断，
   而任务号不是。

## 八、落盘：复用 `daylog.Tree`，不发明第三种

`<state>/tasks/<群>/<日期>.jsonl`，和 `<state>/chat/` 与 `<state>/terminals/`
同一个形状——一个群一个目录、一天一个文件、一行一个 JSON 对象。
群名到目录名的编码只有一处（`daylog.encodeSegment`），这正是
[gaps.md](gaps.md) 第三节警告的：一个状态目录里两套编码规则。

**一行是一个事件**（created / assigned / progressed / closed / cancelled），
不是一行一个任务的快照——因为记录是只追加的，说「任务变了」的唯一方式就是写下它变了。
每行携带任务的**全部**字段，所以中间丢了几行也还能重建：启动时按时间顺序重放。

### 这一节顺手暴露了群的一个不一致，已经补上

面板自动恢复，理由写得很硬（「一块只写不读的面板，就是第二天早上九点那块空屏幕」）。
可**群当时是不恢复的**——`Chat` 是纯内存模型，重启后什么都不剩。于是出现一个谁都
没想要的状态：**重启后任务回来了，而它们所属的那个群不存在。**

补法不是把面板改回去，是把群的那条线画准：

> **群壳（群名 + 简介）自动恢复，成员不恢复。**

原设计拒绝自动还原，理由是那要求程序判断「屏幕上这个终端是不是昨晚那个」，
而那是语义判断，违反 P1。**那条理由只对成员成立。** 群名是一个字符串。
所以和第七节第 3 条是同一个划分：**没有需要判断的地方，程序就自己来；
有判断的地方，交给总管。** 面板交的是事实（第 7 号任务是谁的），
群壳交的也是事实（有过一个叫 build 的群，它是干什么的），
而「谁是昨晚那个终端」仍然只有总管能答。

群列表从 `<state>/chat/<群>/` 这些**已有的记录目录**推导，不塞进 `session.json`
——否则快照会越长越大，而且和记录目录成了两份真相。群名到目录名的编码仍然只有
一处（`daylog.encodeSegment`），它的逆也放在同一个文件里（`daylog.decodeSegment`），
这正是 [gaps.md](gaps.md) 第三节警告的那件事。落地见
`src/poltergeist/GroupLog.zig`，界面那一半见 [chatui.md](chatui.md)。

## 九、面板会被跳过，而且是在读到任何字之前

2026-08-30 有一次实测：一个总管带四个 worker 开工，全程没有调用过一次
`task_create`。它把当晚的计划写成一条长群帖，又发了一张分工表格，然后**逐个
`terminal_send` 把四个人推起来**——群帖两次都没让任何人动，这一点和
`Chat.waking` 的设计完全一致（见第六节），总管自己也观察到了。

事后问它为什么，答案不是「权衡后省了」：

> 开工第一件事我调了一次 ToolSearch，手写了一份工具清单……这份清单是我照着
> 昨晚用过什么默写出来的。`task_create` / `task_assign` / `skill_read` 全都在
> 可用列表里，我一个都没选。**我在做任何决策之前，先把自己的工具面收窄成了
> 昨晚的习惯。**

它那个会话里一次都没有调用过 `skill_read`。

**这件事推翻了一个隐含假设：把机制写清楚在 skill 里就够了。** 不够——失效发生
在读之前。skill 是两段式的，常驻上下文里只有 `name` 和 `description`，正文按需
加载；一个不会去读它的读者，skill 写得再准也拦不住。

所以拦截点必须早于「选工具」这一步，落在两个地方，都不是 skill：

**1. MCP `initialize` 的 `instructions`（`src/cli/mcp.zig`）。** 协议给了这个
字段，宿主把它放进连接方的**系统提示**。系统提示不被上下文压缩吃掉，所以它不
需要任何重放机制——这一点上它比 hook 强，hook 注入的内容活在对话里，正是
ponytail 要在 matcher 里写 `compact` 的原因。内容只是一张**工具族地图**，不是
skill 的副本：缺的不是四百行细节，是「桌上还有 `task_*` 这一族」。

代价要说清楚：`instructions` 在协议里是 MAY，客户端可以忽略（工具的
`description` 不能忽略，那是硬的）；而且它在连接时定死，带不了实时状态。

**2. `group_post` 的返回（`src/poltergeist/rpc.zig`）。** 这一条补上了实时状态。
条件卡得很窄——**调用者是总管、群里不止一个人、面板上一条未关闭任务都没有**
——三者同时成立才回一句话，否则原样返回 `.ok`。

窄是有意的。一条每次发帖都出现的提示会被读过去，那时它比不存在更糟。而且它说
的全是此刻的事实（「这个群里有 4 个终端，面板是空的」），不是劝告——劝告是
skill 的事，每贴一次劝告就是唠叨。

对应测试在 `rpc.zig`：正例、「已经在用面板的总管不被打扰」、「worker 发帖不被
说教」三条，各自都做过负对照（拆掉对应条件后确认变红）。

### 没有做的：Claude Code 的 SessionStart hook

ponytail（`hooks/claude-codex-hooks.json`）走的是这条：`SessionStart` 的 matcher
写成 `startup|resume|clear|compact`，四个时机各注入一次约 5.2KB。它还有一个
`UserPromptSubmit` 每轮重注入的分支，但被 `isQoder` 门住了——那是给一个
SessionStart 不好使的宿主打的补丁，**别抄**。

暂时不做的理由：它只买到一个宿主，却要引入「Polter 打包成 Claude Code 插件」
这条新路径；而 Polter 的前提本来就是**不知道终端里跑的是哪个 agent**（
`claude-code` 插件在 `claude` 不在 PATH 上时静默退出 0，正是这个前提）。上面两
条走 MCP，任何 MCP 客户端都吃得到，和这个前提一致。等它们上线之后看还漏不漏得
住再说。
