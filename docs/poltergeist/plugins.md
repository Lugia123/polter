## 一句话概括

通知走**进程式插件**：一个插件是一个目录，里面一份 `plugin.json` 和一个可执行文件；Polter 把事件作为一行 JSON 写进它的 stdin，用退出码判断成败。这样一个 20 行的 shell 脚本就能把通知发去飞书，而插件崩溃、卡死、乱写都伤不到终端。**存档插件用同一个宿主、同一份清单格式，只是不退出**——它的 stdin 是一条持续的行分隔 JSON 流，见 [storage.md](storage.md)。

## 为什么不能内置了事

R3 的「通知用户」如果只做一种实现，那么这条策略对用不上那一种的人等于不存在。而挂机过夜正是「人不在电脑前」的场景 —— 桌面通知在这个场景里恰恰是最没用的一种：

- 标题上限 63 字节、正文 255 字节（`src/apprt/surface.zig` 的 `desktop_notification`）；
- macOS 上 surface 处于聚焦时 3 秒后自动移除（`SurfaceView_AppKit.swift`）；
- 人睡着了，或者根本不在这台机器前。

真正有用的是能推到手机上的东西：飞书、企业微信、邮件、Bark、ntfy、Telegram。这类渠道有几十种，而且各家协议还在变。**内置任何一种都会立刻过时，内置全部则不可能。**

## 技术路线：五个候选

| | 用户能自己写吗 | 插件崩了会怎样 | 跨平台 | 凭据 | 结论 |
| --- | --- | --- | --- | --- | --- |
| **A 进程式**（子进程 + stdin JSON） | 能，任何语言，`curl` 就够 | 只有这条通知失败 | 一致 | 宿主传入 | **选它** |
| B 内置实现 | 不能，要改 Zig 并发版 | — | 一致 | 配置里 | 否决：加一种就要改一次核心 |
| C 动态库 `dlopen` | 几乎不可能 | **带走整个终端** | ABI 三平台各一套 | 同进程内 | 否决：代价与风险都最高 |
| D WASM 沙箱 | 要会 WASM 工具链 | 只有这条失败 | 好 | 宿主传入 | 否决：见下 |
| E 只做 webhook | 不用写，但只能发 HTTP | — | 一致 | 配置里 | 否决：邮件、命令行工具全做不了 |

**D 为什么否决**：WASM 的沙箱本身很合适，但沙箱里发不出网络请求 —— 得由宿主提供 HTTP 宿主函数。于是「发飞书」变成「WASM 调宿主的 HTTP」，而宿主的 HTTP 又得自己实现 TLS、重试、代理。绕一圈之后，能力上限反而退回到候选 E，成本却高得多。等哪天需要在不可信插件里跑用户逻辑，再回来看它。

**A 为什么合适，四条理由，一条比一条重要**：

1. **Ghostty 本来就是执行进程的**。`src/termio/Exec.zig` 已经把 spawn、环境、工作目录、回收都处理好了，这不是新增能力。
2. **通知频率极低**。收件箱机制保证总管每 `poltergeist-notice-interval` 最多被打扰一次（默认一分钟），到用户这一层只会更少。一次 fork/exec 的开销在这个尺度上不存在。
3. **语言无关**。一个 `curl` 脚本就是一个完整的飞书插件。要求用户为了发条通知去学 Zig，等于这个扩展点不存在。
4. **崩溃隔离**，而这条是挂机场景的硬要求。插件是用户从网上抄来的脚本，它会卡死、会段错误、会把 stdout 写爆。**这些都不该让终端跟着一起完**。进程边界是唯一能免费拿到这个保证的地方。

## 插件契约

### 目录

```text
plugins/
  feishu/
    plugin.json
    send.sh          ← 可执行
  email/
    plugin.json
    send.py
```

三处查找，后者覆盖前者（与 skill 体系同一套规矩，见 [mcp.md](mcp.md)）：

1. 随 Polter 安装的：`<resources>/polter/plugins/`
2. 用户自己的：`$XDG_CONFIG_HOME/polter/plugins/`
3. 配置里显式指定的目录

### `plugin.json`

**是 JSON 不是 YAML，这一条与本章早先的稿子不同。**照抄 Tinia 时写的是 `plugin.yaml` —— 但 Tinia 是 Python，标准库之外就有 YAML；Zig 没有。摆在面前的是「手写一个 YAML 子集解析器」和「用 JSON」，而前者要处理缩进、多行字符串、隐式类型转换，每一样都是能悄悄解析错的地方。清单文件解析错的后果是插件行为与它声称的不一致，那比多打几个引号糟糕得多。

```json
{
  "key": "feishu",
  "name": "飞书群机器人",
  "kind": "notify",
  "version": "1.0.0",
  "description": "发到飞书自定义机器人 webhook",

  "exec": "send.sh",
  "timeout_ms": 10000,

  "params": {
    "type": "object",
    "properties": {
      "webhook": { "type": "string", "title": "机器人 webhook 地址" }
    },
    "required": ["webhook"]
  }
}
```

`params` 是 JSON Schema，理由和 Tinia 的节点一样：schema 能同时用来校验和生成界面，自定义格式两样都要自己写。而它本来就是 JSON —— 用 YAML 包一层 JSON Schema，从一开始就是别扭的。

#### 两个非标准注解

标准 JSON Schema 之外，宿主认两个字段，都是**作者的声明**，不是宿主的猜测：

| 注解 | 意思 | 为什么必须由作者写 |
| --- | --- | --- |
| `"secret": true` | 这个参数持有凭据 | 名字猜不出来。`webhook` 的 `url` 长得像一个地址，实际上是"以用户的名义发消息"的钥匙；而 `token_ttl` 反过来，名字里有 token 却不是秘密。**只有写这份 schema 的人知道**，而他本来就在写这份 schema |
| `"enum": [...]` | 取值是一个封闭集合 | 它是**唯一**一种能把已配置的值回显给 agent 的参数：封闭集合装不下密码 |

`secret` 决定的是**写**：工具面拒绝把明文写进被标注的参数（见下面「工具面能改什么」）。它不决定**读**——明文值一律不回显，标没标都一样。这条不对称是故意的：作者漏标是常态，而回显是不可逆的。

**schema 写坏了不会让插件消失。** `params` 不是对象、`properties` 不是对象、某一项不是对象、名字是空串、声明超过 64 个——宿主一律读成"少声明了一些"，打一句 warn，插件照常加载（`Plugin.specsOf`）。这和 `wants` 是同一条规矩，而且往安全那一侧倒：**没被声明的参数是工具面不会去设的参数**。

### 两种生命周期

| | 生命周期 | stdin | 何时退出 |
| --- | --- | --- | --- |
| `notify` | 一次一进程 | 一行 JSON，写完即关 | 送达或超时 |
| `archive` | **常驻** | 行分隔 JSON 流，一行一批 | 随 Polter 结束 |

分界线是**事件的疏密**。通知一小时几条，每次 fork/exec 的开销在这个尺度上不存在；存档是连续的，每条消息重建一次数据库连接显然不行。

**共用的仍然是宿主那一层**：发现、清单解析、参数与凭据解析、超时与杀进程、退出码语义。常驻多出来的只有「进程要被看着、挂了要重起、退出时要收」，以及游标——都在 [storage.md](storage.md)。

### 一次性插件的调用协议

Polter 起进程，往 stdin 写**一行 JSON**，然后关闭 stdin：

```json
{
  "event": "confirmation_needed",
  "title": "worker-core 需要确认",
  "body": "它停在一个工具授权提示上，已经 12 分钟。",
  "terminal": "0x9491465653644ed0",
  "terminal_name": "✳ Write retry.py",
  "at_ms": 1786819271275,
  "params": {
    "webhook": "https://open.feishu.cn/...",
    "signing_key": "已经解析出来的明文"
  }
}
```

**只有 `params` 一个对象，没有第二个。**`Plugin.call` 在事件本体上只加这一个字段，里面的每个值都已经过 `secret.resolve` 解析。线上不区分"参数"和"凭据"——插件读到的都是可以直接用的值。要区分的那件事在别处：**引用是躺在文件里的东西，值是到达 stdin 的东西**，两者从不在同一个地方出现。

- **退出码 0 = 送达**，非 0 = 失败。没有别的返回通道，因为没有别的需要说的。
- **stderr 进 Polter 日志**，插件想解释失败原因就写那里。
- **stdout 被忽略**。插件不该有话对宿主说；它的职责是把消息送出去。
- **超时即杀**。一个连不上网的插件会一直挂着，而挂机场景里没人会去发现它。

事件类型先只有一个 `confirmation_needed`（R3 的通知分支）。将来加事件只加 `event` 的取值，不改协议形状 —— 插件收到不认识的 `event` 应当直接退出 0 并忽略。

### 失败怎么办

**通知失败不重试，但会记录，并且不影响其他插件。**

不重试的理由：一个送不出去的通知，重试三次仍然送不出去的可能性远大于成功；而重试会把一次失败变成一串延迟，在挂机场景里没人看得见这串延迟。配了多个插件就是多条独立的路，任何一条通了就够了 —— 这比在单条路上重试更有用。

## 凭据：不自己管密码，接到已有的密码管理器上

**这是通知插件与 Tinia 节点最大的不同**：节点处理的是数据，插件握着的是能发消息的钥匙。

### 先说清楚问题

进程式插件的参数总要从某个地方来。最直接的做法是写进一个配置文件，但那意味着**磁盘上有一份明文密码**。加权限 0600 只是把「谁能读」缩小到本机当前用户，文件本身还是明文 —— 备份会带走它，误提交会带走它，一次 `cat` 就会把它打在屏幕上（而这个屏幕现在可能正在被别的 agent `terminal_read`）。

### 做法：配置里存**引用**，不存值

参数值支持前缀，Polter 在**调用插件的那一刻**才解析：

| 写法 | 从哪取 | 用在什么场合 |
| --- | --- | --- |
| `https://…` | 就是字面值 | 不敏感的东西，比如 webhook 地址 |
| `env:FEISHU_TOKEN` | 环境变量 | CI、容器、systemd unit |
| `file:~/.config/polter/feishu.key` | 文件内容（首行，去空白） | 已经有一份密钥文件 |
| `keychain:polter/feishu` | 系统钥匙串 | macOS 用 `security`，Linux 用 `secret-tool` |
| `cmd:op read op://Private/feishu/token` | **执行命令取 stdout** | **任何密码管理器** |

于是配置文件长这样，**里面没有一个字是秘密**：

```json
{
  "webhook": "https://open.feishu.cn/open-apis/bot/v2/hook/xxx",
  "signing_key": "cmd:op read op://Private/feishu/signing-key"
}
```

这份文件可以进 dotfiles 仓库、可以贴进 issue、可以同步到别的机器。

### 为什么 `cmd:` 这一条最重要

它一条就覆盖了全部密码管理器 —— 1Password (`op`)、pass、Bitwarden (`bw`)、gopass、`security`、`secret-tool`、以及用户自己写的任何脚本。**Polter 不需要为其中任何一个写适配，也不需要跟着它们的 API 变。**

反过来说，如果不做 `cmd:`，就要在 Polter 里一个个接：接完 1Password 有人要 Bitwarden，接完 Bitwarden 有人要 pass，而每一个都有自己的认证方式和解锁流程。这是一条永远走不完的路。

`keychain:` 仍然单独列，是因为它是零依赖的默认选项 —— 用户不装任何密码管理器也能用系统自带的。它的实现本身就是 `cmd:` 的一个内置特例（macOS 上等价于 `security find-generic-password -w -s polter -a feishu`）。

### 解析的三条规矩

1. **只在调用时解析，不缓存。**密码管理器可能会锁上，锁上之后就该失败 —— 缓存会让「已锁定」这件事对 Polter 不可见。
2. **解析失败 = 这条通知失败**，写日志，不回退到别的值，也不把引用原样发出去。把 `cmd:op read …` 当成密码发给飞书，比发不出去糟得多。
3. **解析出的值只进插件的 stdin**，不进环境变量、不进日志、不进聊天记录。环境变量会被插件自己 spawn 的子进程继承，而日志和聊天记录都会落盘。

### 仍然允许明文

**手写的文件里可以直接写明文**，因为总有人只想把 webhook 贴进去就用。**设计不该逼一个只想试一下的人先去装密码管理器。**但文档里默认给的例子用 `cmd:`，让省事的那条路是明确选择的结果，而不是唯一的路。

没有单独的 `credentials.json`：设置就一份，在
`$XDG_CONFIG_HOME/polter/plugins/<key>.json`，`Settings.write` 建它时用 0600。

**但工具面不允许写明文**，而这条不对称正是整个工具面的要点。**同一个文件、同一个解析器，区别在于是谁的手：文件是用户的，工具是 agent 的。**用户往自己机器上自己的文件里写自己的密码，是他的事；一个 agent 替他决定把一段明文落到盘上，不是。

### `file:` 的展开

`file:~/.config/polter/feishu.key` 里的 `~/` 现在真的会被展开（按 `HOME`）。这一条**只认打头的 `~/`**：`~user/` 需要查 passwd，没人要过。写在这里是因为上表里那个例子在这轮之前是坏的——`firstLineOf` 从来没做过展开，文档推荐的写法打开即错。

**展开只发生在读的那一刻，而工具面在写的那一刻就要判断，所以两边的规矩不一样：手写的文件里 `~/` 可以用，`plugin_configure` 里不行，它要一条绝对路径。**不是多此一举：`Guard` 是按文本判断这条路径落不落在 polter 目录之下的（文件此刻可能还不存在，而"问一次文件系统"的答案会在检查与写入之间变），而 `~` 展开成什么要到插件被调用时才知道——一个此刻判不了的条件，只能拒绝，不能放行。拒绝的那句话把这件事说完整了（`Guard.refusal.file_tilde`），所以 agent 读完知道下一步是把路径写全。

## 权限声明

**第一天就要有。**清单里声明它要什么，声明之外一律拒绝：

```json
{
  "key": "chat-archive",
  "kind": "archive",
  "wants": {
    "groups": ["*"],
    "network": true,
    "exec": ["psql"]
  }
}
```

三条理由，按重要性排：

1. **插件是别人写的代码跑在你机器上。**2026 年出过真事：Semantic Kernel 的 prompt injection 打到 host RCE；Claude Code 的 Hooks 被报出配置注入，配套 CVE 可通过重定向 API 请求偷 key。这类问题的共同点是「扩展点能做的事，没人说得清」。
2. **能声明才能审计。**用户装插件之前要能一眼看出它要读哪些群、要不要联网、要跑哪些外部命令。一份读不出这些的清单，等于要求用户先读一遍源码。
3. **它同时是差异化。**Warp 让出来的信任市场是免费的。

**`wants` 是按插件声明的，不是按后端。**`chat-archive` 有两个后端——`postgres` 要联网要起 `psql`，`file` 两样都不要——但它声明的是两者的**并集**。一份会随配置缩水的声明，审计没法拿它当依据：审计要看的是"它可能做什么"，不是"它今天配成了什么"。

**声明不是自证清白，是让宿主有得拦。**`groups` 决定喂给它的批次里能出现哪些群的消息 —— 这一条是宿主自己过滤的，插件没有别的通道拿到别的群。`network` 与 `exec` 落地在进程环境上，不承诺是沙箱级别的隔离；一期它们的作用是**声明与告知**，真要做强制隔离得连签名一起设计（见下一节的理由）。**把这条差别写在这里，是为了不让「声明了 network: false」被当成「它上不了网」。**

## 插件从哪来

**一期只做本地目录。**用户把插件目录放进 `$XDG_CONFIG_HOME/polter/plugins/` 就能用。

**远程仓库留接口，不实现。**参照 Tinia 的 `tinia-repo.yaml`：一个仓库是一份清单加一堆插件目录，清单里有 `name`、`version`、`min_polter_version`、`namespace`。留这个位置的意思是：一期的目录结构要与它兼容，这样将来加「从 URL 安装」时不必改插件本身的格式。

**先不做自动更新与签名校验。**从网上下载并执行代码是一件需要认真对待的事，而一期的用户是把脚本放进自己目录的人 —— 那和运行任何别的脚本没有区别。等真的要做「一键安装第三方插件」时，签名与沙箱要一起设计，不能事后补。

## 配置形态

**开关不在主配置里，在插件自己的文件里。**主配置的 `poltergeist-notify` 已经不起作用了，写了会被 `App.updateConfig` 点名警告。

```text
$XDG_CONFIG_HOME/polter/plugins/feishu.json     ← 开关 + 参数，0600
```

```json
{
  "enabled": true,
  "params": {
    "webhook": "https://open.feishu.cn/open-apis/bot/v2/hook/xxx",
    "signing_key": "cmd:op read op://Private/feishu/signing-key"
  }
}
```

**为什么开关搬出了主配置**：装了哪些插件是**扫目录扫出来的**，不是主配置列出来的。于是"开没开"这件事没有必要在主配置里再列一遍——列了就有两份真相，而且一个设置界面想把某个插件打开时，得去改用户手写的那份配置文件。放在插件自己的文件里，界面和用户改的是同一处。

参数不进主配置的理由不变：一条通知渠道常常有五六个字段，塞进 `key=value` 会很难看。

**这个文件是被整份重写的。**`Settings.read` 只认得 `enabled` 和 `params` 里的**字符串**值；别的键、非字符串的值，读的时候被丢掉，`Settings.write` 写回去的时候就此消失。手写的时候没人会碰到这件事（写的人就是读的人），但 `plugin_configure` 让 agent 也能触发它——**在放 agent 碰这个文件之前，要知道文件里读不懂的东西会没**。另外，一个既没有 `enabled` 也没有 `params` 的旧格式文件会被读成"开着 + 一堆平铺参数"，重写之后变成新格式：语义不变，形状变了。

## 工具面能改什么，不能改什么

三个 MCP 工具（`plugin_list` / `plugin_configure` / `plugin_test`）都只给总管。理由与完整论证在 [mcp.md](mcp.md)，这里只放一张对照表，免得两处各写一遍再各自漂移：

| 能 | 不能 |
| --- | --- |
| 把插件**打开** | 把插件**关掉** —— 它是用户听见事情的那条通道 |
| 把已声明的参数设成一个字面值 | 设一个清单没声明过的名字 —— 判不出是不是 secret，就不能写 |
| 设成 `env:` / `keychain:` 引用 | 写 `cmd:` —— 那是让 Polter 在授权结束之后自己去跑一条命令 |
| 设成 polter 目录下的 `file:` 引用 | 把明文写进标了 `secret` 的参数 |
| 让通知插件真发一条，验证它通 | 装一个插件 —— 那仍然是用户的动作：把目录放进 `$XDG_CONFIG_HOME/polter/plugins/` |

**诚实的残余**：一个同时能写文件的 agent 不受这些约束中的任何一条——它直接改那个 JSON 就是了。这些拒绝买到的不是"挡住能写文件的 agent"，而是一条不变量：**装一个 MCP server，绝不会因此多出一份它自己的 harness 本来放在授权闸后面的权限。**

## 给以后留位置

`kind` 字段现在只有 `notify` 一个取值，但插件宿主要按「多种 kind」来写：

| kind | 什么时候被调用 | 生命周期 | 状态 |
| --- | --- | --- | --- |
| `notify` | Polter 决定要通知用户时 | 一次一进程 | 一期做 |
| `archive` | 群聊日志有新消息、且游标落后时 | 常驻 | 二期做，见 [storage.md](storage.md) |
| `sensor` | 采样时，报告一个自定义的「还活着吗」判据 | 未定 | 留位置 |
| `action` | 总管通过 MCP 请求执行一个动作 | 未定 | 留位置 |

**共用的**：发现、清单解析、参数与凭据管理、启用/禁用、超时与失败处理。
**各自的**：stdin 的 JSON 形状、退出码的含义、宿主在什么时机调用。

所以实现时要把这两层分开：一个「插件宿主」只认识 `plugin.json` 和「起进程、喂 JSON、看退出码」；`notify` 的具体契约是宿主之上的一层。**现在不要为 `sensor` 和 `action` 写任何代码** —— 它们的调用契约取决于还没发生的需求，猜出来的接口比没有接口更难改。`archive` 不在此列：它的需求已经发生（群聊要能往回翻、要能同步到外部库），契约也已经写下来了。

## 与既有原则的关系

- **R2（不做自动点 yes）不受影响。**插件是**出口**，只能把消息发出去；它没有任何回到终端的通道。一个插件无论如何都按不了别人的授权键。
- **R8（不管理任务）不受影响。**插件不持有状态。
- **R3 的「通知用户」分支由它落地**，但「什么时候该通知」仍归 [supervisor.md](supervisor.md)。

## 未决问题

1. 一次通知同时配了多个插件时，是全部都发，还是按顺序发到第一个成功为止？倾向全部都发 —— 挂机时多一条冗余比少一条可靠，但这会让手机响两次。
2. 插件的 stdout 现在被忽略。若将来某类插件需要回话（例如 `action`），是给它一条独立的返回通道，还是改成 JSON-RPC over stdio（与 `polter +mcp` 一致）。
3. 是否需要一个 `polter +notify-test <key>` 来当场验一条通知能不能发出去。倾向要 —— 挂机之前不试一次，就是把「通知到底通不通」留到最需要它的那一刻才发现。
