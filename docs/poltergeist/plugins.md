# 插件体系（先做通知）

> 校验方式：`git log -1 --format='%H %h %ad %s'`

## 本章覆盖什么

- 为什么通知必须能扩展，而不是内置几种了事。
- 五条技术路线的逐项核算，以及为什么选进程式插件。
- 插件契约：清单格式、调用协议、失败语义、超时。
- 凭据怎么存 —— 这是通知插件区别于 Tinia 节点的地方，也是最容易做错的一处。
- 插件从哪来：本地目录与远程仓库。
- 怎么给以后的其他插件类型留位置，而不现在就把它们设计出来。

## 本章不覆盖什么

- 什么时候该通知用户（确认策略与通知时间段）—— 见 [supervisor.md](supervisor.md)。本章只管「决定要通知之后，怎么送出去」。
- 静止怎么测 —— 见 [sensing.md](sensing.md)。
- MCP 工具面 —— 见 [mcp.md](mcp.md)。插件不是给 AI 用的工具，是宿主的出口。

## 一句话概括

通知走**进程式插件**：一个插件是一个目录，里面一份 `plugin.yaml` 和一个可执行文件；Polter 把事件作为一行 JSON 写进它的 stdin，用退出码判断成败。这样一个 20 行的 shell 脚本就能把通知发去飞书，而插件崩溃、卡死、乱写都伤不到终端。

## 为什么不能内置了事

R3 的「通知用户」如果只做一种实现，那么这条策略对用不上那一种的人等于不存在。而挂机过夜正是「人不在电脑前」的场景 —— 桌面通知在这个场景里恰恰是最没用的一种：

- 标题上限 63 字节、正文 255 字节（`src/apprt/surface.zig` 的 `desktop_notification`）；
- macOS 上 surface 处于聚焦时 3 秒后自动移除（`SurfaceView_AppKit.swift`）；
- 人睡着了，或者根本不在这台机器前。

真正有用的是能推到手机上的东西：飞书、企业微信、邮件、Bark、ntfy、Telegram。这类渠道有几十种，而且各家协议还在变。**内置任何一种都会立刻过时，内置全部则不可能。**

## 技术路线：五个候选

| | 用户能自己写吗 | 插件崩了会怎样 | 跨平台 | 凭据 | 结论 |
| --- | --- | --- | --- | --- | --- |
| **A 进程式**（子进程 + stdin JSON） | 能，任何语言，`curl` 就够 | 只有这条通知失败 | 一致 | 宿主传入 | **选它** |
| B 内置实现 | 不能，要改 Zig 并发版 | — | 一致 | 配置里 | 否决：加一种就要改一次核心 |
| C 动态库 `dlopen` | 几乎不可能 | **带走整个终端** | ABI 三平台各一套 | 同进程内 | 否决：代价与风险都最高 |
| D WASM 沙箱 | 要会 WASM 工具链 | 只有这条失败 | 好 | 宿主传入 | 否决：见下 |
| E 只做 webhook | 不用写，但只能发 HTTP | — | 一致 | 配置里 | 否决：邮件、命令行工具全做不了 |

**D 为什么否决**：WASM 的沙箱本身很合适，但沙箱里发不出网络请求 —— 得由宿主提供 HTTP 宿主函数。于是「发飞书」变成「WASM 调宿主的 HTTP」，而宿主的 HTTP 又得自己实现 TLS、重试、代理。绕一圈之后，能力上限反而退回到候选 E，成本却高得多。等哪天需要在不可信插件里跑用户逻辑，再回来看它。

**A 为什么合适，四条理由，一条比一条重要**：

1. **Ghostty 本来就是执行进程的**。`src/termio/Exec.zig` 已经把 spawn、环境、工作目录、回收都处理好了，这不是新增能力。
2. **通知频率极低**。收件箱机制保证总管每 `poltergeist-notice-interval` 最多被打扰一次（默认一分钟），到用户这一层只会更少。一次 fork/exec 的开销在这个尺度上不存在。
3. **语言无关**。一个 `curl` 脚本就是一个完整的飞书插件。要求用户为了发条通知去学 Zig，等于这个扩展点不存在。
4. **崩溃隔离**，而这条是挂机场景的硬要求。插件是用户从网上抄来的脚本，它会卡死、会段错误、会把 stdout 写爆。**这些都不该让终端跟着一起完**。进程边界是唯一能免费拿到这个保证的地方。

## 插件契约

### 目录

```text
plugins/
  feishu/
    plugin.yaml
    send.sh          ← 可执行
  email/
    plugin.yaml
    send.py
```

三处查找，后者覆盖前者（与 skill 体系同一套规矩，见 [mcp.md](mcp.md)）：

1. 随 Polter 安装的：`<resources>/polter/plugins/`
2. 用户自己的：`$XDG_CONFIG_HOME/polter/plugins/`
3. 配置里显式指定的目录

### `plugin.yaml`

```yaml
key: feishu                  # 唯一，也是配置里引用的名字
name: 飞书群机器人
kind: notify                 # 见「给以后留位置」
version: 1.0.0
description: 发到飞书自定义机器人 webhook

exec: send.sh                # 相对本目录；必须可执行
timeout_ms: 10000            # 超过就杀掉，默认 10 秒

params:                      # JSON Schema，用来校验与将来生成配置界面
  type: object
  properties:
    webhook:
      type: string
      title: 机器人 webhook 地址
  required: [webhook]

secrets:                     # 只声明字段名。值不在这里，见「凭据」
  - signing_key
```

`params` 用 JSON Schema 而不是自定义格式，理由和 Tinia 的节点一样：schema 能同时用来校验和生成界面，而自定义格式两样都要自己写。

### 调用协议

Polter 起进程，往 stdin 写**一行 JSON**，然后关闭 stdin：

```json
{
  "event": "confirmation_needed",
  "title": "worker-core 需要确认",
  "body": "它停在一个工具授权提示上，已经 12 分钟。",
  "terminal": "0x9491465653644ed0",
  "terminal_name": "✳ Write retry.py",
  "at_ms": 1786819271275,
  "params":  { "webhook": "https://open.feishu.cn/..." },
  "secrets": { "signing_key": "…" }
}
```

- **退出码 0 = 送达**，非 0 = 失败。没有别的返回通道，因为没有别的需要说的。
- **stderr 进 Polter 日志**，插件想解释失败原因就写那里。
- **stdout 被忽略**。插件不该有话对宿主说；它的职责是把消息送出去。
- **超时即杀**。一个连不上网的插件会一直挂着，而挂机场景里没人会去发现它。

事件类型先只有一个 `confirmation_needed`（R3 的通知分支）。将来加事件只加 `event` 的取值，不改协议形状 —— 插件收到不认识的 `event` 应当直接退出 0 并忽略。

### 失败怎么办

**通知失败不重试，但会记录，并且不影响其他插件。**

不重试的理由：一个送不出去的通知，重试三次仍然送不出去的可能性远大于成功；而重试会把一次失败变成一串延迟，在挂机场景里没人看得见这串延迟。配了多个插件就是多条独立的路，任何一条通了就够了 —— 这比在单条路上重试更有用。

## 凭据

**这是通知插件与 Tinia 节点最大的不同**：节点处理的是数据，插件握着的是能发消息的钥匙。

三条硬规矩：

1. **凭据不进 `plugin.yaml`。**插件目录是要被分享、被 git 管理的，`plugin.yaml` 里只声明字段名。
2. **凭据不进 Polter 的配置文件。**配置会被贴进 issue、被同步到别的机器。
3. **凭据存在 `$XDG_STATE_HOME/polter/credentials.json`，权限 0600。**与聊天日志同一套做法（见 [chatui.md](chatui.md)），那套已经在真机上验过。

**为什么不用系统钥匙串**：macOS Keychain、libsecret、Windows 凭据管理器是三套完全不同的 API 和三套不同的失败模式，而 0600 文件在三个平台上都成立、都能人工检查、都能备份。将来若要接钥匙串，它可以作为 `credentials.json` 之外的又一个来源，而不必推翻这一层。

**凭据只在调用插件的那一刻进入它的 stdin**，不写进环境变量 —— 环境变量会被同一进程树里的任何东西读到，包括插件自己 spawn 出来的子进程。

## 插件从哪来

**一期只做本地目录。**用户把插件目录放进 `$XDG_CONFIG_HOME/polter/plugins/` 就能用。

**远程仓库留接口，不实现。**参照 Tinia 的 `tinia-repo.yaml`：一个仓库是一份清单加一堆插件目录，清单里有 `name`、`version`、`min_polter_version`、`namespace`。留这个位置的意思是：一期的目录结构要与它兼容，这样将来加「从 URL 安装」时不必改插件本身的格式。

**先不做自动更新与签名校验。**从网上下载并执行代码是一件需要认真对待的事，而一期的用户是把脚本放进自己目录的人 —— 那和运行任何别的脚本没有区别。等真的要做「一键安装第三方插件」时，签名与沙箱要一起设计，不能事后补。

## 配置形态

```ini
# 启用哪些通知插件。可以写多条，每条是一条独立的路。
polter-notify = feishu
polter-notify = email
```

参数不写在这里 —— 一条通知渠道的配置常常有五六个字段，塞进 `key=value` 会很难看。每个插件一份 JSON：

```text
$XDG_CONFIG_HOME/polter/plugins/feishu.json     ← params
$XDG_STATE_HOME/polter/credentials.json         ← secrets，0600
```

分成两处的理由就是上一节那三条：一份可以放进 dotfiles 仓库，另一份不行。

## 给以后留位置

`kind` 字段现在只有 `notify` 一个取值，但插件宿主要按「多种 kind」来写：

| kind | 什么时候被调用 | 状态 |
| --- | --- | --- |
| `notify` | Polter 决定要通知用户时 | 一期做 |
| `sensor` | 采样时，报告一个自定义的「还活着吗」判据 | 留位置 |
| `action` | 总管通过 MCP 请求执行一个动作 | 留位置 |

**共用的**：发现、清单解析、参数与凭据管理、启用/禁用、超时与失败处理。
**各自的**：stdin 的 JSON 形状、退出码的含义、宿主在什么时机调用。

所以实现时要把这两层分开：一个「插件宿主」只认识 `plugin.yaml` 和「起进程、喂 JSON、看退出码」；`notify` 的具体契约是宿主之上的一层。**现在不要为 `sensor` 和 `action` 写任何代码** —— 它们的调用契约取决于还没发生的需求，猜出来的接口比没有接口更难改。

## 与既有原则的关系

- **R2（不做自动点 yes）不受影响。**插件是**出口**，只能把消息发出去；它没有任何回到终端的通道。一个插件无论如何都按不了别人的授权键。
- **R8（不管理任务）不受影响。**插件不持有状态。
- **R3 的「通知用户」分支由它落地**，但「什么时候该通知」仍归 [supervisor.md](supervisor.md)。

## 未决问题

1. 一次通知同时配了多个插件时，是全部都发，还是按顺序发到第一个成功为止？倾向全部都发 —— 挂机时多一条冗余比少一条可靠，但这会让手机响两次。
2. 插件的 stdout 现在被忽略。若将来某类插件需要回话（例如 `action`），是给它一条独立的返回通道，还是改成 JSON-RPC over stdio（与 `polter +mcp` 一致）。
3. 是否需要一个 `polter +notify-test <key>` 来当场验一条通知能不能发出去。倾向要 —— 挂机之前不试一次，就是把「通知到底通不通」留到最需要它的那一刻才发现。
