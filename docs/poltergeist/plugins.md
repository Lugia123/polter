## 一句话概括

**插件和 agent 是同一个能力面的两扇门。** 一个插件是一个目录，里面一份
`plugin.json` 和一个可执行文件；Polter 起它一次，喂它订阅的事件，用同一套
线协议让它调工具面。**它订阅什么，就只收得到什么**；它声明调什么，就只调得
到什么；它能碰的终端由目标身上的标记决定，而不是由它是插件决定。

# 一、`Kind` 拆掉了

## 它同时管两件事，所以出过两次同一个 bug

`Plugin.Kind` 曾经有三个取值——`notify`、`archive`、`provision`——而它同时
决定**生命周期**（一次性 / 常驻）和**契约**（stdin 什么形状、stdout 认不认）。
三个 kind 就是三套契约，每加一种需求就加一个取值，而每个取值都要在若干处被
穷举。

**这已经出过两次同一个 bug，而且第二次就写在第一次的注释旁边。**
`macos/Sources/Features/Plugins/Plugin.swift` 里那段：

> 这里曾经写的是 `== "notify"`，直到核心侧有了 `archive` —— 那就是
> `chat-archive` 装在 bundle 里却从来不出现在列表里的原因。

上次的修法是「再加一个 case」，于是这次 `provision` 又中了同一枪：它装在
bundle 里、在跑，而设置界面里根本没有它。**只加一个分支不防复发。**

## 换成：清单里声明订阅什么

```json
"wants": {
  "events": ["chat", "terminal.quiet", "provision"],
  "calls":  ["terminal_read", "terminal_list"],
  "groups": ["*"],
  "network": false,
  "exec": []
}
```

于是：

| 从前的 kind | 现在是什么 |
| --- | --- |
| `notify` | 订阅了 `terminal.quiet` 的插件 |
| `archive` | 订阅了 `chat` 的插件 |
| `provision` | 订阅了 `provision` 的插件 |

**没有 kind 可漏，因为没有 kind。** 一个插件同时订阅两种事件也不再需要新概念
——从前它需要两个插件，或者一个新的枚举成员。

`events` 的取值是 `Plugin.Event`（`Plugin.zig`），而 `Feed.Kind` 直接就是
它，不是第二份拷贝：如果 `Feed` 自己维护一份枚举，两份迟早漂移，而漂移的
那天，一个插件会订阅一个永远没有人发布的名字——那看上去和「插件正常但收不到
东西」一模一样。

**`events` 里没有 `"*"`，这是故意的**，而且是它和 `groups` 唯一不一样的地方。
群名是用户随口起的，没有办法枚举还不存在的那些，所以 `"*"` 是「我在哪个群就
要哪个群」的唯一写法；而事件是写死在 `Plugin.Event` 里的封闭集合，插件可以把
它要的每一个都点出来，一个 `"*"` 意味着「以及以后加进来的每一个」——那是对还
不存在的代码的订阅。

**清单里还写着 `kind` 不会让插件加载失败**，只会被点名 warn 一次：一份为三个
kind 的世界写的清单，今天读出来是「订阅了空」，于是根本不启动，而那句 warn 是
它作者唯一能看见的线索。

## 不认识的事件名不是致命错

一份为将来的构建写的清单，可能提到今天这个构建从没发布过的事件名。宿主的做法
是**跳过那一个、warn 一句、其余照收**（`Plugin.eventsOf`）。方向是安全那一侧：
它拿到的比它写的少，绝不会比它写的多。

# 二、一个常驻协议

## 三套契约合成一套

```text
起进程 → 握手 → 一行一批事件 → 一行一个确认
```

就这么多。什么把一个插件和另一个插件区别开来，只有 `wants.events`。

宿主一侧在 `src/poltergeist/Resident.zig`：一个插件一个线程、一个子进程，
随 Polter 的生命周期存在。

## 常驻取代一次性，代价是什么

**这是这轮里唯一一处失去了东西的地方，所以逐条写下来——包括不该失去、因此接了
一根线回来的那一条。**

`Plugin.zig` 从前的模块注释给过三条选进程边界的理由。逐条过一遍：

1. **「Ghostty 本来就在执行进程」** —— 仍然成立，一个字不改。
2. **「崩溃隔离」** —— 仍然成立，而且是最重要的一条。插件是用户从网上抄来的
   脚本，会卡死、会段错误、会把 stdout 写爆，**这些都不该让终端跟着一起完**。
   进程边界是唯一能免费拿到这个保证的地方。
3. **「语言无关」** —— 仍然成立。一个二十行的 `curl` 脚本仍然是一个完整的插件。
4. **「频率极低，所以一次 fork 的开销不存在」** —— **这条不再成立**，而且它
   本来论证的就不是进程边界，是*一次性*那个生命周期。它随那个生命周期一起走了。

失去的东西，三条：

- **一次性会自愈，常驻不会。** 一个卡死的一次性插件随着那次通知一起结束，只
  拖垮它自己那一条；一个卡死的常驻插件会一直卡着。
  **付账的方式**：`reap.Reaper` 界定的是**一次交换**（写一行 + 读一行），不是
  整个进程的寿命，所以一个不再答话的插件在下一批就被杀掉，而不是熬到某个它
  早就熬过了的期限；被杀之后**退避重起、失败十次转休眠、休眠一刻钟再试**——
  这套机器一次性那条路上根本没有，一个失败的一次性通知就只是失败了。
  另外还有**心跳**：默认三十秒一次空批次，一个安静的夜里，没有它，一具尸体
  要到天亮才被发现。
- **凭据一次性是每次调用重解，常驻是每个子进程解一次。** 一个中午锁上的密码库
  要等到下一次重起才被发现。**这一条没有付账，是明说的**：常驻就意味着解析出
  来的值被握到进程死为止。缓解只有一个——重起就重解，所以它不会永远用着半年前
  取出来的那份。
- **一个闲着的插件现在是一个进程。** 从前一个通知插件在两次通知之间不占任何
  东西。**这一条也没有付账**：每个装上并打开的插件一个常驻进程，是「崩溃边界
  对所有人是同一条边界」的价钱。

**只有一条真的失去了：`notify_user` 的回话不再是送达回执。**
从前它 fork 一个进程，退出码就是答案，所以能说「3 条渠道发出去 2 条」。现在
事件被交给 feed，插件在自己的线程上送，这个调用没有办法等它——等就是把 app
线程押在别人的 webhook 上。所以回话改成说**此刻确实知道的事**：有几条渠道订阅
了这件事，其中几条**现在有子进程在跑**。一个正在退避或者休眠的插件正是那个
消息送不出去的，而那恰恰是总管当初需要退出码去分辨的东西——这一半比从前更强。

**失败仍然打到用户屏幕上，而且现在对每个插件都打。** 这一条不是可以让的：
一个插件失败的后果，要么是 agent 没有工具面，要么是用户没有了被通知的渠道——
**第一种里 agent 恰恰是那个收不到消息的人**。所以 `plugin_list` 的 `note`
（agent 读得到）和 `plugin_test`（人主动问）都不够，它们都是等人来问；必须有
一条不请自来的。

常驻带来的困难是真的：失败发生在插件自己的线程上，而屏幕归 app 线程。解法是那条
现成的路——`Resident.Alert` 把一行交给 `App.submitPoltergeistAlert`，它拷一份丢进
mailbox，app 线程 `poltergeistAlert` 打出来。和 socket 线程交请求同一条路。

两处比从前强：**从前只有 provisioning 插件失败会被报出来**（那是唯一同步跑的
一类），现在每一个插件失败都会；而且句子说的是**后果**——「agent 没有 Polter
工具」/「没有东西会告诉你终端需要你」/「聊天的额外那份没在写」——由
`wants.events` 决定，因为那是唯一说得出这个插件是干什么的东西。

节流规则见下。

## 失败怎么到人那里

```text
Resident 线程失败  →  Resident.tell  →  App.submitPoltergeistAlert
                   →  mailbox（App.Message.poltergeist_alert）
                   →  app 线程 App.poltergeistAlert  →  屏幕
```

- **走 mailbox，不直接碰 app 的状态。** 屏幕、surface 列表、bus 都归 app 线程。
- **`instant` 而不是 `forever`**（和 socket 线程交请求相反，理由也相反）：没有人
  在等这一行，而一个挂在满 mailbox 上的常驻线程，就是一个没人在给它的子进程掐表
  的插件。满到丢了一行就写进日志——那是这条路存在之前它本来就要去的地方。
- **有终端就直接打，没有才排队。** 排队是「还没有窗口」的答案，那只在启动时成立；
  有了终端还压着，一个凌晨三点断掉的插件要等到有人下次开标签页才被报出来。
- **打印不是打字。** `poltergeist_alert` 是**印**在屏幕上的，收信人是人；
  `poltergeist_notice` 是**打**进终端的，收信人是里面跑着的东西。这是两件事。
- **插件自己要说的话走同一条路。** 一行 `{"tell":"…"}` 从 stdout 进来，经过剥离
  和截断，在同一个 mailbox 上排队，印在同一块屏幕上。见第二节末尾——那不是第二条
  通道，是同一条通道的另一头。

**说的是后果，不只是故障。** 「chat-archive 挂了」要读的人自己去想他今晚会少
什么。后果由 `wants.events` 决定，因为那是唯一说得出这个插件是干什么的东西：

| 订阅 | 那一行说什么 |
| --- | --- |
| `provision` | an agent started here has no Polter tools |
| `terminal.quiet` | nothing will tell you when a terminal needs you |
| `chat` | the extra copy of the chat is not being written |

一个插件订阅两样就说两句。`report.alert` 对 `Plugin.Event` 穷举，所以加一个事件
必须给它一句后果，而不是产出一句不说代价的话。

**节流：一条 `stopped` 行每个插件每 `dormant_retry_ms` 最多一条。** 常驻会重试，
一个起不来的插件每几毫秒失败一次；重试是同一句话再说一遍，而被一个插件刷满的屏幕
是第二个插件的失败永远读不到的屏幕。间隔复用 `dormant_retry_ms` 而不是另起一个
数——「这件事多久值得再说一遍」在这个文件里已经有答案了，一个问题两个答案会漂移。

**转进休眠另算一条，而且不节流。** 它说的是新事情：不是「它在被重试」，是「它
放弃了，一刻钟才再试一次」。而且按构造它本来就一刻钟才可能发生一次。

> 这里曾经还有第二道闸——「这是不是它上次工作以来第一次失败」。**负对照证明它
> 一次都没起过作用**：把它改坏，没有任何测试变红。子进程要活满一分钟**并且**确认
> 过一批，`Backoff.settled` 才会清零，所以那道闸永远不会比这道更频繁地放行。
> 两套机制里弱的那一套，是靠没人测过它才被相信的。

## 握手

宿主写的**第一行**，整个会话只出现一次：

```json
{"hello":1,"plugin":"archive","cursor":0,
 "events":["chat"],"groups":["*"],"calls":["terminal_read"],
 "socket":"/Users/you/.local/state/polter/polter-ab12.sock",
 "token":"…64 个十六进制字符…",
 "params":{"dir":"/Volumes/backup/polter","sign_key":"已解析出来的明文"}}
```

- `hello` 是协议版本号，是数字而不是标记，**为的是一个不认识这一版的插件可以
  直接退出而不是猜后面的字段**。
- `events` / `groups` / `calls` 是清单里那三份声明**原样抄回来**，好让插件自己
  能核对它会被喂到什么、会被允许调什么，而不是从「什么东西冒出来了」和「什么
  调用被拒了」里反推。
- `socket` / `token` 是工具面。**只有两者都有的时候才写**，没有就整个字段不出现
  ——写一个空串会让插件拿着它去连。见第三节。
- `params` **只在这里出现**，批次行里没有，插件必须在握手时记住它。里面的值已经
  过 `secret.resolve` 解析，插件拿到的是真 DSN 而不是 `cmd:…`。
- `cursor` **在一次新的 Polter 运行里恒为 0**：订阅从建立的那一刻开始，宿主手里
  没有任何更早的东西，也没有一个文件记着上次到哪。

**握手也要回一行确认，和批次一样。** 宿主在写这一行**之前**就把期限装上了
（`Resident.zig` 里 `renderHello` 前面那句 `allow(timeout_ms)`），写完就等一行
回答：

| 插件回的 | 怎么判 | 为什么 |
| --- | --- | --- |
| `ok:false` | **不是失当**：杀掉子进程、退避重起 | 连不上库的插件在这里说出来，拿到的是和"根本起不来"一样的耐心重试 |
| `ok:true`，带 `cursor`（任意方向） | **收下当情报，记一条 info，什么都不改** | 它在陈述自己的状态——"我的库已经到 5000 了"。宿主没有东西可以重放：它手里只有这个订阅还没被确认掉的那些事件，一条不多一条不少 |
| `ok:true`，无 `cursor` | 同上，什么都不改 | |
| 任意 | 非 JSON、一行超过 64KB、stdout 关闭 → 杀掉重起 | |

**什么都不回是最糟的一种**：`timeout_ms` 到点被杀、退避、重起、再被杀，外面看
是一个每 `timeout_ms` + 退避重复一次的重启循环，插件自己看却像在闲等下一批。
随构建装出去的 `archive` 有一版就是这样。挡住这件事的回归测试在 `Resident.zig`
（「the archive plugin we ship answers the greeting the host really writes」）：
它拿 `renderHello` 真正写出来的字节去喂**我们真正装出去的那个脚本**。手写一行
握手喂进去只能证明插件和写测试的人想的一样。

## 批次

握手之后，stdin 是一条**行分隔的 JSON 流**，一行一批：

```json
{"cursor":1042,"through":1049,"events":[
  {"n":1043,"kind":"chat","seq":10432,"at_ms":1786819271275,
   "group":"build","author":"worker-core","text":"…"},
  {"n":1047,"kind":"terminal.quiet","at_ms":1786819274901,
   "reason":"authorisation","title":"worker-core 需要确认",
   "body":"它停在一个工具授权提示上","terminal":"0x9491465653644ed0",
   "terminal_name":"✳ Write retry.py"}]}
```

**字段叫 `events` 而不是 `messages`**：数组里现在装得下不止一种东西，一个按
「当时唯一那种」命名的字段，会让每个插件作者在它第一次装别的东西时重读一遍。

### `n` 和 `seq` 是两个数

这是**多种事件共存之后必然要分开的一对**，写清楚：

| | 是什么 | 谁用它 |
| --- | --- | --- |
| `n` | 这个事件在宿主那**唯一一条流**里的位置，一次运行之内单调 | **游标**。`cursor` / `through` 数的是它，确认回来的也是它 |
| `seq` | 只有 `chat` 有：核心记下这条消息时盖上去的号 | **幂等键**。插件按它去重（`ON CONFLICT (stream, seq) DO NOTHING`） |

从前它们是同一个数，因为从前只有 `chat` 一种事件。一个通知根本没有 chat 日志
序号，所以一个只数 chat 的游标永远迈不过一条通知。

`n` 由 `Feed.publish` 盖，**而且只在那里盖**：三个不同线程上的三个发布者各自
记一个计数器，会让「插件确认到哪」不再是任何东西上的一个全序。

### 一条流，一个顺序

一个同时订阅了两种事件的插件，在**同一条 stdin** 上按发生顺序拿到它们，靠
每个事件自己的 `kind` 区分。**没有按种类分开的流**，理由是游标：两条流就是两个
游标，两个游标就是一个「哪一半确认了」的状态机，而现在它是一个数。

### `through`

`through` 是**这一批看过的最后一个 `n`**，不一定等于最后一条 `events` 的 `n`。
它是为过滤加的：一个只要 `build` 的插件，遇到一整窗都是 `ops` 的流量时，手里
没有任何东西可以确认，队列就永远清不掉。`through` 让它能说「我看到 1049 了，
中间没列出来的不归我」。忽略 `through` 只确认最后一条也仍然正确，只是会把被
过滤掉的尾巴白看一遍。

### 心跳

一行 `events` 为空、`cursor == through ==` 已确认位置的批次，默认每 30 秒一次
（`heartbeat_ms_default`）。宿主对心跳答复的判据**只有一条：`parseAck` 不能返回
null**——能解析成 JSON 对象就算数，`ok` 的值根本不读。写下来是因为它是实打实的
许可：**插件可以不碰数据库就答一次心跳**，心跳要的是"进程还在、还在听"，为它
探一次库会把一次网络抖动变成一次重启。

### 单批上限

256 条 / 256KB（`max_batch` / `max_batch_bytes`）；确认行上限 64KB
（`ack_max_bytes`）。**批次是从订阅队列里取的，取不等于取走**：确认之前它一直在
队列里，所以「重发」不是重读文件，只是没有 `commit`。

## 确认

```json
{"ok":true,"cursor":1043}
```

**确认里带游标而不只是 `ok`**：插件可能只写成功了前半批。带上它实际落库到哪里，
剩下的下一轮自然重发。

`Resident.advance` 的全部判据：

| 插件回的 | 怎么判 | 为什么 |
| --- | --- | --- |
| `ok` 缺失或为假 | 原地不动，下一轮重发；连续 3 次（`max_soft`）之后退避 | 没说成了就是没成 |
| `ok:true`，`cursor` 缺失 | 整批收下，`to = through` | 让最简单的插件保持最简单：读一行，回 `{"ok":true}` |
| `ok:true`，`cursor` **大于** `through` | **杀掉重起** | 它没有第二条通道能拿到这些事件，所以不可能存过没给它的东西。认下这个数，中间那些事件会被从队列里丢掉而没有任何人存过，且没有任何迹象——正是这套设计要防的那一种失败 |
| `ok:true`，`cursor` **小于**批前那个值 | **杀掉重起** | 批次里往回等于凭空推翻一件已经确认过的事。想往回只有握手那一个场合 |
| `ok:true`，`cursor` **等于**批前那个值 | 当作"原地不动"，走退避 | `ok:true` 加"我还在原地"，信息量和 `ok:false` 一样。当成进展会清零软失败计数并立刻再来一轮，而"没有新消息"那条才是带 sleep 的路——于是一个把收到的 `cursor` 原样抄回去的插件（最容易写错的一种）能让这条线程满速空转 |

## `timeout_ms` 界定的是一次交换，不是一整段会话

**写一行 + 读一行，就这么多。** 两次交换之间宿主调 `unhurried()` 把 deadline
撤掉，因为常驻插件的正常状态就是长时间无事可做。所以 `timeout_ms` **不需要覆盖
心跳间隔**，也不该按"一整晚"去设——它该是"这个后端做完一批最慢要多久"。把它写成
一段会话的预算，会让每个插件作者都设得高出一个量级，而那正好废掉了超时。

## stdout 是协议通道

插件写到 stdout 的**任何非确认行、也非 `tell` 行的东西，都会被判成失当并杀掉
进程**。所以一个要起子命令的插件，必须把那个子命令的 stdout 接到管道上自己读，
**绝不能让它继承**。

**stderr 反过来：可以继承，而且应该继承。** 它现在由宿主捕获，落进这个插件自己
的日志文件；一个子命令的报错也是这个插件的报错，落进同一个文件正是要的。见下。

## 一个插件一个日志

```text
$XDG_STATE_HOME/polter/plugins/<key>.log      0600，满 2MB 轮转，保留一代
```

一个文件里三种行，按发生顺序交织，同一个时钟：

```text
2026-08-29 03:11:04  polter  started /opt/polter/plugins/claude-code/provision.sh as pid 4711
2026-08-29 03:11:04  stderr  + mkdir -p /Users/you/.claude/skills
2026-08-29 03:11:04  said    could not write the skill file: permission denied
2026-08-29 03:11:05  polter  it would not answer, so it is being stopped; it said: ...
2026-08-29 03:11:05  polter  it has stopped 1 time(s) in a row; starting it again in 1000ms
```

| 列 | 谁写的 |
| --- | --- |
| `stderr` | 插件（和它起的子命令）写到标准错误上的 |
| `said` | 插件主动报给用户的那种行，见下一节。**无论有没有上屏，都在这里** |
| `polter` | 宿主对它做了什么：起进程、握手被拒、失当、退避、休眠、关机时停掉 |

**打开它**：菜单 **插件 → 打开插件日志**（整个目录），或者 **插件 → 某个插件 →
查看日志**（就那一个文件）。macOS 侧在 `macos/Sources/Features/Plugins/`。

### 为什么是宿主捕获，不是 SDK 写文件

**这一条最容易做反，所以理由写在这里。** 契约上写着「任何语言，一个二十行的
`curl` 脚本就是一个完整的插件」。如果日志是 SDK 提供的，那么日志只对**碰巧用了
SDK 的那些插件**存在——**那不叫日志，叫运气**。

这和本仓关于终端转录的红线 3（[gaps.md](gaps.md)）是同一个论证，一个字不改地
适用：

> **记录是终端的活，不是被托管程序的活。** 靠 agent 自己存，记录就只对碰巧会存
> 的程序存在，格式还各不相同——那不叫记录，叫运气。Polter 是唯一能做出统一记录
> 的位置。

插件按同样的定义就是一个被托管的程序，而 Polter 同样是唯一那个能替**全部**插件
做出一份统一记录的位置。所以 stderr 走回一根宿主读的通道，每个插件都有日志，
**不取决于它的作者有没有想过这件事**。

### 为什么宿主自己看到的也写进同一个文件

人问的问题是「这个插件怎么了」，不是「这个插件打印了什么」。插件的噪音在一处、
宿主的判断在另一处，等于要读的人自己把两个时钟对齐、自己排序、自己得出结论。
**一个文件读完**才是那个问题的答案。

### 上界与轮转

**2MB 一代，保留一代，所以一个插件在磁盘上封顶 4MB。**
理由是红线 4：**不写「量由别人决定」的写入源**。这个文件有多大是一个疯掉的插件
决定的——每秒往 stderr 刷十万行是它能做到的事——而本仓被一个只涨不减的编译缓存
咬过一次（263GB）。

单行上限 4096 字节；更长的行被分片写下去，**不丢**：一条失控长行里有用的那截，
在开头还是在结尾没有人说得准。

### 控制字符在写进文件之前就被剥掉

这个文件是人打开的，而 `cat` 是个解释器；里面的字节来自一个从网上抄来的脚本。
剥离表在 `src/poltergeist/scrub.zig`，**和上屏那条路用的是同一张表**——两处的
区别只在「有没有人主动要看」，而不在字节从哪来。**一条在两个地方各写一遍的规则，
就是其中一个地方会停止遵守的规则。** 表本身抄的是 `src/input/paste.zig` 的理由
（xterm 对每一次粘贴无条件做的事），只是更宽：粘贴的字节还要继续当某个程序的
输入，这里的不用。

### 两个 `plugins` 目录

| 路径 | 里面是什么 | 谁写的 |
| --- | --- | --- |
| `$XDG_CONFIG_HOME/polter/plugins/` | `<key>.json` 设置，以及用户自己放的插件目录 | 用户 |
| `$XDG_STATE_HOME/polter/plugins/` | `<key>.log` | Polter |

同一个末级名字在两个根下面，是故意的：**用户写的是配置，Polter 观察到的是状态**——
那就是 XDG 那条分界线说出声，而不是绕开它。给其中一个另起第三个词只会多一个要
记的名字。

**算不出 state 目录时**，这个插件的 stderr 回落到继承——那是从前的行为，作为
兜底留着而不是作为设计：在一个打包好的 app 里，Polter 自己的 stderr 是**没有
任何地方看得到的**。

## 插件说话：应答通道上多一种行

一个插件要告诉用户一件要紧的事——**用户给的例子：claude-code 插件写 skill
失败**——从前只有两条路，`exit` 非零和往 stderr 打，而**两样用户都看不见**。

现在它在**本来就有的那条 stdout 应答通道**上多写一种行：

```json
{"tell":"could not write the skill file: permission denied"}
```

宿主把它接到上一节那条现成的路上：`Resident` → `App.submitPoltergeistAlert`
→ mailbox → app 线程印到屏幕。**和宿主自己报「这个插件起不来」是同一条路。**

### 为什么是协议的一部分，不是一个工具调用

> **报告自己的状况不是一项能力，是协议的一部分。** 一个插件说「我写不进去」
> 不需要任何权限——那和宿主已经在说的「这个插件起不来」是同一条通道、同一件事。

所以 `notify_user` 对插件**仍然是关着的，一个字都没改**：它在 `callableByPlugin`
的关闭集里，归「总管的方法」那一类（第三节），而且语义也不同——它返回一个字符串
给 agent，不落在任何人的屏幕上。给插件开一个总管的方法，来做一件协议本来就该做
的事，是拿权限去换一个形状。

### 规则

| | |
| --- | --- |
| 写在哪 | stdout，一行一个 JSON，和确认行同一条通道 |
| 什么时候 | 在这一批的确认行**之前**。宿主一直读到拿到答复为止，所以一条只有 `tell` 的行不算答复 |
| 能不能和确认写在同一行 | 能。同一行里带上 `ok` 就既是报告又是答复。**宽的那一侧是故意的**：一个作者把两样写在一行，意图没有疑问，而窄的读法换来的是一个静默的重启循环——宿主还在等一个已经读过的答复 |
| `tell` 不是字符串 | 不当报告，整行按普通确认行读。不是失当：它看上去就是一条确认行 |
| 一次交换能说几条 | **没有另加的上限，因为已经有一个。** `timeout_ms` 界定的是一次交换，所以一个只顾说话不答复的插件，和一个干脆不答话的插件被同一个期限杀掉。为它再加一个计数器，是给一个已经关着的门再上一把锁 |

### 插件的字被做了三件事，三件都是宿主做的

1. **控制字符被剥掉。** 这段文字是**插件给的**，而它要被**印到一个终端屏幕
   上**——终端是个解释器。不剥的话，插件能移光标、改颜色、清屏、改窗口标题，
   甚至画出一条看起来像是 Polter 自己在要密码的提示。表和理由在 `scrub.zig`，
   照的是 `src/input/paste.zig:46-68`。
2. **长度被截断**，按 UTF-8 码点边界，和别的上屏文字同一个上限
   （`report.max_alert`，254 字节，因为 `poltergeist_alert` 是定长的）。
3. **署名是宿主写的**：`polter: the "claude-code" plugin says: …`。这个框插件
   写不出来，所以它说什么都不能把自己冒充成 Polter 在说话。

### 节流：和宿主报的失败共用同一个预算

**每个插件每 `dormant_retry_ms` 最多一条上屏**，`stopped` 和 `said` 一起数。

**一个预算而不是两个**：从读的人那一侧看，一个起不来的插件和一个一直在报错的
插件，是同一个插件在占同一块屏幕；而被一个插件刷满的屏幕，是第二个插件的失败
永远读不到的屏幕。两个计数器只会让「两样都干」的那个插件花掉两倍——而那正是话
最多、最不值得听的那一个。

**被节流掉的行不会消失。** 每一条 `tell` 都**无条件**写进这个插件的日志，节流
只决定哪一条**同时**上屏。这是节流敢这么狠的前提：一个循环失败的插件不能靠重复
把自己失败的记录冲掉。

### 措辞：插件被要求说后果，但不被强制

宿主自己那条（`report.alert`）**强制说后果**，是因为后果是宿主**算出来的**——
对 `wants.events` 穷举，加一个事件就必须给它一句后果。那是 Polter 自己的句子，
所以 Polter 管得住。

插件这条的句子是插件的，而**宿主没有办法检查一个字符串有没有说出后果**：任何
检查都只能是一个对英文的启发式，它会放过「failed」，又拒掉「写不进去，所以这个
agent 起来时不会记得这件事」——**一个两个方向都会错的启发式，比没有检查更糟，
因为它会被相信。**

所以这条义务写在这里给插件作者，并且**明说它没有被执行**：

> 说后果，不只说故障。「写 skill 失败」要读的人自己去想他今晚会少什么；
> 「写不进 skill，所以这个 agent 起来时不会记得约定」不用。

插件比宿主更清楚自己的后果，也比宿主更容易只说故障不说后果——**这两件事都是
真的，而只有第一件是宿主可以依靠的**。宿主能不猜就给出的那一半，它已经给了：
是谁在说这句话。

### SDK 侧

| 文件 | 调用 |
| --- | --- |
| `polter.py` | `tell("could not write the skill file")` |
| `polter.sh` | `polter_tell "could not write the skill file"` |

两个都不违反红线 1（不发明第二套能力词汇）：**`tell` 不是一个工具，是协议的
一条行**。薄客户端里仍然没有一个按工具命名的函数。

## 游标存在哪：不存

**没有游标文件。** `<key>.cursor` 连同 `Cursor.zig` 一起没有了——它存在的全部
理由就是记住跟读到日志的第几行，而现在没有人在跟读任何文件。

插件的进度只有两种存在方式，两种都不在 Polter 这边：

- **一次运行之内**：订阅队列里还没被 `commit` 掉的那些事件，在内存里。
- **跨运行**：插件自己那边已经有哪些 `seq`——那是插件自己的事，而 `seq` 是身份，
  所以它有办法自己判重。

所以 Polter 关掉时什么都不写，起来时什么都不读。**一个不存在的文件不会撒谎**，
而一个被 dotfiles 同步到另一台机器上的游标文件会。

**掉线期间的事件是丢的**，明说而不是默认：订阅是有界的
（`Feed.Subscription.Limits`），满了丢最老的并计数（`Stats.dropped`），
`Resident` 每出现新的缺口就 warn 一次。这是「插件存的是额外的一份」这句话的
必然推论——核心的记录一个字都不缺，而被人和 AI 读回去的正是核心那份。

# 三、能力对等：不写 SDK，发一个薄客户端

## 要求与做法

要求是：**agent 通过 MCP 能做的，插件通过 SDK 都能做。**

如果去写一个 N 个函数的 SDK，那个 N 就要靠人维护，而第一节那个 bug 说明了手
维护的清单会怎样。所以不写。

**插件直接说 MCP 那套线协议。** Polter 已经有全套现成的：

```text
unix socket + 每个调用方一个 token + 一行一个 JSON
首行 {"method":"auth","params":{"token":"…"}}
```

`socket` 和 `token` 在握手行里给出来（`Server.issuePluginToken`）。所谓 SDK 只是
一个几十行的薄客户端：连 socket、发首行、之后一行一个 JSON 来回。**于是对等不是
一个要维护的目标，是一个结果**——工具面加一个方法，插件当天就有，没有第二份清单
会漏。

这和本仓已经做过三次的判断同源：`terminal_key` 复用键位配置的写法、
`terminal_action` 复用动作名、动作清单从类型生成。**第二套词汇迟早和第一套漂移，
而漂移的那天没人会发现。**

薄客户端在 `plugins/_sdk/`：

| 文件 | 依赖 | 用法 |
| --- | --- | --- |
| `polter.py` | 标准库 | `Polter.from_hello(hello)` → `.call("terminal_list")` |
| `polter.sh` | `nc -U` | `polter_open "$hello"` → `polter_call '{"method":…}'` |

两份都**没有一个按工具命名的函数**。`polter.py` 的模块注释把这条写成了红线，
因为写一个 `def group_post(...)` 是每个读到这个文件的人的第一反应。

## 插件的身份

调用方身份从前是 `Bus.Id`，也就是一个终端。**插件不是终端。**

```zig
pub const Caller = union(enum) {
    terminal: Id,
    plugin: Plugin,   // key + 清单里的 wants.calls
};
```

**是 union 而不是一段保留的 id 区间，这是承重的**：一个插件手里根本没有
`Bus.Id`，所以它没有东西可以拿来冒充某个终端。冒充不是被拒绝的——协议里没有
一个地方能把它写出来。

`Server` 那张 token 表现在一张表装两种调用方，故意的：token 就是 token，它代表
什么是值；**只有一个地方把 socket 上的字节变成身份**。两张表就是两条握手路径，
而第二条正是检查会被漏掉的那条。

### 采用的默认：插件永远不是总管

于是按可达性规则（[mcp.md](mcp.md)「只看被干涉的那一方」），它能碰的只有**无标记
终端**；碰总管和被监管终端一律被拒。理由是方向——放宽容易，收紧难。

这一条不需要第二份「插件不能做的事」清单来实现：`requiresSupervisor` 那一条
判据对插件天然为假，于是每一个改变监管安排的方法都被同一句话、同一个错误码
拒掉——**和一个没有总管身份的普通终端拿到的一模一样**。所谓对等，指的就是这个。

「用户在设置里授予插件总管身份」这条路留着，形状现成：和 `held`、`shielded` 一样
**只有用户能设**。

### `shielded` 对插件照样绝对

这一条专门写下来，因为同样的错误刚犯过一次：`terminal_action` 曾是一条**没有
任何权限检查的旁路**，能绕开 `set_watch` 的总管限制，也能解开用户的 `held`——
真机验证过，`clock_out` 的拒绝和放行之间只隔一次调用。

**插件是第二扇门，每开一扇门就要重问一遍所有的闸。** 所以：

- `isShielded` 在 `authorize` 里被无条件问，**在任何和调用方身份有关的分支之前**；
- `rpc.zig` 里有一条专门的测试，把 `terminal_read` / `terminal_send` /
  `terminal_key` / `terminal_action` 四个都对着一个 shielded 终端试一遍，
  然后**把护盾摘掉再试一次**——否则这条测试量的可能是别的东西在拒。

### 哪些方法插件根本调不了

`rpc.callableByPlugin` 是一个**对 `Method` 穷举、没有 `else` 的 switch**：加一个
方法而不给它归类，编译不过。这正是旧 `Kind` 那个 switch 没有的性质——那里漏一个
是静默的，而且真的漏了两次。

关掉的那些是两类，**没有一类是「插件比较不可信」**：

1. **这是总管的方法。** 插件永远不是总管，所以 `requiresSupervisor` 已经拒了它，
   而且拒的理由和句子跟普通终端一样。覆盖 `notify_user`、`set_watch`、上下班、
   群工具，和三个 `plugin_*` 工具。
2. **这个方法问的是「谁在问」。** `group_post` 要一个作者、`group_read` 要一个
   成员，而插件不在任何群里；`me`、`notices`、`stand_down`、`become_supervisor`
   问的是一个它没有的身份；`terminal_open` 在调用方自己的窗口里开标签页，插件
   没有窗口。

**留下来开着的是：`terminal_list`、`terminal_read`、`terminal_send`、
`terminal_action`、`terminal_key`、`terminal_actions`、`terminal_keys`、
`config_get`、`skill_read`。** 这不是一个小面：它就是一个无标记 agent 能做的
全部，而且判据是同一条。

`become_supervisor` 值得单独说：它是唯一一个「本来就该被非总管调用」的方法，
所以 `requiresSupervisor` 对它是 false，**必须在这里显式关掉**，否则上面那条
「插件永远不是总管」的默认只有一次调用那么深。

## `wants.calls`：执行，不是披露

**未决问题 1 的答案：执行。**

### 判据

`network` 和 `exec` 只是披露，`events`、`groups`、`calls` 被执行。分界线**不是
这件事有多危险**，是**宿主站不站在路上**：

> 每一个事件都过 `Feed`，每一个群都过批次写出器，每一次工具调用都过这个进程
> 正在监听的那个 socket ——这些是**卡口**。一个卡口上不被执行的声明，是一个
> 主动选择不关的闸。而一个插件自己的 `connect(2)` 不经过我们任何东西，那里
> 根本没有闸可关，两边都一样。

### 它和可达性规则的关系：**更窄，不会冲突**

`wants.calls` 是**在 `authorize` 最前面**按方法名拦的一层，而且它**只会减**：
一次调用要同时过它**和**可达性规则。所以

- 它不可能让一个插件多拿到什么——声明 `set_watch` 不会让它变成总管，只是过了
  第一道闸然后被第二道拒掉；
- 它也不可能和可达性规则打架——两者是交集，不是并集。

**空的 `calls` 拒绝一切。** 这是缺省必须失败的方向：一份没写 `calls` 的清单，
是它作者从没想过这件事的清单，而装它的用户读到的是「这个插件什么都不调」。

拒绝的话里说的是**清单**而不是权限（`error.NotDeclared`），因为改的地方是
`plugin.json` 里的一行；一句关于身份的话会把作者送去翻错的文件。

**只认精确名字，没有通配符。** 声明是用户装之前要读的东西，而 `"*"` 会让那次
阅读在最要紧的地方变得毫无价值。

# 四、界面

## Polter 不编译任何东西

**插件交付的是 HTML + JS。** 作者爱用 TSX、Vue、Svelte 都行，那是作者的构建，
装进来的必须是产物。

Polter 里没有 node 工具链，也不该有——那等于把一个前端构建系统塞进终端。
Tinia 能直接吃 TSX 是因为它有构建沙箱和一个前端加载器，而它的代价是一张
**import 白名单**：不许 axios、不许 lodash、不许任何组件库，因为插件和主应用
共用运行时。

**Polter 不共用运行时，所以不需要白名单。** 页面自带什么就是什么，这一点上比
Tinia 自由。

## 承载

macOS 用 `WKWebView`。**这不是打包一个浏览器引擎**——它是系统组件，代价接近零。

GTK 侧要 `WebKitGTK`，而上游 Ghostty 不链它，是一个真实的新依赖。
**采用的默认：先只做 macOS，GTK 退回声明式表单。** 这不堵死另一条路。

## 页面的桥比插件进程窄

页面拿到的是**只能读写自己那份设置**的桥，不是整个工具面。

理由不是页面不配，是污染面：插件作者随手装一个前端依赖，那个依赖就跑在这个
页面里。插件进程有全套能力是它自己的事，**把同样一套放进一个 npm 依赖树里是
另一件事**。Tinia 靠 import 白名单挡这个，而我们刚决定不要白名单——那么就得在
别处挡。

一个页面需要给终端打字的场景，本章想不出来。想出来了再开，那时它是一次有理由
的放宽，而不是一开始就敞着。

## 声明式表单不会消失

没有页面的插件仍然靠 `plugin.json` 的 JSON Schema 生成表单——它是**兜底**，不是
次等选择：一个只有两个字段的插件不该被迫写网页。

今天这份兜底比它该有的样子差得远：只渲染文本框，`enum`、`boolean`、条件显示全
都不支持。**至少要补的是枚举和布尔**，理由见 Tinia 踩过的同一个坑——schema 里
写了 `enum` 而渲染器不看，用户就能往一个只接受三个值的字段里输入任意文字。

# 五、为什么是进程式插件

（这一节是当初五条技术路线的核算，**结论没有变**，因为其中四条理由和生命周期
无关。）

## 为什么不能内置了事

R3 的「通知用户」如果只做一种实现，那么这条策略对用不上那一种的人等于不存在。
而挂机过夜正是「人不在电脑前」的场景 —— 桌面通知在这个场景里恰恰是最没用的
一种：标题上限 63 字节、正文 255 字节（`src/apprt/surface.zig` 的
`desktop_notification`）；macOS 上 surface 处于聚焦时 3 秒后自动移除；人睡着了，
或者根本不在这台机器前。

真正有用的是能推到手机上的东西：飞书、企业微信、邮件、Bark、ntfy、Telegram。
这类渠道有几十种，而且各家协议还在变。**内置任何一种都会立刻过时，内置全部
则不可能。**

## 五个候选

| | 用户能自己写吗 | 插件崩了会怎样 | 跨平台 | 凭据 | 结论 |
| --- | --- | --- | --- | --- | --- |
| **A 进程式**（子进程 + 行分隔 JSON） | 能，任何语言，`curl` 就够 | 只有这个插件停了，而且会被重起 | 一致 | 宿主传入 | **选它** |
| B 内置实现 | 不能，要改 Zig 并发版 | — | 一致 | 配置里 | 否决：加一种就要改一次核心 |
| C 动态库 `dlopen` | 几乎不可能 | **带走整个终端** | ABI 三平台各一套 | 同进程内 | 否决：代价与风险都最高 |
| D WASM 沙箱 | 要会 WASM 工具链 | 只有这个停 | 好 | 宿主传入 | 否决：见下 |
| E 只做 webhook | 不用写，但只能发 HTTP | — | 一致 | 配置里 | 否决：邮件、命令行工具全做不了 |

**D 为什么否决**：WASM 的沙箱本身很合适，但沙箱里发不出网络请求 —— 得由宿主
提供 HTTP 宿主函数。于是「发飞书」变成「WASM 调宿主的 HTTP」，而宿主的 HTTP 又
得自己实现 TLS、重试、代理。绕一圈之后，能力上限反而退回到候选 E，成本却高得多。
等哪天需要在不可信插件里跑用户逻辑，再回来看它。

# 六、清单、设置、查找

## 目录

**下划线打头的目录不是插件**（`App.scanPlugins` 跳过它），所以 `_sdk/` 不会在每次
扫描时冒一句「加载失败」——那句 warn 只该在一个真的插件真的坏了的时候出现。

```text
plugins/
  _sdk/                  下划线打头 = 不是插件，宿主跳过
    polter.py            薄客户端，标准库
    polter.sh            薄客户端，需要 nc -U
  archive/
    plugin.json          元数据：key、订阅声明、参数 schema
    archive.py           可执行；常驻，stdin 是一条行分隔的 JSON 流
    settings.json        随目录一起装的缺省设置；用户配置目录里那份压过它
    i18n/zh-Hans.json    设置界面上那几句话的翻译；清单本身不变
  claude-code/
    plugin.json
    provision.sh
    settings.json
```

**两处查找，近的赢**（`App.pluginSearchPath`）：

1. 用户自己的：`$XDG_CONFIG_HOME/polter/plugins/`
2. 随 Polter 安装的：`<resources>/ghostty/polter/plugins/`

按目录名去重，**先看到的赢**，所以用户放一个同名目录就能顶掉我们发的插件，不用
动 app bundle。（早先的稿子写过「三处查找、后者覆盖前者」，**两处都不对**：第三
处「配置里显式指定的目录」从来没有实现过，而覆盖方向是近的赢。）

装出去的是 `src/build/GhosttyResources.zig` 里**写出来的一份名单**，不是对
`plugins/` 做 glob，每个目录**只排除 `.md`**。glob 两个方向都错：为别的用途放进
那个目录的东西会没人决定就发出去，而一个不再发布的插件只能靠删目录来实现。写名单
让这两件事都变成一行 diff，而且漏加一行的后果是响的——新插件装不出去，找的人第一
时间就发现。

> **删掉一个插件目录，装出去的那份不会跟着消失。** `addInstallDirectory` 只拷贝，
> 从不删除。所以一次增量构建之后，日志里照样会出现
> `plugin <已删掉的 key> is installed but off`。**这不是代码 bug，是「装」和
> 「删」不对称。** 要真的没有：`rm -rf zig-out` 再构建，装 app 时也先删再拷。

## `plugin.json`

**是 JSON 不是 YAML。** Tinia 是 Python，标准库之外就有 YAML；Zig 没有。摆在面前
的是「手写一个 YAML 子集解析器」和「用 JSON」，而前者要处理缩进、多行字符串、
隐式类型转换，每一样都是能悄悄解析错的地方。清单文件解析错的后果是插件行为与
它声称的不一致，那比多打几个引号糟糕得多。

```json
{
  "key": "feishu",
  "name": "飞书群机器人",
  "version": "1.0.0",
  "description": "发到飞书自定义机器人 webhook",

  "exec": "send.py",
  "timeout_ms": 10000,

  "wants": {
    "events": ["terminal.quiet"],
    "calls": [],
    "groups": [],
    "network": true,
    "exec": []
  },

  "params": {
    "type": "object",
    "properties": {
      "webhook": { "type": "string", "title": "机器人 webhook 地址" }
    },
    "required": ["webhook"]
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `key` | 必填，且只能是一个平实的名字。**写成和目录名一样** —— 宿主不校验这一条，但查重按目录名，而下游全按 `key`（设置是 `<key>.json`），不一致就得到一个设置文件叫着另一个名字的插件 |
| `name` | 给人看的名字，缺省等于 `key` |
| `version` / `description` | 给读这个目录的人看的；宿主今天不解析它们 |
| `exec` | 必填。相对目录名，被拼成绝对路径后**直接当 argv[0]**（没有 shell 兜底，shebang 必须自己成立，文件必须有执行位） |
| `timeout_ms` | 正整数，缺省 10000。**它只界定一次交换** |
| `wants` | 订阅与权限声明，见下 |
| `params` | JSON Schema，见下 |
| ~~`kind`~~ | **已废弃。** 写了不会让插件加载失败，会被 warn 一次；决定插件是什么的是 `wants.events` |

`wants` / `params` 里的一个笔误只让那一部分降级为空，**不会让整个插件消失** ——
后者对插件作者来说更难发现。方向是安全那一侧：它拿到的比它写的少。

## `wants`

| 字段 | 被执行吗 | 意思 |
| --- | --- | --- |
| `events` | **是** | 订阅哪些事件。空 = 什么都不订 = **根本不启动**，并被点名警告 |
| `calls` | **是** | 能调工具面上哪些方法。空 = 一个都不能调 |
| `groups` | **是** | 喂给它的批次里能出现哪些群的消息。`["*"]` = 全部 |
| `network` | 否，只是披露 | |
| `exec` | 否，只是披露 | |

**声明不是自证清白，是让宿主有得拦。**

**`wants` 是按插件声明的，不是按配置。** 一个既能写本地文件、又能推到 pg 的存档
插件，要按两条路的**并集**声明——即使今天配的是那条既不联网也不起 `psql` 的。
一份会随配置缩水的声明，审计没法拿它当依据：审计要看的是"它可能做什么"，不是
"它今天配成了什么"。

**为什么第一天就要有**，三条理由按重要性排：

1. **插件是别人写的代码跑在你机器上。** 2026 年出过真事：Semantic Kernel 的
   prompt injection 打到 host RCE；Claude Code 的 Hooks 被报出配置注入，配套
   CVE 可通过重定向 API 请求偷 key。这类问题的共同点是「扩展点能做的事，没人
   说得清」。
2. **能声明才能审计。** 用户装插件之前要能一眼看出它订阅什么、要读哪些群、
   要调哪些工具、要不要联网。一份读不出这些的清单，等于要求用户先读一遍源码。
3. **它同时是差异化。** Warp 让出来的信任市场是免费的。

**订阅了 `chat` 却没写 `groups` 会被 warn，但插件照常启动**：它可能同时订阅了
别的东西，而那一半是好的。缺省绝不会被读成 `["*"]`——那会让一份什么都没声明的
清单拿到全部群，权限声明存在的意义当场归零。

## `params`

JSON Schema，理由和 Tinia 的节点一样：schema 能同时用来校验和生成界面，自定义
格式两样都要自己写。而它本来就是 JSON —— 用 YAML 包一层 JSON Schema，从一开始
就是别扭的。

标准之外，宿主认两个字段，都是**作者的声明**，不是宿主的猜测：

| 注解 | 意思 | 为什么必须由作者写 |
| --- | --- | --- |
| `"secret": true` | 这个参数持有凭据 | 名字猜不出来。`webhook` 的 `url` 长得像一个地址，实际上是"以用户的名义发消息"的钥匙；而 `token_ttl` 反过来，名字里有 token 却不是秘密。**只有写这份 schema 的人知道**，而他本来就在写这份 schema |
| `"enum": [...]` | 取值是一个封闭集合 | 它是**唯一**一种能把已配置的值回显给 agent 的参数：封闭集合装不下密码 |

`secret` 必须是真正的 JSON 布尔值：`"true"`、`1` 都被读作**缺省的 false**，而
false 正是让那条拒绝规则失效的东西。

`secret` 决定的是**写**：工具面拒绝把明文写进被标注的参数。它不决定**读**——明文
值一律不回显，标没标都一样。这条不对称是故意的：作者漏标是常态，而回显是不可
逆的。

`enum` 只对**字面量**生效 —— `env:BACKEND` 会被放行，然后带着环境里的任何东西
到达插件，所以**插件自己也要再校验一遍**。

## 设置

**开关不在主配置里，在插件自己的文件里。** 主配置的 `poltergeist-notify` 已经
不起作用了，写了会被 `App.updateConfig` 点名警告。

```text
$XDG_CONFIG_HOME/polter/plugins/<key>.json      {"enabled": bool, "params": {…}}   0600
```

**为什么开关搬出了主配置**：装了哪些插件是**扫目录扫出来的**，不是主配置列出来
的。于是"开没开"这件事没有必要在主配置里再列一遍——列了就有两份真相，而且一个
设置界面想把某个插件打开时，得去改用户手写的那份配置文件。

**没有 `<key>.json` 就是没开** —— 除非插件目录里自带一份 `settings.json`：那是
发行带的缺省，只在用户没有自己那份文件时才生效。**用户那份存在就赢，包括它写
的是「关」**（两者不合并：合并分不清「关掉了」和「从没配过」，升级就会把用户
关掉的东西打开）。运行时永不写发行那份。

**这个文件是被整份重写的。** `Settings.read` 只认得 `enabled` 和 `params` 里的
**字符串**值；别的键、非字符串的值，读的时候被丢掉，写回去的时候就此消失。手写
的时候没人会碰到这件事（写的人就是读的人），但 `plugin_configure` 让 agent 也能
触发它——**在放 agent 碰这个文件之前，要知道文件里读不懂的东西会没**。

**布尔参数写成字符串 `"true"` / `"false"`**，因为这个文件只认字符串值：一个
`type: "boolean"` 的参数在这里没有第二种写法，JSON 的 `true` 会被当成读不懂的
值丢掉。**不勾写 `"false"`，不是把这个键删掉**——键不在，插件读到的是它自带的
缺省，而那和「用户把它关掉了」是两回事。

> 这一句是补写的，因为在此之前**没有任何文档、核心代码或插件规定过拼成哪个
> 串**：核心从不解读参数值（`Resident.zig` 原样写进 `hello` 行交给插件），出厂
> 插件一律用 `enum: ["yes", "no"]` 绕开了这件事。于是这个约定只存在于某一份实现
> 的复选框里——**一个只存在于某一份实现里的约定，和没有约定的区别只在于「今天
> 恰好只有一个实现」**，而第一个写 `type: "boolean"` 的插件作者只能靠猜。

## `i18n/`：给人看的那几句话

清单是英文，**而且不动**。要翻译就在插件目录里放边车文件，一个 locale 一个：

```json
{
  "name": "存档",
  "description": "…",
  "params": { "dir": { "title": "…", "description": "…" } }
}
```

- 只覆盖要覆盖的字段，没写的回落到清单（英文）。
- 文件名是语言标签，匹配从具体到笼统（`zh-Hans-CN` → `zh-Hans` → `zh-CN` → `zh`），
  **script 排在 region 前面**。**第一个存在的文件整份赢，不合并。**
- **只有设置界面读它**：`plugin_list` 给 agent 的一律是清单原文，否则同一个 agent
  在中文机器和英文机器上会看到不同的工具描述。
- `i18n/*.json` 不是 `.md`，所以**会随插件目录一起装出去**。

规则与理由见 [boundary.md](boundary.md) 第四节。

# 七、凭据：不自己管密码，接到已有的密码管理器上

**这是插件与 Tinia 节点最大的不同**：节点处理的是数据，插件握着的是能发消息的
钥匙。

## 先说清楚问题

进程式插件的参数总要从某个地方来。最直接的做法是写进一个配置文件，但那意味着
**磁盘上有一份明文密码**。加权限 0600 只是把「谁能读」缩小到本机当前用户，文件
本身还是明文 —— 备份会带走它，误提交会带走它，一次 `cat` 就会把它打在屏幕上
（而这个屏幕现在可能正在被别的 agent `terminal_read`）。

## 做法：配置里存**引用**，不存值

参数值支持前缀，Polter 在**起这个子进程的那一刻**才解析：

| 写法 | 从哪取 | 用在什么场合 |
| --- | --- | --- |
| `https://…` | 就是字面值 | 不敏感的东西，比如 webhook 地址 |
| `env:FEISHU_TOKEN` | 环境变量 | CI、容器、systemd unit |
| `file:~/.config/polter/feishu.key` | 文件内容（首行，去空白，`~/` 会展开） | 已经有一份密钥文件 |
| `keychain:polter/feishu` | 系统钥匙串 | macOS 用 `security`，Linux 用 `secret-tool` |
| `cmd:op read op://Private/feishu/token` | **执行命令取 stdout** | **任何密码管理器** |

于是配置文件长这样，**里面没有一个字是秘密**，可以进 dotfiles 仓库、可以贴进
issue、可以同步到别的机器。

## 为什么 `cmd:` 这一条最重要

它一条就覆盖了全部密码管理器 —— 1Password (`op`)、pass、Bitwarden (`bw`)、
gopass、`security`、`secret-tool`、以及用户自己写的任何脚本。**Polter 不需要为
其中任何一个写适配，也不需要跟着它们的 API 变。**

反过来说，如果不做 `cmd:`，就要在 Polter 里一个个接：接完 1Password 有人要
Bitwarden，接完 Bitwarden 有人要 pass，而每一个都有自己的认证方式和解锁流程。
这是一条永远走不完的路。

`keychain:` 仍然单独列，是因为它是零依赖的默认选项。它的实现本身就是 `cmd:` 的
一个内置特例。

## 解析的三条规矩

1. **在子进程起来的那一刻解析，不缓存跨进程。** 密码管理器可能会锁上，锁上之后
   就该失败 —— 缓存会让「已锁定」这件事对 Polter 不可见。**常驻的代价是这份解析
   出来的值被握到进程死为止**（见第二节），所以每次重起都重解一遍，是这条规矩在
   常驻世界里剩下的全部。
2. **解析失败 = 这个子进程不起**，写日志，不回退到别的值，也不把引用原样发出去。
   把 `cmd:op read …` 当成密码发给飞书，比发不出去糟得多。
3. **解析出的值只进插件的 stdin**，不进环境变量、不进日志、不进聊天记录。环境
   变量会被插件自己 spawn 的子进程继承，而日志和聊天记录都会落盘。

## 仍然允许明文

**手写的文件里可以直接写明文**，因为总有人只想把 webhook 贴进去就用。**设计不该
逼一个只想试一下的人先去装密码管理器。** 但文档里默认给的例子用 `cmd:`，让省事
的那条路是明确选择的结果，而不是唯一的路。

**但工具面不允许写明文**，而这条不对称正是整个工具面的要点。**同一个文件、同一
个解析器，区别在于是谁的手：文件是用户的，工具是 agent 的。** 用户往自己机器上
自己的文件里写自己的密码，是他的事；一个 agent 替他决定把一段明文落到盘上，不是。

## `file:` 的 `~/` 展开

`~/` 现在真的会被展开（按 `HOME`），**只认打头的 `~/`**：`~user/` 需要查 passwd，
没人要过。

**展开只发生在读的那一刻，而工具面在写的那一刻就要判断，所以两边的规矩不一样：
手写的文件里 `~/` 可以用，`plugin_configure` 里不行，它要一条绝对路径。** 不是
多此一举：`Guard` 是按文本判断这条路径落不落在 polter 目录之下的（文件此刻可能
还不存在，而"问一次文件系统"的答案会在检查与写入之间变），而 `~` 展开成什么要到
插件被调用时才知道——一个此刻判不了的条件，只能拒绝，不能放行。

# 八、工具面能改什么，不能改什么

三个 MCP 工具（`plugin_list` / `plugin_configure` / `plugin_test`）都只给总管，
**因此对插件也一律关着**。完整论证在 [mcp.md](mcp.md)，这里只放一张对照表：

| 能 | 不能 |
| --- | --- |
| 把插件**打开** | 把插件**关掉** —— 它是用户听见事情的那条通道 |
| 把已声明的参数设成一个字面值 | 设一个清单没声明过的名字 —— 判不出是不是 secret，就不能写 |
| 设成 `env:` / `keychain:` 引用 | 写 `cmd:` —— 那是让 Polter 在授权结束之后自己去跑一条命令 |
| 设成 polter 目录下的 `file:` 引用 | 把明文写进标了 `secret` 的参数 |
| 让一个通知插件真发一条 | 装一个插件 —— 那仍然是用户的动作 |

**对一个正在跑的插件改参数：写文件，不重启。** 参数下次 Polter 启动时生效，回复
里明说。**两个实例是两个订阅者**，同一件事会被完整地处理两遍，而且两个实例各自
握着连接、各自答一套心跳，谁也不知道另一个存在。查重有两道——`App.scanPlugins`
按 `manifest.key` 去重，`App.startResident` 起之前再按 key 查一次现有实例。两道
都不能省：前一道防的是清单，后一道防的是时序。

**`plugin_test` 什么都不起。** 每个插件都是常驻的，起第二个就是上面那件事。它
报的是 `status()` 与「为什么没在跑」；对一个订阅了 `terminal.quiet` 的插件，它
**真的发一条**（走 feed，绕过通知时间段——测试的意义就是它发得出去），然后说清
这不是送达回执。协议里根本没有干跑通道，而**宿主没有任何办法强制别人写的脚本
干跑**——加一个 `dry_run` 字段只是加一个作者可以不理的字段。

**诚实的残余**：一个同时能写文件的 agent 不受这些约束中的任何一条——它直接改那个
JSON 就是了。这些拒绝买到的不是"挡住能写文件的 agent"，而是一条不变量：**装一个
MCP server，绝不会因此多出一份它自己的 harness 本来放在授权闸后面的权限。**

# 九、照着写一个

## 9.1 从零一个通知插件

放进 `$XDG_CONFIG_HOME/polter/plugins/say/`：

```text
say/
  plugin.json
  say.py          ← chmod +x，shebang 要自己成立
```

`plugin.json`：

```json
{
  "key": "say",
  "name": "Say it out loud",
  "exec": "say.py",
  "timeout_ms": 8000,
  "wants": { "events": ["terminal.quiet"], "calls": [], "groups": [] },
  "params": {
    "type": "object",
    "properties": {
      "voice": { "type": "string", "title": "Voice", "enum": ["Alex", "Samantha"] }
    }
  }
}
```

`say.py` 的骨架——**每一行都要回一行**：

```python
#!/usr/bin/env python3
import json, subprocess, sys

def answer(obj):
    sys.stdout.write(json.dumps(obj, separators=(",", ":")) + "\n")
    sys.stdout.flush()

hello = json.loads(sys.stdin.readline())
voice = (hello.get("params") or {}).get("voice") or "Alex"
answer({"ok": True})                      # 握手也要回

for line in sys.stdin:
    if not line.strip():
        continue
    batch = json.loads(line)
    for ev in batch.get("events") or []:
        if ev.get("kind") != "terminal.quiet":
            continue                       # 宿主不会发别的，但别赌
        done = subprocess.run(
            ["say", "-v", voice, ev.get("title", "")],
            stdout=subprocess.DEVNULL,     # 绝不能 inherit
            stderr=sys.stderr,             # 反过来：让它落进这个插件的日志
        )
        if done.returncode != 0:
            # 说后果，不只说故障。这一行会被印在用户屏幕上。
            answer({"tell": "say(1) 没能发声，所以终端安静下来时没有人会念给你听"})
    answer({"ok": True})
```

`answer({"tell": ...})` 和 `answer({"ok": True})` 走的是同一个函数，因为它们走的
是同一条通道——这正是这件事被做成协议而不是一个工具调用的原因。用薄客户端的话
`from polter import tell` 也一样。

**打开它**：`$XDG_CONFIG_HOME/polter/plugins/say.json` 写
`{"enabled": true, "params": {"voice": "Samantha"}}`，或者让总管调
`plugin_configure`。

## 9.2 不启动 Polter 怎么测

**最快的一层：手工喂两行。**

```console
$ printf '%s\n%s\n' \
  '{"hello":1,"plugin":"say","cursor":0,"events":["terminal.quiet"],"groups":[],"calls":[],"params":{}}' \
  '{"cursor":0,"through":1,"events":[{"n":1,"kind":"terminal.quiet","at_ms":0,"reason":"authorisation","title":"hi","body":"b","terminal":"0x0","terminal_name":""}]}' \
  | ./say.py > /tmp/x.log 2>&1; echo "EXIT=$?"
```

stdout 上应当**正好两行** `{"ok":true}`——加上你自己写的每一行 `{"tell":…}`。
除此之外多一行、少一行、或者出现别的东西，都是会被宿主判成失当的形状。

往 stderr 打什么都可以，那是给日志看的：装上之后它会出现在
`$XDG_STATE_HOME/polter/plugins/<key>.log` 里，和宿主对这个插件的判断在同一个
文件里。

**第二层：插件自带 `--self-test`。** 把逻辑那一半（批次 → 确认）和 IO 那一半分开，
自测只驱动前者，在 `mkdtemp()` 下跑，跑完不留东西。`plugins/archive/archive.py`
是参考实现。**理由是：拿到插件的人不该为了验它先装一套东西。**

**第三层：真的发一次。** 打开插件，让总管调 `plugin_test`。

## 9.3 常见错误

| 症状 | 原因 |
| --- | --- |
| 插件在跑，但什么都收不到 | `wants.events` 没写，或者写了一个这个构建不发布的名字（日志里有 warn）。**订阅什么才收得到什么** |
| 订阅了 `chat`，还是什么都收不到 | 没写 `wants.groups`。日志里点名了，还把该补的那一行抄给你 |
| 每 `timeout_ms` 被杀一次，重起，无限循环 | **握手没回确认。** 宿主写握手之前就装上了期限 |
| 工具调用回 `NotDeclared` | `wants.calls` 里没有这个方法名。改 `plugin.json`，不是改权限 |
| 工具调用回 `NotPermitted` | 这是总管的方法，而**插件永远不是总管** |
| 工具调用回 `Supervised` | 目标终端带着标记（是总管，或者有人在看它）。**无标记的终端对插件是开着的** |
| 工具调用回 `Shielded` | 用户把那个终端拿出了工具面的射程。**没有任何东西能解开它**，去问键盘前面那个人 |
| 工具调用回 `NotATerminal` | 这个方法问的是「谁在问」（作者、成员、窗口），而插件没有终端 |
| 进程莫名其妙被杀，日志说 misconduct | 插件（或者它起的子命令）往 stdout 写了非确认行。子进程的 stdout 必须自己接管道 |
| 想看插件到底出了什么事 | `$XDG_STATE_HOME/polter/plugins/<key>.log`，或者菜单 **插件 → 打开插件日志**。stderr 和宿主的判断在同一个文件里 |
| 写了 `{"tell":…}`，插件每 `timeout_ms` 被杀一次 | **一条只有 `tell` 的行不算确认。** 后面还要跟一行 `{"ok":true}`，或者把 `ok` 加进同一行 |
| `tell` 的内容上屏了，但只上了一条 | 节流：每个插件每 `dormant_retry_ms` 最多一条，`stopped` 和 `said` 共用这一个预算。**其余的都在日志里** |
| `tell` 里的颜色 / 光标控制不见了 | 故意的。那段文字要被印到一个终端屏幕上 |
| 参数设不进去 | 清单里没声明这个名字。**没被声明的参数是工具面不会去设的参数** |
| `plugin_configure` 拒了你的 `cmd:` | 故意的。手写文件里可以用，工具面不行 |
| `plugin_configure` 拒了 `file:~/…` | 工具面要绝对路径。`~` 展开成什么要到调用时才知道，此刻判不了的条件只能拒绝 |

## 交付前自检

- [ ] `exec` 有执行位，shebang 自己成立（宿主直接 `argv[0]`，没有 shell 兜底）。
- [ ] `key` 和目录名一样。
- [ ] `wants.events` 写了，而且是这个构建认识的名字。
- [ ] 订阅了 `chat` 就写了 `wants.groups`。
- [ ] 要调工具面就写了 `wants.calls`，精确到方法名。
- [ ] `wants.network` / `wants.exec` 按**最大能力**写，不按今天的配置写。
- [ ] 凭据参数标了 `"secret": true`（真正的 JSON 布尔）。
- [ ] **每一行都回一行确认，握手那一行也算。**
- [ ] stdout 上只有确认行和 `tell` 行；子进程的 stdout 自己接管道
      （**stderr 反过来，让它继承**：那是这个插件的日志）。
- [ ] 要报给用户的事写成 `{"tell":"…"}`，而且**说的是后果，不只是故障**
      （没有人会替你检查这一条）。
- [ ] `--self-test` 能跑，退出码 0，不留文件。

# 十、插件从哪来

**一期只做本地目录。** 用户把插件目录放进 `$XDG_CONFIG_HOME/polter/plugins/`
就能用。

**远程仓库留接口，不实现。** 参照 Tinia 的 `tinia-repo.yaml`：一个仓库是一份清单
加一堆插件目录，清单里有 `name`、`version`、`min_polter_version`、`namespace`。
留这个位置的意思是：一期的目录结构要与它兼容，这样将来加「从 URL 安装」时不必改
插件本身的格式。

**先不做自动更新与签名校验。** 从网上下载并执行代码是一件需要认真对待的事，而
一期的用户是把脚本放进自己目录的人 —— 那和运行任何别的脚本没有区别。等真的要做
「一键安装第三方插件」时，签名与沙箱要一起设计，不能事后补。

# 红线

1. **不发明第二套能力词汇。** 插件说的就是 agent 说的那套线协议；SDK 是薄客户端，
   不是一份要维护的函数表。
2. **不为插件编译任何东西。** 装进来的是产物。
3. **每开一扇门，重问一遍所有的闸。** 插件是继 `terminal_action` 之后的第二扇，
   而第一扇当初就漏掉了 `held` 和 `set_watch`。
4. **声明是为了有东西可拒绝**，不是良民证。宿主站在路上的（`events`、`groups`、
   `calls`）就真的拦；站不到路上的（`network`、`exec`）就明说自己只是披露。
5. **不为插件牺牲输入延迟。** 插件全部独立进程，绝不进渲染路径。
6. **不追数量。** 质量、可发现性、默认关闭，都比数量重要。
7. **日志由宿主记，不由插件记。** 一份只有用 SDK 的插件才有的日志不叫日志，叫
   运气——和 [gaps.md](gaps.md) 红线 3 是同一句话。而既然是宿主在记，它就要有
   上界并轮转（红线 4）：这个文件的量是别人决定的。
8. **插件给的字不直接上屏。** 它要被印进一个终端，而终端是个解释器。剥离和截断
   在 `scrub.zig`，署名的框由宿主写——插件说什么都不能冒充成 Polter 在说话。

# 与既有原则的关系

- **R2（不做自动点 yes）不受影响。** 插件能调 `terminal_send` 和 `terminal_key`，
  和一个无标记 agent 一样多——**而那从来就不是「替人点 yes」的授权**：R2 说的是
  程序不替人判断该不该点，而不是没有键盘通道。判断仍然只能由人做。
- **R8（不管理任务）不受影响。** 插件不持有状态。
- **R3 的「通知用户」分支由它落地**，但「什么时候该通知」仍归
  [supervisor.md](supervisor.md)。

# 未决问题

1. ~~`wants.calls` 是执行还是披露~~ —— **已定：执行。** 见第三节。
2. ~~插件断线重连时事件从哪里接上~~ —— **已定：接不上，掉线期间的事件是丢的，
   而且被数着。** 见第二节「游标存在哪」。
3. ~~一个插件同时订阅多种事件时怎么区分与排序~~ —— **已定：一条流，一个 `n`
   的顺序，每个事件自带 `kind`。** 见第二节。
4. 页面怎么知道自己该显示什么——设置是它自己读，还是宿主注入。**未定。**
5. 一次通知同时配了多个插件时全部都发，这会让手机响两次。倾向保持——挂机时多
   一条冗余比少一条可靠。
6. 一个插件想在群里说话（`group_post`）今天做不到：它不是任何群的成员。要开的
   话正确的形状是**让它成为成员**，而不是给它一条绕过成员判断的特例。
