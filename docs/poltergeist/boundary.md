# 边界：什么是功能，什么是扩展

> 最后更新对应的 git commit：`816b348eb`
> 校验方式：`git log -1 --format='%H %h %ad %s'`
> 状态：**本轮决策记录，实现进行中。** 四条决定都已拍板，落地分散在
> `Plugin.zig`、`Archive.zig`、`register.zig` 与 `Termio.zig` 的抽头。
> 各条末尾标注了它当前的状态。

## 本章覆盖什么

- 核心存储与插件存储的分界：谁是功能，谁是扩展，以及为什么核心不作为插件的数据源。
- 「预装」不是一种特权：所有插件一视同仁，`enabled` 的默认值属于发行，不属于插件模型。
- `.claude` 目录的产出为什么从核心退成插件，以及启动期失败为什么必须对用户可见。
- 插件的多语言：为什么设置界面本地化而 MCP 工具面固定英文。

## 本章不覆盖什么

- 插件宿主契约、清单格式、凭据引用、权限声明 —— 见 [plugins.md](plugins.md)。
- 存档插件的协议、分块、部分确认 —— 见 [storage.md](storage.md)。
- 怎么动手写一个插件 —— 见 [writing-a-plugin.md](writing-a-plugin.md)。
- 终端转录录哪一层、密钥立场 —— 见 [gaps.md](gaps.md) 第三节。
- MCP 工具面覆盖到哪里 —— 见 [surface.md](surface.md)。

## 一句话概括

**核心负责「一定有」，插件负责「还可以有」。** 一件事只要缺了它 Polter 就不成立，
它就是功能，不许挂在任何插件上；插件写的永远是额外的那一份。

## 一、核心存储是功能，插件存储是扩展

### 曾经的划法，以及它错在哪

`Archive` 曾经靠游标**跟读核心自己的日志文件**拿数据：`Cursor.zig` 记住它读到
`~/.local/state/polter/chat/chat.jsonl` 的第几行。也就是说，**核心的存储同时是
插件的数据源**。

这条耦合带来三个具体后果：

1. **核心的轮转策略动不了。** 流是 8MB 轮转、留两代（`ChatLog.zig` 的
   `rotate_bytes`）。`Archive` 的 `Tail` / `Mark` 依赖「一个文件、一个偏移」，
   改轮转就要动它们。
2. **插件落后会永久丢数据。** 插件掉线或落后超过两代（16MB），第三代已经被
   `rename` 覆盖，那段内容对插件**永远不存在，而且没有任何迹象**。
3. **终端转录接不进来。** 终端输出天然没有「一个文件一个偏移」这种东西可跟读，
   照这个模式做就要为它再发明一套。

### 现在的划法

> **核心的流、记录、轮转是必须的核心功能，不因插件存在或缺席而改变，也不把
> 内容提供给插件。插件拿到的是实时事件，存的是额外的一份记录。**

三个后果因此同时消失：轮转策略随便改，插件掉线只丢它自己那份，终端和群聊走
同一条通道。**丢数据的风险本来就是从耦合里来的，拆掉就没了**，不需要再为它设计
一层保留策略。

`Cursor.zig` 随之退场——它存在的全部理由就是记录「跟读到哪了」，而没有跟读之后
这个问题不存在。

**落地在 `src/poltergeist/Feed.zig`**：一个事件、多个订阅者、各拿一份拷贝，
有界队列满了丢最老的并计数；发布方（`App.logChat`，紧跟在 `ChatLog.append`
之后）不会失败也不会等待。`Archive` 从此不认识任何路径，`ChatLog` 一行未改
——这正是「不因插件存在或缺席而改变」的字面意思。事件是一个 union，今天只有
`chat` 一个成员，终端那一路的形状**故意不猜**，留位置给第三节。

### 这一条和红线 2 的关系

[gaps.md](gaps.md) 的红线 2 写着「本地留一份能读的，是核心的事，不是插件的事」。
本节不是修订它，**是它的另一半**：红线 2 说核心必须自己写一份，本节补上「而且
核心那份不为插件服务」。两句话合起来才是完整的分界——否则「核心写一份」可以被
实现成「核心写一份给插件读」，那正是现状。

**状态：已实现。**

## 二、预装不是特权：所有插件一视同仁

### 问题

有两个插件必须默认就是开的，否则它们承担的职责会静默消失：

- 记录插件默认关 → 升级后用户的额外记录停止
- `.claude` 插件默认关 → **升级后 Claude Code 直接失去 Polter 的工具面**

而 `Plugin.Settings` 的 `enabled` 默认是 `false`，[storage.md](storage.md) 的
红线 3 也写着「默认关闭」。

### 被否掉的做法：给插件模型加一个特权位

最直接的写法是给清单加一个 `default_enabled`，或者在宿主里区分「内置插件」与
「第三方插件」。**这条被否掉了**，理由不是安全，是它会把**「谁写的」变成代码里
的一个分支**——一旦存在这个分支，以后每一条能力都要回答「这是内置的还是第三方
的」，而那是一个和技术无关的问题。

> **只有预装和不预装，没有内置和第三方。**

### 做法：让它完全不进插件模型

清单（`plugin.json`）和 skill **早就是两层查找**：配置目录的副本压过发行目录里
的那份（`src/build/GhosttyResources.zig:142-158` 安装发行侧那一份，
`register.zig` 的 `readSkill` 做同样的事）。settings 缺的就是这一层。

补上之后：

|              | 位置                                 | 谁写                       |
| ------------ | ------------------------------------ | -------------------------- |
| 用户的设置   | `<config>/polter/plugins/<key>.json` | 用户、`plugin_configure`   |
| 发行带的默认 | 随插件目录一起装的 `settings.json`   | 只有发行，**运行时永不写** |

配置目录有文件就完全用它，没有才看发行那份。**代码路径对所有插件完全相同**——
一个第三方插件放进发行目录，行为一模一样。「预装」因此是一件关于**装了什么**的
事，不是关于**插件是谁写的**的事。

**用户关掉之后升级不会被重新打开**，因为「关」是写在配置目录里的一个值，而不是
「没说过」。`Plugin.Settings` 的解析本来就分得清这两者（`enabled: bool = false`
加上那个判定「有 `params` 或有 `enabled` 字段」才算配置过），这个区分不能破坏——
它是这条需求的全部要害。

### 红线 3 不用改

「默认关闭」说的是**用户装进来的东西**不该一装上就在跑。预装带一份 settings 是
发行的事，不是插件的特权，两句话不冲突。

**状态：已落地**（`Plugin.zig` 的 `Settings` 现在写着「读两处、写一处」，
`readFirst` 按「哪个文件存在」而不是按合并内容来选）。

## 三、`.claude` 产出退成插件，且失败必须对用户可见

### 现状是硬编码的 Claude Code

启动时两处：

1. `register.ensure`（`src/App.zig:1014` 调用）→ 跑 `claude mcp add --scope user polter`
2. `register.ensureSkills`（`src/App.zig:1034` 调用）→ 把 skill 拷进 `~/.claude/skills/polter-*/`

两处都只认 Claude Code 一种运行时。这和「Polter 是通用的 AI 原生终端」直接矛盾：
换一个 agent CLI，这两步不但没用，而且**没有任何位置可以让别人补上**。

### 划法

**核心产出数据**（有哪些 skill、MCP 端点在哪、token 是什么），**插件把它翻译成
某个 AI CLI 认识的形状**。这需要一个新的 `Kind`（暂称 `provision`），生命周期是
「启动时一次性，但要喂输入数据」——和 `notify` 的一次性不同，和 `archive` 的常驻
也不同。

[plugins.md](plugins.md) 有一句「现在不要为 `sensor` 和 `action` 写任何代码，
猜出来的接口比没有接口更难改」。这条对 `provision` **不适用**：它的调用契约不是
猜的，现有的两个函数就是它的第一个实现。这和当初 `archive` 被放行是同一个理由。

### 失败必须对用户可见，而且这条不能等

现在这一步的失败一律只有日志：

```text
src/poltergeist/register.zig:86   log.warn("poltergeist: could not register the MCP server", .{})
src/poltergeist/register.zig:196  log.warn("poltergeist: no source for skill {s}", .{name})
src/poltergeist/register.zig:231  log.warn("poltergeist: could not make {s} err={}", .{ dir, err })
src/poltergeist/register.zig:239  log.warn("poltergeist: could not write skill {s} err={}", .{ name, err })
```

`log.warn` 用户看不见。而 `notify_user` 那条路是把字符串**返回给 agent** 的，
这里用不了——**用不了的理由恰恰是这件事的要害**：

> **这一步失败的后果就是 agent 没有工具面。所以失败信息永远不能只发给 agent——
> 它正是那个收不到的人。必须发给用户。**

现有唯一到得了用户的路是 `surface_message`（`src/App.zig:2717` 分发，
`App.surfaceMessage`）。

这和本仓刚修掉的 `set_watch` 是同一个形状：**做了相反的事，还回了个 ok。** 那次
是参数被静默丢弃，这次是整个启动步骤静默失败，两次都是「没有报错告知」。所以
报错口要和 `provision` 同一轮做出来，不能留到它咬人的时候。

**状态：未实现。**

## 四、多语言：设置界面本地化，工具面固定英文

### 现状是没有

`plugin.json` 里的 `name`、`description`、每个参数的 `title` 与 `description`
全是硬编码英文（见 `plugins/webhook/plugin.json` 与
`plugins/chat-archive/plugin.json`）。而 Polter 自己走 gettext（`po/`、
`src/os/i18n.zig`），插件的字符串进不了那套流程——第三方插件不在我们的翻译里。

### 形态：per-locale 边车文件

```text
plugins/chat-archive/
  plugin.json          清单本身不变，值仍是字符串，英文兜底
  i18n/zh-Hans.json    只覆盖需要翻译的那几个字段
```

不把清单字段改成 `{"en": …, "zh-Hans": …}` 这种对象：那会让
`"description"` 时而是字符串时而是对象，污染所有解析路径，而且第三方工具读
`plugin.json` 就此失效。边车文件可以单独交给译者、单独增删。

### 关键决定：工具面不本地化

`plugin_list` 的结果是**给 AI 读的**，设置界面是**给人看的**。

> 如果两边都跟随用户 locale，**同一个 agent 在中文机器和英文机器上会看到不同的
> 工具描述，行为不可复现**。

所以：**设置界面走边车文件，MCP 一侧一律用清单原文。** 人看到母语，agent 看到的
东西和这台机器的语言设置无关。

**状态：未实现。**
