## 本章覆盖什么

群聊消息怎么被保存、怎么往回翻、以及怎么把它同步到外部数据库。插件
体系本身在 [plugins.md](plugins.md)，这里只讲存档这一类插件多出来的东西：
**常驻进程**、**游标**、**权限声明**。

## 本章不覆盖什么

**终端里你和 AI 的完整对话不在这一期。** 那是 pty 的全部输出——量级
比群聊大几个数量级，而且里面必然有密钥、路径、报错。它更像"录屏"而
不是"聊天记录"，风险和存储量都不是一回事，单独议。

## 一句话概括

**本地那份 append-only 日志是唯一的事实来源，插件只是它的跟读者。**

## 为什么这一条是整个设计的地基

反过来的做法很自然：消息来了，写数据库。但那样一来**耐久性就依赖插件**
——数据库连不上、凭证过期、插件崩了，消息就丢了，而你不会立刻发现。

现在 `$XDG_STATE_HOME/polter/chat/chat.jsonl` 是同步写的，写完才算数。
插件从这个文件往后读，读到哪里由**游标**记着。于是：

- **插件挂了一小时** → 游标不动 → 起来之后自动补齐，一条不丢
- **插件卡住** → 不产生背压，我们只是不推进游标
- **数据库连不上** → 同上，恢复后自己追

**不需要重试队列，不需要缓冲区——日志本身就是队列。**

这也是[通知那次](supervisor.md)教训的推广：**发出去不等于送达，确认才算。**
通知那边的做法是"交付后仍持有，读到才清"；这里是"插件确认写入后，
游标才前进"。同一条道理的两种形态。

## 游标是什么：日志自己的序号

**现有的 `seq` 不能当游标用。**`Chat.Message.seq` 是**每群一份、进程内
从 1 开始**的计数器（`src/poltergeist/Chat.zig:143`）。它服务的是「这个
成员看到哪儿了」，而重启之后它从 1 重新数 —— 同一个日志文件里就会有两
条 `build/seq=7`，插件按它去重会去错，往回翻会翻到上一次运行的消息。

所以日志带**自己的序号**：全局、单调、跨群共用，`ChatLog` 打开时读最后
一行恢复。写下来的一行长这样：

```json
{"seq":10432,"at_ms":…,"group":"build","from":"0x…","author":"…","text":"…"}
```

这个 `seq` 是系统里**唯一的游标**：插件确认它，`group_history` 按它翻页。
群内那个 `seq` 原样不动，继续只在 `Chat` 内部当成员游标用。

**内存里的消息也要带上它。**`Chat.Message` 加一个 `log_seq`，由宿主在
`append` 返回后填。不这么做，界面翻到内存边界时手里只有群内 `seq`，没
有任何东西能和日志对齐，只能靠比对文本去猜接缝 —— 那是会接错的。
`log_seq == 0` 表示这条没落盘（日志被关掉了），此时往回翻直接到底。

## 生命周期按种类分

|          | 生命周期     | 为什么                                     |
| -------- | ------------ | ------------------------------------------ |
| `notify` | 一次一进程   | 稀疏、突发；崩了只影响那一条               |
| `archive`| **常驻**     | 连续，而且要握着数据库连接                 |

通知一小时几条，每次起一个进程无所谓。存档是连续的：每条消息起一次
`psql`（建连 + TLS 握手）显然不行。

**常驻的代价是要管进程**：会挂、会卡、要重启、退出时要收。杀进程那套
（`std.posix.kill` + 超时）通知插件已经有了，直接复用。

### 协议

常驻插件的 stdin 是一条**行分隔的 JSON 流**，一行一批：

```json
{"cursor":1042,"messages":[{"seq":1043,"group":"build","author":"…","text":"…"}]}
```

每行的 `cursor` 是**这一批之前**已确认到哪里，`messages` 里每条带自己的
`seq`。插件写回一行确认，`ok` 为真时 Polter 才把游标推进到它给的位置：

```json
{"ok":true,"cursor":1043}
```

**确认里带游标而不只是 `ok`**：插件可能只写成功了前半批。带上它实际
落库到哪里，剩下的下一轮自然重发。

## 一个插件，多个后端

**「聊天存档」是一个插件，pg 只是它当前用的后端。**

不是 `archive-pg`、`archive-mysql`、`archive-minio` 三个。理由有两条：

1. **用户视角**：你要的是"把聊天存下来"这一件事，不是在三个名字相近的
   插件之间挑
2. **工具面不该膨胀**：MCP 生态的教训是装 3–5 个封顶，多了 schema 挤爆
   上下文、agent 反而变笨。插件数量同理

配置形态：

```json
{
  "enabled": true,
  "params": {
    "backend": "postgres",
    "dsn": "cmd:op read op://Private/polter-pg"
  }
}
```

以后加 mysql 是**给它加一个后端**，不是多一个插件。

## 往回翻

`chat.jsonl` 已经存着全部，所以**往上翻不需要任何插件**。

`group_history(group, before_seq, limit)` 现在就在工具面上：它从日志倒着
读，`before_seq` 是上一节那个日志序号，回来的一批按时间升序，和 `group_read`
共用同一个 `messages` 形状，读的人一套解析代码就够。

**这一批的 `seq` 恒为 0。**日志没有记过群内序号，所以这一批只能拿 `log_seq`
翻页；把 0 或者任何编出来的号当成 `group_compact` 的 `through` 递回去，删掉
的会是另一段。界面滚到内存边界（当前保留最近 500 条）时，拿手里最老那条的
`log_seq` 往下要，接缝是精确的，不靠比对文本；`more` 为 false 就是到底了。

**插件在这里的角色是日志被轮转掉之后**——8 MB 就轮转且只留一代，那时
候才需要问外部存储要更老的。也就是说：

- 没装插件 → 能翻到本地日志的极限
- 装了插件 → 无限往上翻

## 权限声明

**第一天就要有，不能等生态起来再补。**

2026 年出过真事：Semantic Kernel 的 prompt injection 打到 host RCE；
Claude Code 的 Hooks 被报出配置注入，配套 CVE 可通过重定向 API 请求偷
key。插件是别人写的代码跑在你机器上——**「这个插件能读什么、能跑什么」
必须能被声明，也必须能被审计。**

`plugin.json` 里声明，声明之外一律拒绝：

```json
{
  "key": "chat-archive",
  "kind": "archive",
  "wants": {
    "groups": ["*"],
    "network": true,
    "exec": ["psql"]
  }
}
```

这既是安全，也是**差异化**：Warp 让出来的信任市场是免费的。

## 三条红线

1. **不为插件牺牲输入延迟。** 插件全部独立进程，绝不进渲染路径。
   Ghostty 内核的性能是唯一不能亏的资产
2. **不做 block 模型。** 要结构化输出就用富渲染 + MCP 暴露语义，
   不改终端契约
3. **不追数量。** 质量、可发现性、默认关闭，都比数量重要
