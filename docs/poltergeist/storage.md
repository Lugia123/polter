## 本章覆盖什么

群聊消息怎么被保存、怎么往回翻、以及怎么把它同步到外部数据库。插件
体系本身在 [plugins.md](plugins.md)，这里只讲存档这一类插件多出来的东西：
**常驻进程**、**实时事件通道**、**权限声明**。

## 本章不覆盖什么

**终端里你和 AI 的完整对话不在这一期。** 那是 pty 的全部输出——量级
比群聊大几个数量级，而且里面必然有密钥、路径、报错。它更像"录屏"而
不是"聊天记录"，风险和存储量都不是一回事，单独议。

## 一句话概括

**核心的存储是核心功能：独立完整，不因插件存在或缺席而改变，也不作为
插件的数据源。插件存的是额外的一份记录。**

所以插件拿到的是**实时事件**（`Feed.zig`），不是核心那份文件的尾巴。
一句话的三个推论，下面每一节都是在展开其中之一：

- 核心的轮转、布局、保留策略随便改，不牵动任何插件——这个方向的耦合被
  彻底切断了，`Archive.zig` 现在不认识任何路径、不打开任何文件
- 插件掉线只丢它自己那份，核心记录照样完整；丢了多少被数着并且说出来
  （`Feed.Subscription.Stats.dropped`），一份假装完整的副本比一份说得
  出自己缺了什么的副本更坏
- 终端内容天然没有「一个文件一个偏移」可跟读，用实时事件两边才是同一套

**从前不是这样。** 插件曾经靠游标跟读 `chat/chat.jsonl`，代价是核心存储
同时也是插件的数据源：动一次轮转就要动 `Tail`/`Mark`，而插件手里那个位置
是一个核心随时可以 `rename` 掉的文件里的字节偏移。买到的是「插件一条不丢」，
付出的是整个设计。

## 两种形状：流与记录

本地写的是两份，用途不同，边界也不同。**分清这两个是读懂这一章的前提。**

| | 路径 | 给谁 | 边界 | 谁读它 |
| --- | --- | --- | --- | --- |
| **流** | `chat/chat.jsonl`（+`.1`） | 机器 | 8MB 轮转，留两代 | **只有核心自己**（`ChatLog` 的回填比对） |
| **记录** | `chat/<群>/<日期>.jsonl` | 人和 AI | 按天，**什么都不删** | `group_history`、`less`、`grep`、`jq` |

两份是同一次 `ChatLog.append` 里写下的**同样的字节**——记录拿的就是流刚写完的
那一行，不是第二次渲染，所以不存在两个渲染器漂移的问题。

**更完整的是记录，不是流。** 这一条容易说反：流会轮转，第三代是被 `rename`
覆盖掉的，真的没了；记录一行都不删。所以「记录坏了就重放流重建一遍」这句话
**只对最近 16MB 成立**，本章不做这个承诺——写下一个兑现不了的安全网，和
[gaps.md](gaps.md) 里骂 pg 后端是同一类错。

### 为什么是「群 + 日期」

**群是人脑子里的单位**（「昨晚那摊 Kairos 的活」），**日期是唯一天然有界的
东西**——一个群能活几个月，一天不会。按大小轮转产生的边界对人没有任何意义：
没人说过「我要看第二代日志」。

仍然是 JSONL、一行一条、字段不变。理由不是省事，是**两边都读得动**：人用
`less`/`grep`/`jq`，AI 用 `group_history` 或者直接 `cat`。任何需要先装一个客户端
才能看的格式，都会重蹈 pg 后端的覆辙。

### 群名怎么进路径

`%XX` 单射编码：`[A-Za-z0-9._-]` 之外的每个字节编成 `%XX`，**开头的 `.` 也编掉**
——一条规则同时干掉 `.`、`..` 和隐藏目录，而不是三个特例。`kairos-15r` 原样不变。

**单射是要求，不是讲究。** 把碍事的字节换成 `_` 更短，但那会让 `a/b` 和 `a_b`
落进同一个目录，两个群的记录悄悄交织，而没有任何地方说过这件事。

`Chat.isValidName` 本来就把群名限死在 48 字节的 `[a-z0-9-]`，所以走模型进来的
东西一个字符都用不上这套编码。它防的是**没走模型进来的**：手改过的日志里读回
的一行，或者绕过模型的调用者。**一条用别人的字符串拼出来的路径，不该依赖另一个
文件里做过的检查。**

### 一天之内超限：开续篇，不轮转

日期文件超过 8MB 就写 `2026-08-28.part2.jsonl`、`part3`……**什么都不移开、
什么都不覆盖**，边界仍然落在这一天之内。这个上限约束的是「一个人 `less` 打开的
单个文件有多大」，**不是磁盘占用**。

**记录是无上界的**，这就是「什么都不删」的字面意思。开发这套东西的机器上两周
攒了 2.8MB，约合 70MB/年。这个量级需要的是写明白，不是加机制。

### 记录落后了怎么办：每次启动测一次

`ChatLog.open` 末尾会比一次「记录走到哪」和「流走到哪」，落后就把差的那一截从
流里重放进来。这一次比对同时是**升级迁移**（老装机的记录为空，930 条一次灌进去）
和**故障自愈**（某次写记录失败留下的缺口）。

- 判据是精确的而不是启发式的：两份是同一次调用里按 seq 顺序写的，流在前，所以
  **记录缺的必然是一个后缀**，「记录的最高 seq」就是缺口的起点
- 稳态代价是每个群目录一次 64KB 读，什么都不写
- **不用标记文件**。「已经做过了」这种标记本身会撒谎（写完标记之后崩、拷贝到
  另一台机器、手工删过文件），而一个从文件本身量出来的数字不会
- 量不出来时（记录里有内容但读不回最高 seq）**整个跳过回填**，不当成 0。当成 0
  会把已有的全部再灌一遍，而**重复的记录没有任何东西能修**，短一截的记录下次
  启动就补上了

**写记录失败绝不会让 `append` 失败。** 顺序是先流后记录，记录那一半的任何错误
只落一条 warn。理由：流是发 seq 的那一份、也是回填要比对的那一份，为了「更好读」
引入的东西不该能让消息真的丢。这不是「吞掉错误」——缺口下次启动会被上面那次
比对发现并补上。

## 为什么这一条是整个设计的地基

反过来的做法很自然：消息来了，写数据库。但那样一来**耐久性就依赖插件**
——数据库连不上、凭证过期、插件崩了，消息就丢了，而你不会立刻发现。

现在 `$XDG_STATE_HOME/polter/chat/chat.jsonl` 是同步写的，写完才算数，
**而这件事跟插件没有关系**：`ChatLog.append` 里没有一行是为插件写的，它
不知道有没有人在听。写完之后宿主把这条消息作为一个**事件**交给通道
（`App.logChat` → `Feed.publish`），谁订阅了谁收到一份拷贝。

### 通道：`Feed.zig`

- **一个事件，多个订阅者，各拿各的一份拷贝。** 没有共享位置，一个插件读
  到哪跟另一个插件无关
- **发布者绝不被拖住。** `publish` 不会失败、不会等待、不会返回错误：它把
  拷贝丢进每个订阅者自己的有界队列就返回。慢的插件不可能变成敲键盘的延迟
- **有界，满了丢最老的并计数。** 一个插件是「额外的一份」，它背后的队列
  绝不该成为 Polter 吃光内存的理由。丢掉多少被数着（`Stats.dropped`），
  `Archive` 每出现新的缺口就 warn 一次
- **轮询，不唤醒。** 读的那一侧睡半秒再看一眼。半秒的入库延迟没有人感觉
  得到，写者线程上的一次调度往返有

### 于是（和从前哪里一样、哪里不一样）

- **插件卡住** → 不产生背压，我们只是不确认。**和从前一样**
- **数据库连不上** → 同上，恢复后接着往下走。**和从前一样**
- **插件挂了一小时** → **和从前不一样**：它丢了这一小时。它自己那一份
  有个洞，**核心的记录一个字都不缺**——而被人和 AI 读回去的正是核心那份，
  这才是要紧的一半

**「一条不丢」曾经是买来的，价钱是让插件去读核心的文件。** 那个耦合的
真实代价是：核心的存储从此不能自由演进，而终端输出那一路根本没有一个
「文件加偏移」可以跟。所以这一条被换掉了，换掉的时候把它明说出来，而不是
留一个「它其实会丢」的暗坑。

**仍然不需要重试队列，也不需要第二个缓冲区——订阅队列本身就是队列。**
取一批不等于取走：`take` 只是拷贝出来，插件确认之后 `commit` 才真的丢弃。
所以插件说「现在不行」、或者拿着一批死了，代价只是同一批再来一次。

这也是[通知那次](supervisor.md)教训的推广：**发出去不等于送达，确认才算。**
通知那边的做法是"交付后仍持有，读到才清"；这里是"插件确认写入后，队列
才丢弃"。同一条道理的两种形态。

## `seq` 是什么：日志自己的序号，也是插件的幂等键

**现有的 `seq` 不能当游标用。**`Chat.Message.seq` 是**每群一份、进程内
从 1 开始**的计数器（`src/poltergeist/Chat.zig:143`）。它服务的是「这个
成员看到哪儿了」，而重启之后它从 1 重新数 —— 同一个日志文件里就会有两
条 `build/seq=7`，插件按它去重会去错，往回翻会翻到上一次运行的消息。

所以日志带**自己的序号**：全局、单调、跨群共用，`ChatLog` 打开时读最后
一行恢复。写下来的一行长这样：

```json
{"seq":10432,"at_ms":…,"group":"build","from":"0x…","author":"…","text":"…"}
```

这个 `seq` 是系统里**唯一的号**：事件带着它、插件确认它、`group_history`
按它翻页。群内那个 `seq` 原样不动，继续只在 `Chat` 内部当成员游标用。

**它是身份，不是位置。** 插件拿到它不是为了拿它回文件里定位——插件根本
不打开那个文件——而是因为**幂等有了一个可以挂的东西**：一个 pg 后端的插件
可以把它做进主键，`ON CONFLICT (stream, seq) DO NOTHING` 之后同一条消息见
两次仍然只有一行；随构建装出去的 `archive` 更简单，它记着自己确认到哪，
`seq` 不比那个大的直接跳过。
正因为它是核心记下这条消息时盖上去的号，所以**日志没开就没有这个号**，
此时什么也不发布（`App.logChat`）。

**内存里的消息也要带上它。**`Chat.Message` 加一个 `log_seq`，由宿主在
`append` 返回后填。不这么做，界面翻到内存边界时手里只有群内 `seq`，没
有任何东西能和日志对齐，只能靠比对文本去猜接缝 —— 那是会接错的。
`log_seq == 0` 表示这条没落盘（日志被关掉了），此时往回翻直接到底。

## 生命周期按种类分

|          | 生命周期     | 为什么                                     |
| -------- | ------------ | ------------------------------------------ |
| `notify` | 一次一进程   | 稀疏、突发；崩了只影响那一条               |
| `archive`| **常驻**     | 连续，而且要握着数据库连接                 |

通知一小时几条，每次起一个进程无所谓。存档是连续的：每条消息起一次
`psql`（建连 + TLS 握手）显然不行。

**常驻的代价是要管进程**：会挂、会卡、要重启、退出时要收。杀进程那套
（`std.posix.kill` + 超时 + 防 pid 复用的锁）通知插件已经有了，抽成
`reap.zig` 给两种生命周期共用。常驻多出来的是：每次重起换一个子进程
（`rearm`）、插件每答一次就把 deadline 往后推（`allow`）、关机时把
deadline 改成"现在"（`hurry`，而且**是黏的**——之后再起的子进程也不给宽限，
否则关机前一微秒 fork 出来的那个能把整个退出流程拖满一个超时）。

### 协议

常驻插件的 stdin 是一条**行分隔的 JSON 流**，一行一批：

```json
{"cursor":1042,"through":1049,"messages":[{"seq":1043,"at_ms":1786819271275,"group":"build","author":"worker-core","text":"…"},{"seq":1047,"at_ms":1786819274901,"group":"build","author":"…","summary":true,"text":"…"}]}
```

`cursor` 是**这一批之前**已确认到哪里（**这一次运行之内**，见下），
`messages` 里每条带自己的 `seq`。
`summary` **只在为真时出现**（`Archive.writeBatch`），缺失即假。**没有 `from`
字段**：那是终端 id，插件拿它没用，而它会把"哪个窗口说的话"带出机器。现在
连「留出来不写」都不必了——事件类型 `Feed.Chat` 里根本没有这个字段。

单批上限 256 条 / 256KB（`max_batch` / `max_batch_bytes`）。**批次是从订阅
队列里取的，取不等于取走**：确认之前它一直在队列里，所以「重发」不是重读
文件，只是没有 `commit`。

**握手行**（`renderHello`）在流的最前面，整个会话只出现一次：

```json
{"hello":1,"plugin":"archive","cursor":1042,"groups":["*"],"params":{"dir":"/Volumes/backup/polter","sign_key":"已解析出来的明文"}}
```

`params` **只在这里出现**，批次行里没有，插件必须在握手时记住它。里面的值
已经过 `secret.resolve` 解析，插件拿到的是真 DSN 而不是 `cmd:…`。每次子进程
重起都重新解析、重新握手——**一个锁上的密码库因此在下一次
重起时就会失败，而不是永远用着半年前取出来的那份**。

**握手也要回一行确认，和批次一样。**宿主在写这一行**之前**就把期限装上了
（`Archive.zig` 里 `renderHello` 前面那句 `allow(timeout_ms)`），写完就等一行
回答；`parseAck` 解析不出对象是失当（当场杀），`ok` 为 false 是「现在还不行」
（耐心重试）。**什么都不回是最糟的一种**：`timeout_ms` 到点被杀、退避、重起、
再被杀，外面看是一个每 `timeout_ms` + 退避重复一次的重启循环，插件自己看却像
在闲等下一批。随构建装出去的 `archive` 有一版就是这样——它读了握手就直接去等
批次了。挡住这件事的回归测试在 `Archive.zig`（「the archive plugin we ship
answers the greeting the host really writes」）：它拿 `renderHello` 真正写出来
的字节去喂**我们真正装出去的那个脚本**。手写一行握手喂进去只能证明插件和写测试
的人想的一样。

握手行里的 `cursor` **在一次新的 Polter 运行里恒为 0**：订阅从建立的那一刻
开始，宿主手里没有任何更早的东西，也没有一个文件记着上次到哪。这不是丢了
信息——更早的消息在核心的记录里，而插件自己的库里存着它上次存到哪。

**心跳**：一行 `messages` 为空、`cursor == through ==` 已确认位置的批次，
默认每 30 秒一次（`heartbeat_ms_default`，`:56`）。宿主对心跳答复的判据
**只有一条：`parseAck` 不能返回 null**——能解析成 JSON 对象
就算数，`ok` 的值根本不读。写下来是因为它是实打实的许可：**插件可以不碰
数据库就答一次心跳**，心跳要的是"进程还在、还在听"，为它探一次库会把一次
网络抖动变成一次重启。

`through` 是**这一批看过的最后一个 seq**，不一定等于最后一条 `messages`
的 `seq`。它是为群过滤加的：一个只要 `build` 的插件，遇到一整窗都是 `ops`
的流量时，手里没有任何东西可以确认，队列就永远清不掉。`through` 让它能说
"我看到 1049 了，中间没列出来的不归我"。`groups` 是 `["*"]` 时 `through`
恒等于最后一条的 `seq`；忽略 `through` 只确认最后一条也仍然正确，只是会把
被过滤掉的尾巴白看一遍。

插件写回一行确认，**上限 64KB**（`ack_max_bytes`，`:60`）：

```json
{"ok":true,"cursor":1043}
```

**确认里带游标而不只是 `ok`**：插件可能只写成功了前半批。带上它实际
落库到哪里，剩下的下一轮自然重发。

#### 批次确认怎么判（`Archive.advance`）

| 插件回的 | 怎么判 | 为什么 |
| --- | --- | --- |
| `ok` 缺失或为假 | 原地不动，下一轮重发；连续 3 次（`max_soft`）之后退避 | 没说成了就是没成，和一次性插件看退出码同一条规矩 |
| `ok:true`，`cursor` 缺失 | 整批收下，`to = through` | 让最简单的插件保持最简单：读一行，回 `{"ok":true}` |
| `ok:true`，`cursor` **大于** `through` | **杀掉重起** | 它没有第二条通道能拿到这些事件，所以不可能存过没给它的东西。认下这个数，中间那些消息会被从队列里丢掉而没有任何人存过，且没有任何迹象——正是这套设计要防的那一种失败 |
| `ok:true`，`cursor` **小于**批前那个值 | **杀掉重起** | 批次里往回等于凭空推翻一件已经确认过的事。想往回只有握手那一个场合 |
| `ok:true`，`cursor` **等于**批前那个值 | 当作"原地不动"，走退避 | `ok:true` 加"我还在原地"，信息量和 `ok:false` 一样。当成进展会清零软失败计数并立刻再来一轮，而"没有新消息"那条才是带 sleep 的路——于是一个把收到的 `cursor` 原样抄回去的插件（最容易写错的一种）能让这条线程满速空转 |

#### 握手确认怎么判

| 插件回的 | 怎么判 | 为什么 |
| --- | --- | --- |
| `ok:false` | **不是失当**：杀掉子进程、退避重起 | 连不上库的插件在这里说出来，拿到的是和"根本起不来"一样的耐心重试 |
| `ok:true`，带 `cursor`（任意方向） | **收下当情报，记一条 info，什么都不改** | 它在陈述自己的状态——"我的库已经到 5000 了"。宿主没有东西可以重放：它手里只有这个订阅还没被确认掉的那些事件，一条不多一条不少。往前也不是失当——**每一次重启，插件的库都必然跑在这一次运行的游标前面**，把它判成失当会让所有正常插件被杀 |
| `ok:true`，无 `cursor` | 同上，什么都不改 | |
| 任意 | 非 JSON、一行超过 64KB、stdout 关闭 → 杀掉重起 | |

> **这一格是这次改动里唯一变了含义的协议行为。** 从前 `cursor` 小于宿主
> 的值意味着「回拨并重放」，那只在宿主读的是一个能 seek 的文件时才成立。
> 插件那一侧不用改：`archive.py` 照旧可以把自己的位置说出来，宿主照旧不会
> 因此杀它，只是不再重放。

#### `timeout_ms` 界定的是一次交换，不是一整段会话

**写一行 + 读一行，就这么多。**两次交换之间宿主调 `unhurried()`
把 deadline 撤掉，因为常驻插件的正常状态就是长时间无事可做。所以
`timeout_ms` **不需要覆盖心跳间隔**，也不该按"一整晚"去设——它该是"这个
后端做完一批最慢要多久"。把它写成一段会话的预算，会让每个插件作者都设得
高出一个量级，而那正好废掉了超时。

#### stdout 是协议通道

插件写到 stdout 的**任何非确认行都会被判成失当并杀掉进程**。所以一个要
起子命令的插件，必须把那个子命令的 stdout 接到管道上自己读，**绝不能让它
继承**。stderr 是继承的，落进 Polter 的日志——那才是插件说话的地方。

### 游标存在哪：不存

**没有游标文件。**`<key>.cursor` 连同 `Cursor.zig` 一起没有了——它存在的
全部理由就是记住跟读到日志的第几行，而现在没有人在跟读任何文件。

它从前必须放在 state 而不是 config，理由是「它是**这台机器**这个日志文件
里的一个位置」。**这句话本身就是那个耦合的自白**：一个插件的进度，被表达
成核心某个文件里的偏移量。现在插件的进度只有两种存在方式，两种都不在
Polter 这边：

- **一次运行之内**：订阅队列里还没被 `commit` 掉的那些事件，在内存里
- **跨运行**：插件自己那边已经有哪些 `seq`——那是插件自己的事，而 `seq`
  是身份，所以它有办法自己判重（数据库里做成主键，文件里比一个数）

所以 Polter 关掉时什么都不写，起来时什么都不读。**一个不存在的文件不会
撒谎**，而一个被 dotfiles 同步到另一台机器上的游标文件会。

## 一个插件，多个后端

**「聊天存档」是一个插件，落到哪儿只是它的一个参数。**

不是 `archive-pg`、`archive-mysql`、`archive-minio` 三个。理由有两条：

1. **用户视角**：你要的是"把聊天存下来"这一件事，不是在三个名字相近的
   插件之间挑
2. **工具面不该膨胀**：MCP 生态的教训是装 3–5 个封顶，多了 schema 挤爆
   上下文、agent 反而变笨。插件数量同理

配置形态：

```json
{
  "enabled": true,
  "params": {
    "dir": "/Volumes/backup/polter",
    "sign_key": "cmd:op read op://Private/polter-archive"
  }
}
```

以后加 mysql 是**给它加一个后端**（多一个参数取值），不是多一个插件。

## archive：这个插件长什么样

`plugins/archive/`，随构建装进 resources，用户不需要装任何东西，而且**预装即开**
——目录里带一份 `settings.json`（`{"enabled": true, "params": {}}`），用户配置目录
里那份压过它，包括写着「关」。为什么这不是插件模型里的一个特权位，见
[boundary.md](boundary.md) 第二节。

**它写的是额外的一份。**核心的流和记录不因它开没开而改变，**也不给它供数据**：
它订阅的是 `Feed.zig` 上的实时事件，不认识任何路径。所以它掉线只丢它自己那一份。

### 按天，不按群

核心的记录是 `<群>/<日期>.jsonl`，回答「那摊活说了什么」。这一份是
`<日期>.jsonl`，**所有群一条时间线**，回答「那天晚上按顺序发生了什么」。

这个差别是承重的。[gaps.md](gaps.md) 里那条反对——插件不该在另一个路径上再写
一份形状一模一样的平文件，那是把核心已经在做的事重做一遍——**依然成立**，
`chat-archive` 的 `file` 后端就是死在它上面的。避开它的办法不是不写，是**写
另一种切法**：一个 `tail -f` 就能看完一晚上的文件，核心那边没有。

落点缺省是 `~/.local/state/polter/archive`（有 `XDG_STATE_HOME` 就在它下面）。
**那是一个起点，不是兜底**——「本地有没有一份能读的记录」永远是核心的事，
和这个插件开不开无关；缺省存在只是为了让「把它指到同步盘/移动硬盘上」是改一个
值，而不是先想一个路径出来。

### python3，只用标准库

不用 pip、不用 venv、不用第三方库。理由按重要性：

1. **它必须真的解析 JSON，而 shell 做不对。**要读的是 `messages` 数组——嵌套
   对象、转义引号、CJK 的 `\uXXXX`、正文里可能含 `}`。用 `sed` 读它必然在
   某些输入上读错，而**读错的后果是回一个它其实没存的 cursor**，正是整套
   确认机制要防的那个静默的洞。
2. `jq` 能救 shell，但它是一个依赖，而且不在 stock macOS 里；`python3` 在。
3. 只用标准库意味着没有版本漂移，插件被拷到别人机器上仍然能跑。

### 先答应，再说别的

握手行被当成第一条要确认的行：`greet()` 解析它、把落点目录建出来，然后
**立刻回一行** `{"ok":true}`；建不出来就回 `{"ok":false}` 再 exit 2——宿主
读到 false 是「等会儿再试」，而**读不到任何东西是「它挂了」**。

### 确认之前先落盘

一批写完 `flush` + `fsync` 再回 `{"ok":true}`。**确认是一句承诺，而关于还在
缓冲区里的字节的承诺，这个进程自己退出一次就能毁掉。**写到一半失败时只确认
已经落盘的那一条（`{"ok":true,"cursor":N}`，那个 N 取自这一批的 `messages`，
按定义 ≤ `through`），一条都没落就回 `{"ok":false}`——**宁可重发，绝不撒谎**。

`seq` 还兼作去重键：宿主会重发一个没收到确认的批次，插件记着自己确认到哪，
`seq <= acked` 的直接跳过。这就是「重复是常态，去重是你的事」在文件后端上的
全部实现。

### `sign_key`：可选的凭据

填了它，每行带一个 HMAC-SHA256，签的是这一行**除 `hmac` 外**的规范形式
（键排序、无多余空格）。这不是加密——正文照样是明文——而是**让被改过的副本
说得出自己被改过**。这一份常常落在比 state 目录更没人管的地方（同步盘、移动
硬盘、公司共享），而一份没人能验的记录，在真需要拿它当证据的那天等于没有。

**它是清单里唯一标了 `"secret": true` 的参数**，因为拿到这个密钥的人可以改写
存档再重新签一遍。工具面据此拒绝往里写明文（见 [mcp.md](mcp.md)）。它同时是
本仓那条「工具面拒绝明文凭据」的安全测试**唯一的验证对象**
（`src/build/SharedDeps.zig` 把这份清单编进二进制，`rpc.zig` 里那条测试读它）
——所以这个标注掉了，不只是这个插件变松，是那条规则失去被检验的对象。测试自己
也会在名单空掉时失败，理由写在那条测试里。

### 不依赖任何外部东西的自检

```console
$ ./archive.py --self-test
ok
$ echo "EXIT=$?"
EXIT=0
```

全部在一个 `mkdtemp()` 之下跑，跑完不留东西。逐条断言：整批确认、重发的批次
不重复写、心跳不写文件、群过滤后的 `through` 照样推进、跨午夜的一批分进两个
文件、写到一半只确认落盘的那一条、一条都没落回 `{"ok":false}`、签名能被校验
也能因为改了正文而对不上、以及**清单里写的缺省值和代码里用的是同一个**。

## 工具面对存档插件做什么，不做什么

| 动作 | 发生什么 |
| --- | --- |
| `plugin_configure` 改参数，且实例在跑 | **写文件，不重启**。参数下次 Polter 启动时生效，回复里明说 |
| `plugin_configure` 打开一个没有实例的存档插件 | **起一个**，起之前按 key 查重 |
| `plugin_test` | **什么都不起**，只报 `status()` 与"为什么没在跑" |

理由：**两个实例是两个订阅者**，同一条消息会被完整地存两遍，而且两个
实例各自握着一条数据库连接、各自答一套心跳，谁也不知道另一个存在。查重有两道——`App.scanPlugins` 按 `manifest.key` 去重
（两个目录声称同一个 key 时，后来者被 warn 掉），`App.startArchive` 起之前
再按 key 查一次现有实例。两道都不能省：前一道防的是清单，后一道防的是时序。

另一半理由在 [mcp.md](mcp.md)：协议里根本没有干跑通道，而**宿主没有任何
办法强制别人写的脚本干跑**——加一个 `dry_run` 字段只是加一个作者可以不理的
字段，那是宿主兑现不了的承诺。

## 往回翻

记录里存着全部，所以**往上翻不需要任何插件**。

`group_history(group, before_seq, limit)` 现在就在工具面上：它从记录倒着
读（一个群的日期文件由新到旧，一天之内续篇在前），`before_seq` 是上一节那个日志序号，回来的一批按时间升序，和 `group_read`
共用同一个 `messages` 形状，读的人一套解析代码就够。

**这一批的 `seq` 恒为 0。**日志没有记过群内序号，所以这一批只能拿 `log_seq`
翻页；把 0 或者任何编出来的号当成 `group_compact` 的 `through` 递回去，删掉
的会是另一段。界面滚到内存边界（当前保留最近 500 条）时，拿手里最老那条的
`log_seq` 往下要，接缝是精确的，不靠比对文本；`more` 为 false 就是到底了。

`group_history` 读的是**记录**那一份，不是流。两个好处：一个安静的群不再需要
先读过别人几 MB 的流量才能被找到（它自己的天是它自己的文件），而且能翻到的
深度不再被上一次轮转碰巧切在哪里决定。

一次调用有 2MB 的扫描预算（`history_scan_bytes`）。翻到一个很大的日期文件中间
时，它会**返回空页并且说 `exhausted = false`**——意思是「还没到底，再问一次」，
这是诚实的答复，而不是丢失。

**插件在这里的角色是「送到别处去」，不是「本地留一份」。** 本地这两份都不依赖
任何插件开没开。装了存档插件之后多出来的是：这些内容也在数据库/共享盘/公司内网
里有一份，可以从别的机器查、可以活得比这台机器久。

## 权限声明

**第一天就要有，不能等生态起来再补。**

2026 年出过真事：Semantic Kernel 的 prompt injection 打到 host RCE；
Claude Code 的 Hooks 被报出配置注入，配套 CVE 可通过重定向 API 请求偷
key。插件是别人写的代码跑在你机器上——**「这个插件能读什么、能跑什么」
必须能被声明，也必须能被审计。**

`plugin.json` 里声明，声明之外一律拒绝：

```json
{
  "key": "archive",
  "kind": "archive",
  "wants": {
    "groups": ["*"],
    "network": false,
    "exec": []
  }
}
```

**没有 `wants` 的清单等于什么都不要**，而且不是悄悄不干活：存档插件因此
根本不启动，并且被点名警告，连该补的那一行都抄给用户。反过来把缺省当成
`["*"]`，会让一份什么都没声明的清单拿到全部群——权限声明存在的意义当场归零，
而这恰恰是最需要被声明的那种能力。

对 `notify` 没有影响：今天没有任何东西按群过滤通知，旧的通知清单一个字
都不用改。而 `archive` 是本轮才有的种类，世上没有旧的 archive 清单要兼容。

**只有 `groups` 是真的被强制的**，而且强制得彻底：喂出去的批次就是按这份
清单筛出来的，插件没有第二条通道能碰到这些事件——它也不再能碰到日志文件，
那条通道整个不存在了。`network` 与 `exec` 是声明与
告知——给装之前的人读，给审计当依据，**不是沙箱**，也没有任何东西阻止插件
去联网或者去起进程。`"network": false` 绝不能被读成"它上不了网"。

这既是安全，也是**差异化**：Warp 让出来的信任市场是免费的。

## 三条红线

1. **不为插件牺牲输入延迟。** 插件全部独立进程，绝不进渲染路径。
   Ghostty 内核的性能是唯一不能亏的资产
2. **不做 block 模型。** 要结构化输出就用富渲染 + MCP 暴露语义，
   不改终端契约
3. **不追数量。** 质量、可发现性、默认关闭，都比数量重要
