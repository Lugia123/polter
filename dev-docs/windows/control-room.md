# 总控台在 Windows 宿主里放哪、用什么画（方案）

这是方案，不是已经做成的东西。**放哪已经定了：标签栏里的一个标签页，可以拖出去（§2）。**总控台是什么见 [../poltergeist/control-room.md](../poltergeist/control-room.md)；
它的纯逻辑层已经有了（`windows/control-room`，见本文末尾「已经有的」）。下面每一条判断都写了依据是
读代码还是量过；**没有一条在 Windows 上跑过**。

## 1. 宿主现在的界面是怎么做的

读 `windows/host/src/` 得到的，按「总控台会借用哪一种」排：

| 界面 | 文件 | 怎么画 | 和总控台的关系 |
|---|---|---|---|
| 标签栏 | `strip.rs` | 宿主自绘：GDI 画进内存 DC 再贴到窗口；每次重画都从模型取快照（`tabs::strip_snapshot`），不留第二份标签列表；鼠标一律解析成 `TabId` | 总控台如果是一个标签页，就画在这里面 |
| 标签页的内容 | `tabs.rs` | 一个 `Tab` 就是一棵分屏树加一组 `Pane`，每个 pane 是一个 libghostty surface（OpenGL 子窗口） | **没有「不含终端的标签页」这个概念** |
| 设置窗口 | `settings_win.rs` + `roles_ui.rs`、`general_ui.rs`、`plugins_ui.rs`、`projects_ui.rs` | 一个**不属于任何终端窗口**的顶层窗口，启动时建一次，关掉是隐藏；内容是 GDI 自绘加标准控件；规则全在 `polter-settings-shell` 里，能在 mac 上测 | 结构上最像总控台 |
| 截图工具栏与覆盖层 | `shot.rs` | GDI；每显示器 DPI；圆角用 `CreateRoundRectRgn`；规则在 `polter-shots` | 圆角、亮暗的现成做法 |
| 四个小牌子 | `hud.rs` | 不抢焦点的小窗口，画核心给的东西，不自己判断 | 「只画核心说的」的现成例子 |
| 快速终端 | `quick.rs` | 滑入滑出用 `SetTimer` 16 ms 一帧加一条缓动曲线 | 动画的现成做法 |
| 命令面板 | `palette.rs` | 输入框用原生 `EDIT`，因为它自带输入法文档 | 「回一句」的输入框照此 |
| 插件自己的页 | `plugin_page.rs` | WebView2，运行库可能不在机器上，所以按路径延迟加载 | 不用它，见 §3 |
| 群聊页 | `tabs.rs` 的 `NewTabWith` | **是一个终端**：新开一个标签页，里面跑 `polter +chat`（一个 TUI） | 总控台第一期右栏的群聊、任务页签可以先借它 |

几条和选型直接有关的事实：

- **没有 Direct2D / DirectWrite。** `windows/host/Cargo.toml` 的图形特性只有 `Win32_Graphics_Gdi`、
  `Win32_Graphics_Dwm`、`Win32_Graphics_OpenGL`。所有文字是 GDI 的 ClearType。
- **进程是每显示器 DPI 感知的**（`DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2`），窗口各自处理
  `WM_DPICHANGED`。
- **亮暗**：标题栏用 `DWMWA_USE_IMMERSIVE_DARK_MODE`（`shell.rs`），截图工具读注册表的
  `AppsUseLightTheme`。没有一处统一的「现在是亮还是暗」。
- **通知**走通知区图标的气泡（`notify.rs`，写明了为什么不用 WinRT 的 toast）。任务栏按钮上的数字
  还没有任何代码。
- **宿主的测试只能在 Windows 上跑**，所以能出错而看不出来的规则都被搬到了旁边的 crate 里。

## 2. 定了的方向：标签栏里的一个标签页，可以拖出去

**用户定的（2026-10-12，原话）：「windows行为和mac保持一致，也是标签栏，但也可以拖出去」。**
这一节此前推荐的是「先做独立顶层窗口，标签页留到后面」，理由是 `Tab` 的定义就是一棵终端的分屏树。
那个难处是真的，现在正面解决它；此前的推荐和它的两条退路（独立窗口、标签栏上一粒假按钮）作废。

下面的行号都是 `cr-win` 这棵树在 `4f6e507ed` 上的。

### 2.1 标签页模型怎么容纳一个没有终端的标签页

**改法：`Tab` 的内容变成枚举，原来的三个字段从 `Tab` 上消失。**

```rust
pub struct Tab {
    pub id: TabId,
    pub body: Body,          // 原来的 tree / panes / focused 搬进去了
    pub title: String,
    // 颜色、角色、被护住、被按住、persona、cwd、title_override 留在原处（见下）
}

pub enum Body {
    Terminal(Terminal),      // 一棵分屏树
    ControlRoom(RoomTab),    // 总控台：一个自绘的子窗口，没有 surface
}

pub struct Terminal { pub tree: Tree, pub panes: Vec<Pane>, pub focused: PaneId }
pub struct RoomTab  { pub hwnd: isize }   // 面板的子窗口；全应用至多一个
```

为什么这样而不是给 `panes` 留空：留空的话今天这 87 处一处都不用改，全都继续编得过，每一处的答案就是
「碰巧」——焦点落空、关窗口不问、UIA 给出一个 `PaneId(0)` 的文档。字段搬走以后 **`tab.panes`、
`tab.tree`、`tab.focused` 这三种写法不再存在**，87 处全部编不过，逐处重新回答；以后新写的代码也拿不到
一个「看上去是终端」的标签页。

各处通过四个取法拿东西，每个取法里面是一条**写全了两个分支、没有 `_ =>` 的 match**，名字说的是它回答的
那个问题：

| 取法 | 回答什么 | 总控台标签页的答案 |
|---|---|---|
| `tab.panes()` / `panes_mut()` | 这个标签页里有哪些终端 | 空（它确实一个都没有） |
| `tab.terminal()` / `terminal_mut()` | 给我它的分屏树，我要分屏 / 缩放 / 调整 | `None`，调用处必须写出没有时做什么，并打一行日志 |
| `tab.front()` → `Front::Pane(&Pane)` / `Front::Room(hwnd)` | 这个标签页在前面时，键盘和内容区给哪个窗口 | 面板的子窗口 |
| `tab.kind()` → `Kind::Terminal` / `Kind::ControlRoom` | 要按种类分开走的（关闭、改名、搬窗口、UIA、菜单） | 调用处 match，两支都写 |

`Body`、`Front`、`Kind` 在宿主里一律穷举 match。`windows/tools/a-tab-body-is-matched-in-full.py` 读
`windows/host/src/*.rs`：对这三个类型不许出现 `_ =>`、`Some(_) =>`、`if let`、`while let`、`matches!`、`let … else`，
`Tab` 上也不许再出现 `tree` / `panes` / `focused` 字段。以后加第三种标签页时，每一处都是编译错误，
编译器点名。

**做的时候编译器数出来的是 83 处，分在四个文件里**，比下面这张表多三个文件：`divider.rs` 6 处（分隔条
按前面那个标签页的树摆、拖分隔条改树）、`hud.rs` 2 处（按 surface 找 pane 的窗口）、`project_ui.rs` 2 处
（存项目读树）。下表动手前只数了 `tabs.rs` 和 `uia.rs`，漏了它们——这正是把字段搬走而不是靠搜索的理由。
三处的答案：分隔条在总控台标签页上要的是「一条都没有」（不是提前返回，前一个标签页留下的要收走）；
`hud.rs` 归「反查」那一类；存项目对它无可存。

### 2.2 「可以拖出去」

**宿主现在的事实（读 `strip.rs` 得到）：鼠标拖标签页只能在本窗口的标签栏里换位置**（`on_mouse_move` →
`tabs::move_tab_to`）。把标签页拿出去成为新窗口只有一个入口：动作 `move_tab_to_new_window`（标签页右键
菜单、命令面板、键绑定），落到 `tabs::move_tab_to_new_window`——建一个新的框架窗口，把那个标签页从一个
窗口的单子里拿出来放进另一个，再把它的子窗口 `SetParent` 过去。**没有「用鼠标把标签页拖出标签栏」这个
手势，也没有「把标签页拖进另一个窗口」；对任何标签页都没有。**

所以「可以拖出去」分两步交：

1. **这一块**：总控台标签页支持「移到新窗口」这个动作，和终端标签页走同一条路（上表「搬到新窗口」）。
   窗口里只有它一个标签页时拒绝，理由和终端标签页一样：它已经在自己的窗口里了。
2. **后一块，对所有标签页一起做**：鼠标把标签页拖出标签栏（竖直方向离开超过一个标签栏高度）松手 → 在
   松手的位置开新窗口；拖到另一个窗口的标签栏上松手 → 并进那个窗口。这是标签栏的新功能，不是总控台的；
   放在总控台里单独做一份会得到「只有一个标签页能拖出去」的怪样子。**暂定**这样分；要不要第二步、
   先后顺序，等用户或总管表态。

与 mac 逐条对：

| | mac | Windows（这一块做成的） | 出入 |
|---|---|---|---|
| 全应用几个 | 一个（暂定） | 一个。规则是 `rules::trigger`：开着就切过去，不新建；宿主在建之前和建之后各在锁里查一次 | — |
| 打开在哪 | 当前终端窗口的第一个标签页；没有能放标签页的窗口时自己开一个窗口 | 发起的那个窗口的第一个标签页。Windows 的每个窗口都有标签栏，所以「自己开一个窗口」那一支只在一个终端窗口都没有时出现——那时进程要么已经退出，要么只剩设置窗口开着（`winid.rs` 里调 `polter_settings_shell::quits` 的那一处），而设置窗口里没有这个入口，所以到不了 | 少一支，原因写明 |
| 排第一是不是一直保持 | 只在创建时排第一，用户挪走不拉回来（暂定） | 相同 | — |
| 能不能关 | 能，不问（暂定） | 能，不问 | — |
| 再开回来 | 菜单、命令面板、键绑定，同一个核心动作 | 相同：`toggle_poltergeist_control_room`。从终端里按键 → 核心 → `cb_action`；菜单与命令面板直接调宿主的同一个入口；焦点在总控台上时走 `ghostty_app_key`（上表） | — |
| 再按一次开关 | 开着就切过去（不是关） | 相同；它在另一个窗口里时把那个窗口带到前面 | — |
| 拖出去以后是什么 | 一个只含它的窗口，系统的标签栏 | 一个只含它的窗口，带自己的标签栏和 `+`；按 `+` 在它旁边开终端标签页 | — |
| 还能不能拖回来 | 能（系统的标签页拖放） | **这一块不能**：没有跨窗口并入的手势。要回到原窗口：关掉它，在原窗口再开一次。第 2 步做了以后能 | 有，等第 2 步 |
| 关掉只含它的那个窗口 | 等于关总控台 | 相同，不问 | — |
| 关一个还有终端标签页的窗口，而它是其中之一 | 交给一个终端标签页去问 | 窗口的关闭本来就由宿主统一问一次（`close_all_tabs_of_asking`），它不贡献「忙」 | 做法不同，结果相同 |
| 打开时默认选中 | 第一个有 AI 的群 | 规则若还没进逻辑层，这一块留一个明确的未做标记：先用 `restored_selection`，没有就不选 | 等核心字段 |
| 重启后 | 回原来那组，选中还在 | 不会自动开着（宿主没有标签页恢复）；选中的群记着 | 有，见上表「会话」 |

### 2.3 右栏放真终端（方案与风险；同一窗口的情形已做，见 §10）

mac 的做法是「终端不离开它所在标签页的分屏树，搬的只是视图」（主文档 §12.5）。Windows 上照同一条原则：
**pane 仍然属于原标签页的树，借出的只是它那个子窗口摆在哪。** surface 一辈子绑在一个 `HWND` 上
（`windows/AGENTS.md`），所以搬的只能是这个窗口本身，不能换一个窗口装它。

分两种情形，难度差很多：

| 情形 | 做法 | 依据 |
|---|---|---|
| 总控台与总管的标签页**在同一个窗口** | **不改父窗口。** pane 的子窗口本来就是这个框架窗口的孩子；总控台在前面时，`layout` 把这一个 pane 摆进右栏的矩形并显示，其余照旧藏。还回去 = 不再摆。整件事是 `layout` 里的一条规则 | 读代码；每个 pane 都是框架窗口的直接子窗口（`create_pane`） |
| 在**不同的窗口**（总控台被拖出去了，或总管在另一个窗口） | `SetParent(pane, 总控台所在的框架窗口)`，还回去再 `SetParent` 回原窗口 | `move_tab_to_new_window` 已经对 pane 做同一件事。**它在真机上验没验过，`dev-docs/windows/status.md` 里没有找到记录**，按没验算 |

每个问题现在知道什么：

| 问题 | 现在知道的 | 风险 | 上测试机先验什么 |
|---|---|---|---|
| `SetParent` 行不行 | API 允许同一线程的顶层窗口之间搬子窗口；宿主已有一处这样做 | 没有真机读数 | 把一个在跑程序的标签页「移到新窗口」，看它还在画、还能打字、`stty size` 对 |
| 渲染上下文跟不跟 | `wgl.zig` 对那个 `HWND` 拿的是 `CS_OWNDC` 的设备上下文并一直留着；上下文绑的是窗口的 DC，不是父窗口。读代码的结论是跟 | 换父窗口后 DWM 对子窗口的合成、垂直同步的归属没有读数；测试机是 Server 2022 走 llvmpipe，和有显卡的机器可能不一样 | 上一条里顺带看有没有黑一帧、有没有停在旧画面；有显卡的机器上要再看一次 |
| 尺寸 | 平时分屏、拖窗口都在改 pane 的大小，所以改大小本身是通的 | `windows/AGENTS.md` 写着「surface 的窗口必须按最终尺寸创建，之后 `set_size` 修不回来」。那条说的是创建时；`status.md`（「仍未检验的是机制」那一段）写明「init 之后的 resize 追不上」这个机制**没证过** | 借出、还回各一次，在核心收尺寸的入口各记一行（mac 那一轮就是这么量的）：应当每次只有目的地的尺寸，没有中间值 |
| 焦点 | 点一下 pane，它的窗口过程自己拿焦点；`tabs.rs` 的 `focus_pane_at`随后把模型里的 `focused` 和 **`win.active`** 改成它所在的标签页 | **这是确定会出事的一处**：借出期间点右栏的终端，`win.active` 会被改成总管自己的标签页，总控台当场被切走。要改成：借出的 pane 拿焦点时不动 `active` | 逻辑放进 crate 先在 mac 上测（谁借着、该不该还、焦点算谁的，对应 mac 的 `ControlRoomLending`）；真机上点一下右栏再读 `active` |
| 输入法 | 输入法文档跟着拿到焦点的那个 pane 窗口走（`ime_set_window`） | 跨窗口时 TSF 的文档管理器是按线程的，按理不受父窗口影响；没有读数。`ShowWindow` 藏一个可见的 pane 会结束它正在进行的组字（`layout` 里那一大段注释），借出与还回都会藏 / 显 | 在右栏的终端里用中文输入法打一个词；组字进行到一半时切走总控台，看有没有半个音节被提交进终端 |
| DPI 不同的显示器 | `move_tab_to_new_window` 在两个窗口缩放不同时调 `surface_set_content_scale` | 借出要做同一件事，还回要调回去；漏了的样子是「字能看、大小不对、日志里什么都没有」 | 测试机只有一块屏，**这一条在那里验不了**；要一台双屏、两种缩放的机器 |
| 叠放 | 面板是自绘的子窗口，pane 是它的兄弟 | 两个兄弟窗口重叠时谁盖谁；面板重画会不会刷掉终端 | 面板带 `WS_CLIPSIBLINGS`，右栏那一块面板不画；看拖动窗口大小时有没有闪 |
| 原处那一格 | mac 画占位和「拿回来」 | 同一窗口的情形下原标签页本来就不在前面，看不到，不需要占位；跨窗口时需要 | — |
| 关闭、分屏、存盘 | 树没变，照旧 | 在借来的终端里按关闭键关的是谁：mac 关的是总控台标签页。Windows 上键到的是 pane，核心会对那个 surface 发关闭——关掉的是总管的终端。**要定**：照 mac（拦下来改成关总控台标签页）还是照现状 | — |

结论：**同一窗口的情形可以先做**（只动 `layout` 和焦点那一处，不涉及 `SetParent`），它的前三条风险都不
存在；跨窗口的情形要等上表第一、二、三行在测试机上有读数。

### 2.5 没有终端在前面时还能做什么：三类动作，和键盘的那张封闭的表

键到的是拿着键盘的那个窗口，绑定由核心在那个终端上执行。总控台的面板不是终端，所以不管的话，它在前面时
配置里绑的每个键都是死的；菜单行和命令面板的条目也一样，它们同样是「在前面那个终端上执行」。

规则全在 `polter_control_room::reach`（在 mac 上测），宿主只问和转交。一个动作按名字分三类：

| 类 | 是哪些 | 宿主怎么做 |
|---|---|---|
| **宿主自己的** | 封闭的一张单子（下表） | 不经终端，直接走宿主已有的入口（`tabs::perform_hosted`） |
| **应用的** | 核心划给应用的那些：`quit`、`open_config`、`reload_config`、`close_all_windows`、`check_for_updates`、`toggle_quick_terminal`、`toggle_visibility`、`screenshot`、`undo`、`redo`…… 一条测试读 `Binding.zig` 的 `Action.scope`，这份单子和它不是同一个集合就红 | 键：交给 `ghostty_app_key`，核心自己比对、自己执行。菜单 / 命令面板：借应用里任意一个终端执行（哪个都一样）；一个终端都没有时置灰 |
| **终端的** | 其余全部：复制、粘贴、分屏、搜索、字号、监管开关…… | 键不响应；菜单置灰；命令面板里选了就打一行拒绝（以前是安静地返回 false） |

**宿主自己的那张单子，以及键盘上问配置的是哪几个**（`reach::Host` 与 `reach::KEYED`）：

| 动作 | 宿主做什么 | 键盘问配置吗 |
|---|---|---|
| `goto_tab:1` … `goto_tab:8` | 切到第 N 个标签页（超过就是最后一个） | 问 |
| `last_tab`、`next_tab`、`previous_tab` | 切标签页 | 问 |
| `new_tab` | 开一个终端标签页 | 问 |
| `close_tab` / `close_tab:this` | 关前面这个标签页（就是总控台自己，不问） | 问 |
| `close_window` | 走窗口自己的关闭，问法和点叉一样 | 问 |
| `toggle_command_palette` | 开命令面板 | 问 |
| `new_window`、`poltergeist_toggle_control_room` | 开新窗口；去总控台（已经在前面，等于不动） | 不问：这两个是应用级的，`ghostty_app_key` 先一步处理了。留在单子里是给菜单和命令面板用的 |

**为什么是这些**：都是「标签栏是干什么的」那几件事，每一件宿主都已有不需要终端的入口。**为什么没有那些**：

- `close_tab:other` / `close_tab:right`：要逐个问别的标签页里的终端，留给终端标签页去做。
- `move_tab`、`move_tab_to_new_window`、`toggle_tab_overview`：各有自己的规则还没写（一个没有终端的标签页挪到哪、
  概览里它是什么）。`move_tab_to_new_window` 在右键菜单里是有的。
- 一切关于终端的：没有终端。
- `keys.rs` 的加速键表（四行）**没有动**：它只在终端有焦点时跑，那四行又都是分屏和最大化。

**键是怎么对上的。** 核心只在 surface 上把键对到绑定（`ghostty_surface_key`），而在那里执行还会把没绑定的键
**打进那个终端**，所以不能借一个终端来问。于是宿主问配置「这个动作现在绑的是什么」，自己比。比法是核心
`Binding.Set.getEvent` 的前三步：先按物理键位加修饰键，再按不带修饰打出来的字符加修饰键，修饰键要正好相等。
物理键位用的码表不是抄的：`reach` 直接读核心的 `src/input/keycodes.zig`（Windows 那一列）。每次按键都重新问
配置、不缓存，所以改绑以后立刻跟着走。

**对不上的（已知）**：键序列和键表里的绑定、`catch_all`、带参数的动作的 `performable` 绑定（带参数的动作只能
用反查，而反查表里没有它们）——**`goto_tab` 除外**；带参数的动作一个动作只认一个键（不带参数的认它的每一个键）。

**`goto_tab` 是怎么对上的（#1439）。** 默认的 `Alt+1…8` 在 mac 以外带 `performable`（`Config.zig` 里
「Cmd/Alt+N for goto tab N」那一段），所以反查 `goto_tab:2` 的回答是「没绑」；正查的表有全部十六个键，但只给
动作的标签 `goto_tab`，分不出 3 和 7。真机第一轮 Alt+2 得到的就是 `not a binding the control room answers`。
现在的做法：正查表里 `goto_tab` 的每个键，**键上的数字是几就去第几个**（`reach::goto_tab_of`，1–8）；反查查得到
的照旧用。拼表的规则整个在 `reach::bindings`，宿主只转交——上一版的测试拿的是一张手写的、已经拼好的表，
所以比较那一步是测过的，拼表这一步从来没被测到。**暂定，有一处会错**：`alt+1=goto_tab:5` 这种键和标签页不同号
的绑定会去第 1 个；不是数字的键（`ctrl+j=goto_tab:3`）不猜，带 `performable` 的话就对不上。要根治得让核心的
`ghostty_config_keybind` 把参数也带出来，那是核心的改动，没做。

**应用级的键做成没有，日志怎么说（#1439）。** `ghostty_app_key` 回真只表示「这是个应用级绑定，核心接了」；
事情本身是核心再以动作的形式交回宿主做的，而应用级动作**不带窗口**。真机第一轮 Ctrl+Shift+N：动作回来是
「new_window，谁也不是」，宿主没处放，没排队；面板那一行却写「the core performed it」。现在：面板把键交给核心
的那一刻记下自己是哪个窗口（`control_room_keys::asking`，只在那一次调用期间有值），没带窗口的 `new_window`
就用它；动作回调把「做成没有」数给它，日志按数出来的写三种之一（`reach::app_key_outcome`）：
`the host carried it out` / `NOT carried out, see the [action] / [ops] line above` /
`nothing was asked of the host, so what it did is not known here`。

**Alt 和弦**：默认的「切到第 N 个」是 `Alt+数字`，到的是 `WM_SYSKEYDOWN`。面板执行了就吞掉随后的 `WM_SYSCHAR`
（不然是一声「咚」）；没执行的原样交给 `DefWindowProcW`，`Alt+F4` 和系统菜单在那里。

## 3. 用什么画

**GDI，和宿主其它界面一样；不引入 Direct2D，不用 WebView2。**

- **WebView2 不行**：`plugin_page.rs` 写明运行库在 Server 2022 上默认没有，那边的做法是「没有就在页
  签里说没有」。总控台是头号功能，不能在一部分机器上是一句「安装不完整」。而且那样判断就会跑进
  页面脚本里，「宿主不比较类别」的检查够不着。
- **Direct2D 的好处是真的**（抗锯齿的圆角、半透明、亚像素定位），但它是这个宿主的第二套绘图栈：
  新的特性开关、新的设备丢失处理、新的 DPI 换算，而截图工具已经用 GDI 把圆角和亮暗做出来了。
  **如果 §5 的动画在 GDI 下达不到帧率，再只为总控台这一个窗口引入**，这是有读数以后的决定。
- **图形**（气泡、三角、圆点、转圈）：mac 用系统图标。Windows 上自己画四个 14 单位的路径，按 DPI
  放大；GDI 的多边形和弧没有抗锯齿，办法是先以 4 倍大小画进内存位图再缩小（`StretchBlt` 配
  `HALFTONE`），每个 DPI、每种颜色缓存一份。**这一条没验**：小尺寸下缩出来的边好不好看要上测试机看。
- **文字**：GDI + ClearType，字体走 `uifont.rs`。群名用等宽字体、数字用等宽数字（§3.5 第 8 条），
  GDI 没有「等宽数字」这个开关，要选一款数字等宽的字体或者按位画；这一条是已知的出入。
- **最小字号**：系统菜单字号，`look::font::MIN` 已经守着 13。

## 5. 动画

| 效果 | 定稿 | Windows 上怎么做 | 风险 |
|---|---|---|---|
| 选中片滑动 | 弹簧，周期 0.36 秒、阻尼比 0.72，冲过头约 4%；抬起、沿向拉长；0.41 秒停稳 | 群列表的行与窗口标签栏两处都做了。**在哪、多大、抬起多少、何时算完全在逻辑层**（`slide`，与 mac 的 `ControlRoomChipSlide` 同一套数，对照闸逐时刻比）；宿主用 `SetTimer` 16 ms 一帧去问「现在在哪」，逻辑层说「完了」的那一次停表并打一行日志。系统关了动画时不滑。片子里面的字按选中时的写、外面按没选中的写：同一份场景画两遍，第二遍只画在片的轮廓里（`scene::Lit`） | GDI 每帧重画整块面板 / 整条标签栏够不够快，**没量**；滑动中的样子**没在真机上看过** |

| 等你的图形明暗 | 2.4 秒一轮，100% → 50% → 100%，一个窗口只有一个 | 哪一个明暗由 `pulse::pulsing` 给；宿主用一个 100 ms 的定时器改图形的不透明度（预先缩好的位图配 `AlphaBlend`），只重画那 14 单位见方 | 定时器只在有东西明暗时开着 |
| 在干活的转圈 | 1.2 秒一圈，一格一格跳 | 12 帧位图，100 ms 换一帧 | 同上 |
| 出问题的晃动 | 进入时晃一次，0.3 秒 | 一次性的 16 ms 定时器 | — |

**定时器与「什么都没变时不醒」**（§13.2 第一行）：那一条说的是「不定时取快照」。上面的定时器只在有
图形在动的时候存在，停下来就 `KillTimer`；窗口被遮住或最小化时也停。系统设置关了动画
（`SPI_GETCLIENTAREAANIMATION`）时一个都不开，靠形状和颜色分。验收时要量的是：没有任何群在等、没有
任何群在干活时，60 秒里宿主为这个窗口醒了几次——应当是 0。

## 6. DPI 与亮暗

- **DPI**：`look.rs` 和 `layout.rs` 的数全是设计稿的单位。宿主在画的那一刻乘 `GetDpiForWindow / 96`，
  别处不乘。0.5 的线在 100% 缩放下是半个像素，GDI 画不出来：**100% 下画 1 像素、用更淡的颜色**
  （把线的透明度折进颜色里），150% 以上按四舍五入的像素画。这一条是 Windows 特有的出入，要在
  100% / 125% / 150% / 200% 各看一次。`WM_DPICHANGED` 时丢掉缓存的图形位图和字体重建。
- **亮暗**：`look::theme(dark)` 给整套颜色。「现在是暗吗」读 `AppsUseLightTheme`（截图工具已有读法）
  并在 `WM_SETTINGCHANGE` 时重读；配置里指定了窗口主题的以配置为准。标题栏照 `shell.rs` 的做法设
  `DWMWA_USE_IMMERSIVE_DARK_MODE`。暗色版红字改白字的那几处已经在表里（`problem_text_on_*`），宿主只读
  字段。
- **高对比度模式**没有设计，第一期照系统颜色画、不用自己的色板；这是一条待定。

## 7. 数据怎么来、动作怎么去

- 收到核心的 `CONTROL_ROOM_CHANGED`（`ffi::ACTION_CONTROL_ROOM_CHANGED`，`cb_action` 里现在是一条
  `owed` 分支）→ 调 `ghostty_app_control_snapshot` 取 JSON → `snapshot::decode` → `List::from_snapshot`
  → 重画。解码失败（未知图形、缺字段）**画一行错误，不画空表**。
- 收到通知就取一次（全宿主一次，再分发）：标签栏上别的标签页的图形也要它，所以不能等总控台标签页
  在前面才取。没有通知就不取，没有定时器。
- 用户的动作 → `act::encode` → `ghostty_app_control_act`；返回假时把错误名交给 `Refusal::parse`，
  用 `message()` 的英文过一遍 `i18n::tr` 显示在那一行上；`means_look_again()` 为真时不等通知，立刻
  重取一次快照。
- 任务栏按钮上的数字：`needs_me`（终端数）。用 `ITaskbarList3::SetOverlayIcon` 画一个带数字的小
  图标，需要给 `windows` crate 加 `Win32_UI_Shell` 里对应的接口；宿主里现在没有任何任务栏代码。
- 通知：第一期不含（主文档 §13.1）。

## 10. 做成了什么、没做什么，和 Windows 真机验证清单

**真机跑过一轮**（2026-10-13，#1437，Windows 11 26200，包 72af59caf；全文
`Polter_Pub/assets/control-room-design/verify-win-01/RESULTS.md`）。没有群时的面板、标签页模型、多数键、

**改完以后还没有在 Windows 上跑过**，所以下面每一条的「修了」都只到 mac 上验得到的地方。

| 真机上看到的 | 原因（读代码查的） | 改了什么 | mac 上钉住的 |
|---|---|---|---|
| 面板里一有带状态的行，宿主就崩：`USER32.dll` `0xc0000005` 偏移 `0x24a82`，日志停在 `opened as` | 面板用 `DrawTextW` 画字、`GetTextExtentPoint32W` 量字，交的是「指针 + 字数」。场景里**本来就有空字符串**：没人等的群状态词是空的（核心的 `none`），等待也可能没有停因。空的 `Vec<u16>` 是字数 0 加一个不指向任何东西的指针（`0x2`），这个版本的 `USER32` 会顺着它读。**不是图形**：标签栏用的是同一个 `draw_glyph`，它没事；「无人看管」的行有字，所以不崩。截图工具栏之前死过同一件事（#1199，`shot.rs`） | `control_room.rs` 里画字、量字各只剩一处（`draw_text`、`text_width`），先问 `scene::draws`，空的不交；面板第一次画完打一行 `first paint drawn` | 逻辑层一条测试：核心的夹具场景里**确实**有空字符串，`draws` 全部拦下；闸 `control-room-hands-user32-no-empty-text.py`：这个文件里两个调用只在那两个函数里、且在提问之后 |

**第二轮（2026-10-13，#1441，包 72af59caf+fix1439；`verify-win-02/RESULTS.md`）**：上表三处都成立——四个场面 4/4 不崩、
每次都有 `first paint drawn`、事件日志 0 条；Alt+数字、Ctrl+Shift+N 成立；右栏借终端、已看、UIA、亮暗成立。新查出的和这一轮
改的（**改完以后还没在 Windows 上跑过**）：

| 真机上看到的 | 原因 | 改了什么 | mac 上钉住的 |
|---|---|---|---|
| 切到别的标签页再切回，右栏写「在左边选一个群。」，原来那一行点不动；首开时亮片在、右栏没跟上 | `tabs::layout` 用 `ShowWindow(SW_HIDE)` 藏面板、用 `SetWindowPos(SWP_SHOWWINDOW)` 显示它——前者发 `WM_SHOWWINDOW`，后者不发，所以面板只听到「走了」没听到「回来了」；而「走了」发的是 `Closing`，把选中也忘了；点同一行又因为「没变」直接返回 | 面板改听 `WM_WINDOWPOSCHANGED`（显示、隐藏都有）；看不见时发新事件 `OutOfSight`（终端还回去，右栏的话保持为真，与 mac 的 `outOfSight` 同）；点同一行也同步一次右栏 | `lend` 三条测试（藏起来再回来会借回；一开始就看不见时说对的话；藏起来会忘掉「人拿回去过」）。消息接线要真机验 |

**折行是自己做的，不是 GDI 的。** `DrawTextW` 的自动折行按字体自己的行高排，而行是按设计的行高（20）排的，三行就差出半行。
所以哪里断行在逻辑层（`layout::wrap`：在放得下的最后一个空格后断，没有空格——路径、长参数——就在放满处断），宿主只回答
「这串字的前多少个放得下」（`fit_chars`，`GetTextExtentExPointW`），然后一行一行画；行高、点击、滑动的两端、读屏的矩形都用
同一个实测版式（`list_layout`）。**没验的**：真字体下行数与 mac 是否一致（两边各量各的字体，本来就可能差一行）。

这一轮没做、仍然开着的：右栏标题条在 worker 等待时写的是行上的字（mac 已改成只读总管自己的，要成员表进逻辑层）；
悬停提示里的全文（`list::tooltip` 有，面板没接）；英文界面里 `1 groups waiting for you`（没走复数形式）；UIA 里借出又还回
的终端 Document 矩形仍是右栏那一块、多一个没名字的 Pane。

⚠ **崩溃的原因没有在真机上证实**（第二轮证实了「改了以后不崩」，没有证实「就是它」——没有做「改回去再崩」的对照）：没有 dump，`USER32` 内部会读那个指针是从两次同样特征的崩溃和代码读出来的
（#1199 那次也没有重跑证实）。如果第二轮还崩，`first paint drawn` 那一行在不在，能分出是死在画里还是画完以后。
宿主里另外三十多处 `DrawTextW` 没有逐个查过会不会收到空字符串。

在 mac 上验到的是：逻辑 crate 的测试、变异体、两套闸、核心那三条读宿主
源码的测试、宿主交叉编译与 Debug 构建链接成功。凡是要窗口的都算没验。

做成的（代码在）：

- 标签页模型：`tabs::Body`（§2.1）；全应用一个（`rules::trigger`，宿主在建面板前后各查一次）、开在第一位、
  可关不问、不进「重开已关的标签页」、不能改名、右键菜单只出四项、`+` 在它前面时直接开终端标签页、
  移到新窗口。入口：核心动作 `toggle_poltergeist_control_room`（键绑定、Agents 菜单第一行、命令面板）。
- 面板（`control_room.rs`）：左栏的两段、行、选中片（弹簧滑动、抬起、平的投影、片里外两种字）、时间带；右栏一句说明加「去它的标签页」；
  亮暗两版（跟系统设置）；按窗口 DPI 画。画什么全部来自 `polter_control_room::scene`。
- 取数（`control_room_source.rs`）：收到 `control_room_changed` 取一次、全宿主分发；没有取数的定时器。
- 标签栏：每个终端标签页右端的状态图形与明暗（`pulse::tab_status` / `draws_on_window_tab`）。
- **标签栏的槽与选中片**（#1449）：标签栏原先是一排方块加一条下划线；现在是一条比标签栏底色暗一级的槽，选中的标签上
  一粒亮片，没选中的没有底（鼠标悬停的有一片淡的，正在拖的有一片更亮的），相邻两个都没有底时中间一条短竖线。
  切换标签时亮片从旧标签滑到新标签（同上一行的规则；按 `TabId` 认，重排不滑，旧标签没了就直接到位）。
  槽、片、竖线、投影在哪、多圆、什么颜色都由 `polter_control_room::tabstrip` 给，**全是整像素**（100%–200% 五档有测试）。
  选中标签的字用 600 的字重。**标签栏只有暗色一套**：它的底色本来就不跟系统的亮暗走（标题按钮、菜单按钮画在同一条里），
  这一次没有动这件事，所以槽与片取的是暗色表；群列表那一处亮暗两套都有。标签上的字不再以空格开头，左边距从 4 改成外观表的 8。
- 选中停留即已看（`act::SeenMarker`）。
- 动画的钟只在画面上有会动的东西时存在（明暗、转圈），没有时自己停。
- **默认选中**（第二块）：打开后的第一份快照、且没有选中时，选核心给的 `open_on`；已有选中不换；自动选中的
  不算人看过，不开始「已看」的计时，直到人自己选它（`list::Selection`）。人选过的那个在关掉再开时还在。
- **键盘出口**（第二块）：§2.5。焦点在面板上时，面板自己的键（上、下、回车）之外，先交 `ghostty_app_key`，
  再比那张封闭的表（`control_room_keys.rs`）。
- **菜单置灰**（第二块）：总控台在前面时，需要终端的行置灰（`rules::menu_row_offered`）；宿主自己的照常；
  「Save as Project…」是唯一一条作用在标签页上的宿主行：右栏借着终端时可用，存的是那个终端的标签页
  （`rules::project_tab`、`tabs::tab_saved_as_project`，任务 #1485），没借着置灰。
  应用级的借任意一个终端执行。`main.rs` 的 `binding` 在没有终端在前时不再安静地返回 false：三类各有一行日志。
- **窗口标题**（第二块）：总控台在前面时是「Polter — Control Room」（译过的），换到别的标签页还回去；没有可还的
  就是「Polter」（`rules::caption`）。标签上只写名字。
- **UIA**（第二块）：面板有自己的提供者——一个列表，每个群一个列表项，名字是这一行说的话（群名、状态的字、
  停因、等了几分钟、还有几个），`SelectionItem` 给出是否选中并可选中。按群名认行，不按位置。

- **行上不放任何处理按钮**（用户 2026-10-12 定的，原话：「不太行，这个勾叉是同意确认内容吧，但是左侧按钮这么小
  界面根本看不清，不要做这个，还需要让agent调特定mcp来执行，而且很多时候不是同意否则这种是非，会比这个复杂的
  多，只要提示出来」）。总控台只提示、不代办：一行说的是谁在等、等什么（图形、谁在等、状态的字、等什么、还有几个；分钟数已撤，见 `poltergeist/control-room.md` §3.2），
  人自己进终端去处理。第三块里做过一天的勾与叉、被拒时替换第二行的那句话、Y / N 键、读屏上的两个按钮都撤了。
  核心的 `ghostty_app_control_act` 里 approve / refuse / reply 还在，只是这个宿主没有任何入口发它们；发的只有
  `seen`。逻辑 crate 里一条测试读画行与处理输入的源码，出现这三种动作或 `approvable` 就红。
- **中文**（第三块）：界面文字在源头用 `n_` 标（`windows/control-room`、`windows/settings-shell`），生成步骤
  扫这两个 crate 和宿主三处目录；`po/zh_CN.po` 里总控台的 17 句都有译文。
- **右栏放进总管的真终端，同一窗口**（第三块）：选中的群的总管在本窗口的某个标签页里时，它那一格被摆进右栏
  的总管框里（`lend::Lending` 定谁借、何时还；`tabs::layout` 按 `scene::terminal_rect` 摆）。那一格不离开它
  标签页的分屏树，所以关它、存它、按 surface 找它都照旧；没有 `SetParent`。详见下面「右栏的真终端」。

**右栏的真终端：每种情形怎么处理**（与主文档 §12.5 的 mac 情形表对着看）：

| 情形 | Windows 上 | 与 mac |
|---|---|---|
| 选中一个群，总管在本窗口 | 先还上一个，再把这个的那一格摆进右栏；键盘留在列表，点一下终端才进去 | 相同 |
| 两个群同一个总管，在它们之间切 | 不动 | 相同 |
| 没有总管 / 总管的终端已不在 / 没有选中 | 还回上一个；右栏一句话 | 相同 |
| 总管在**别的窗口** | 不搬。右栏写「在它自己的标签页里」加「Go to Its Tab」 | **不同**：mac 搬。跨窗口要 `SetParent`，没验过，没做 |
| 点右栏的终端 | 键盘进终端，前面的标签页仍是总控台（`focus_pane_at` 对借出的格不再改 `active`）；总管框的边变深 | 相同 |
| 切到别的标签页（含总管自己的） | 面板一藏就还回；切回来再借。在总管自己的标签页里看到的就是终端，没有占位 | 结果相同；mac 的占位在同一窗口的情形下本来也看不到 |
| 原处的占位与「拿回来」 | **没有**：同一窗口里原标签页与总控台不会同时在前面，没有地方显示它。逻辑层里 `Reclaimed` / `AskedFor` 两个事件保留并与 mac 对照，宿主现在不发它们 | 出入，随跨窗口一起补 |
| 关总控台标签页 / 关窗口 / 退出 | 那一格从没离开过树，面板销毁时清掉借出记录即可 | 相同 |
| 借出的那一格被关（程序结束） | 立刻清掉借出记录，右栏写终端已关掉 | 相同 |

### 12.2 借出的总管调 `terminal_open`：Windows 上原来是什么样（读代码定性，没有真机读数）

**不是 mac 修之前那样。** mac 是「回 ok、没有终端」：视图在总控台的窗口里，开标签页的处理只认终端窗口。
Windows 借出的那一格没有离开它的窗口，动作带着它的表面，宿主找得到窗口，**标签页开得出来**——但
`create_tab_with` 把新标签页设成了前面那个，于是人正看着总控台，被一把拉到新标签页上，右栏借着的总管也随之还回去。
现在这一格走 `rules::new_tab` 的「开在后面」。

真正「回 ok 而没开出来」的另有一处，这一轮顺带看到并改了：**不带终端的新标签页请求**（应用自己要的——总控台
启动总管就是）原先在 `ACTION_NEW_TAB` 里直接被拒（「这个动作没有指明窗口」），回的是「没做」，所以核心回
`OpenFailed`。也就是说**在这次改动之前，Windows 上「启动总管」必然失败**，那句话是「开不出标签页」。
能写成测试的是规则本身（`where_a_tab_the_core_asked_for_goes`，对照闸 40 格）；宿主里「不切过去」那几行没有测试。

### 12.3 第三轮的宿主侧问题：查到的原因

| 现象 | 原因 | 处理 |
|---|---|---|
| 成员标题长时那一行的群名整个不见 | 那一行里群名被排成「左右两边排完剩下的地方」，谁在等与状态的字都不缩；谁在等一长，剩下的地方是零，群名就不画。**不是 #1450 改 `paint_line` 时碰到的那一处**：那次只管住了左边的字不压右边，群名当时不算左边的字 | 排字的先后搬进 crate 并有测试（`place_line`）：状态的字整个留着；群名排第二，只被状态的字截；谁在等拿剩下的，截尾、末尾省略号，一点地方都没有就不画。宿主只量字宽、照着画 |
| 同样的场面在 mac 上 | **mac 也会挤群名**，只是挤法不同：谁在等与状态的字都是 `fixedSize`，群名是 `lineLimit(1)` 截尾，所以群名被压成「we…」直到只剩省略号（`ControlRoomListView.waitingRow`）。没有在 mac 上造过这个场面，这是读布局代码的结论；没有改 mac | 要不要把 mac 也改成「截的是谁在等」，留给定夺 |
| 字整体小两号（群名 13 对 15、命令 11 对 13） | **字号没取错，换算也没错**：两边要的都是 15 与 13（`font.group_name` / `font.body`），Windows 是 `CreateFontW(-15)` / `(-13)` 乘缩放。差在**字体**：Consolas 同字号下字宽 0.55、x 高 0.49，mac 的等宽字是 0.60 / 0.53，所以看上去小一号多；设计的 41 字一行也是按 0.6 算的。（这几个度量是字体本身的数，凭资料写的，没有在测试机上量；「原因是字体」因此是推断，换了字体以后第 13 步的读数才是证据） | 等宽字改用 Cascadia Mono（字宽 0.586，Windows 11 自带），没装才回到 Consolas；日志里有一行说用的是哪个。**界面字（Segoe UI）没有动** |
| 「还有 N 步」比上面的步骤大一号 | 同上：那一行是界面字 13，上面的步骤是 Consolas 13 | 随上一条 |

核心是**当场**读宿主对 `new_split` 的回答的（`App.zig`）：回 `will_split` 它就等那个标签页里冒出终端；回别的它当场改开
标签页，并在给 agent 的回话里写 `placed:"tab"`、`fallback:"split_refused"`。Windows 宿主原来是「先回 will、把分屏排进队列，
轮到时才发现这一格借在总控台而拒掉」——于是借着的总管要 worker（`place` 不写、`auto`、多半还有 `here`），回话说开了，
实际什么都没开，约 30 秒后核心自己记一行「之前要的分屏没有出终端」。

现在回答之前先问同一条判断（`lend::SplitAnswer::to`，`tabs::split_answer`）：这一格借出着，或前台是总控台而没点名哪一格
⇒ 不排队、不回 will，日志一行 `[split] refused when asked: …`。核心那边不用改：它随后发的 `new_tab` 走 §12 的
「开在后面」。轮到时的那次检查留着（两次之间总控台可能刚借走这一格），用的是同一个函数。键盘上的分屏键走同一条路：
按键照旧算被接住，不会漏进终端。

### 14.2 右栏标题条写总管终端自己的标题与状态（观察 6）

原来写的是群名加 `Supervisor`，状态是**那一行**的（可能是某个 worker 的「等批准」）。现在照 mac 的 `SupervisorTitle`：
名字、图形、字都是核心给总管那个终端写的（Windows 从快照的 `terminals[]` 里按 `steward` 取；mac 从群的 `members` 里取，
对照闸在夹具上比两边取到的是同一组）。核心没列这个终端时只写群名，不写状态。状态的字是空的时候不画。

### 14.3 标签多到顶到头时「+」盖住最后一个标签的关闭叉（观察 8）

标签原来排满整条，「+」再钉到右端、压在最后一个标签上。现在标签不占「+」脚下那 22（×缩放）的位置；溢出后滚到头也
让出它。同样数目的标签因此各窄几像素（1000 宽、5 个标签：190 → 186）。纯算术，在 mac 上把这几个函数原样抽出来跑过
（旧代码红在「最后一个标签到 299、+ 从 278 起」）；宿主里那条测试只编过。

### 14.4 查了、没改宿主的

- **缺陷 5 前半（菜单点「允许总管代答」以后勾不跟）**：宿主的勾读的是核心上一次发来的 `poltergeist_mark`，开菜单时现读，
  点完没有「忘了重读」这回事——缺的是核心点完不发标记，以及配置里那一组设置启动时没到核心（#1477 A，cr/core edfb340af）。
- **观察 2（总控台没开时每 5 秒两行 `[control-room] fetch`）**：不是定时器。宿主只在核心说 `control_room_changed` 时取一次
  （`control_room_source.rs`），而标签栏上每个标签的状态图形读的就是这份快照，所以总控台没开也要取。那 5 秒一次是核心在
  发通知（读数里 `rev` 一直在涨，当时有两个标着「在干活」的被看管终端）——要不要在没有可见变化时不涨 `rev` 是核心的事。
- **缺陷 4（打印的通知与随后打的字叠在一起）：只写方案。** 打印这条路不在宿主里：核心的 `Surface.showPoltergeistAlert`
  直接往终端的屏幕状态里 `printString`，不经 pty。mac 上 shell 自己记着光标，问题小；Windows 上屏幕内容是 ConPTY 按它
  自己那份缓冲发过来的，它不知道我们在光标下面多写了两行，下一次重画（PSReadLine 每个键都重画）就按它以为的位置写，
  落在通知那一行中间——缓冲没坏，坏的是两份屏幕对不上。在核心里补换行救不了，因为错位的是 ConPTY 的坐标。
  可行的办法按动静从小到大：①Windows 上不往屏幕里写，改由宿主画在终端上方（`hud.rs` 已有贴在终端上的条），几秒后或
  下一个键后收起——核心加一个给宿主的动作，宿主画；②让 shell 那一侧知道：往 ConPTY 的**输入**里送不行（那是打字），
  要有一个挂在同一个控制台上的进程往 `CONOUT$` 写，动静大且要多一个进程；③走系统通知。建议 ①。
  另一处读数（23628 里「没连着」的普通 PowerShell 收到的是**打字**而不是打印）是核心判「有没有 agent 连着」
  的事（`Server.agentPresent` 看的是有没有一条点名这个终端的 MCP 连接；**推断**：那次一次性的 `mc.cmd` 的连接当时还占着
  一格，没有验），不在宿主。

`windows/control-room`（零依赖，`cargo test -p polter-control-room` 在任何机器上都能跑）：

| 模块 | 内容 |
|---|---|
| `look` | 外观表（生成的） |
| `snapshot` | 读核心的快照；未知的图形是错误，不画成空白；不读核心的类别 |
| `list` | 两段、每行说什么、选中怎么移动、重启后的选中；选中的一生（`Selection`：谁选的、算不算看过） |
| `layout` | 面板里每样东西在哪；一行随它等的东西有多高、每一步占几行（`AskFit`）；选中片的弹簧曲线。时间带已撤 |
| `pulse` | 哪个等你的图形在明暗；一个窗口标签页带哪个图形、画不画（「在干活」按外观表的暂定项不画） |
| `act` | 用户动作编成请求；每种拒绝说什么（这个宿主现在只发 `seen`，拒绝只进日志） |
| `lend` | 右栏借的是哪个终端、每种变化之后该还该借（与 mac 的 `ControlRoomLending` 逐步对照）；键盘在列表还是在终端；关闭与分屏对借出的那一格怎么办 |
| `rules` | 总控台的标签页：全应用一个、开在哪、关它问不问、记不记进重开单、能不能改名；编号写成快照的写法；窗口标题听谁的；菜单行在它上面出不出 |
| `reach` | 没有终端在前面时一个动作归哪一类；按下的键是那张封闭的表里的哪一个（§2.5） |
| `scene` | 面板画的每一样东西：矩形、字（字体、字重、颜色）、图形，宿主照着画；一行被读出来时说什么；哪些行按「选中」的写法写（`Lit`） |
| `slide` | 选中片从一处到另一处的一次移动：滑不滑、每一刻在哪多大抬多高、何时算完（`Run::frame` 的 `last`，宿主据此停表）。与 mac 的 `ControlRoomChipSlide` 逐行对应 |
| `tabstrip` | 窗口标签栏的槽、选中片、竖线、投影：位置、圆角、颜色，全是整像素 |
| `glyph` | 四个状态图形在 14 单位画板上的形状 |

两道闸（仓根 `tools/`）：

- `control-room-hosts-agree.py`：同一份夹具，mac 的 `ControlRoomList.swift` 与这个 crate 各算一遍，逐行
  比较，含哪一行/哪个终端在呼吸（`pulses`）、每一行谁在等（`waiter`）与等什么（`what`：哪一种、是不是全文、每一行的字）、行高与每一步占几行、每一行的 `unseen` 与
  「看了多久算看过」、每个窗口标签页带哪个图形/画不画/呼不呼吸（`tabs`）。没比的：快照顶层的 `now_ms`
