## 三、菜单系统（S4-A）

### 3.0 先撤销一个裁决

`design.md` §1.7 第五项写过：

> **主菜单栏本身**：同上，不做。那 103 条命令通过命令面板（S3 块 E）和右键菜单到达。

**用户 2026-09-01 当面推翻了它。** 原话：「缺少重要的菜单栏……
windows 下没有 head bar 和菜单栏，可以在最左侧加一个菜单按钮，
点击后可以展开多级菜单」。

**原裁决错在哪，要说准。** 它的推理是「Windows 终端没有菜单栏」——这句话本身是对的，
Windows Terminal 确实没有。**但它回答的是「要不要一条横贯窗口顶部的 menu bar」，
而用户问的是「那 96 条命令，一个没被人告诉过的人怎么找到」。**
这正是 §1.7 自己量出来的那个维度——可发现性——**而当时那一节的结论是
「模型里没有这一栏」，紧接着下一段就用「不做」把它填平了。**
同一份文档里，隔了三十行。

### 3.1 主菜单按钮：放哪，长什么样

**放在标签条最左端，x = 0。** 用户指定的位置，而且有两条它自己的理由：

1. **它不动。** 放在最后一个标签右边（Windows Terminal 的 `⌄` 那个位置）
   会随标签增减而移动，标签溢出时还会被挤走。一个每次都在别处的入口，
   等于每次都要重新找。
2. **右端是标题栏按钮的地盘。** 我们用的是标题栏内嵌标签条
   （`shell.rs` 的非客户区自绘），右端 138px 归最小化/最大化/关闭。
   Windows Terminal 的 `⌄` 不在右端，正是因为这个。

**尺寸与画法**（都用 `strip.rs` 已有的 token，不要新造一套）：

| | 值 |
| --- | --- |
| 宽 | `46 * scale`，高 `strip_h(scale)` |
| 图标 | Polter 的 `≡`（三横），线宽 `1.0 * scale`，居中 |
| 常态 | 不画底 |
| 悬停 | 与标签悬停同一个填充色，圆角 `4 * scale` |
| 按下/菜单展开中 | 与选中标签同一个填充色 |
| 键盘 | `Alt` 单击或 `F10` 打开（Win32 惯例），方向键导航由 `TrackPopupMenu` 白送 |

**标签的第一个槽位要整体右移这个宽度。** `strip.rs:84` 的 `layout()` 目前从 0 起算，
新增一个左内缩参数；`is_interactive` 和 `Hit` 都要跟着改，
**`Hit` 要加第六个成员 `Menu`**——像块 B 当初加 `New` 那样。

### 3.2 菜单树：结构照抄 macOS，动作全部来自核心

> **订正（2026-09-02，W1 报的，我逐条核过）**：本节初稿写错了四个动作名——
> `next_search_result` / `previous_search_result` / `toggle_surface_read_only` /
> `poltergeist_conversations`，`src/input/Binding.zig` 的 93 个 Action 成员里
> 一个都没有。照原文写会得到四条静默失效的菜单项，**正是本节下一段警告的那种**。
> 下面的表已改成核心的真名。**这份文档不是动作名的依据，`Binding.zig` 才是。**

**这是本块唯一的硬约束：菜单里的每一条都必须是核心已经发布的命令。**
和 `ctxmenu.rs` 一样，标题可以是人话，动作字符串必须能被
`ghostty_surface_binding_action` 认出来。一条认不出来的动作**不会报错，只会静默什么都不做**——
所以要有编译期的 `assert_actions_exist` 测试**和**运行期的计数日志，两道都要。

根菜单（六个分组 + 尾部两条）：

### 3.3 三处右键菜单

| 位置 | 现状 | 要做什么 |
| --- | --- | --- |
| **surface 上** | `ctxmenu.rs` 已有 13 条，走 `WM_CONTEXTMENU` | 对着 `SurfaceView_AppKit.swift:1585` 补齐；加只读/改标题 |
| **标签上** | **没有。用户报的缺陷。** | 见下 |
| **标签条空白处** | 没有 | 新建标签 / 重开关闭的标签 / 命令面板，三条 |

**标签右键菜单**，照 macOS 的 `configureTabContextMenuIfNeeded`
（`TerminalWindow.swift:717`）逐条搬，**它是这个仓自己写的，不是 AppKit 白送的**：

```
关闭标签              close_tab:this
关闭其他标签          close_tab:other
关闭右侧的标签        close_tab:right
移到新窗口            move_tab_to_new_window
---
重命名标签…           （复用 strip.rs 已有的就地改名，double_click 那条路）
标签颜色 ►            （八色，当前色打勾）
---
设为总管              poltergeist_supervisor      ☑ 当此终端已是总管
监督此终端            poltergeist_toggle_watch    ☑ 当已被监督
禁止 agent 进入       poltergeist_toggle_shielded ☑ 当已护盾
```

**三条 agent 项必须带勾选态**，理由 macOS 侧的注释已经写了，照抄：
一个点过的项要和没点过的长得不一样，否则唯一确认上次点中没有的办法是再点一次。

**关键的一条：菜单作用于「被右键的那个标签」，不是当前焦点标签。**
macOS 那份代码专门为这件事绕了一圈去拿 `targetController`。Windows 侧同理：
`WM_CONTEXTMENU` 的坐标先过 `strip.rs` 的命中测试拿到 tab index，
**这个 index 要一路传到动作执行处**，不能中途退化成 "current"。
**这是本块最容易写错、而且错了看起来完全正常的一处**——你右键第三个标签选「关闭」，
关掉的是第一个，而你多半会以为是自己点错了。

### 3.4 可发现性：三件不写代码就不存在的事

1. **每条菜单项要显示快捷键**（`\t` 后面那半，`ctxmenu.rs` 已经这么做了），
   **而且必须从核心的绑定表取，不能手写常量**。手写的会和用户改过的配置不符，
   且不会有任何东西报错。
2. **同义词。** `windows/host/src/synonyms.txt` 已有 24 行。菜单用的是人话
   （「查找…」），核心叫 `start_search`——菜单这边是对的，**要保证的是反过来
   在命令面板里搜「查找」也能搜到**，这是 §1.7 量出来的那个 20 条改名问题。
3. **不可用的项灰掉，不要隐藏。** 一个消失的菜单项和一个从来不存在的菜单项，
   用户分不出来；一个灰掉的项告诉他「有这个功能，现在不能用」。

### 3.5 验收判据（可观察，且带地板）

> **订正（2026-09-02，W1 实测）**：「约 41 条」是我数漏了三个子菜单的内容
> （查找 4 / 选择分屏 4 / 调整分屏 5，共 13 条）。**叶子项实测 55 条**（先测得 54，后来「改标签标题…/改终端标题…」补成两条），
> 其中动作串 55 个、`unresolved=0`。根菜单上一眼看见的是 **8 项**
> （6 分组 + 设置… + 关于），和 `items=8` 那行对得上。**M3 要逐条点的是 55 条。**

> **订正二（2026-09-02，真机跑 M3 时暴露）**：M3 原写「每条都有 `ok=1`」，
> **这条判据在构造上不可能通过，而且是我写的。** `ghostty_surface_binding_action`
> 返回 false 有两种含义——**解析不了**，和**认得但此刻没什么可做**。
> M1 已经读到 `0 unresolved`，54 个名字核心全认得，**所以 ok=0 只可能是后者**：
> 没有选区时复制、没开查找条时 `end_search`、没关过标签时 `undo`。
> 实测 40 ok / 11 failed / 3 skipped，11 条里至少 7 条是这一类。
> **一个数把「动作被派发」和「动作做成了事」压成了一件事。**
> 判据已改成四个数，并加了一条翻转地板——**否则「状态依赖」是一句不可证伪的借口。**

**判据行一律用 `logf!` 打，不许用 `println!`。** `main.rs:506` 的 `log_line`
对 stdout 和日志文件各 flush 一次，所以用它打的行是即时可见的；
`println!` 在 stdout 被重定向到文件时是块缓冲（约 8KB），
**读到空文件既可能是没打、也可能是没 flush、还可能是进程根本没起来**，三者分不开。
（`main.rs:246` 那条注释是唯一的例外，看守狗不能走 `log_line`，因为它会阻在自己的
`println!` 的全局锁上。）

宿主要打这四行日志，**每行自足**（`[palette]` 那三行的形状）：

```
[menu] built 6 groups, 41 items, 0 unresolved
[menu] root shown at 0,30 items=8
[menu] pick "复制" -> copy_to_clipboard ok=1        ← 前提：此刻有选区
[tabmenu] shown for tab 3 of 5 at 412,18 items=10
```

判据，逐条：

> **M0（W4 于 2026-09-02 加，排在全部判据之前）**：每个今晚新增或改动的文件，
> 先注入一行**语法错误**看构建变红、再注入一个**类型错误**看它走到类型检查
> （语法错误只证明文件被 parse 到了）；撤销后 `touch` 再编，确认回绿。
> **改动过测试的，`cargo build` 绿不算数，要 `cargo test --no-run` 绿**——
> `cargo build` 不编译 `#[cfg(test)]` 代码，而测试编不过时目录里那个同名
> 测试 exe 照样在。**测试 exe 的体积变化本身是一个读数**：它不涨，多半是
> 你的测试根本没进去（实测 10,090,367 → 23,792,825，多出来的一倍就是那批）。

| # | 判据 | 地板（不满足就说明判据本身瞎了） |
| --- | --- | --- |
| M1 | 启动日志有 `[menu] built …, 0 unresolved` | **故意写一条不存在的动作，`unresolved` 必须变成 1** |
| M2 | 点最左端按钮，出现根菜单，日志有 `[menu] root shown` | 点标签条别处不出现 |
| M3 | 55 项逐条派发，汇总行四个数：`N ok, N nothing-to-do, N failed, N skipped`。**`failed` 必须是 0**——那一档只留给「不依赖当前状态却仍返回 false」的 | **挑一条 `nothing-to-do` 的，把它的前提造出来再跑一次，必须变成 `ok`**（最省的是复制：先选中一段文字）。一条都翻不过来，「状态依赖」就还是借口不是读数 |
| M4 | 右键第 3 个标签，日志 `for tab 3 of 5` | **右键第 1 个必须是 `tab 1 of 5`**——这一条是 3.3 那个陷阱的唯一探针 |
| M5 | 右键第 3 个标签选「关闭标签」，剩下的是 1/2/4/5 | 缺了这条 M4 只证明日志对，不证明动作对 |
| M6 | 「监督此终端」在已被监督的终端上带勾 | 在没被监督的终端上**不带勾** |
| M7 | 未实现的「检查更新…」是灰的，不是没有 | — |

**M1/M3/M4 的地板必须真的注入一次再撤掉**，不是想一想觉得会过。
这是 `status.md` 第七节第 4 条：「如果被测的那个东西是错的，这条判据会看见吗」。

## 四、今晚做什么，不做什么

### 5.1c ⭐ **cmd 不需要集成脚本：`PROMPT` 环境变量就是注入点**（2026-09-02 实测）

`PROMPT` 支持 `$E`(ESC) 和 `$P`(当前盘符与路径),所以
```
set PROMPT=$E]7;kitty-shell-cwd://localhost/$P$E\W4-$P$G
```
**每画一次提示符就发一条 OSC 7**。真机读数:`cd` 两次 → 两条 `[action] pwd … attached=1`,
路径跟着走。**一个变量、零文件、零 profile**,而「往子进程环境里塞变量」正是
`shell_integration.zig` 本来就在做的事。

三条实测出来的形状,写脚本前必须知道:
· **`file:///C:/…` 会被拒**（`host` 为 null,`stream_handler.zig:1069`）。
  **必须带主机名**,用 `kitty-shell-cwd://<host>/…`——和我们自己 bash/zsh 那两份一致。
· **`localhost` 会短路 `isLocal`**（`hostname.zig:15`),真机器名走逐字节比较。
  **探针先用 `localhost`**,机器名对不对是另一个问题、另一步。（实测真机器名也过。）
· **收尾只能用 `$E\`(ST),不能用 BEL**——cmd 的 `PROMPT` 转义表里没有 BEL,
  和 bash/zsh 用 `\a` 不一样**是被迫的,不是笔误**。

### 5.1b ⭐ **Windows 上没有任何一个原生 shell 有集成——这一条比它挡住的功能大**

`src/shell-integration/` 出厂带五份:**bash / zsh / fish / elvish / nushell**。
**没有 PowerShell,没有 cmd。**

后果不是「少一个可选功能」,是 **`GHOSTTY_ACTION_PWD` 在 Windows 的默认 shell 下
永远不会到达**。2026-09-02 真机实测:在 cmd 里 `cd` 两次,屏幕上目录确实变了,
整场会话 PWD 动作**零条**。

已知被它挡住的:

| | 症状 |
| --- | --- |
| 「重开关闭的标签」 | 关掉的标签**根本不进栈**(`no cwd known`),菜单项永远是灰的 |
| 新标签继承当前目录 | 未验,但走同一个来源,多半同样不工作 |

> ⚠️ **而「没有目录就不记」这个行为是对的,不要改。**
> `ClosedTabs.swift:47` 的 macOS 版逐字是同一条
> (`guard let directory, !directory.isEmpty else { return }`)。
> **在 macOS 上它不咬人,只是因为那五份集成覆盖了 macOS 用户实际用的 shell。**

> ⚠️ **同一个用户可见现象,两个完全不同的原因**:菜单项永远灰着,
> 可能是「关闭栈写了但没接上」,也可能是「接上了,而它如实拒绝记一个不知道目录的标签」。

**要做什么**:给 PowerShell 写一份集成(cmd 几乎没有可注入的点,
现实的做法是 PowerShell + 记录 git-bash/WSL 是可用的真实路径)。

##### 那三行为什么是先决条件，以及它们把这条红劈成了哪两半

`winid::window_finished(frame)` 是全树唯一的 `PostQuitMessage` 落点，设计是只有
窗口数减到 0 才发。于是那几行把这条红劈成两个**完全不同**的缺陷：

- **没数到 0** —— 登记表里还挂着一个已经销毁的窗口。缺陷在记账。
- **数到 0 了却没退** —— 该发的发了，消息循环没走掉。缺陷在退出路径。

两者的修法互不相干，而**猜错方向的那个修法，看起来也会像修好了**：随手在别处补一
次退出，能让现象消失而记账依然错，下一个多窗口场景再把它翻出来。

**读数出来后：`M = 1` 且 `-> quitting` 零次 → 没数到 0，缺陷在记账。退出路径这一轮
根本没有被考验过**——这一点要写下来，否则「退出路径没问题」会被当成一条已验的结论，
而它只是一条没被问过的问题。

##### 缺陷本身：一句日志把一个已销毁的窗口放回了计数

`winid::of()` 从前做两件事——查号，以及**没见过就发号并入表**。后一件只有
「这个窗口现在存在」那一个调用者需要，而 `wlogf!` 的每一次命名都会触发它。

`WM_DESTROY` 的顺序（`main.rs`，`per-window.md` 第三节说这个顺序是故意的）：

```
winid::window_finished(hwnd);  // destroyed() 摘掉它、取计数、决定退不退
tabs::remove_window(hwnd);
strip::forget(hwnd);
```

**落点在第一行里面，不在后两行。** 行序说话：`destroyed` 那行之后先出现
`w2 = frame 0x...`（`of()` 的配对行），**再**出现 `1 window(s) remain; the process
stays`——而后者正是 `window_finished` 自己那句 `wlogf!`。第一个碰到已摘句柄的
命名调用就在 `window_finished` 内部，只给后两步加护栏，这条红会原样活下来。

于是：一个窗口时全绿（`PostQuitMessage` 抢在日志行前面发出去了），两个窗口时第一个
窗口的句柄在关闭后被放回表里，第二次关闭数到 1 就停下。**每一行日志单独看都是对的。**

修法（`57c7384a9`）：把「查号」和「发号」拆开，`of()` 只查不发、未知句柄回 `0`，
发号只留给 `created()`；`tag()` 对未知句柄回 `w?`。

**`w?` 丢了窗口编号，而这不是代价，是把伪造换成了空白**：从前那三行并没有保住编号，
它是**伪造了一个**——给已经有号的句柄发个新号，把读者一整轮都在叫 `w1` 的东西印成
`w2`。**错的号会被当成对的读，`w?` 会被当成它本来的意思读。** 而伪造这个号的代价，
就是计数再也回不到 0。

##### 这一格翻绿了，而它红过的那一段值得留着

这一格曾经写着「🔴，红的是**修法没验**，不是修法没写」。那不是措辞讲究：**这两种红
在一张表上长得一模一样，对接手的人却意味着完全不同的下一步**——「修法没写」要去写
代码，「修法没验」要去开机器。当时如果翻绿，会正好复制 B1-e 第一轮的错误：那一轮也是
实现做到了、判据全绿、而反面在暗处。

翻绿的条件当时写死成了 E8 的通过读数，**现在它满足了**（真机 Windows 11，
exe 编自 `ef243fdb2`）：

| 读数 | 结果 |
| --- | --- |
| **E8**：四条关闭路 × N∈{1,2} = 八次 | **八次全过**——每次 `destroyed;` 那行都在、`M=0`、带 `-> quitting`、有 `[main] exiting`、pid 消失；走的是哪条路逐次核过没串 |
| **E9**：同一句柄的配对行不许出现两次 | **过**，无重复配对 |
| **E10**：第一条 `destroyed;` 之前不许有 `w?` | **过** |
| 九个单元测试（六个注册表 + 三个不变量） | **全绿**，逐条用计数差值确认真的跑了 |

**其中三件事本身就是读数，写下来：**

**一、那九个测试差点被数错，是计数判据把它顶出来的。** 三个不变量测试不在
`registry_tests` 里，在 `winid::invariant_tests`。照「九个都在一处」去跑，会看到
`6 passed` 而以为漏了三个——而 `-Dtest-filter` 是加法不是过滤，**不匹配时照样
`exit=0`、`running 0`**，退出码分辨不出任何东西。

**二、有一次跑作废了，作废的理由是仪器不是缺陷。** 第一次 `e8m2` 里探针取不到 dump
行，第一次预关闭没执行，于是最后关的并不是最后一个窗口（还剩一个可见）——**那时
进程还活着是正确行为，不是红**。竞态出在「取日志里最后一条 dump 行」：第一次取空，
之后可能取到上一轮的陈旧行。改成「先数条数、再等条数增长」后重跑通过，统计用的是
重跑那一次。**一次由测试装置造成的假红如果被记下来，会让人去修一个不存在的缺陷。**

**三、同一个 `wN` 在一份日志里可以指两个不同的窗口。** 幸存的那个窗口创建时是 `w2`
（frame `0x2f07a0`），到它自己被销毁时那行写的是 `w1`——号是登记表的**位置**，
摘掉一个，后面的整体前移。**E9 用句柄不用编号，正好没被这个骗到。** 这条另开了
任务追。

##### 写一条新判据之前：三种假绿，三样不同的防法

**一条判据可以在三种完全不同的意义上「绿而无用」，而三种在输出上长得一模一样。**
今晚三种都遇到了，所以写在判据的前面而不是后面。

| 假绿 | 它的意思 | 防它的东西 |
| --- | --- | --- |
| **测量根本没发生** | 命令没跑、日志路径写错、参数没进来、被过滤掉了 | **地板**：先取一个「什么都没做」的读数，或一个必然为真的读数 |
| **它什么都抓** | 判据太宽，正常路径也会红 | **负对照**：一个明确不该被抓到的样本 |
| **它什么都不抓** | 判据测的不是它声称测的那个东西，**只是今天恰好没有病** | **拿一个已知有病的对象跑一遍。它必须红。** |

前两样我们一直在用。**第三样今晚才有名字，而它是最贵的那一种**——前两种失败会让人怀疑，
第三种不会：它安静、对称、看起来完备。

**第三样在这棵树上便宜得不像话：旧构建的日志就是「bug 还在」这个状态的现成标本。**
一条新判据在被接受之前，先拿一份旧日志跑一遍。**它不红，那它测的就不是它声称测的
那个东西。**

###### 还有一种：**判据的选项表本身漏了一维**

上面三种都是「判据会假绿」。这一种不同：**判据没有假绿，它是把真相排除在选项之外了。**

一个覆盖层清不掉的缺陷，判据写成了两支：**清除从没发出去** ／ **发出去了又被重绘盖掉**。
两支都对应一种成因，各有相反的修法，看起来是完备的二分。

**真相是第三支：发出去了，发给了错的对象。**

而那份日志一直在说真话——每一行 `-> surface 0x…` 的值都是对的，**只是「哪个 surface」
这个问题从来没人问过**。

> **一个打印了正确值的日志，和一个打印了正确对象的日志，不是一回事。**

**那张表不是写坏了。** 是「这件事有没有发生」这个问法**预设了只有一个收件人**，于是
「发给了谁」根本没进选项，连成为一支的机会都没有。

**所以写这类判据时，「发给了谁」要和「发没发」并列成一维，不能默认它。** 凡是判据里出现
「送/写/发/通知/清除」这类动词，都要问一遍：**它有几个可能的收件人？** 如果答案大于一，
那一维必须出现在读数里——**否则那份读数会在全对的情况下指向错的结论**。

（同一条的另一个样子：真机上「新建标签」不出这个问题、「分屏」才出，**两次形状不同而
不是随机**——一个只在一半场景里复现的缺陷，往往是因为那一维在另一半里恰好取对了值。）

###### 还有一种：**观测手段的作用域，和被观测对象的实际形状，不是同一个集合**

上面几种讲的是判据本身。这一种讲的是**拿来看它的那个东西**——过滤条件、探针、命令。

**它落空的时候，输出和「通过」长得一样。** 一夜之内五个实例，三个方向，**五次的错误
输出全部落在「看起来干净 / 看起来通过」那一侧**，所以没有一次会引发复查。

| # | 观测手段 | 它的作用域 | 被观测对象的实际形状 | 落空时的输出 | 它被读成 |
| --- | --- | --- | --- | --- | --- |
| 1 | `[mouse] wheel … lines_per_notch=3` | 读回来的那个数 | 系统设置**恰好等于**写死的默认值 3 | 绿 | 「读了系统设置」 |
| 2 | 「打字时光标要隐藏」 | 那条日志在不在 | `mouse-hide-while-typing` **默认 `false`** | 一条日志都没有 | 「守卫把它拦下了」 |
| 3 | `Get-Process polter` | 名字精确等于 `polter` | 进程叫 `polter-host` / `polter-wt-<commit>` | 空 | 「进程已经没了」 |
| 4 | `taskkill /f /im polter-host.exe` | 一个映像名 | 产物有五六个名字 | 「已清场」 | 「机器是干净的」 |
| 5 | 按命令行文本过滤进程 | 含有那个字面量的进程 | **探针自己的命令行里也含有它** | 「还剩一个」 | 「有残留」 |
| 6 | `out=$(闸 \| tail -8); rc=$?` | **`tail` 的退出码** | 被测的是闸的退出码 | 恒为 0 | 「这道闸返回 0」 |

> **第 6 格的仪器不是被测对象的一部分，它是量它的那个 shell。**
>
> 这一格是量前五格的时候当场发生的：拿它去测「十六道闸在空树上会不会红」，
> 读到 `ps1-parses.py` **打印 `FAIL` 却返回 0**，并且已经准备把它写成本轮最严重的
> 一条。去看源码才发现它第 175 行就有 `sys.exit(1)`——**接管道之后 `rc` 取的是
> `tail` 的退出码。它不是最坏的那一道，它是做得最对的那一道。**
>
> **前五格的代价是浪费时间，这一格的代价是一份诬告**，而那份报告读起来会完全可信：
> 它有命令、有输出、有退出码，每一样都是真的，只有「这个退出码属于谁」是错的。
>
> **而这条早就写下来过。** 一条写下来的教训，和一条用得上的教训，不是同一个东西——
> 判断只有用在自己正在做的那件事上才算数，而「我正在验证别人的工具」恰好是最不会
> 回头检查自己工具的时刻。
>
> 做法：**退出码不要接在管道后面取**。`cmd > log 2>&1; rc=$?`，要看输出再去读 log。

**分两层，因为修法不同：**

- **1、2 是判据缺前提。** 判据成立需要一个条件（系统值 ≠ 默认值；开关是开的），
  而那个条件没有写进判据。**修法是把前提写下来，并写清前提不成立时长什么样。**
- **3、4、5 是仪器指错了对象。** 判据没问题，是拿来量它的东西根本没对准。
  **修法是换仪器，或者给仪器加自检**——补前提救不了它。

**这两层不能混**：给一个指错对象的仪器补前提，只会得到一个写得更详细的错误读数。

> **一个不变量的沉默，不代表它检查过了。**
>
> 同一条在代码里的样子：`winid::empty_agrees` 比的是两张登记表**空不空**，不是**在不在**。
> 一张剩三个、另一张剩两个是合法状态，它按设计沉默。而读日志的人分不出
> 「检查过，没问题」和「这条根本不在它的射程里」。

**可执行的做法**（每一条都是被上面某一格咬出来的）：

- **写过滤条件时，把「过滤的外延」和「自己实际造出来的东西」各列一遍。** 对不上就改
  条件，不是改结论。
- **取不到时要出声，不许静默返回空。** `windows/tools/uia-tree-dump.ps1` 是这么写的：
  `if ($p.Count -eq 0) { throw "no $ProcessName process is running" }`。
  上面第 3 格如果当初这么写，它第一次跑就会报错，而不是安静地返回「干净」。
- **用命令行文本过滤时排掉自己的 pid**，否则「还剩一个」永远为真。
- **地板记 pid / 句柄，不记个数。** 个数看不出「这几个是不是上一轮剩的」；
  这也是 E9「用句柄不用编号」那条的同一个理由。
- **陌生的父 pid 先查它是什么再下结论。** 「父 pid 是个我不认识的号」不等于
  「父进程已经不在」——那次查下来，那个号是量它的人自己。
- **凡是判据依赖一个默认值（配置的、系统的），把那个默认值写进判据**，并说明
  它和被测值相等时这一格没有区分力。**第 1 格是这么救回来的**：把系统设置临时从 3
  改成 5、读到 `per_notch=5`、再改回去——**改一个不该相等的值，是让这一格重新有
  区分力的唯一办法。**

###### 这一族能不能做成一道闸：**不能，而这是结论不是回避**

`windows/tools/` 有十五道闸，所以「再加一道」是本能的下一步。**这里不行，理由要写下来，
否则每隔一阵就会有人重新提。**

**五个实例的载体互不相同**：一个是配置项的默认值、一个是文档里的 PowerShell 名字、
一个是 shell 脚本的映像名、一个是正则匹配到自己、一个是不变量的射程。**没有一个共同
的文本形状。** 任何宽到能同时抓住它们的模式，会把每一处 `Get-Process`、每一个默认值
引用、每一条过滤都报一遍——**而这些绝大多数是对的**。

**一道天天误报的闸，会训练所有人跳过闸的输出**，那时它的代价不止是它自己没用，
而是**它旁边那些有用的闸也开始被跳过**。（对照：台账那道闸误报率量到 0，因为它管的是
一节固定结构的文档，载体单一。）

**窄的切法确实存在，但它们各自属于别的族，不属于这一族：**

- 「PowerShell 里 `Get-Process <裸名>` 必须带通配符或 `throw`」——这可以做成一道
  文本闸，**但它只能抓第 3 格**，而且这个仓库里 PowerShell 只有三个文件，
  **一道闸去管三个文件，不如把规矩写在这里**。
- 「判据引用了一个配置默认值，必须同时写出那个默认值」——**没有可靠的文本特征**，
  判据是散文。

**所以这一族只能靠文档，而这就是那份文档。** 一条写下来的规矩不会像闸那样每次都跑，
但它也不会把别的闸一起拖下水。**说「做不成闸」比造一道会误报的闸有用**——前者留下一个
准确的边界，后者留下一个所有人学会忽略的输出。

###### 同一条判据的另一面：什么时候**可以**做成闸

上面那段不是「这类事都做不成闸」，它是一条判据的一侧。**两侧要放在一起读，否则它会被
当成一句泄气话：**

| | 载体 | 断言的是 | 误报率 | 结论 |
| --- | --- | --- | --- | --- |
| 「作用域 ≠ 目标集合」这一族 | **五个互不相同**（配置默认值／进程名／映像名／正则自匹配／不变量射程） | **文本模式** | 宽到必然误报 | **写文档** |
| 「闸自己会不会在空树上放行」 | **单一**（一个目录里的同构脚本，每个都以退出码结束） | **一次真实的运行** | **结构上是 0** | **做成闸** |

**判据是两条合取，不是「载体单一」一条**：载体单一 + 断言行为 → 可以做；载体分散 +
匹配文本 → 不能做。**中间两格也要各自判**——载体单一但只能匹配文本（比如「判据引用了
一个配置默认值就必须写出那个默认值」），仍然不做，因为判据是散文，没有可靠的文本特征。

**「断言行为」为什么把误报率压到 0**：没有什么可以判断错。要么那个脚本在空树上返回
非零，要么它没有。**一个模式会对「看起来像」的东西开火，一次运行不会。**

后者就是 `windows/tools/gates-fail-on-empty.py`。它把每道闸拷进一棵主体为空的树里跑，
**要求退出码非零**；它自己带两个种下去的探针（一个有守卫的、一个没有的），**并且在找不到
任何一道闸时判自己红**——否则它就是第五道。

###### 为什么自检探针替代不了它

`windows/tools/` 那些闸都带正反两个探针，那是好的，但探针防的是前两种。
**一个构造出来的探针，测的是实现符不符合作者的模型；一个真实的病样本，测的是那个
模型本身对不对。**

E11 的第一版就死在这里。它写的是「同一个 `wN` 出现在两个不同句柄的配对行上即红」，
而作者（我）对那个 bug 的模型是「配对行里会出现重复的号」。**照那个模型构造的探针
会通过，判据也会通过，而 bug 原封不动**——因为重编号根本不发生在配对行上：`assign`
每个句柄只登记一次、当场发号，那一行在有病的构建里也是对的；号是在**读**的时候
才变的。拿六份旧日志跑一遍，六份全绿——**这就是发现它的方式，而且没有别的方式。**

###### 同一条判断，用对过一次也可能第二次想不起来

**这不是一条新道理，它当天在另一处已经被用对了。** `line-number-references.py` 的
反向自检用的**不是**构造的近似例，而是从这棵树里原样抄来的五条真实误报，理由写在
那个文件里：

> 一个构造出来的近似例只证明作者想象过这种失败；这五条证明它发生过。

**同一个人，同一天，在一个地方用对了，在另一个地方没想起来用。** 所以这条要写在
纸上而不是留在人的判断力里——**一条只在需要它的时候才想得起来的规矩，等于没有。**

##### E8 / E9：朝没人问过的方向问

**这一格的教训与 B1 其余五格是同一条**：判据写在实现之前是对的，但 E1–E7 全部朝
一个方向问。**一个只朝一个方向问的判据集，会把它的反面留在暗处，而且全绿。**

**E8 —— 关掉最后一个窗口的最后一个标签，进程必须退。**

> **前提不是「最后一个标签」，是「这个进程生命周期里已经关过窗口」。**
> 真机量出来的就是这个：关过至少一个窗口之后，再关最后一个才复现。写成
> 「关最后一个窗口的最后一个标签」的话，**单窗口跑一遍是绿的**，而那正是这条红
> 藏了一整轮的原因。
>
> **N（先关掉几个窗口）至少取 1 和 2 各跑一遍。** 编号是数组下标加一、会被回收
> 复用，说明这里的计数**有别名**；只测 N=1 可能刚好躲开一个别名恰好抵消的排列。
>
> 四条关闭路——菜单 / 标签条的叉 / 窗口自己的 X 或 Alt+F4 / 核心的 `close_window`
> ——**各跑一遍，不要抽一条**。`winid.rs` 的 `CloseVia` 就是为这件事存在的，
> 它自己的注释写着理由：四条路终点相同，所以只记终点的日志说不出人走的是哪条，
> 而**只修好三条的实现看起来是完整的，直到有人用第四条——窗口自己的 X，
> 也就是人用得最多的那条**。
>
> 每次读四项：
>
> 1. 最后一次 `[win] wN destroyed; M window(s) left`：**M 是几**，有没有
>    `-> quitting` 后缀，**以及这一行在不在**。不在也是读数，而且信息量最大：
>    `destroyed()` 是幂等的，frame 已不在表里时它一行都不打（`winid.rs`），
>    所以「没有这一行」说明这个 frame 在 `WM_DESTROY` 之前就被摘掉了。
> 2. 有没有 `[main] exiting: session flushed, ...`（**在消息循环之后**才打印，
>    所以它出现 = 循环真的走掉了）。
> 3. `tasklist` 里 pid 有没有消失。
> 4. 还在的话：`Get-Process -Name 'polter*' -ErrorAction SilentlyContinue |
>    Select Id,ProcessName,MainWindowHandle,MainWindowTitle`
>    ——`MainWindowHandle = 0` 即「没有窗口但还活着」。
>    **这一步原来写的是 `Get-Process polter`，而进程叫 `polter-host` / `polter-wt-<commit>`**，
>    不带通配符要求精确匹配，**所以它永远返回空，而空读起来就是「进程已经没了」**。
>    八次判定没有被它带偏，因为定案靠的是第 3 步的**那个 pid**（按 pid，不按名字）——
>    第 4 步是条件分支，八次都没走到。**它是一步死代码，不是一个假绿；但它是随时会被
>    当成读数的死代码。** 见本节「观测手段的作用域」一条。
>
> **通过 = 四条路 × N∈{1,2} 共八次，每次都是 `M = 0` 带 `-> quitting`、有
> `[main] exiting`、pid 消失。** 八次全过，这一格才可以翻绿。

**E9 —— 窗口计数里有没有混进不是窗口的东西。**

> E1–E7 全都在读日志里的那个数字，**没有一条问过这个数字本身可不可信**。
> 而 `of()` 从前会给任何非空句柄发号，`dad9a8194` 已经因为这个踩过一次（只堵了
> null），`57c7384a9` 是第二次。
>
> **判据（纯读日志，不需要复现缺陷）**：日志里同一个 `frame 0xH` 的配对行
> `[win] wM = frame 0xH` **出现两次即红**；等价地，紧跟在 `destroyed;` 之后
> 出现的配对行，其句柄若等于刚被报告销毁的那个，即红。
>
> **不要用编号写这条判据。** 第一版写的是「每个 `wN = frame` 都要有对应的
> `wN created`」，真机把它否了：**本轮的幽灵编号正好是 w2，而 `w2 created` 是
> 有的**——号是数组下标加一，摘掉再入表就被回收复用了。**编号会复用，句柄不会。**
> 一条用会复用的值做身份的判据，在缺陷成立时是绿的，而它和一条真正通过的判据
> 长得一模一样。

**E10 —— 正常运行的日志里，`w?` 只许出现在三个地方。**

> `57c7384a9` 让 `tag()` 对「不在 `winid::FRAMES` 里的句柄」回答 `w?`。这个字符串
> 是那些「两个登记表暂时不一致」的瞬间**唯一可见的形态**，所以它可以当探针用——
> 但只对其中一个瞬间有效，见下面的边界。
>
> **判据**：**任何出现在第一条 `destroyed;` 之前的 `w?` 即红**，请连整行原文报回来。
>
> **这条判据曾经有前半句，实测把它删掉了。** 原来还要求「每一个 `w?` 都必须是下面
> 三行之一」：`N window(s) remain`、`state dropped`、`[strip] interaction state
> dropped`。真机上出现的是**五种**形状——走核心那条路会多一条
> `w? [menu] pick "关闭窗口"`，走菜单那条路会多两条 `w? [tabmenu] …`。**它们全都
> 合法**：菜单的 pick 行是在动作跑完之后才写的，那时窗口已经拆了。按三行判，
> **八次里有四次会判红**。
>
> 留下的教训不是「少列了两行」：**一条按白名单写的判据，会把每一个它没预见到的
> 合法情形判成缺陷，而清单是照写作当天的代码列的。** 而「第一条 `destroyed;` 之前」
> 那一半不列举任何东西，它说的是一个时间关系，所以新增日志行不会让它假红。
>
> **地板**：这份日志里必须**至少有一个** `w?`。一个都没有，说明要么这一轮没关过
> 窗口，要么 `w?` 这条路根本没走通——那样「没有异常的 `w?`」不是通过，是没测到。
> （E10 的三条主断言全是「预期为空」性质的，一组全是预期为空的断言分不出
> 「预测中了」和「测量根本没发生」，所以旁边必须站一条预期非空的。）

**E10 的边界：它看得见哪些瞬间，看不见哪些**

> 「三个登记表」那两个必然不一致的瞬间（`per-window.md` 第三节的表），
> **E10 两个都看得见**——因为两个瞬间里 `FRAMES` 都说「否」，于是那里的日志行
> 会印 `w?`。
>
> **但这是做完 (乙) 之后才成立的，而这句话本身就是这条边界最该记的部分。**
>
> `57c7384a9` 之后一度存在第三个瞬间：`created` 之后、`tabs::add_window` 之前，
> `FRAMES` 说「是」而 `tabs` 说「否」。**E10 对它是全瞎的**——那里的 `wlogf!` 拿到
> 一个漂漂亮亮的窗口号，一个 `w?` 都不会出现。
>
> 一度以为 `window-tagged-logs.py` 的棘轮能兜住它（那个瞬间里 `hlogf!` 会退化成
> 无标签行）。**去读了那道闸，它兜不住**：它是源码静态扫描，按宏名分类调用点，
> `hlogf!` 被无条件算作已分类（那句
> `if macro in ("wlogf", "alogf", "hlogf")`）。在那两行之间新加一句 `hlogf!`，
> 基线 38 纹丝不动。
>
> **而那个瞬间的运行时特征是「缺席」不是「出现」**：`uia::live()` 返 false，于是
> `[uia] WM_GETOBJECT -> root provider` 那行**不被打印**；`tabs::window()` 返 `None`，
> 于是 `apply_min_max` 静默返回。**缺席无法用日志判据抓**——这才是 E10 不能被
> 拉长去盖住它的原因，比「字段对不上」深一层。
>
> 所以它不是被判据盖住的，是**被取消掉的**：两次登记收进了 `winid::created`
> 一个函数（见 `per-window.md` 第三节），中间没有地方可以站人。**一个既没有判据
> 也没有棘轮看着的瞬间，唯一可靠的处置是让它不存在**——这和 `assign` 私有化、
> `count()` 私有化是同一条：**能让它无法不成立时，就不要事后检查它成不成立。**
>
> **留下的缝，说清楚而不是假装没有**：`tabs::add_window` 仍是 `pub(crate)`，
> 全 crate 可达。Rust 没有「只许某个函数调你」这种词，所以「只有 `winid::created`
> 调它」是写在它文档里的一句话，不是编译器守着的规则。一个没写下来的约定和一个
> 没被注意到的第二调用者，从这里看是一样的。

**E11 —— 窗口编号有没有被复用。**

> `winid` 的编号从前是 `FRAMES` 里的**位置**加一，所以 `Vec::retain` 摘掉一个之后，
> 排在它后面的窗口全部前移。真机日志里出现过：创建时 `w1 = 0x1a009c`、
> `w2 = 0x2f07a0`，关掉 `0x1a009c` 之后，**`0x2f07a0` 自己被销毁那行写的是 `w1`**
> ——同一份日志里 `w1` 指过两个不同的窗口。修法是单调计数器（`081bc0546`）。
>
> **判据**，跨两种行做：
>
> - **A** = 全部 `[win] wN = frame 0xH` 里 N 的多重集（**发出去过的号**）
> - **D** = 全部 `[win] wN destroyed;` 里 N 的多重集（**销毁时用的号**）
>
> **任一成立即红**：D 里有重复的 N；或 D 不是 A 的子多重集（出现了从没发过的号）。
>
> 拿上面那份日志验：A={1,2}，关掉 0x1a009c 得一条 `w1 destroyed`，前移后的
> `0x2f07a0` 又得一条 `w1 destroyed`，D={1,1} → **重复 → 红**。修好之后 D={1,2} → 过。
>
> **地板**：`|A| ≥ 2` 且 `|D| ≥ 2`。只开过一个窗口的日志里「D 无重复」是因为 D 只有
> 一个元素，不是因为没复用——**那种绿和真的绿长得一模一样**。

**E11 的第一版是错的，写在这里而不是删掉**

> 第一版是：**「同一个 `wN` 出现在两个不同句柄的配对行上即红」**。
> 拿六份旧构建的日志跑（那些日志里这个 bug 确实存在），**六份全绿**。
>
> 原因：**重编号不发生在配对行上。** `assign` 对每个句柄只登记一次、当场发号并打那
> 一行——**在有病的构建里这一行也是对的**。号是在 `destroyed` **读**它的时候才变的。
> 所以只看配对行的判据，看的是这个 bug 唯一没有碰过的地方。
>
> **它为什么看起来很对**：E9 用句柄、E11 用编号，两条一对，方向互补。**对称让它
> 看起来完备**，而没有人问它能不能红——包括写它的我和批准它的主控。
>
> 这一版也从来没有进过仓，只活在一次对话里。**那本身就是它没被看穿的一个原因**：
> 没有人能把它和 E9 摆在一起读一遍。（同 E1–E7，见本节开头。）
>
> 判据错的方式比判据本身更该留档——和 E9 那次是同一条。

**这条判据被证明过能红，证据在下面**

> 本节开头那条规矩——**「拿一个已知有病的对象跑一遍，它必须红」**——这一段就是它在
> E11 上被兑现的记录。没有这一段，下一个读 E11 的人只知道**有人说**它能红，不知道
> **有人证过**；而「有人说过」和「有人证过」在文档里长得一模一样，那正是本节第三种
> 假绿在文档层面的样子。
>
> **全部取自 `ef243fdb2` 的产物，也就是 `081bc0546`（单调编号）之前。**
> 这一句是这张表能被重跑的前提：**在今天的构建上重跑这九份的做法会得到九个绿，
> 然后被读成「判据坏了」。** 要重现红，必须用修复前的构建。
>
> | 日志 | A（发过的号） | D（销毁时用的号） | 地板 | 结果 |
> | --- | --- | --- | --- | --- |
> | `e8w1.log` | {w1,w2} | {w1×2} | OK | **红** — w1 用了 2 次，只发过 1 次 |
> | `e8w2.log` | {w1,w2,w3} | {w1×3} | OK | **红** — w1 用了 3 次，只发过 1 次 |
> | `e8c1.log` | {w1,w2} | {w1×2} | OK | **红** |
> | `e8c2.log` | {w1,w2,w3} | {w1×3} | OK | **红** |
> | `e8x1.log` | {w1,w2} | {w1×2} | OK | **红** |

> | `e8m2b.log` | {w1,w2,w3} | {w1×3} | OK | **红** |
> | `p3.log`（新构建 `1fc0376c9`） | {w1,w2,w3} | {w1,w2,w3} | OK | 过 |
>
> 八份有病的日志覆盖四条关闭路 × N∈{1,2}；**九份的地板全部成立**（`|A|≥2` 且
> `|D|≥2`），所以没有一份是靠「样本太小」过关或失败的。
>
> **顺带一个读数值得单独看：八份里 D 全都是 `{w1×N}`。** 也就是说在旧构建里，
> **每一条 `destroyed` 行都说 `w1`**——那个号完全不携带信息。这八份的关闭顺序下
> 是这样；它是观察，不是对所有顺序的证明。

**为什么是「D 是 A 的子多重集」而不是「D 等于 A」**

> 第一版脚本写的是等式。**等式会把一份完全正常的日志判成红：进程结束时还有窗口
> 开着**——那种日志里发过的号比销毁用掉的号多，A ⊋ D，而那是正常状态不是缺陷。
>
> 这是本节第二种假绿（**它什么都抓**）的一个实例，而且它的代价和别的一样：一条会
> 在正常路径上开火的判据，会被关掉，**而关掉它的人不会回来**。

*（判据的规则形式由本文作者从缺陷的机制推出，上面九行读数与脚本由 WT 在真机日志上
取得——`/tmp/wt128/e11-multiset.py`，副本在它的 scratchpad。两者独立到达同一个规则，
但**实现以 WT 那份为准**：我推的是规则，它跑的是数据。）*

### 5.1e `ghostty.ps1` 两条分支的验证状态：**5.1 真机已验，6+ 引擎侧已验、Windows 侧仍是空的**

那个二选一的守卫，两支现在都被执行过，但**执行它们的不是同一种机器**，
所以两支能证明的事情不一样。

| 分支 | 条件 | 状态 | 在哪验的 |
| --- | --- | --- | --- |
| 5.1 回落（包 `prompt`） | 属性不存在 | ✅ 含守卫取反地板 | Windows 真机，Windows PowerShell 5.1 |
| 6+ （`LocationChangedAction`） | 属性存在 | ⚠️ **引擎侧已验、Windows 侧未验** | macOS 上的 pwsh 7.6.5 |

**6+ 那一轮拿到的读数**（`-File` 非交互跑法，仓库文件全程只读，
取反的副本生成在 scratchpad）：

```
HOOK=event                      走了这一支
LOCATION_ACTION_SET=True        钩子真的挂上了,不只是标记写对了
OSC 7 = 3 条 / 3 个不同目录      读字节,不读日志;第三次回到同一目录没有第四条(去重成立)
PROMPT_BEFORE == PROMPT_AFTER   逐字相同(-ceq),len=211
```

**`LOCATION_ACTION_SET` 是必要的第二个读数**：`HOOK=event` 只说明
**代码走了那条分支**，不说明**那一行赋值成功了**——而 115 的整个缺陷
正是「走进了分支、赋值炸了」。

**地板里真正的本体是那个没变的信道**：

| | 原样 | 取反 |
| --- | --- | --- |
| `HOOK` | `event` | `prompt` |
| `LOCATION_ACTION_SET` | `True` | `False` |
| `PROMPT_IDENTICAL` | `True` | `False` |
| **`HAS_EVENT_PROPERTY`** | **`True`** | **`True`** ← **不变** |

属性在两次里都确实存在，**变的只有守卫**——所以这组读数排除的不是
「两次环境不同」，**而正是「守卫在挑」**。

**模块注释里那句 `on 6+ this file never touches the user's prompt`，
至此从一句断言变成一条读数**，而且取反那次 `PROMPT_IDENTICAL=False`
证明这个探针有分辨力，不是一个恒真的断言。

#### ⚠️ 两处会被读宽的，先挡住

1. **取反那一轮 OSC 7 只有 1 条，不是 3——那不是 `prompt` 支坏了。**
   `-File` 是非交互的，`prompt` 函数根本不会被调用，所以那一支在这种跑法下
   只有启动那一条。**`prompt` 支的 `cd` 追踪是在 Windows 真机 5.1 上验的
   （三次 `cd` 三条 pwd）**——两条证据来自两台机器、两种跑法。

2. **这是 macOS 上的 pwsh。** 能力检测、事件挂载、`cd` 触发、OSC 字节生成
   都是 PowerShell **引擎**行为，与操作系统无关，所以是真验;
   **但「Windows 上的 pwsh 7 会不会有别的行为」这一格仍然是空的**，
   它和 ConPTY 那一格是**两件不同的未验**，不要合并成一句「Windows 未验」。

### 5.1f ⚠️ Windows 上没有任何写法能给 `command` 传一个带空格的参数

真机验 111 的 P7 时撞到的,**而挡住半轮的不是这个限制,是一句指错路的注释。**

| 写法 | 怎么切的 | 能不能表达 `"a b"` |
| --- | --- | --- |
| `command = x -a "a b"`（默认 shell 形） | Windows 上 `tokenizeAny(v, " \t")` | ❌ |
| `command = direct:x -a "a b"` | `splitScalar(str, ' ')` | ❌ |

**两条路都不行,而 `Exec.zig` 原来的注释把用户指向第二条**,说它
`takes an argv array as-is`——那句话对**程序里构造**的 `Command` 成立,
对**配置文件里写**的不成立(`config/command.zig` 的 `parseCLI` 同样朴素按空格切)。

**代价是可测量的**:真机上那一轮的读数是「参数没生效 ＋ `shell could not be
detected`」两件事同时发生,而验证者**判不了是自己写法错还是缺陷**——
因为仓库里唯一一句谈这件事的话告诉他那样写是支持的。
**一句指错路的注释,比没有注释贵**,贵在它把「不知道」变成了「知道了一件错的」。

已做的两件:注释改成说出实情(并写明它原来说了什么);
`config/command.zig` 里加一条**断言这个限制**的测试——
`direct:cmd "a b"` 切出 **3** 个参数,引号是普通字符。
**写成测试而不是只写注释**,是因为原来那句就是注释,而**错的散文安静地一直错着**;
哪天有人给这个解析器加上引号支持,这条测试会红,**那正是该被发现的时刻**。

**没做的**:让它真的支持引号。那是核心行为、影响所有平台,不在这一档里。
所以这条今天是一个**已知且已写下的能力缺口**,不是缺陷单。
