## 1. 定位

**群不是项目。** 项目与 agent 无关：它是布局、目录、历史。群与 agent 强相关：它是一件正在做的事，有人在管、
有人在干、有话要说。两者不合并；群只记一个工作目录，不依赖项目，也不改项目。（用户定）

**总控台是 Polter 的主力窗口：只看这一个界面，就知道哪个群在等你，并且能当场处理，不必关心开了多少
tab 和分屏。** 它取代现在的「终端群聊」页成为入口；群聊、任务、统计都留着，变成它里面的页签。

要解决的事只有一件：同时开着几个总管、很多群以后，用户又回到了一个个 tab 去看谁在等他。下面每个决定都
用这一条来衡量。

三条已定的约束（用户定）：

1. **第一维度是群**，不是终端，不是会话。群跨重启保留；总管是「现在谁在管这个群」。
2. **纯原生**。不做 TUI，不做两平台共用的网页。mac 与 Windows 各写一套界面；状态、排序、文件记录、
   用量累计全部在核心算好，界面只画。性能是验收判据（§13.2）。
3. **冷启动不要求起名**，重开后**一键开总管接手**（§6）。

### 1.1 这条路走过一次，这次哪里不一样

mac 上做过一个原生的群聊窗口，用户用过后否掉了，窗口、C 接口、菜单全部删除，回到了终端里的 TUI
（`dev-docs/poltergeist/chatui.md:171-208`）。那次记下的账是：四条不满里只有一条是渲染方式造成的
（比例字体、代码对不齐），另外三条是数据不够（看不出谁在说、几点说的、群里有几个人）。

这次重新做原生，理由是用户定的「最高频的界面，性能优先」。但那四条不能再犯一遍，所以本文把它们写成
约束而不是留给实现去碰：

- **数据先于界面。** 第一期先交付核心的快照与排序函数，带测试；界面在它之上只画。上次是界面做完才发现
  数据不够。
- **凡是终端里的内容，就用终端画。** 总管的屏幕、它最后一轮说的话里的代码，不在原生控件里用比例字体
  重排。第 ③ 档直接显示真终端（§7）；消息正文用终端的等宽字体与同一套回退字体。
- **C 接口这次是必要的。** 上次的结论是「TUI 走 socket 就够，不必加导出」。原生界面没有这条路：
  群与任务数据在 `156fa1785` 上没有任何给宿主的导出，只有 TUI 每 500 ms 经 socket 轮询
  （`src/cli/chat.zig:56,187`）。§5.4 给出要加的导出，并限制它的面。

## 2. 名字

**中文「总控台」，英文 Control Room。**（用户定，2026-10-11）

- 避开 macOS 自带的 Mission Control，也避开各家都在用的 dashboard（那个词暗示「只能看」）。
- 「总」对上产品里已有的「总管」；「台」是一个你坐在那儿操作的地方，不是一张报表。

备选：

| 名字 | 好处 | 问题 |
|---|---|---|
| 值班台 / Watch Desk | 直说「谁在等我」这件事 | 听起来只有监看，没有「在这里把事办了」 |
| 指挥台 / Command Deck | 强调下指令 | 和「命令面板」（Command Palette）撞词 |
| 群 / Groups | 最老实，第一维度就是群 | 说不出它是主力窗口，和群聊页签分不开 |

### 3.2 左栏的一行

本文别处说的「卡片」，在定稿里就是左栏的一行。

**用户定的（2026-10-13），原话：**

> 我要的是一眼看出谁在等、等什么，然后自己进终端去处理

> 等了几分钟 这个我实在想不出，除了提示用户你很久没处理了，没有半点作用，包括左下角图形，也没有任何作用。

> A比较好，可以加宽，先这样看看

所以一行答三件事——**哪个群、谁在等、等什么**——别的都让开。「等了几分钟」的数字、左下角「今天让你等过的」
时间带、右栏标题条右端的分钟，全部撤掉了（任务 #1435），快照里对应的 `waited_min` 和 `band` 也拿掉了，不留
没人读的字段。先后已经由顺序说了：等得久的在前（§4.3），那是核心内部的事，不外露成数字。设计稿是 v18 的
方向 A（不在仓内），渲染图在设计资料的 `build-05/`。

**在等你的行**（高度跟着内容走：第一行 24，下面每行 20，上下各留 8）：

1. 最左一列是状态图形。所有行、包括不用你管的行，图形都站在同一条竖线上，眼睛顺着这一列往下扫。
2. 第一行：群名（等宽字体）；右端先写**谁在等**，再写状态的字。
   - 谁在等是核心给的（快照的 `waiter`，§5.4）：群的总管自己，写「总管」；它手下的某个 worker，写
     「ios-build，经总管」（名字用等宽字）；没有总管的群里的 worker，只写名字。宿主只把核心给的那个词
     换成字，**不拿 `steward` 和终端号去比**——有一道闸守着（`tools/control-room-hosts-do-not-decide.py`
     第 5 条）。worker 的名字**暂定**取它终端的标题，这是总控台手里唯一的名字。
   - 状态的字说的是**具体哪一种**——图形只有四种（§3.5 第 2 条），「等批准」还是「等回答」、「出错」还是
     「疑似卡住」由这几个字分开。
3. 下面是**等什么**，是这一行里最重的内容：用主要的字色，占满这一行的宽（322，放 41 个等宽字符）。
   是命令还是话由核心说（快照的 `what.form`），宿主不靠来源去猜：
   - 命令用等宽字，**一步一行**：核心按 shell 的规矩把命令切成步骤（`src/poltergeist/ShellSteps.zig`），
     在引号外的 `&&` `||` `|` `;` 和换行处断，接头留在它引出的那一步开头；引号、转义、`$(…)`、反引号、
     括号、heredoc 里面不断。切不了的（引号没闭合、不像 shell）整条一段。只有 `Bash` 工具的输入按 shell 切；
     文件工具的路径、PowerShell 的命令原样一段，也用等宽字。
   - 问句、出错的说明用界面字。
   - 核心给的是**它拿得到的全部**，并说明是不是全文（快照的 `what.cut`，§5.4）：
     - 等批准：hook 带来的全文（上限 16KB）。
     - 等回答：对话框式的提问（`Notification` 的 `elicitation_dialog`）取它的 `message` 全文；写在话里的提问
       （hook 只说「在等输入」，`message` 是一句套话，不取）取**上一轮最后一段**的全文，前面还有别的段落时标成
       「这是结尾」，行首有省略号。原先这两种都只有 hook 的一行摘要，而真实的 `Notification` 连摘要都没带。
     - 只拿到一行摘要、而且摘要顶到了上限（总线留 160 字节，`+hook` 的摘要是 120 个字符）：标成「这是开头」，
       行尾有省略号。短于上限的摘要就是全文。
4. **放不下时截的是一行的末尾，不是一步**（上限在外观表里，两项都是**暂定**）：
   - 一句话最多折三行（`ask_max_lines`），最后一行以省略号收。
   - 三步以内的命令：每一步先各占一行，剩下的行给最先需要折行的那一步；还放不下的那一步在它自己的最后
     一行以省略号收。
   - 多于三步的命令**不压回三行**：一步一行，行跟着长高，每一步的开头都露在外面——危险的那一步可能正好
     是第四步。到六行为止（`ask_max_steps`）；再多，前五步各一行，第六行写「还有 N 步」，不无声地吞掉。
   - 全文在悬停提示里（每步一行），读屏读的也是全文。
5. 群里另有终端也在等时，「等什么」下面多一行次要色的字：「还有 1 个」。设计稿这一轮没有画这种行，
   位置是**暂定**的：单独一行最不挡别的东西，代价是这一行高 20。定稿去掉了原先「一个 worker 一个小点」
   的那一排（§10.1 第 11 条）；worker 各自的状态在右栏的层叠标签与分屏标题条上看。
6. 状态来源过期时，停因后面跟一个灰色的「？」和年龄（§4.2）。定稿没有画这一项，也还没做。
7. **行上不放处理按钮。** 一行只提示「有人在等你、等的是什么」——图形、谁在等、状态的字、等什么、「还有 N 个」——
   人自己进终端去处理。用户定的（2026-10-12，看了带勾叉的渲染图 `build-02/` 之后），原话：
   「不太行，这个勾叉是同意确认内容吧，但是左侧按钮这么小界面根本看不清，不要做这个，还需要让agent调特定mcp来执行，而且很多时候不是同意否则这种是非，会比这个复杂的多，只要提示出来」
   总管的理解：左栏的一行太小，看不清要批准的到底是什么；真实的提示常常不是「同意 / 拒绝」两选一。
   - 曾经做过一版（任务 #1428）：等批准的行右端有勾与叉、`Y` / `N` 键、被拒绝时就地一句话、读屏上两个动作，
     快照里为它加过一项 `approvable`。**全部撤掉了**（任务 #1433），那一项也从快照里拿掉——它只为按钮存在。
   - 底层没有动：核心照旧接受批准、拒绝、回一句（`ControlAct.zig`），两个宿主里写这三种请求的那几行也留着，
     只是没有任何界面入口。总控台现在只发「已看」。
   - 有一道闸守着这件事：`tools/control-room-rows-only-tell.py`（行上再出现按钮、或总控台里再有地方发这三种
     请求，就红）。

**核心实际给的停因**（快照每行的 `reason`：`from`、`text`、`missing`）：

| 状态 | 停因取自 | 取不到时 `missing` 写什么 |
|---|---|---|
| 等批准 | hook 的 `note` | `empty_note` |
| 等回答 | hook 的 `note` | `empty_note`；若是自报提上来的，`self_report_text`（自报还没有，见 §4.2） |
| 出错 | hook 的 `detail` 与 `note`，写成「类型：说明」；进程异常退出写「进程退出」 | `empty_detail` |
| 疑似卡住 | 「屏幕 N 分没动，M 分没调工具」；hook 约好没来写「约好的 hook 没有来」 | — |
| 做完了，没看 | 它最后一轮的话的最后一行（§4.2 第 3 条） | `no_turn_kept` |
| 停了，原因不明 | 「屏幕 N 分没动」 | — |

取不到的不留空串冒充：`text` 为空时 `missing` 一定说明是哪一种取不到。这几句话是**暂定**的措辞，集中在
`ControlRoom.zig` 的 `Reason.words`。「疑似卡住」「停了，原因不明」这两种停因里仍然带着「N 分没动」——那是
在说它为什么被判成卡住，不是在说你等了多久；这一轮没有动它。

**在干活的群此刻在做什么**（`reason.from` 是 `task`）：取这一行所说的那个终端自己的、面板上进度是「进行中」的
任务的标题，有几条取编号最大的。这是三个候选里唯一诚实的来源：hook 只在调工具的那一瞬间带工具名和参数，
说的不是「在做什么」；自报这条通道还不存在（§4.2）。没有这样的任务就**留空，不编**。任务被关掉或改了进度，
下一次快照这句话就没了；标题本身写得不准时照样显示，这一点核心管不了。

**不用你管的行**（一行高，28）：图形站在同一列里，后面是群名（等宽），再后面一句此刻在做什么（次要的字色，
放不下以省略号收，全文在悬停提示里）。做完没看的写它最后一轮的最后一行，在干活的写它正在做的任务；核心
不知道在做什么时，这里退回状态的字（「在干活」「做完了，没看」）。闲着的只有名字，退后一级，没有图形。
设计稿去掉了这种行上的状态字；读屏仍然读出来。在等后台任务的归在「在干活」。

**没有群在等时**（核心给的 `groups_needing_me` 是 0）：标题写「没有群在等你」，下面直接是各个群，没有分隔线，
没有第二个标题。

**选中的行**是一粒亮片，别的行没有底（§3.5 第 5 条）。

正常的东西不占地方，颜色只给需要用户的。

### 3.4 Windows 的差异

布局、分段、每一行的内容、排序完全相同，都出自核心。差异只在这几处（视觉定稿只出了 mac 的图，
Windows 版照 §3.5 的同一套规矩画，没有单独出图）：

- **画法**：Windows 宿主的非终端窗口全是 Win32 + GDI + 标准控件，没有 Direct2D
  （`windows/host/Cargo.toml:72` 只开了 `Win32_Graphics_Gdi`）。总控台照设置窗口的做法：
  纯逻辑放进一个能在 mac 上测的 crate，窗口只负责画。
- **窗口**：两边都是标签栏里的一个标签页。mac 已经是这样（主窗口的第一个标签页，可以拖出去成为自己的
  窗口）。Windows 也定为标签栏里的标签页、可以拿出去；它的标签栏与标签页是宿主自己画、自己管的，没有
  「不含终端的标签页」这个现成的东西，怎么做与分几步见 `dev-docs/windows/control-room.md`。
- **快捷键**：mac 的 `⌘` 换成 `Ctrl`，其余键位相同。
- **系统通知**：走 Windows 的通知中心；任务栏按钮上的数字用覆盖图标。
- **权限面板**：Windows 不需要 mac 那些授权提示。

### 3.5 视觉定稿

来源是设计稿 v12–v18（不在仓内）：以 v14 为底，层叠标签的缩进取 v13 的，选中的样子取 v17 的，左栏的行取 v18 的方向 A（2026-10-13 用户选的）。
v15、v16 两轮作废，不引用。用户看过后说可以开发（2026-10-11）。

**下面的数都是设计稿上的读数，不是产品上的。** 长度单位是 pt。标「暂定」的是总管代定、用户还没有
明确表态的，汇总在本节末尾。

**1. 配色：「雾银」，亮、暗两版。**

- 亮色版整个是亮的：银灰的窗口底，上面浮着白的面；终端也是亮底、深色的字。
- 暗色版用同一套处理换到暗处：窗口底最暗，上面浮着亮一级的面，终端是暗底、浅色的字。
- 两版共用的六条处理：
  1. 层次靠浮起来和又软又大的投影，没有挖下去的面；越要紧的面越亮。
  2. 左栏是一片独立的面板；面板里没选中的行没有底、没有边，行之间只有留白。
  3. 窗口标签栏的轨道很淡，选中的那一片亮而浮。
  4. 层叠标签不描边，当前标签和内容区同一种底色；worker 的标题带下面没有线。
  5. 状态的字带颜色：「等批准」这几个字直接用状态色写。
  6. 边极淡：0.5 的线，分隔主要靠留白。
- **不设品牌强调色，带颜色的只有状态。** 不再沿用截图工具的设计语言；截图工具以后跟着这边改。

**2. 状态：给人看的只有四种。**

核心算出来的类别不变（§4.3），显示时归并：

| 给人看的 | §4.3 的类别 | 图形 | 颜色 |
|---|---|---|---|
| **等你** | 1 等审批、2 等回答 | 气泡 | 蓝 |
| **出问题** | 3 出错、4 疑似卡住 | 带叹号的三角 | 红 |
| **做完了，没看** | 5 一轮结束未看 | 圆点（小一号） | 蓝 |
| **在干活** | 7 在干活 | 转圈 | 中性 |
| （不画图形） | 8 闲着；下班；普通终端 | — | — |

- **具体是哪一种，由旁边的字说**：等批准 / 等回答 / 出错 / 疑似卡住。图形只负责让人一眼知道
  「要不要管」。
- **优先级：等你 > 出问题 > 做完了没看 > 在干活。** 一个位置只画一个图形时取最高的。
- **被按住、被护住**（核心里的 `held`、`shielded`）不进窗口标签页和群列表，只出现在那一格分屏的
  标题条上，并且带字（暂停的图形 +「被按住」）。
- **状态不只靠颜色**：四个图形形状互不相同；同是蓝的两个，一个是气泡、一个是小圆点。
- 「疑似卡住」是推断，和「出错」共用红三角，在没有字的地方（窗口标签页）分不开。**暂定**共用。

这张表有三处对不上，都没有定，见本节末尾「与别处对不上的」。

**3. 图形的画法与动法。**

画法照系统图标：气泡是 `bubble.left.fill`，三角是 `exclamationmark.triangle.fill`，圆点是
`circle.fill`，转圈是系统的进度转圈。设计稿里是照样子自己画的路径（14 的画板），真做的时候直接用
系统的。

| | 怎么动 |
|---|---|
| 等你 | 等得最久的那一个慢慢地明暗（100% → 50% → 100%，2.4 秒一轮）；其余等你的不动；正在看的那个标签上不动 |
| 出问题 | 进入时左右晃一次（±2，0.3 秒），之后不动 |
| 做完了，没看 | 不动 |
| 在干活 | 一直转，1.2 秒一圈，一格一格地跳 |

连续地动的只有转圈和等你的明暗；同一个窗口里同时只有一个等你的在明暗。系统开了「减弱动态效果」时
全部不动，靠形状和颜色分。

**4. 窗口标签页。**

- 每个标签只有三样：最左关闭（系统的，悬停才出现）、中间标题（居中）、最右一个状态图形
  （14 × 14）。**不要数字，不要左侧标记。** 闲着的、普通终端的，右边空着。
- 选中的那一片用系统自带的样子。macOS 26 上系统的标签栏本身就是「一条槽 + 每个标签一片玻璃」
  （量到的：槽高 28、左右各缩 8，标签高 24、离槽边 2、圆角 12——与本节的网格同数），选中的那个标签的
  玻璃视图里画着玻璃，别的是空的；切换时系统不做动画。
- **切换时这一片滑过去**：只在切换的那一下，给新选中标签的那片系统玻璃加一段表现层动画——从旧标签
  的位置用同一根弹簧滑到位，途中抬起 8%、沿运动方向略拉长——播完自己移除
  （`macos/Sources/Features/Terminal/WindowTabChipSlide.swift`）。标签栏里不加视图、不藏东西、不改任何
  值；折射是系统玻璃自带的。找不到那片玻璃时（低于 26 的系统、系统改了内部结构）就是系统原样，不滑。
  系统开了「减弱动态效果」时不滑。**没在真窗口里看过**（§12.4）。
- 在干活在窗口标签页上**不画转圈**（**暂定**）：这样一排标签里有图形的，都是要你看一眼的。层叠
  标签、分屏标题条、左栏的行上照画。
- 状态图形放在标题右边的附加视图里。提交 `504f77013` 已经把这个位置收成一个写方并留好了加图形的
  地方：往 `TabAccessory.Item` 里加一个 case
  （`macos/Sources/Features/Terminal/TabAccessory.swift`）。
- **与代码不一样，没有定**：`504f77013` 上那个附加视图里现有四样——标签颜色点、Poltergeist 标记、
  `⌘1` 这类快捷键提示、还原缩放按钮。用户说的「不要数字、不要左侧标记」是对着设计稿里表示状态的
  数字和标记说的；Poltergeist 标记由状态图形取代（监管身份改由分屏框表达，见第 6 条）。快捷键
  提示、颜色点、还原缩放按钮定稿没有画，用户也没有单独说过，去留没有定——在定之前照现状留着。

**5. 左侧群列表。**

- 独立面板：**宽 380**（v18 方向 A；原先 308），圆角 12、内边距 6，里面的行圆角 6（12 = 6 + 6，同心）。
  加宽是为了「一步一行」：行内等什么的宽是 322，放 41 个等宽字符，常见命令的一步大多在 40 个以内；308 时
  只放 34 个。代价是 1440 宽的窗口里右边的终端从 1108 变 1036，少 9 列左右。窗口很窄时左栏该不该自己收窄，没有画，没有做。
- 行的左右内边距 12、上下 8，行与行之间 8；图形一列宽 14，与字之间 8。行高跟着内容走，选中片滑动的目标是那一行真实的框。
- 没选中的行没有底。**选中的行是一粒干净的亮片**：一道又软又短的投影，没有亮边、没有彩边。
  亮色版是往白里掺 72% 的一片，贴边 2.5 里一圈很淡的暗；暗色版是往白里掺 11% 的一片，贴边一圈
  很淡的亮。
- **切换时这一片滑到新的一行**：抬起来一点，用弹簧滑过去（周期 0.36 秒、阻尼比 0.72），到位冲过头
  约 4% 再回来；贴边一窄圈（停着 3、滑动时 6）折射它压到的字。片子里面是这一行选中时的字，外面是
  没选中时的样子。折射与回弹**暂定**保留。时长和曲线是对着参考短片估的。
- **折射不自己算**：macOS 26 上滑动的那一下，片子底下垫一层系统的玻璃，折射是它的；低于 26 没有
  这一层，只有抬起和滑动。**停着的片不带玻璃**（**暂定**）：停着时它后面没有任何实时的东西，旁边的
  终端怎么滚都不会让它重画。「片子里面是选中时的字、外面是没选中时的字」没有做：字在滑动开始的那
  一刻就整行换成了选中时的样子。系统开了「减弱动态效果」时不滑、不抬，直接换。
- 行里的内容见 §3.2。

**6. 分屏框三种。**

| | 边 | 标题 | 圆角 | 别的 |
|---|---|---|---|---|
| 总管 | 四周一圈 4 宽的边框 | 边框的上沿加厚成标题条 | 外 12，里面的终端 8 | 有投影，浮着；聚焦时边上那条线变深（暗色版变亮） |
| worker | 细线一圈（0.5） | 一条标题带，带下没有线 | 8 | 不浮 |
| 普通终端 | 没有线 | 没有带；标题退后一级，直接写在终端的底上 | 8 | 没有投影 |

- 标题条上从左到右：名字、身份的字（总管 / worker）；右端是状态图形、状态的字。没有分钟（§3.2）。
- 一眼看过去：有厚边、浮着的是总管；有一条带的是 worker；光的一块是普通终端。身份不占状态色。
- 被按住、被护住画在这里（第 2 条）。
- 监管身份因此不再靠窗口标签页上的标记表达（第 4 条）。

**7. 层叠标签。**

- 浏览器式。标签高 28；当前标签的底和内容区是同一种底色，上面两角圆角 8，**底部两角各用一段半径 8
  的反向圆弧接到内容区**，中间没有线；不描边。
- **标签条左右各缩进 20**：标签的身体到内容区左、右边缘都不小于 20。20 = 内容区圆角 8 + 直边 4 +
  反向圆弧半径 8（worker 的框里拆成直边 12 + 弧 8）；它也正好是终端文字的左边距，第一个标签和终端
  的字对齐在一条竖线上。缩进取 20 是**暂定**，另一个候选是 16（弧的脚紧接圆角的末端，两段弧连成
  一条 S 形）。
- 标签里名字在左、状态图形在右，和窗口标签页同一个顺序。末尾一个加号。
- **标签多到排不下时怎么办（挤窄、滚动、还是把加号挪走）没有定。**

**8. 沿用的规矩。**

- 最小字号 13。用到的字号只有 13（正文、标签、终端）和 15（左栏里群的名字）。
- 线只用 0.5 和 1：0.5 给一切边、分隔、高光；1 给加号与叉的线。没有第三个值。
- 留白：窗口边到一切 8；独立的框之间 8；框里到内容 12；总管边框到里面的终端 4；标签条顶到标签 4。
- 数字全部用等宽数字；群名和终端内容用等宽字体。
- 状态不只靠颜色（第 2 条）。

**暂定的（总管代定，用户尚未明确表态）：**

| # | 暂定的是什么 | 另一种 |
|---|---|---|
| 1 | 在干活在窗口标签页上不画转圈 | 画，一排标签里会有几个一直在转 |
| 2 | 疑似卡住与出错共用红三角 | 分成两个图形 |
| 3 | 暗色版较亮的面上，红字改白字 | 接受 3 左右的对比度 |
| 4 | 去掉小饼图 | 留着 |
| 5 | 选中片的折射与回弹保留 | 只留抬起和滑动 |
| 6 | 层叠标签的缩进取 20 | 16 |
| 7 | 层叠标签排不下时怎么办 | 未定，没有暂定值 |
| 9 | 群列表的选中片停着时不带系统玻璃，只在滑动时带 | 停着也带（停着的玻璃在它后面的内容变化时要重新合成） |
| 10 | 低于 macOS 26 时窗口标签页的选中片不滑 | 在原生标签栏上另盖一片自己画的 |
| 8 | 终端窗口设了半透明（`background-opacity` 小于 1）时，总控台不跟着变透：它的窗口照旧不透明（真机读数：终端窗口不透明关着、底色 alpha 接近 0，总控台窗口不透明开着、底色 alpha 1） | 跟随，整个总控台透出桌面 |

§3.1 对照表里的六处也是暂定，不在这里重复。

**与别处对不上的（没有定，写在这里免得各自猜）：**

- **「八种」对「九类」。** 设计稿说底层是八种状态（等批准、等回答、出错、疑似卡住、有结果没看、

### 3.6 左下角的额度

（用户定，2026-10-13：v19 做法三。设计稿 `control-room-design/v19/`，做出来的图 `build-08/`。）

所有 agent 共用一份订阅额度，撞上限时所有群一起停。这一块让人在撞上之前回答三件事：还要不要再开
agent、要不要让某个群先停、还要多久恢复。**一行是一个账号，不是一个 agent。**只画已用的百分比和恢复的
时刻，没有绝对量，没有钱（§8.2）。

**画出来的样子。**固定在左栏底部，不跟列表滚。

| 状态 | 画什么 | 高 |
|---|---|---:|
| 平常 | 一行：「额度已用　Claude 61%　Codex 20%」。每家取它几段里用得最多的那一段；是哪一段、另一段多少、数是什么时候的，悬停给出 | 38.5 |
| 过八成 | 那一家从这一行里拿出来，在上面展开：红字「Claude 5 小时已用 92%」，右边「40 分钟后恢复」，下面一条通栏的红条 | 88.5 |
| 用完 | 同上，加三角，写「Claude 5 小时的额度用完了」，右边写时刻「13:40 恢复」，条是满的 | 88.5 |
| 用完，另一家有余量 | 条下面多一行「Codex 还有余量。」 | 112.5 |
| 数旧 | 数字退一级，后面写「，3 小时前」；展开的那一家的条只剩一圈线、不填实 | — |
| 已过恢复时刻 | 那一家写「已恢复」，旧的数不写 | — |
| 读不到 | 那一家写「读不到」，不画条，不写 0 | — |
| 一个数都没有 | 「额度　还没有数」 | 38.5 |

没有新颜色：平常是中性的灰，过八成和用完都用已有的那个红，三角只在真的用完时出现。尺寸在外观表的
`quota` 一组（`src/input/control-room-look.json`）。这一块没有任何可以按的东西。

**谁算。**全部是核心算好的（`src/poltergeist/quota.zig`，快照里的 `quota`；形状写在那个文件头）：哪一家
展开、哪一家留在那一行、数旧不旧、过没过恢复时刻、那句出路写不写、恢复的时刻用哪种说法。宿主只把核心的
词换成人的话，格式化一个数和一个时刻；宿主里没有「八成」这个数。不认识的词整份快照不读。

规则（都是**暂定**，每一条在 `quota.zig` 里各有一条测试）：

- **线在 80**：`quota.near_percent`，只写在这一处。到 100 才算用完（百分比向下取整，99.6 是 99）。
- **数旧**：数的时刻距现在满 60 分钟（`quota.stale_after_ms`）。不满两天按小时说，之后按天说。
- **已过恢复时刻的那一段不算数**：一家的几段里只看还没过恢复时刻的；全都过了，这一家写「已恢复」。
- **出路**只在用完时写，而且只在另一家的数不旧、没过八成、读得到时写。只写「还有余量」，不写「可以把活
  换过去」：Polter 没有那个动作。
- **恢复的时刻**：过八成时写还有多久（90 分钟以内按分钟，两天以内按小时，之后按天）；用完时写时刻
  （一天以内只写几点，之外带日期）。
- **用 API key 的账号不出现**：它没有窗口。**拿不到数的 CLI（Gemini、opencode、Qwen、Copilot、Cursor）不出现**，
  也不写「读不到」；「读不到」只用于本该有数而读失败的两家。

快照里有会自己变的东西了：展开的那一家按分钟倒数，所以这时核心每分钟醒一次；平常那一行只在数变旧、
某一段到了恢复时刻时醒。额度的时刻都在墙上时钟上，而唤醒走的是核心自己的钟（机器睡着时不走）：
机器睡过一觉以后，这一块要等到下一件事发生才追上。`at_ms`（数的时刻）不参与 `rev` 的比较。

**数从哪来。**两家都是读文件，都在核心的一条线程里读，不在 app 线程上（`src/poltergeist/QuotaWatch.zig`）。
没有定时器：终端里有事发生时才读，等 1.5 秒让文件落盘；期间又有事，15 秒后再读一次。

- **Claude Code**：它把账号的额度交给状态栏命令（stdin 里的
  `rate_limits.{five_hour,seven_day}.{used_percentage,resets_at}`，百分比与 Unix 秒；2026-10-13 在 2.1.296 上
  实际取样证实：一个会话的第一次应答之后才有这一项，之前没有）。这是 Polter 能读到它的唯一地方。所以
  **只对 Polter 按角色启动的会话**，适配器在带 hooks 的同一个 `--settings` 里把 `statusLine` 设成
  `'<polter>' +statusline --cli claude-code`（`plugins/claude-code/adapter.py`；条件与 hooks 完全相同，
  没带 hooks 的会话也不带它）。`+statusline`（`src/cli/statusline.zig`）把额度写进
  `<状态目录>/quota/claude.json`，别的什么都不做。
  - **用户原来的状态栏照旧。**适配器按 Claude Code 自己的先后找到这个会话本来会用的那一条（角色自带的
    `--settings`、项目的 `settings.local.json`、项目的 `settings.json`、用户的 `~/.claude/settings.json`），
    把它的命令放进环境变量 `POLTER_STATUSLINE_CHAIN`，它的其它字段（`padding` 等）原样留在 `statusLine` 上。
    `+statusline` 用同一份 stdin 起它，它的 stdout 和 stderr 直接就是 Claude Code 的——这边不读，所以
    改不了；退出码也是它的。有一条测试在真进程上量：一条带颜色、非 UTF-8 字节、NUL、不以换行结尾的输出
    逐字节不变，它读到的 stdin 也逐字节不变。**用户的设置文件只读不写。**
  - 用户自己手开的 claude 没有这一条，也就没有数：这一家显示上一次的数并慢慢变旧，或者「还没有数」。
  - Windows 上不带：状态栏没有 exec 形式，是交给当地 shell 的一行，同一个字符串在 Git Bash 和 PowerShell
    里引号的写法不一样（#888 同类）。
- **Codex**：只读它自己的会话记录 `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-*.jsonl`，每条 `token_count` 行带
  `rate_limits.{primary,secondary}.{used_percent,window_minutes,resets_at}`（在 codex-cli 0.142 写的记录上
  证实）。取最近三个有记录的日期目录里最新的五个文件，从尾部往回读 256 KB，取时刻最新的一条。免费档只有
  一段 30 天的窗口；用 API key 的记录两段都是 `null`，不出现。

**两个账号。**两家给的东西里都没有账号标识（Claude Code 的 stdin 里没有；Codex 的记录里只有 `plan_type`、
`limit_id`，分不开两个同档的账号；凭据文件没有读，也不该读）。所以**一家就是一行**：同一家登了两个账号时，
这一行是最后报数的那一个。任务说明里的备选是「合成一行取最大」，没有照做：同一个账号的多个会话里最后
报的那个最准，取最大会让一个已经重置的旧会话的数压住新数。

**没验证的：**

- 没有在真 app 里看过这一块（离屏渲染与设计稿并排过，`build-08/`）；真实会话下从 statusLine 到左栏这一整条
  没有走过。
- 用户没有自己的状态栏时，Polter 的那一条什么都不输出。Claude Code 对一条空的状态栏会不会留一行空白，
  没有看过。
- Claude Code 用哪个 shell 跑状态栏命令没有证实；`+statusline` 用 `/bin/sh -c` 跑用户原来的那一条。用户的
  命令如果依赖别的 shell 的写法，结果可能不同。
- `+statusline` 每次刷新起一个进程（状态栏在 agent 说话时一秒刷新几次）。花多少时间没有量。
- 列表很长时，行会画到这一块底下：列表本身还不会滚，也不裁剪，这是现状，不是这一块引入的。
- Codex 续接一个更早日期的会话时，那个文件不在最近三个日期目录里，新数读不到。
- Windows 宿主不画这一块；`windows/control-room` 读得进它、算得出它的高度，对照闸逐项比过。

## 4. 数据模型

### 4.1 群要多记的

`156fa1785` 上，群在内存里是 `name / created_by / next_seq / log / members / brief / last_ms`
（`src/poltergeist/Chat.zig:200-227`），而**写回磁盘再读回来的只有两个字段**：`brief` 与 `listed`
（`src/poltergeist/GroupLog.zig:221-238`），群名取自目录名。工作目录、角色、会话编号都没有。

群的记录文件新增这些字段，都是可选的，旧文件读进来等于「都没有」：

| 字段 | 含义 | 谁写 |
|---|---|---|
| `cwd` | 这个群的工作目录，一个 | 冷启动时用户选的；`group_set_cwd` |
| `steward` | 上一任（或现任）总管：`{ role, cli, session_id, since_ms, ended_ms }` | 核心，在总管入群、收到会话编号、离开时 |
| `auto_named` | 群名是自动取的，还没被改过 | 核心 |
| `seen_ms` | 用户上次看过这个群的时刻（§4.3 的「未看」靠它） | 总控台 |
| `snooze` | 先放着：`{ at_ms, until: next_event \| <时刻> }` | 总控台 |
| `archived_ms` | 归档的时刻；没有就是没归档 | 总控台 |

三点说明：

- **群名仍然是身份**，规则不变：1–48 字节，小写字母、数字、连字符
  （`src/poltergeist/Chat.zig:264-271`）。自动取名必须落在这条规则里（§6.1）。
- **`session_id` 现在只在内存**（`src/poltergeist/Bus.zig:300`），重启即丢。要恢复上一任的会话，
  必须在它每次变化时写进群的记录。
- **`listed: false` 已有含义，不借用。** 归档用新的 `archived_ms`，免得两种「不在列表里」分不开。

**重启后的上限要改。** 现在重启最多放回 24 个群（`max_groups` 32 减去预留，
`src/App.zig:1546-1569`），其余的留在盘上却没有办法再选出来——代码注释自己写了这是欠账。
群成了第一维度以后，这个上限会直接表现为「我的群不见了」。改法：首屏只把**活跃的**群装进内存；
归档与不活跃的群由总控台直接从盘上的记录列出来，点「恢复」才装进内存。

**已经做成的**（`group.json`）：`seen_ms` 与 `snooze`。两个都是**墙上时间**；旧文件读进来等于都没有，
没标记过的群写出来的文件和以前逐字节相同。重启以后：

- 「这次运行里看过没有」从空开始——重启后的群本来就是无人看管，新来的总管的状态都是新的。
- 「到下一个事件」的先放着，重启即结束（重启算一次变化）；「到某时刻」的照墙上时间继续。

`cwd`、`steward`、`auto_named`、`archived_ms` 还没有。

### 4.2 状态模型：机器事实，加一行自报

每个群有一个**关注状态**，由核心从下面几路信号算出。每一路都带来源与年龄；**「过期」与「不知道」是
画出来的状态，不是悄悄退回成「没事」**。

| 路 | 读的是什么 | 现在有没有 | 过期规则 |
|---|---|---|---|
| hook | agent CLI 自己报的状态：`idle / in_turn / ended / failed / awaiting_approval / awaiting_input`，加 `detail`、`note`、`waiting_on_background`（`src/poltergeist/Bus.zig:225-233,290-307`） | 有，但只有 Claude Code，而且只在按角色启动时装 | `hooks` 不是 `live` 就不读；`in_turn` 超过阈值且屏幕静止，降为「疑似卡住」 |
| 屏幕 | 屏幕多久没变（`quiet_ms`） | 有，但**只量被监管的终端**；总管自己没有读数 | 采样失败单列为「读不到」，不当成「没动」 |
| 调用 | 多久没调 Polter 的工具（`call_silent_ms`，默认 15 分钟，`src/poltergeist/Bus.zig:659`） | 有 | 它只是算术，只用来加重「疑似卡住」 |
| 进程 | 子进程退没退；这个终端的 agent 连没连着（`src/poltergeist/Server.zig:659`） | 有，但后者不在 `terminal_list` 里 | 进程没了，否决 hook 留下的任何旧状态 |
| worker | 每个 worker 自己按同一套规则算出的状态；任务面板的开着、卡住数量 | 有（任务）；worker 状态要新算 | 同上 |
| 自报 | 总管自己写的一行：在做什么、卡在哪、下一步（新工具，§5.1） | 无 | 带时间戳；超过阈值显示年龄；状态变了就标「说这话时还在上一个状态」 |

三条规则：

1. **机器事实定类别，自报只填那一行字。** 自报不能把「等审批」「出错」改成别的。
2. **自报只能把关注往上提，不能往下压。** 总管说「我卡住了，要用户定」可以让这张卡进「等你」；
   总管说「一切正常」不能让一张「出错」的卡离开「出错」。往上提错了只是多看一眼，往下压错了是漏掉。
3. **hook 的 `ended` 分不开「做完了」和「在用一段话问你」。** Claude Code 一轮结束时用正文提问，
   hook 报的是 `ended`，不是 `awaiting_input`（后者只对应表单式提问与空闲提示：装的是
   `Notification` 的 `idle_prompt|elicitation_dialog`，`plugins/claude-code/adapter.py:90-97`）。
   所以「一轮结束、未看」这一类的卡必须把它最后一句话露出来，由用户一眼判断；总管也可以用自报把它
   提成「等回答」。

读代码后要补的缺口，都是这个模型成立的前提：

- **总管的屏幕没人量。** 屏幕静止只对被监管的终端采样。总控台要对有群的总管也开采样。
  代价未验证：每秒比一次屏幕指纹，总管数量通常是个位数；验法是开 8 个总管量采样线程的 CPU。
- **hook 状态只有一个时间戳。** `since_ms` 是状态上次变化的时刻（`src/poltergeist/Bus.zig:294-295`），
  不是上次收到事件的时刻。年龄要读后者，需加 `last_event_ms`。
- **进程信号没露出来。** `agent_present` 只在 `terminal_capabilities` 里；总控台的快照要带上它与
  子进程是否已退出。
- **CLI 退出 hook 不报。** 装的六个事件里没有会话结束（`plugins/claude-code/adapter.py:90-97`）。
  所以「agent 退了只剩 shell」只能由进程信号判断，这正是第 4 路存在的理由。

**实际做成的与还没有的**（核心 `Bus.facts` 一次取齐，`Attention.classify` 判类别）：

- **`last_event_ms` 有了**，和 `since_ms` 分开：`since_ms` 只在状态变化时动，同一状态再报一次不动
  （§4.3）；`last_event_ms` 每个事件都动，年龄读它。对两种「等」的状态，在等的东西（`detail` / `note`）
  换了也算变化——第二个授权框不是第一个还开着。
- **采样失败带时刻**，单列为「读不到」。没有 hook 时它记在第 6 类并写「读不到屏幕」；有 hook 且
  `in_turn` 时，读不到屏幕**不**判疑似卡住。
- **调用那一路不说话时不投票**（配置为 0，或这个终端从没调过 Polter 的工具）：这时只凭屏幕静止 ≥ T1
  判疑似卡住。否则没接 MCP 的 agent 永远判不出卡住。
- **按终端单独设的静止阈值会被读到**：某个终端有自己的 T1 就用它的，没有才用全局的。
- **进程**：能分清的只有两种——终端的子进程异常退出（记为出错）与正常退出（终端不在了）。
  **「agent 退了只剩 shell」还没有信号**，核心留了「走了，原因不明」的位置（hook 留下的旧状态作废，
  改看屏幕），但现在没有任何东西会报它；MCP 连接断开不当成 agent 退出，那是猜。
- **自报还没有。** 快照里等回答若来自自报，停因会写明取不到（`self_report_text`）；规则（只升不降、
  说话时的状态一变就失效、不能改等批准与出错、能盖过疑似卡住）已经在 `classify` 里。
- **「屏幕在动 = 在干活」只在 hook 不是 `live` 时用**；hook 活着时以 hook 为准。屏幕静止不到 T1 一律
  算在动。
- 总管的屏幕仍然没人量：有 hook 的总管 `in_turn` 时判不出疑似卡住。

### 4.3 排序与计数：一个函数

所有地方的数字——标题栏的「等你 N」、左栏分段的计数、Dock 徽标、主窗口的提示条、系统通知要不要发——
都出自同一个函数。宿主不许自己数。

> **2026-10-12 起，worker 的等批准先归它的总管**（用户原话与对照表在 [supervisor.md](supervisor.md)
> 的「两类确认」）。对这一节的影响有两处，都已接上（2026-10-13）：
> (a) 总管调 `notify_user(reason: authorisation)` 把事提到用户面前时，那个群立刻进「在等你」，类别是
> `needs_answer`、来源 `self_report`，`waiter.is = supervisor`，`reason.from = raised`，`what` 是总管那句话整句；
> 立到用户看过这个群为止（`Bus.raise` / `Bus.raisedOf`）。(b)「第一分钟归总管」只在那个终端的代答开关开着时成立，
> 开关关着（`answer=off`）或被护住时没有那一分钟，直接算在等你，核心也不为那一分钟设唤醒。
> 同一次调用里还发系统通知（§9）。宿主不用改：两边都只画核心给的字。

```
类别（Kind），按先后：
  1 needs_approval   等审批          hook = awaiting_approval
  2 needs_answer     等回答          hook = awaiting_input；或自报提上来的
  3 failed           出错            hook = failed；或 agent 进程退出且不是用户关的
  4 suspect_stuck    疑似卡住        hook = in_turn 且屏幕静止 ≥ T1 且无工具调用 ≥ T2；
                                     或 hook 约定要来却没来
  5 done_unseen      一轮结束未看    hook = ended 且没有后台任务挂着 且 since_ms > seen_ms
  6 quiet_unknown    静止，原因不明  没有 hook，屏幕静止 ≥ T1
  7 working          在干活          hook = in_turn；或 ended 且有后台任务挂着；或屏幕在动
  8 idle             闲着            其余，且有总管在
  9 unattended       无人看管        群里没有任何活着的终端

attention(群) -> { kind, since_ms, what, source, age_ms }
  取这个群的总管的类别；
  worker 的 needs_approval / failed 超过 60 秒没被总管处理，冒到群上，what 写明是哪个 worker；
  snooze 生效期间，kind 记为 snoozed，不进下面的 needs_me。

needs_me(群) = attention(群).kind ∈ { 1, 2, 3, 4 }   -- 真的动不了的：等批准、等回答、出错、疑似卡住
unseen(群)   = attention(群).kind ∈ { 5, 6 }         -- 停下来了，你还没看：只在列表里，不计数、不通知
            或 这一行是总管用 notify_user 提上来的    -- 提上来的话写着「直到你看过」；见下面「看过撤什么」

排序键 = ( kind 升序, since_ms 升序 )          -- 同一类里，等得最久的在最上
等你 N = | { g : needs_me(g) } | + | { 单独的终端 t : needs_me(t) } |   -- 数行，见 §4.4
```

为什么是这个顺序：

- 1–3 是「不处理它就不会动」，4 是「可能已经不会动了」，5–6 是「它停了，看一眼才知道要不要管」，
  7–8 不需要用户。
- **「等你」只算 1–4。**（用户定，2026-10-11）总管报告做完了什么，不算等你，也不通知——看不看由用户，
  都不影响。5–6 仍然排在在干活的前面、有自己的一段，但不进「等你 N」。总管真要用户一句话的时候，
  用自报把它提成「等回答」（§4.2 第 2 条）。调研里五家产品各自收敛到同一个顺序；反例是默认按项目分组，活跃的会话被埋进历史里。
- **组内按等了多久**，而不是按最近有动静。计时从进入这个类别算起，总管再追问不重置——否则越催越靠后。
  用户一回复，它离开这个类别，自然沉下去。
- **行的身份稳定。** 卡片的快捷键是群的编号，不是它在列表里的位置；排序变化只在窗口不在前台、或用户
  超过 2 秒没有动键盘鼠标时才生效，其余时候新来的卡只在段内末尾出现并闪一下。通知一来就把列表重排，
  用户会点错，别家已经为此挨过骂。

阈值 `T1`、`T2` 沿用现有配置的默认值（屏幕静止 3 分钟、无工具调用 15 分钟），不另起一套。

实现时定下、文档原先没说的（除标明的以外都是总管接受的代定）：

- **`since_ms` 取进入这个类别的那一刻。** 疑似卡住与静止不明是越过阈值的那一刻，不是屏幕停下的那一刻；
  所以界面上的分钟数比屏幕实际静止的时间短一个 T1。
- **同一状态再报一次不重置 `since_ms`**，这就是上面「总管再追问不重置」的实现（§4.2）。
- **第 6 类也认 `seen_ms`**：看过以后落回闲着。
- **类别多一个 `snoozed`**，排在最后；快照里另带 `under`（没被放着时是什么）。
- **总管不在、worker 还活着的群**记为闲着；worker 的等批准 / 出错照样在 60 秒后冒上来。
  只有这两种会冒，而且冒不过总管自己更靠前的类别。
- **排序键末尾加终端编号**做平局裁决，两行不会自己换位置。
- **下一次可能变化的时刻由核心算**（越过 T1 / T2、60 秒冒泡、hook 超时、定时的先放着到点；不再有「整分钟」这一项，§5.4），
  只在那一刻重算；没有这样的时刻就不醒。没有固定周期的定时器（§5.4、§13.2）。

### 4.4 一个总管管几个群

关注状态属于终端，卡片属于群。一个总管管三个群时，它在等审批这件事只有一件：

- **计数数的是行，不去重**（任务 #1440，**暂定**）：三个群都在等你，左栏标题是 3，Dock 也是 3。原先 Dock 用的
  `needs_me` 按终端去重、这时是 1，理由是「它在等审批这件事只有一件」。这个理由没有错，但人在屏幕上数得出来的
  只有行：四行在等、标题写 4、Dock 写 3（真机第三轮），没有任何地方告诉他 3 是什么的个数。而且那个 3 也不是
  「在等的终端数」——一行里总管和 worker 都在等时只算了一个。所以改成一个意思：**一行在等就是 1**。
  要「一件事只响一次」的地方（通知）另用按终端去重的那个函数（`Attention.needsMeCount`，还在），不拿 Dock 的数。
  没改的另一种做法：Dock 仍按终端去重，同时把同一个总管的几行折成一行、标题也跟着少——那要重画列表，没做。
- 三张卡排在一起；停因与动作只画在一张上，另外两张写「同一个总管，见 ×××」（快照里的 `same_as`）。
  **暂定**：画停因的那张是「群里最后有人说话」的那个群，不是「这个总管最后说话」的那个——后者没有现成的数。
- 对其中任何一张操作，三张一起变。
- `seen_ms` 属于群，类别按终端算：一个终端作为哪个群的成员被看，就用那个群的；它在窗口标签页上的图形
  用「在任何一个群里看过就算看过」。

### 4.5 活跃、先放着、无人看管、归档

- **首屏只放活的**：群里有活着的终端。
- **先放着**（snooze）：用户说「知道了，先别提醒」。卡片挪到底部折叠入口里，不计入「等你」。
  回来的条件二选一：它的状态再变一次（默认），或到某个时刻。**先放着不是归档**：它一定会回来。
- **无人看管**：群还没归档，但没有任何活着的终端——重启之后的群都是这样。折叠在底部，每一行带
  「开一个总管」（§6.2）。超过 7 天没动静的，自动落到归档视图里（用户定，2026-10-11）。
- **归档**：用户明确归档。不删任何东西，只是从首屏拿走、不占内存。群里还有活终端时不让归档，
  和销毁群同一条判据。

### 4.6 未归组

两类终端单列一栏，用同一个排序函数：

- 是总管但还没建群的；
- 不属于任何群、也没被监管的独立 agent（有 hook 的，或者有 agent 连着的）。

这一栏存在的理由：用户要的是「不用管开了多少 tab」，如果只有进了群的才上总控台，那么一个手敲出来的
agent 在等审批，用户仍然得去翻 tab。

实际做成的（快照里的 `ungrouped`）：没建群的总管；被监管但不在任何群里的 worker；不在任何群、没被监管、
而且有 hook 或有 agent 连着的终端。这一栏的行进 `needs_me` 的计数，不进 `groups_needing_me`。

### 5.3 归属：接手一个别人建的群

这是读代码后与设想冲突最大的一处。

现状：群的归属在建群时写一次，之后不变。六个操作要求调用者是建群的总管，否则 `NotYours`
（`src/poltergeist/rpc.zig:5643-5662`，调用点在 `:6254`、`:7040`、`:7053`、`:7059`、`:7089`、`:7296`），
其中包括 `group_add`——**新总管连把自己加进去都不行**。上一任的终端关掉或卸任都不动归属，
群就锁在一个已经不存在的终端上。只有重启之后，群以「无主」回来（归属记成用户，
`src/poltergeist/Chat.zig:326`），任何总管才能接。

所以「一键开一个总管接手这个群」在同一次运行里今天走不通。改法：

1. **归属跟着活人走。** 持有归属的终端关闭或卸任时，归属退回「无主」。这一条本身就是修一个缺陷。
2. **用户可以移交。** 新增一个只有用户（总控台）能发起的操作 `group_hand_over(group, to)`：
   把归属交给另一个终端。agent 不能调——被监管的终端是最容易被注入一句话的地方，
   不能让一句话就把群抢走，这和 `become_supervisor` 拒绝被监管终端是同一个理由
   （`src/poltergeist/rpc.zig:7004-7008`）。
3. **群有活着的总管时，一键开总管要先问。** 提示「这个群现在由 ××× 在管，换成新的吗」；确认后
   原总管保留成员身份、失去归属，并收到一条通知。不确认就不开。

顺带暴露的一个已有缺口：`task_edit / task_assign / task_close / task_cancel` 不查群的归属，
任何总管都能动别的总管群里的任务。一个总管时没人注意，几个总管并存时就是真问题。建议第一期一起补上
归属检查（会改变现有行为；§11 第 6 项，已定：补）。

### 5.4 核心给宿主的接口

现状：核心到宿主只有两种通道。**拉**：一族把 JSON 写进缓冲区的导出，宿主自己轮询
（`src/apprt/embedded.zig:2067,2100`）；**推**：只有按终端的监管标记动作
（`include/ghostty.h:1368`）。没有「数据变了，来取」的机制，群与任务数据没有任何导出。

新增，面尽量小：

| 导出 | 作用 |
|---|---|
| `ghostty_app_control_snapshot` | 整个总控台的快照：每个群的 §4.1 字段、`attention`、worker 小点、`needs_me`、`rev` |
| `ghostty_app_control_group` | 一个群的详情：成员、任务、最后一轮的话、文件、用量 |
| `ghostty_app_control_messages` | 一个群的消息，按序号分页 |
| `ghostty_app_control_act` | 用户在总控台上的动作：批准、拒绝、回一句、先放着、归档、已看、移交、开总管 |
| 动作 `CONTROL_ROOM_CHANGED` | 快照变了。合并发送，每秒不超过 4 次，带 `rev` |

做到哪了：

| 导出 | 现状 |
|---|---|
| `ghostty_app_control_snapshot` | **有。** JSON 的形状写在 `src/poltergeist/ControlRoom.zig` 文件头，夹具是 `src/poltergeist/testdata/control_snapshot.json`。返回 0 字节表示还没算过，不是空的总控台 |
| 动作 `CONTROL_ROOM_CHANGED` | **有。** mac 的宿主还没有接它的分支；Windows 宿主记为欠账；gtk 记为未实现 |
| `ghostty_app_control_act` | **有一部分**：已看、先放着（到下一个事件 / 到某时刻）、取消先放着、批准一次、拒绝、回一句、新建群（`new_group`）、给没有总管的群启动总管（`start_supervisor`，§6.4）。**没有**：归档、移交。请求与每一种拒绝写在 `src/poltergeist/ControlAct.zig` 文件头 |
| `ghostty_app_control_group` | 还没有 |
| `ghostty_app_control_messages` | 还没有 |

快照里宿主要知道的几件事：

- **两个钟。** `since_ms`、`event_ms`、顶层的 `now_ms` 是核心自己的钟（机器睡着时不走）；`last_ms`、
  `seen_ms`、`snooze` 是墙上时间。不要拿墙上时间去减 `since_ms`。
- **快照里没有任何「多久」。** `waited_min` 和 `band` 撤掉了（§3.2）。所以有人在等时核心也不再每分钟醒一次：
  只在快照里有东西可能变的时刻才重算（核心有一条测试守着：五行在等，空转一小时，一次通知都没有）。
- **谁在等：`groups[].waiter`**（单独的终端那几行也有）。`is` 是五个词之一：`supervisor`（群的总管自己）、
  `worker_via_supervisor`（它手下的 worker，等满第一分钟才提到这一行）、`worker`（没有总管的群里的 worker）、
  `terminal`（不在任何群里的终端）、`none`；`name` 只在两种 worker 时非空。**只有需要你的行才有人在等**，
  不需要你的行一律是 `none`——否则 `supervisor` 一个词要同时说「总管在等」和「这一行说的是总管」。
  核心的结构体里这一项没有默认值，漏填编不过；两个宿主遇到不认识的词都当作读不了，不当作「没人」。
- **等什么：`groups[].what`。** `form` 是 `command`（shell 命令，`lines` 一步一条）、`code`（原样的一段，
  等宽）、`words`（一句话）、`none`。`cut` 说 `lines` 是不是全文：`none`（就是全部）、`tail`（是开头，后面可能
  还有：只拿到摘要、摘要顶到了长度上限）、`head`（是结尾：一轮话的最后一段）。**宿主不许把一部分当全文**：
  `tail` 在最后一行后面、`head` 在第一行前面加省略号，画、量行高、悬停、读屏用的都是加了记号的那几行
  （mac 的 `What.drawn`、Windows 的 `list::drawn`）；缺这一项或不认识的词，整份快照不读。行数上限、怎么截是宿主外观表的事（§3.2 第 4 条），
  两边用同一条分配规则（mac 的 `ControlRoomAskFit`、Windows 的 `layout::AskFit`），对照闸逐项比。
  一步要折几行是量出来的，量是宿主的事（各用各的字体）；对照闸和测试用「41 格一行、宽字符算两格」代替。
- **年龄不进比较。** 两份快照除了 `age_ms`、`now_ms` 以外逐项相同，`rev` 就不变。
- **哪个图形在明暗：`pulses`。** 所有显示成「等你」的终端，等得最久的在最前。一个窗口里明暗的那一个，
  是这张单子里第一个「不在这个窗口正显示的标签页里」的（画在标签栏和分屏上的图形，还要它在这个窗口里）。
  宿主只做「是不是我正显示的这个标签页」「是不是我这个窗口」两种相等判断，顺序是核心排的。
- **一个群的总管是哪个终端：`groups[].steward`。** 终端号，没有总管时是 `null`。mac 的右栏拿它去找
  那个终端的视图（按 `ghostty_surface_poltergeist_id` 做相等判断），宿主不从成员表里自己挑。
- **这个群能不能启动总管、用哪个角色、在哪个目录：`groups[].supervisor`，以及顶层的 `supervisor_roles`
  与 `choose_supervisor_role`。**（§6.4）`state` 是 `present` / `absent` / `starting` / `failed`；
  **宿主出不出「启动总管」按钮只看 `can_start`**，不从 `state` 推；`state` 与 `failed` 只用来挑右栏那句话。
  `role` 与 `cwd` 是人不另选时用的默认值，`cwd_from` 说这个目录是怎么来的。要不要出角色选择看
  `choose_supervisor_role`，宿主不数 `supervisor_roles` 有几个。
- **打开时停在哪个群：`open_on`。** 总控台打开而没有选中时选它：按列表顺序第一个「里面有 AI」的群；所有群都是空的
  就是第一个群；一个群都没有是 `null`。「有 AI」是核心的判断，与「单独的终端算不算 agent」是同一条：群里有一个
  开着的终端是总管、或被总管看着、或它的 agent 说过话、或有 agent 连着。一个只加了普通 shell 的群、成员的标签页
  都已关掉的群，都算空。**暂定**，而且「有 agent 连着」比听上去宽：一个终端只要调用过 Polter 的接口就算
  （真机上，一个只跑过几条接口命令的普通终端所在的群被算作有 AI）；被总管看着的终端即使里面只是 shell 也算。
  没有成员的群排在有人管的群之后，所以「空群排在第一行而后面有带 AI 的群」只在那些群都被先放着时才出现。
  宿主只做相等查找：只在刚打开的那一次用它，已有的选中不换，之后选中没了也不再替人选。
  **自动停上去的那一行不算人看过**（不开始「已看」的计时），人点它一下或用键盘移过才算（mac 已做；用户定的）。
- **已看与先放着重启后读得回来了（任务 #1451）。** 它们一直写在 `group.json` 里，但恢复群的那一步没有读——
  `Chat.restoreMarks` 没有任何调用方，所以「先放着到四点」每次重启都没了。现在 `Chat.restoreShell` 必须带上这两样
  （没有默认值，漏了编不过）。读回来的是「上次的记号」，不是「这次运行里看过」：重启后新发生的事不会因为
  以前看过而算看过，状态一变「先放着到下一次变化」也就结束——所以重启后「做完没看」既不会全部复活（群里还没有
  终端，没有东西可以没看），也不会被旧记号盖掉。
- **左下角的额度：`quota`。** 每个账号的额度用了多少，展开哪一家、哪一家留在那一行、数旧不旧、出路
  写不写，都是算好的（§3.6；形状在 `src/poltergeist/quota.zig` 文件头）。它的时刻是墙上时间。宿主没有
  「八成」这个数；缺这一项的快照不画这一块，带着不认识的词的整份不读。
- **时间带没有了。** 原先的 `band`（今天让你等过的）连同核心里记它的那张表一起撤掉了（任务 #1435）。

用户的动作带守卫：

- 批准一次 = 回车，拒绝 = Esc（§7.1）。请求带上那一行画出来时的 `since_ms` 与 `event_ms`；核心核对
  目标终端仍在等批准、两个时刻都没变、而且（屏幕有人量时）授权框画出来以后屏幕没再动过，否则
  **一个键都不发**，回 `PromptGone`。最后一条是为了在终端里直接答掉的授权框——那不触发任何 hook。
- 回一句只发给在等回答、一轮结束、出错的 agent，带 `since_ms`；状态变了回 `Stale`，授权框和进行中的
  一轮不收一句话（`NothingToReplyTo`）。
- 三样都走 agent 打字的同一条路：那个终端 10 秒内有键到过就拒绝（`UserPresent`），输入行里有没提交的
  字就拒绝（`DraftInLine`）。
- MCP 的 `terminal_answer_prompt` 也有这道守卫了，但是**可选的**：调用方带上 `terminal_list` 里那个终端的
  `state_at_ms` 与 `event_at_ms`（两个都给或都不给）才核对，不符回 `PromptGone` 且不发键；不带就和以前
  一样数着格子盲发。参数名没有叫 `since_ms`：`terminal_list` 里的 `since_ms` 是时长，不是时刻。

三条约束：

- **宿主只在收到 `CONTROL_ROOM_CHANGED` 时取快照，没有定时器。** 现有 TUI 每 500 ms 轮询一次；
  原生窗口什么都没变时应当一次都不醒（§13.2）。
- **用户的动作只走 `ghostty_app_control_act`。** 宿主已有的 `ghostty_surface_text` 一类通用入口
  走的是「用户本人在那个终端里打字」的路，不过 Polter 的任何守卫，也不记账。总控台的「批准」
  「回一句」如果走它，就绕开了 `PromptGone`、`DraftInLine` 这些检查。
- **快照里全是算好的东西。** 排序、分段、计数、谁在等、等什么、要显示的那一行字，都在里面。
  宿主里出现任何对状态的判断，都算缺陷（§13.1 第一期的地板里有一道检查）。

`ghostty_app_control_act` 的请求里没有「我是谁」这个字段：能调到这个导出的只有宿主，调它就是用户
本人，agent 没有任何工具能到这里。

总控台窗口是「用户的手」，和现在的群聊页一样：它发出的请求以用户身份到达
（现有做法见 `src/App.zig:2299-2302`）。这个身份由宿主在创建窗口时登记，不是窗口自己声称的。

## 6. 冷启动与恢复

### 6.1 冷启动：新建群

1. 用户点「+ 新建群」（或快捷键）。
2. 弹出一个很小的面板：**工作目录**（默认上次用的那个，可以换）、**角色**（默认上次用的总管角色）、
   **一句要做什么**（可空）。没有「群名」这一栏。（用户定）
3. 核心取群名：目录名转成合法的名字（转小写；不在 `[a-z0-9-]` 里的字符换成连字符；首尾与连续的
   连字符收掉；截到 48 字节）。重名加序号 `-2`、`-3`。转完是空的（比如目录名全是中文）就退回编号
   `g-<n>`。标记 `auto_named`。
4. 核心建群：写入 `cwd`；那句话写成简介的初稿。
5. 核心按 §6.3 开一个总管并绑到这个群。卡片立刻出现在「在干活」里，写着「正在启动」。
6. agent 连上以后，那句话作为第一句发给它（走 `terminal_send` 的同一条路）。
7. 总管弄清要做什么以后，用 `group_rename` 改名、用 `group_set_brief` 写简介；`auto_named` 清掉。
   启动提示里写明这一步。在它改名之前，卡片上的名字后面带一个「暂名」的标记。

**现有的路保留**：普通终端里的 agent 自己 `become_supervisor` 再 `group_create`。群一建，总控台自动
出现它的卡片，不需要它另外做什么。这种群没有 `cwd`，卡片上提示「没有记工作目录」，总管可以用
`group_set_cwd` 补上；核心在建群时把建群终端的当前目录填进去作默认值（用户定，2026-10-11）。

### 6.2 恢复：重开以后

重启后群从盘上回来，成员是空的。这是有意的：终端的编号每次启动都重新生成，「屏幕上哪个终端是昨晚
那个」是一个判断，Polter 不替人做（`src/App.zig:1534-1569`、`src/poltergeist/Chat.zig:314-339`）。
总控台不改这一点，只把「重新找人来管」做成一步：

1. 重启后，昨天的群都在「无人看管」里。每一行显示：群名、简介的第一行、工作目录、上一任是谁
   （角色与 CLI）、上次说话的时间、还开着几个任务。
2. 用户点「开一个总管」。有两个按钮：
   - **接着上次的会话**：只在上一任的 CLI 支持续接、而且记着会话编号时出现。
   - **新会话**：总是有。
3. 核心按 §6.3 开终端：目录是群的 `cwd`，角色是 `steward.role`。
4. 它起来就已经是总管、已经在这个群里、已经持有归属，不需要用户再告诉它用哪个群。（用户定）
5. 启动提示里写明：你接手的是哪个群、它的简介、开着的任务有哪些、上一任的会话记录可以用
   `session_recall` 查。新会话的第一件事是读这些，而不是建一个新群。
6. worker 不自动重开。总管读完面板自己决定要谁；这和「不自动重起」的现有立场一致。

### 6.3 启动即绑定：现在有什么、缺什么

- **启动即总管：已经有。** 角色带总管标记（`src/poltergeist/persona.zig:179`）时，核心先替这个终端
  存一份待认领的身份，agent 的第一条请求到达时认领并成为总管
  （`src/poltergeist/PersonaStore.zig:584-598`）。它第一次问「我是谁」就已经是总管。
- **启动即绑群：没有。** 角色定义和启动请求里都没有群；启动链路里没有任何入群或建群。现在只靠启动
  提示让它自己去建。要加的：待认领的身份里带上群名；认领时把终端加进群、移交归属（§5.3）、
  写 `steward`。
- **认领有 60 秒的期限**，过期只打一行日志（`src/poltergeist/PersonaStore.zig:587-590`）。绑群以后
  这个沉默不能留：过期时卡片要写「总管没连上」，并给「再试一次」。
- **启动行不带参数。** 核心往终端里打的是一行固定的启动命令（`src/App.zig:2647`）。群和会话编号
  不经这一行传，免得出现在屏幕与历史里；它们走待认领的身份和适配器的请求。
- **续接会话：没有一等支持。** 启动请求里没有会话字段；会话编号只在内存。要加的：把编号写进群的
  记录（§4.1）；启动请求带 `resume`；适配器把它换成那家 CLI 的参数。目前只有 Claude Code 有适配器，
  其余几家的按钮就是不出现——不显示成灰的，免得用户以为是出了错。

### 6.4 做成了什么：在总控台里新建群、给没有总管的群启动总管（任务 #1445）

§6.1–§6.3 是设计；这一节是代码里现在有的那一部分，以及它和设计不一样的地方。**除非另外标明，都是暂定**：
用户 2026-10-13 提了两条（「总控台点击新建群聊无效」「群没有总管时要有办法快速启动」），做法是总管代定的。

**新建群（`new_group`）。** 点左栏右上的「新建群」，标题那一行原地变成输入框；回车建、Esc 取消。名字的规则
是群名一直以来的规则（小写字母、数字、短横线，最长 48），**核心只去掉首尾空白，不替人把名字改成别的**；
空名、不合规则、重名、数量到上限，各有一句话写在输入框正下方，输入框留着。建成以后新群在核心下一份快照里
出现，宿主等它出现再选中（提前选会被「选中的群已经不在列表里」那条规则清掉）。新群没有总管，右栏就是下面
那个状态。与 §6.1 不一样：这里要人起名、不问目录和角色、不顺手开总管——开总管是右栏的事，一步一件。
人不经 agent 建群原本只有群聊页里的命令，走的是同一个核心函数（建群、把人放进去、落盘）。

**启动总管（`start_supervisor`）。** 没有总管的群——新建的、重启以后回来的——右栏的框里是一句话加：
角色（只在有不止一个总管角色时出现）、目录（可换）、主按钮「启动总管」。点了以后：

1. 核心在这个群上记一笔「正在启动」，开一个标签页（**不切过去**，见下），把角色的启动行打进去——和
   `role_launch`、菜单里的「用角色启动」是同一个 `startRoleIn`、同一行 `polter +launch`。
2. 角色的总管身份照旧是「待认领」的（§6.3）：agent 的第一条请求到达时这个终端成为总管。**绑群是这次加的**：
   认领之后，如果这个终端是总控台为某个群启动的、而且它此刻确实是总管，核心把它加进那个群（看得到全部
   历史）。群的总管是谁本来就是快照现算的（建群的那个终端如果是总管且还在群里，否则群里任何一个总管），
   所以它一进群，`steward` 就是它，右栏按原来的规则把它借过来。**没有新增「群的总管」这个存盘字段。**
3. 这一段右栏写「正在启动总管…」。三处会等不到，各有一句话，按钮回来可以再试：标签页没开出来（10 秒）、
   标签页开了但没有 agent 连上（60 秒，与待认领身份同一个期限）、标签页在连上之前被关了。到期那一刻没有
   任何别的事件，所以快照自己要一个到点的唤醒。当场就能知道的失败（目录不存在、角色没了、开不出标签页）
   是这个动作的拒绝，写在按钮下面。

**默认角色**：角色库里第一个带总管标记而且配了 CLI 的角色（内置的 `polter-supervisor` 排在最前）。
一个角色配了几个 CLI 时用第一个——右栏给的选择是角色和目录，没有第三样。
**默认目录**，依次：这个群上一任总管所在的目录；群里现有终端最多的那个目录（并列取字典序靠前的）；
用户主目录。**上一任总管的目录以前核心没有记**（成员和它们的目录只在内存里，重启就没了；会话快照里有，
但那是给总管读的材料，程序不读回来）。现在记了：总管建群、总管被加进群时，把它当时的目录写进
`<state>/chat/<群>/group.json` 的 `supervisor_dir`，重启后随群一起回来。**这一版之前建的群没有这一项**，
第一次会落到主目录，要人自己选一次。

**这是右栏占位里的按钮，不是行上的按钮。**「行只提示」（`tools/control-room-rows-only-tell.py`）没有放宽：
左栏仍然只有「新建群」一个按钮。

与 §6.2 不一样、没做的：没有「接着上次的会话」；启动提示里没有写「你接手的是哪个群」（它起来以后已经在群里，
`group_list` 看得到，但没有人告诉它先读什么）；不显示上一任是谁。

**在总控台里开标签页（mac）。** 上面第 1 步、以及总管自己在右栏里调 `terminal_open` / `role_launch`，
都要在「人正看着总控台」的时候开标签页。规则在 `ControlRoomRules.newTab`：

| 谁要的 | 开在哪 | 切不切过去 |
|---|---|---|
| 一个被借进右栏的终端 | 它自己那个窗口的标签组（`homeWindow`） | 不切 |
| 一个在自己标签页里的终端 | 它旁边 | 切（一直如此） |
| 应用自己（总控台启动总管），总控台在前、旁边有终端标签页 | 总控台所在的标签组 | 不切 |
| 应用自己，其它情形 | 最近用过的终端窗口；一个都没有就开新窗口 | 切 |
| 一个不在任何窗口里的终端 | 不开，告诉核心没开 | — |

**这里修过一个真缺陷**（装机版 0.10.1781，2026-10-13 总管自己撞上）：终端被借出时 `view.window` 是总控台的
窗口，而开标签页的处理只认终端窗口，于是静默什么都不做；核心又把宿主「做没做」的回答丢了，所以
`terminal_open` 回 `{"ok":true,"placed":"tab"}`、没有 id、也没有终端——和「标签页还没建好」长得一模一样。
现在宿主没有向任何窗口要标签页时回「没做」，核心回 `OpenFailed`，等着角色的那次启动也一并取消（否则 10 秒内
人手开的下一个终端会被当成它）。**原先还剩两格会回 ok 而没有终端**：窗口装饰关着、以及快速终端里——宿主弹了提示框，回「做了」（键盘触发的新标签页
也走这条路，回「没做」会让按键漏进终端）。任务 #1451 把两条路分开了：`new_tab` 这个动作多了一个应答单元
（`apprt.action.NewTab.result`，头文件里的 `ghostty_action_new_tab_s.result`），核心替 agent 要标签页时带上它，
键盘和菜单不带。带了的，mac 宿主在这两格写 `REFUSED`、不弹框（人没要任何东西），核心回 `OpenFailed`；不带的照旧
弹框。单元没被写（`UNANSWERED`，值为 0）时核心仍按返回值判断，所以 Windows 宿主与 GTK 不用改、行为不变
（规则在 `ControlRoomRules.newTabAnswer`）。

不切过去的标签页是「加进标签组、不选中、不显示」：终端在建控制器时已经起来了，标签栏上有它，点它才显示。
**这一条只在构建里编过，没有在真机上看过**（清单在本节末）。

真机上才看得出、还没看的（给 mac 测试用）：

1. 总管在右栏里调 `terminal_open`（`auto` / `tab` / `here` 各一次）与 `role_launch`：标签栏多出一个标签页、
   总控台仍在前、右栏的总管还在、返回里有 id、`terminal_list` 里有它。
2. 后台开出来的标签页点过去：终端大小对不对、里面的 CLI 起来没有、标签上的编号对不对。
3. 总控台单独一个窗口、借的是另一个窗口里的总管时，同上；那个窗口不应该被带到前面。
4. 「新建群」：输入框拿到键盘；回车建、Esc 取消；空名 / 大写 / 重名三种各自那句话的位置与换行；建成后新群被
   选中、右栏是「没有总管」加按钮。
5. 「启动总管」：按钮按下后右栏变「正在启动总管…」，agent 连上后变成它的终端；目录显示（`~`）与「选择…」
   面板；有两个总管角色时角色选择出现、默认是第一个。
6. 失败三格：启动后立刻关掉那个标签页；把角色的 CLI 改成一个不存在的命令再启动（60 秒后）；目录填一个
   不存在的路径（当场）。
7. 重启后：昨天的群右栏默认目录是上一任总管的目录（要先用这一版建过或加过一次总管）。
8. 字号：新加的字都是 13；主按钮、输入框的描边与左栏选中行的对齐。

## 7. 三档介入

界面能缩短的只有「每次应答要多久」。三档从轻到重；每一档解决上一档解决不了的那部分。

### 7.1 第 ① 档：卡片上直接处理

> **这一档现在没有界面。** 用户定的（2026-10-12）：行上不放处理按钮，只提示，原话与缘由见 §3.2 第 6 条。
> **同一天定的另一半：这一档的事由总管做。** worker 一等批准，核心不排队地通知它的总管，通知里带着守卫
> 要的两个时刻；总管读屏、判断、用 `terminal_answer_prompt` 回答，答不了才 `notify_user` 提到用户面前
> （步骤在随 app 发的 `supervising` skill 里）。用户要亲自处理的那少数情形走第 ③ 档。
> 下面写的批准、拒绝、回一句怎么送、守卫怎么核，核心里都在（`ControlAct.zig`、`terminal_answer_prompt` 的
> 守卫），没有东西从总控台的窗口调用它们。「先放着」的界面也没有做；「已看」是停留够久自动发的：人自己选中的行、总控台在前面，停够
> `seen_after`。**正选中的那一行在选中期间做完，也算**——从核心第一次说它「没看」那一刻起计时，同样的时长、
> 同样要在前面；人选中了它、它的总管就在右边，他是看着它做完的。原先要点别的再点回来才发（真机第三轮）。
> 自动停上去的那一行仍不算。规则在纯逻辑里：mac 的 `ControlRoomSeenTracker.listChanged`、Windows 逻辑层的
> `SeenMarker::list_changed`（Windows 宿主还没调它）。
>
> **看过撤什么（任务 #1451，暂定）。** 快照里一行的 `unseen` 说的是「看一眼会改变这一行」，两个宿主都只对
> `unseen` 的行起「看过」的计时。它原先只对「做完没看」「停了原因不明」两类为真，而核心的 `seen` 其实还撤另一样东西：
> 总管用 `notify_user(reason: authorisation)` 提上来的那句话（工具的回话写的就是「直到他们看过」）。于是那一行
> 既在「等你」里、`unseen` 又是假，宿主永远不发 `seen`，那句话就撤不掉（Windows 真机第三轮：选中、在前、停 5 秒，
> 没有任何 seen 的日志）。现在核心在这种行上把 `unseen` 置真，所以**一行可以同时 `needs_me` 和 `unseen`**；
> 两个宿主不用改，规则仍是同一条：人自己选中、总控台在前、停够 `seen_after`。撤掉以后那一行回到它真实的状态
> ——worker 的授权框还在的话，满一分钟照样冒上来；看一眼不会撤掉 worker 的授权框。
> **没做的另一半**：「那个 worker 的提示消失时跟着撤」。总管提的那句话在核心里只挂在总管身上，不知道它说的是
> 哪个 worker 的哪个提示（`notify_user` 的参数里没有），要做就得让工具带上终端号；这一版只有「人看过就撤」，
> 以及总管再提一次会顶掉上一句。单独的终端（不在任何群里的总管）提上来的行仍然撤不掉：`seen` 的请求只认群名。

卡片上只放**不需要看上下文就能安全做**的动作：

| 状态 | 动作 | 怎么送 |
|---|---|---|
| 等审批 | 批准一次、拒绝 | 见下 |
| 等回答（有选项） | 选项 1…n | 带守卫的选择 |
| 等回答（自由文本）、一轮结束 | 回一句 | `terminal_send` 的同一条路 |
| 出错 | 重试（发一句「继续」）、看原因 | 同上 |
| 任何 | 先放着、已看 | 只改总控台自己的状态 |

**批准与拒绝怎么送，是这一档的关键，也是与设想冲突的一处。** 设想是直接复用
`terminal_answer_prompt`。但它是数着格子盲发键的：提示换了一个、选项顺序不同、提示已经没了，
它都照发并报成功。把它放到一个一键的按钮后面，等于把「数错了」的后果从一个会回头读屏幕的 agent
手里，交到一个不看屏幕的人手里。

所以第 ① 档只做两个**不靠数格子**的动作：

- **批准一次** = 回车（接受默认高亮的那一项）。
- **拒绝** = Esc。

并且都带守卫：按钮按下时带上卡片画出来那一刻的 `since_ms`；核心核对目标终端的 hook 状态仍是
`awaiting_approval` 且 `since_ms` 没变，否则不发任何键，回 `PromptGone`，卡片当场刷新。
「总是允许」「允许并记住」这类靠位置的选项不放在卡片上，进第 ② 档。

未验证，第一期开工前要先验：

- Esc 在 Claude Code 的授权提示上等于拒绝，而且不会顺手打断整轮。验法：在测试实例里造一个授权提示，
  发 Esc，读 hook 的下一个事件与屏幕。
- 默认高亮是否总是「批准一次」。验法同上，覆盖 Bash、写文件、联网三种提示。
- 更干净的做法是让授权的 hook 自己把决定带回去：Claude Code 的这个 hook 可以返回允许或拒绝，
  这样完全不发键。但 hook 要等用户的决定，等多久会超时、等的时候终端上显示什么，都没有读数。
  列为调查项；验得通就替换发键的做法，验不通就留着发键。

「回一句」沿用 `terminal_send` 现有的守卫：那个终端 10 秒内有人打过字就拒绝，输入行里有没提交的
字就拒绝。拒绝时卡片上说明原因，并给「进终端」。**回执要分两种**：字打进去了，和 agent 已经开始
下一轮了（hook 报 `in_turn`）。只有后一种才把卡片从「等你」里拿走。

### 7.2 第 ② 档：预览并回话

选中一张卡，右栏的「终端」页签显示：

1. **它在等什么**，完整的：工具名与完整输入、它问的原话。
2. **它最后一轮说的话**，取自 hook 带来的最后一条消息（现有的 `terminal_turn`），不是刮屏幕。
   这是结构化的、不随 CLI 改版而坏的那一路，所以排在屏幕之前。
3. **屏幕的最后若干行**，纯文本，等宽，每秒最多刷新两次。来源是现有的读屏接口
   （`src/apprt/embedded.zig:2557`，源码要求调用方节流）。它没有颜色、没有属性，全屏界面的结构
   会丢——所以它是辅助，不是主体。没有 hook 的 CLI 只有这一路，预览上写明「这家 CLI 没有接 hook，
   下面是屏幕的文字」。
4. 一个输入框，和全部动作（包括靠位置的选项，带同样的 `since_ms` 守卫）。

为什么不在这一档就上真终端：预览要在用户上下移动卡片时立刻跟着换，每换一张就搬一次终端，
两边的终端都会被改尺寸、重排一次。预览只读文字，换卡片没有代价。

### 7.3 第 ③ 档：真终端进来

三个方案，读了两个平台的代码以后的判断：

| 方案 | mac | Windows | 代价 |
|---|---|---|---|
| **真镜像**：同一个终端画在两处，两处都能输入 | 要改渲染器 | 明显更难 | 高，而且有做不干净的地方 |
| **借过来**：把视图挪进总控台，用完还回去 | 有先例 | 整个 tab 有先例，单个窗格要新写 | 中 |
| **跳转往返**：跳到它所在的 tab，一个键回来 | 现成 | 现成 | 几乎没有；但离开了总控台 |

事实依据：

- **一个终端只有一个渲染器，画到创建时给定的那一个视图上**（`src/Surface.zig:89`）。mac 的渲染器
  自己建图层并设到视图上（`src/renderer/Metal.zig:114-117`）；Windows 每个窗格是一个子窗口加一个
  OpenGL 上下文。两边都没有把画好的帧交给第二个视图的接口（`src/renderer/OpenGL.zig:563`）。
- **真镜像做不干净的地方**：两处大小不同时，终端只有一个网格尺寸，另一处只能缩放或留边；视图不可见时
  渲染会停；两处都能输入时焦点、输入法、鼠标坐标都要分两份。Windows 上还要在渲染线程里对第二个
  窗口再提交一次。
- **借过来有现成的搬法**：mac 上分屏拖放本来就能把同一个视图从一个窗口的树搬到另一个窗口的树
  （`macos/Sources/Features/Terminal/BaseTerminalController.swift:1017,1053`）；Windows 上
  「把标签页移到新窗口」不重建窗格，是把它们换一个父窗口（`windows/host/src/tabs.rs:4262`）。
- **单个窗格的搬动 Windows 没有**；两边的分屏树叶子都还是单个视图
  （`macos/Sources/Features/Splits/SplitTree.swift:15-17`、`windows/split-tree/src/lib.rs:188-191`）。

**定的方案：借过来，而且借的是整个 tab，不是一个窗格。**（用户定，2026-10-11）

- 用户要管的是「总管加它那一组 worker」，而现有规则就是 worker 开在总管自己的 tab 里。借整个 tab，
  右栏看到的就是这个群的全貌；只借总管那一格，worker 还得另外去找。
- 整个 tab 换窗口，两个平台都有先例；单个窗格离开 tab，Windows 要新写。
- 被借走的 tab 在原窗口留一个占位，写「在总控台里，点这里收回」。关掉总控台或选别的卡，自动还回去。
- 代价要说清：借过来和还回去各改一次尺寸，里面的程序各重排一次。所以它是用户**明确要进去**
  （`⌘⏎`）时才做的事，不是选中卡片就做——选中卡片只到第 ② 档。

**分期上先做跳转往返**：第一期的「进终端」就是跳到那个 tab，并在那个 tab 上留一个「回总控台」的键。
它几乎没有成本，而且在借过来做完之前，三档是完整的。借过来放到第三期。

不做真镜像。理由是上面那几处做不干净的地方，以及 Windows 上的代价；它换来的只是「不搬动」，
而借整个 tab 已经让用户不必离开总控台。

**值得用户知道的另一条路**：调研里与 Polter 形态最接近的几家，做法是让侧栏直接取代标签栏——
所有 tab 都住在这一个窗口里，侧栏按「谁在等我」排，点一行就是切到那个 tab。那样就没有「借」这回事。
没有推荐它，是因为它要动 mac 上「一个 tab 一个系统窗口」这个基础，范围比 0.10 大；
但如果借整个 tab 做下来顺，下一版自然会走到那里。

## 8. 文件与用量

### 8.1 文件

设想是：写文件的 hook 经过 Polter，可以直接记「这个群动过哪些文件」。读代码的结论是**现在没有经过**：
装的六个事件里没有工具调用前后的那两个，核心遇到它们会直接拒绝
（`src/poltergeist/agent_event.zig:440-441`）。Polter 现在唯一见到文件路径的时刻，是需要授权的写入——
路径的开头进了 `note`；不需要授权的写入完全看不到。

所以分两步：

1. **加一个工具调用之后的 hook，只匹配写文件的那几个工具。** 核心只取路径，记成
   `{ 路径, 哪个终端, 时刻, 新建还是修改 }`，按群累计，同一路径只留最后一次。
   代价未验证：每写一个文件多起一个进程。验法：让 agent 连写 200 个文件，量这一轮多花的时间；
   超过 5% 就把这个 hook 改成批量上报。
2. **自报只标交付物。** `deliverable_mark` 的意思是「这个是要给你看的」。动过的文件可能上百个，
   交付物只有几个。路径必须在群的 `cwd` 之下，否则拒绝并说明，免得一句被注入的话让用户去打开别处
   的文件。

「文件」页签：最上是交付物，其次是动过的文件（按时间），最下是工作目录的入口。
点一个文件是就地预览（§15.1）：看它现在的内容，不做 diff。目录树与完整的浏览不在这里做——
那是 0.10 的文件窗格 E，用户已经定了它是 TUI；预览顶上有进 E 的入口。

没有 hook 的 CLI：这一页只有交付物与目录入口，并写明「这家 CLI 没有接 hook，看不到它动过哪些文件」，
不显示成一张空表。

### 8.2 用量

现状：**核心里没有任何 token 或费用的量**，统计页签的输入里也没有 agent 一侧的数据；hook 带来的
会话记录路径没有存，也没有任何代码读 agent 的会话记录。

设想是从 agent 的会话记录里加总。**这是按机制推的，未验证**，所以它是用量这一期开工前的第一件事：

- 要验的：Claude Code 的会话记录里每一条助手消息是否带输入、输出、缓存读写的 token 数；续接会话与
  上下文压缩之后会不会重复计；子 agent 的用量记在哪。
- 验法：跑一段已知的会话，把自己加出来的数和那家 CLI 自己的用量命令报的数对比，三段会话的误差都在
  2% 以内才算可用；带一个故意漏算缓存的对照，证明这把尺子量得出差别。
- 验不通时的退路：用 CLI 的状态栏接口——那里有它自己算好的累计 token 与时长——代价是要在启动时
  替它配一个状态栏脚本，和 hook 是同一种配法。

显示：

- 「用量」页签：按会话列出输入、输出、缓存、时长；按天累计；总管与每个 worker 分开。
- 卡片上不放数字。只有一种情况例外：**因为限流或额度停下**是一种明说的停因，出现在卡片的停因那一行。
  并行时额度比注意力更早撞墙，它应当是状态，不是统计页里事后才看到的数字。
- **额度窗口用了多少已经有了**，不在这一页，在左栏底部（§3.6）：那是「再开一个 agent 之前看一眼」的东西，
  不该等人点进某个群的页签才看到。
- **不显示金额。** 订阅用户没有按量的价格，按列表价估一个数会误导。只显示 token 与占额度窗口的比例
  （拿得到时）。（用户定，2026-10-11）
- 拿不到数的 CLI：那一行写「这家 CLI 的用量拿不到」和原因，不显示 0。0 和「不知道」是两件事。

## 9. 通知

> **已经有一条通道在发了，而且不照下面的规则走**（#1438，2026-10-13 用户答「要」）：总管调
> `notify_user(reason: authorisation)` 时，核心从总管的窗口发一条系统通知（mac 走 UserNotifications，
> Windows 走托盘气泡，都是现成的 `desktop_notification` 动作），**立刻发、不等 2 分钟、不做在场抑制**。
> 理由：这一条不是程序数出来的，是总管读过屏以后判断「要人来」才发的，下面那套逐级加响是给程序自己
> 数出来的状态用的。限流只有原有的两条（1 秒 1 条；同一内容 5 秒 1 条），被限掉时工具返回值照实说没发。
> **在场抑制没做（暂定）**：用户正看着总管终端时也会弹一条。mac 上是否显示取决于用户有没有给 Polter
> 通知权限，核心看不到这个答案，返回值只说「已交给系统」。

- **在场抑制先做。** 总控台窗口在前台且那张卡看得见时，不发系统通知，不出声，只在卡片上动。
  用户正在那个终端里时也不发。拆到第二块屏以后，「在前台」按每个窗口各自算，不按应用算。
- **分级。** 只有「等审批」「等回答」「出错」配打断；「一轮结束未看」「静止原因不明」不通知、不计数，
  只在列表里有自己的一段。
- **逐级加响，不是一律响。** 进入「等你」先只亮计数；过了 2 分钟没人理，出一声并发系统通知；
  之后不再重复，除非状态又变了。
- **同一个总管的事合成一条。** 它管三个群，只通知一次；它在等用户时，它下面 worker 的次级状态
  不另发。
- **先放着之后不通知**，直到它回来。

### 10.2 五个坑

| 坑 | 怎么防 |
|---|---|
| 靠刮屏幕文字判状态 | 屏幕这一路只输出「静止了多久」，不匹配任何文字。类别只由 hook 与进程信号决定。没有 hook 的 CLI 得到的是「静止，原因不明」，不是猜出来的「等输入」 |
| 拿不可靠的状态触发自动动作 | 总控台**自己不做任何自动动作**：不替人批准，不自动催，不自动重开。用户点的动作带 `since_ms` 守卫。重启后不重放状态变化，卡片从当前读数算起 |
| 自报通道断了，和「没事」长得一样 | 每路信号带来源与年龄；hook 约定要来却没来是「疑似卡住」而不是「闲着」；进程没了否决旧状态；采样失败单列。卡片上的「？」就是为这个 |
| 就地回复的三种错（乱序覆盖、把排队当等人、答错了对象） | 快照带 `rev`，宿主丢弃比手里旧的；动作带 `since_ms`，对不上就 `PromptGone`；回执分「字进去了」和「开始下一轮了」 |
| 总览自己乱动，或把等人的藏起来 | 行的身份与快捷键跟群走；重排只在用户没在操作时生效；首屏默认就是按状态排的，不需要用户去找这个视图；群聊页签不兼任「谁在等我」的入口 |

### 12.2 单独的调查项：终端状态协议

Claude Code 的文档里有一节：终端如果实现了 OSC 7501 程序状态协议，就能拿到每个会话是在干活、
在等用户还是做完了，agent 一侧不用配置。这对 Polter 是一路不依赖 hook 的信号，而且对手敲出来的
`claude` 也有效。但协议的规范文本、哪些终端已经实现，都没有找到；已知的限制是在 tmux 里和后台会话里
不报。**不作为本期依赖**；单独立一个调查任务，找到规范再评估。

「快速查看」的未验证项在 §15.1 与 §15.2，不在这里重复。

### 12.3 风险

- **厂商自己在做多会话的界面。** Claude Code 已经有按状态分组的会话总览和项目面板，别的 CLI 也在做。
  Polter 的位置是它们做不了的那一块：跨厂商、跨 CLI，以及群这个比会话大的单位——一个总管、
  一组 worker、一个任务面板、一段群聊。总控台如果做成「又一个会话列表」，会被厂商自己的东西替掉；
  做成「群的队列」不会。第一维度是群，护的就是这一条。
- **两套原生界面的维护成本。** 这是用户定了的代价。控制它的办法只有一个：让界面真的只画。
  快照里是算好的字符串、算好的顺序、算好的计数；两边各自的代码里没有业务判断。§13.1 每一期的地板里
  都有一条专门守这个。上次那个原生窗口约 200 行 Swift；这次每个平台会是它的十倍以上。
- **非 Claude 的 CLI 质量差一档。** 只有 Claude Code 有 hook。别的 CLI 在总控台里只能得到「在动」
  「静止，原因不明」「进程没了」。这不是能在总控台里补的，要靠 0.10 的 H（其它 CLI 的 hooks）。
  总控台做出来以后，H 的价值比原来排的位置高。
- **只有按角色启动的才有 hook。** 手敲的 `claude` 没有。未归组一栏里它们会显示成「静止，原因不明」。
  这是诚实的，但用户会觉得「它明明在等我」。把状态协议那一路验通，是补这个洞最便宜的办法。
- **`ended` 的含义分不开**（§4.2 第 3 条）。用户定了「一轮结束未看」不算进「等你」。
  代价是：总管用一段话问了用户却没有用自报提上来的时候，这件事只在列表的「未看」那一段里，不亮数字。
  对策在总管的提示词里——要用户一句话就明说。
- **做了总览以后，用户会开更多。** 界面解决的是「找到谁在等我」与「快速应答」，解决不了审查只能
  一个一个来。总控台不应当暗示相反的东西：不做「同时在跑 N 个」的炫耀式数字。

### 12.5 右栏的真终端（mac）：做成了什么，每种情形怎么处理，哪些没验

**真机上看过一轮**（任务 #1389，提交 `df2a4bd6f` 的调试构建，隔离的测试实例，假群假内容；证据在设计资料的
`verify-cr-01/`）。那一轮查出的三处键盘问题随后改了（任务 #1425，见本节末尾「改了、还没在真机上复验的」），
**改过以后没有再起过实例**。下面每一格写的是哪一种，都标了。

做法与 §7.3 定的不一样的两处，**暂定**：选中一个群就把终端搬进右栏（§3.1 的表里「定稿画的」那一行），
不等 `⌘⏎`；搬的是总管那一个终端，不是整个标签页。

**终端不离开它所在标签页的分屏树，搬的只是视图。** 借出期间原处那一格画占位，总控台把视图放进右栏；
还回去就是「不再借出」，原处那一格重新画它。所以关闭、分屏、存盘这些按树找终端的事照旧。跟着视图走、
必须另外说的有两样：原标签页的控制器不再替它报焦点与可见性（改由总控台报）；`view.window` 变成了
总控台的窗口，核心动作里要「它所属的窗口」的 14 处改问 `homeWindow`（第 14 处是开标签页，§6.4；它原先漏了，
借出期间开不出任何标签页）（其中一处是核心问「这个终端在哪个
窗口哪个标签页」，所以借出期间标签页上的图形仍然算在原标签页上）。

谁在哪、该不该还、还给谁是 `ControlRoomLending`（不碰视图，`macos/Tests/ControlRoom/ControlRoomLendingTests.swift`）；
带视图的部分是 `ControlRoomLender` 与 `ControlRoomController`。

**树怎么改（S2）：叶子不动，叠在后面的另存。**

不把 `leaf(view:)` 改成 `leaf(members:current:)`。叶子里的那个视图继续是「这一格此刻显示的那一个」，树上另加
一张表：`stacks: [Stack]`，`Stack = { shown: 视图的 id, members: [视图]（含显示的那一个，按标签的顺序）}`，
**只有成员多于一个的格子才有一项**。于是：

- 没有任何一叠的树，内存里与今天的树多的只是一张空表，存盘时空表不写、版本号仍写 1——**只有一个成员的组不是
  「与今天的叶子等价」，它就是今天的叶子**，逐字节。这一条不靠小心，靠「空的时候不写」加一条字节对照测试守着。
- 布局类的函数（`spatial`、`calculateViewBounds`、`focusTarget`、`equalize`、`resizing`、放大的路径、
  `structuralIdentity`）按节点走，一行不用改，它们看到的永远是显示的那一个。
- 新增四个操作，都返回新树：`stacking(view, onto:)`（放到某一格的后面并显示它）、`showing(view)`（把叶子里的
  视图换成同一叠的另一个）、`unstacking(view, direction:)`（拿出来成为旁边的一格）、以及 `removing` 要多管一件事：
  拿掉的是显示的那一个时由同一叠的下一个顶上，剩一个成员时那一项从表里删掉。

**按叶子遍历的那些地方怎么不漏。** 这是这一块真正的风险：167 处里有两种意思，现在写法一样。

- 「这个标签页里的**每一个终端**」：关闭前问有没有进程在跑、退出、按 id 找终端、核心问某个终端在哪个标签页、
  存项目、AppleScript 列终端、总控台按 id 找视图。漏掉叠在后面的 = **不问就杀掉一个在跑的进程**，而且没有任何
  东西会报。
- 「**看得见的**每一格」：画、算位置、移焦点、拖放。把叠在后面的算进去 = 焦点跑到看不见的视图上，当场看得出来。

所以默认取不出声的那一种的反面：**树的 `Sequence` / `Collection`（`for … in`、`contains`、`count`、`first`）给全部
成员**；按节点取叶子的 `leaves()` 改名为 `shownLeaves()`、`leftmostLeaf` / `rightmostLeaf` 留着但只在布局里用。
改名是故意的：文件外那 9 处 `.leaves()` 会各自编不过，逼着逐处回答「你要的是哪一种」（仓根 CLAUDE.md「让沉默
编不过」）。`for … in surfaceTree` 的 14 处与 `contains / first / …` 的 46 处语义自动变成「全部」，仍要逐处读一遍，
把其实想要「看得见的」那几处改成 `shownLeaves()`——这 60 处的清单在这一步的提交说明里列全，一处一句。

**可见性与借出合成一个规则（S4）**

现在有一种「在树里、不在眼前」：借给总控台的。层叠加第二种：叠在后面的。两种在 `BaseTerminalController` 里
要的是同一件事（原标签页的控制器不替它报焦点、不替它报可见），不同的只是谁来报。合成一个纯函数，两处调用
都问它，不再各写各的 `if isLent { continue }`：

| 这个终端 | 原标签页的控制器报什么 | 另外谁报 |
|---|---|---|
| 是它那一格显示的，没借出 | 照今天：可见 = 窗口可见，焦点 = 它是不是焦点格 | — |
| 借给总控台了（不管它在不在后面） | 不报 | 总控台报（今天的做法） |
| 叠在后面，没借出 | 报「不可见、没有焦点」，一次；被切到前面时走第一行 | — |

规定三件事：焦点格永远不能是叠在后面的（`showing` 换人时，如果被换下去的是焦点格，焦点跟到换上来的）；
借一个叠在后面的终端，原处不画占位（那一格显示的本来就不是它），还回去也不改谁在前面；被借走的正好是显示的
那一个时占位照今天画，这时在原处切到同一叠的另一个是允许的，占位跟着消失。这张表进 `ControlRoomLending`

#### 12.6.3 S1 在 Windows 宿主上（任务 #1450）

**编过了，没有在任何一台 Windows 上跑过。** 规则、几何与要画的东西有测试；宿主那一层只有交叉编译。没有图：
Windows 的画法是 GDI，在 mac 上出不了图。真机清单在本小节末尾。

**哪一格画哪种框，与 mac 是同一张表**（§12.6.1 的表原样适用）：`windows/control-room/src/pane.rs` 的 `drawn`
与 mac 的 `PaneFrame.drawn` 用同一批用例，`tools/control-room-hosts-agree.py` 拿同一份夹具让两边逐个终端回答——
夹具里的 12 个终端、一个快照里没有的、一个没有 id 的，各放在「分屏里 / 只有一格 / 开关关着 / 快速终端」四处——
答案（画哪种、名字、图形、字）、有没有底、身份的英文字，逐行相同。

**怎么上屏的，和 mac 不是一回事。** Windows 上一格是一个子窗口，终端的表面一辈子绑在它上面
（`windows/AGENTS.md`），框没法由终端自己画。所以：

- 分屏树照旧铺满内容区，**不知道有框**；`tabs::layout` 拿到树给每一格的矩形以后，把那一格的子窗口放到
  `pane::well_px` 说的位置——标题下面、边框里面。子窗口变小，系统给它 `WM_SIZE`，核心照原来那条路收到新尺寸。
- 框由父窗口画：它本来就负责画子窗口没盖住的地方（`strip::paint` 的最后一段），现在那里有框时画的是底与各格的框
  （`pane_frames::paint`），没有框时照旧清成原来那个颜色。画的东西是 `pane::build` 给的一串矩形、字与图形，
  交给总控台面板用的同一个画手（`control_room::paint_scene`）。
- 分隔条仍是树的接缝上的小窗口，接缝现在在两个框之间的间隔正中。有底时它整个画成底色、不画那条线，
  鼠标在上面时才显出线；命中区与拖动没有动。
- 间隔与边距在 `pane::frame_px` 里算：一格朝着另一格的那几边各让出半个间隔，贴着内容区边缘的那几边让出整个
  边距。所以两个框之间永远是 `between_frames`，最外面的离窗口边永远是 `window_edge`，树不用改。

**取整**（设备像素，`round(点 × 缩放)`，与画手同一种取整，所以放的位置与画的位置对得上——有测试守着）：

| 缩放 | 标题 32 | 总管的边 4 | 框间 8（= 两个半间隔） | 窗口边 8 | worker 的线 0.5 |
|---|---|---|---|---|---|
| 100% | 32 | 4 | 4 + 4 = 8 | 8 | 1 |
| 125% | 40 | 5 | 5 + 5 = 10 | 10 | 1 |
| 150% | 48 | 6 | 6 + 6 = 12 | 12 | 1 |
| 175% | 56 | 7 | 7 + 7 = 14 | 14 | 1 |
| 200% | 64 | 8 | 8 + 8 = 16 | 16 | 1 |

**Windows 做不到、或者这一轮没做的**（对着 §12.6.1 逐条）：

| 项 | mac | Windows |
|---|---|---|
| 终端自己的圆角 | 用底色盖角 | **方的。** 子窗口是矩形，裁成别的形状要每次改大小都重算一个 region，而且是锯齿边；没做。于是 worker 与普通终端的框**上面两角圆（12）、下面两角方**；总管的框外面圆（12）、里面的终端方（边宽 4，圆角切进来不到 4，碰不到终端） |
| 投影 | 总管的框有 | **没有。** 画手的那套东西里没有「投影」这一种；总控台右栏的总管框在 Windows 上本来也没有 |
| 圆角的边缘 | 抗锯齿 | 面积大于 40 万像素的圆角矩形走系统自己的 `RoundRect`，是锯齿边（画手原有的界限，为了不在每次重画时分配几十兆的遮罩）。一格通常都大于这个数 |
| 「在干活」的转圈 | 转 | **不转**，画的是重画那一刻的那一帧。框不拥有任何定时器，也不要总控台的那个动画时钟（停着时没有定时器） |
| 明暗 | 跟这个窗口的外观 | 跟系统设置（与 Windows 的总控台同一个来源，配置里的窗口主题还没读） |
| 「拿到键盘时边变深」 | 标签页里最后聚焦的那一格 | 同：这个标签页记着的焦点格。键盘换格的每条路都走 `focus_active`，那里请父窗口重画 |
| 快速终端 | 不画（识别出来的） | 不画（它是单独的窗口、一个表面、没有标签页，根本不走 `tabs::layout`） |
| 借给总控台的那一格 | 原处画占位，框照画 | Windows 借出时前面是总控台的标签页，原标签页不在前面，没有「原处」可画；回到原标签页时它已经还回来了。框的规则没有特例 |
| 开关改了以后 | 配置重载后立刻 | **下一次布局或下一次快照变化时**才跟上（重载配置本身不触发布局；没接） |
| 身份的字「worker」 | 中文界面写「worker」 | 新的可翻译字串 `Worker` **还没进翻译目录**（`po/`），所以现在任何语言下都是英文 `Worker`。没有在这一单里重出目录：别的工作树今晚也在加字串，重出一次留给合并的人 |
| 名字太长 | 中间截断 | 末尾截断加省略号，并且不会压到右端的状态上（为此改了画手的 `paint_line`，见下） |
| 读屏 | 标题条合成一个元素 | 没有接 UI Automation：框是父窗口上的画，不是元素 |
| 「被按住」 | 没画 | 没画（同一个原因） |

### 13.2 性能判据

性能是验收的一部分（用户定）。下面的门槛是**建议值**，没有量过现有界面作参照；第一期的第一件事是
在两个平台上量一遍现有群聊页，把这张表定下来（§11 第 11 项）。读数取自被测的那个产物，报告里写明
是哪个提交、哪种构建。

| 读数 | 怎么量 | 建议门槛 |
|---|---|---|
| 什么都没变时的开销 | 窗口开着 60 秒，没有任何状态变化，数宿主为它醒了几次 | 0 次定时唤醒；CPU 低于 0.5% |
| 从事件到画面 | hook 事件到达核心的日志时刻，到卡片重画完成的时刻 | 95% 的情况低于 100 ms |
| 算快照 | 32 个群、128 个终端，算一次 | 发布构建下低于 1 ms |
| 按键到动作 | 按下批准，到核心收到动作 | 低于 50 ms |
| 开窗 | 从快捷键到第一帧画完整 | 低于 150 ms |
| 滚动 | 200 张卡的队列连续滚动 | 不掉帧（按显示器刷新率） |
| 内存 | 窗口开着比不开多出的常驻内存 | 低于 30 MB |

第一行是这张表里最要紧的：现在的群聊页每 500 ms 轮询一次，不管有没有事。原生窗口如果也这么做，
「纯原生是为了性能」这句话就不成立。地板：在宿主里加一个定时取快照的定时器，这一行的检查必须红。

## 15. 快速查看

用户的痛点只有一个：**没法快速看。** agent 说了一个文件、一个任务号，用户得自己去访达里找目录、
去面板里翻任务。这一节只做两件事，让这两样东西点一下就看得到。

### 15.1 点文件路径 → 就地预览

**现在是什么样**（行号取自 `156fa1785`）：

- 终端里的路径**已经能认出来**。默认的链接规则同时匹配网址和文件路径：以 `/`、`./`、`../`、`~/`
  开头的，以及 `src/config/url.zig` 这种不带前缀的相对路径（`src/config/url.zig:4-5,77-114`）。
- 按住 ⌘（mac）或 Ctrl（其它平台）悬停会高亮，点一下就打开（`src/config/Config.zig:1968-1974`、
  `:4698`）。
- 点了以后：核心取出那段文字；是相对路径就用这个终端的当前目录补成绝对路径，并且**只在文件存在
  时才补**（`src/Surface.zig:2538-2559`）；然后把它作为「打开网址」这个动作交给宿主
  （`src/Surface.zig:5903-5941`）。
- mac 宿主：没有协议头的当成文件路径，展开 `~`，交给系统用默认程序打开
  （`macos/Sources/Ghostty/Ghostty.App.swift:908-950`）。Windows 宿主：先过一道「能不能打开」的规则，
  再交给系统的外壳去打开（`windows/host/src/links.rs:64-102`）。
- 链接规则**现在不能配置**：配置项在，注释写着「目前设不了」（`src/config/Config.zig:1965-1966`）。
- 两个宿主里都没有任何预览的代码。

所以用户说的麻烦有一半不是「认不出路径」，而是**认出来以后做的是「用默认程序打开」**：一个 Markdown
文件弹出一个编辑器，一个目录弹出访达，一个相对路径在没有当前目录信息时什么都不发生。

**要做的：把「点路径」的结果从「用默认程序打开」改成「就地预览」。** 识别、高亮、手势、相对路径的
解析都是现成的，改的只是宿主收到这个动作以后做什么：

- 宿主收到的是一个本地路径（不是网址），而且文件或目录存在 → 出预览。
- 是网址 → 和今天一样。
- 路径不存在，或相对路径解析不出来 → 出一个很小的提示，写明它找的完整路径是什么。**不许什么都不
  发生**——今天就是这样，用户分不清是没点中还是文件不在。
- 原来的行为留一个入口：预览顶上的「用默认程序打开」；另有一个配置项把默认改回去。
  这改变了现有的默认行为；用户已点头（§11 第 14 项，2026-10-11）。
- 终端程序自己声明的链接（OSC 8）指向本地文件的，今天走的是另一条更严的路
  （`macos/Sources/Ghostty/Ghostty.App.swift:913-918`）。它不变，不进预览：那个路径是屏幕上的程序
  给的，不是用户看着点的那段文字。

**预览用什么画：**

| | 文本 / Markdown / 代码 | 图片 | PDF | 目录 | 其它 |
|---|---|---|---|---|---|
| mac | 系统的快速预览（Quick Look） | 同左 | 同左 | 自己画一个列表 | 文件信息 + 在访达中显示 |
| Windows | 自己画：只读、等宽的文本视图 | 系统的图像解码 | 先不做，给「用默认程序打开」 | 自己画一个列表 | 文件信息 + 在资源管理器中显示 |

- **mac 上用快速预览是可行的**（未验证，按系统能力判断，仓里没有先例）：系统提供一个可以嵌进自己
  窗口的预览视图，文本、代码、图片、PDF 都是它自带支持的类型。把它放进一个自己的小面板里，顶上加
  路径和三个按钮；目录的列表是自己画的，因为快速预览对文件夹只显示信息，不显示内容。要验的两点：
  它在一个不抢焦点的面板里能不能正常工作；Markdown 是渲染出来还是按纯文本显示（按纯文本也可以接受）。
- **Windows 没有对应的系统功能。** 资源管理器的预览窗格背后有一套预览处理器，可以宿主进自己的窗口，
  但那是一套组件接口，各类型由谁提供、装没装都不一定（未验证）。所以 Windows 的最小集自己画：
  文本用一个只读的等宽视图（宿主现在全是系统控件加 GDI，这在它的能力之内），图片用系统的解码器；
  PDF 第一版不做预览，直接给「用默认程序打开」，并在预览里说明，不显示成空白。
- **大文件**：文本只读开头的一段（默认 256 KB），顶上写「只显示了开头」。
- **两个平台不一样没有关系。** 预览是轻的：它回答「这个文件长什么样」，够用就行。

**它和文件窗格 E 的关系：预览是轻的，E 是完整的。**

- 预览：一个文件，一眼，关掉。不需要 E 存在。mac 上是系统的画法，Windows 上是最朴素的画法。
- E（v0.10.md §5，TUI，用户定）：目录树、在目录之间切换、语法高亮、git 状态、把路径发给旁边的终端。
- 预览顶上的「在文件窗格里打开」是从轻到重的那一步：E 做出来之前这个按钮不出现。
- 目录的预览（一个列表）和 E 的目录树是同一个需求的轻重两版；E 做出来以后，目录的预览里加一个
  「在文件窗格里打开这个目录」。
- **不做 diff**，预览和 E 的本期范围里都没有。

**三个地方用同一个预览：**

- **终端屏幕上的路径**：上面说的改法。
- **总控台里出现路径的地方**（卡片上的停因、预览里它说的话、文件页签）：同一个预览。
- **群聊消息里的路径**：消息正文用同一条规则找路径，相对路径相对群的工作目录解析；找到的画成可点的。
  群聊页签在原生重画之前嵌的是终端里的那个界面（§11 第 3 项），那时它就是「终端屏幕上的路径」，
  不用另做。

**它可以很早单独交付。** 「终端里点路径 → 就地预览」不依赖总控台的任何东西：不需要群、快照。
它改的是两个宿主各自处理一个已有动作的那一段，加一个小面板。所以把它排在**第一期的最前面**，
作为一个单独的小功能先出（任务 R0p）；总控台里的路径随后直接用它。

未验证的，开工前要验：

| 项 | 怎么验 | 验不通怎么办 |
|---|---|---|
| 中文路径、带空格的路径认不认得出 | 在终端里打印 10 种路径（中文目录、带空格、带括号、`~/`、相对、末尾带标点），逐个 ⌘ 点 | 认不出的记下来；这次不改识别规则，只改点了之后做什么。认不出的那几种就点不了，如实写进说明 |

### 15.2 点任务号 → 看任务是什么

总管在终端或群里说「#1289 做完了」。按住 ⌘（Ctrl）点 `#1289`，出一张**只读的卡片**。

卡片上的东西**全部来自现成的数据，不要求任何人多填一个字**：

| 段 | 来自 |
|---|---|
| 标题、分类、属于哪个群 | 任务面板 |
| 状态、进度、负责人（名字，不是编号）、多久没动 | 任务面板 |
| 时间线：什么时候建的、派给过谁、进度怎么变的、什么时候关的 | 任务的历史记录（每条有时刻、动作、负责人、状态、进度，`src/poltergeist/TaskLog.zig:177-196`） |
| 群里提到 `#1289` 的消息，最近的在上 | 群的聊天记录，按这个号找 |

卡片上还有两个入口：跳到这个任务所在群的卡片；跳到负责人的终端。没有任何能改任务的按钮。

一行标题读不懂这个任务是什么的时候，下面那一段「群里提到它的消息」通常就是答案——派活的那句话、
做完时的那句话都在里面。**如果以后发现这样还不够，再考虑给任务加说明；现在不设计它。**

**读代码的结论**（行号取自 `156fa1785`）：

- **任务号是全局递增的，不是每个群各自编号。** 所有群的任务在同一张表里，共用一个计数器，号码
  不回收（`src/poltergeist/Tasks.zig:197-202`、`:230`）；重启后从记录里读回来，计数器被推到最大号
  之后（`:271-278`）。所以**一个终端属于几个群也没有歧义**：`#1289` 只指一个任务，它属于哪个群
  记在任务自己身上。
- **能加一条认「#数字」的规则，而且不用碰「链接规则设不了」那个限制。** 那个限制说的是用户的配置项
  （`src/config/Config.zig:1965-1966`）；链接规则本身是一张表，默认的那一条就是代码里加进去的
  （`src/config/Config.zig:4694-4699`），每个终端启动时把这张表编成自己的一份
  （`src/Surface.zig:446-461`）。在这一步再加一条内置的规则即可，配置项不动。
- **动作要新增一种。** 链接的动作现在只有两种：用默认程序打开、打开程序声明的超链接
  （`src/input/Link.zig:24-32`）。加一种内部的「打开任务」，和后者一样不许用户配置。处理点击的地方是
  对动作的穷举分支（`src/Surface.zig:5905-5927`），新加的动作不处理就编不过。
- **限定范围在匹配的那一刻做**（`src/Surface.zig:5857-5875` 那个循环里）。认出 `#数字` 以后再问三件事，
  有一件不成立就当它是普通文字——不高亮、点不了：
  1. 这个号的任务存在；
  2. 这个终端和它有关系：是群聊页、是总管、或者是这个任务所在群的成员；
  3. 前后不是字母数字（`a#12`、`#12ab` 不算）。
  普通终端里的 `#123`（提交信息、议题号、颜色值）因此不会变成链接。
- **群聊页里怎么点**：现在的群聊页是跑在终端里的程序，它打出来的 `#1289` 就是终端屏幕上的文字，
  同一条规则直接生效，不用另做。它开了鼠标上报，但点击链接的处理排在鼠标上报之前
  （`src/Surface.zig:5404-5416`），所以点得中（未验证：没有在群聊页里实际点过）。群聊页是「用户的手」，
  上面第 2 条对它总是成立。群聊页签以后原生重画时，消息里的 `#数字` 用核心的同一个判断画成可点的。
- **宿主一侧**：核心发一个新动作「显示任务 N」，宿主向核心取这张卡片的数据（和现有的几个
  「把 JSON 写进缓冲区」的导出同一种形状，`src/apprt/embedded.zig:2067`），自己画。两个宿主各画一张。

一个已知的撞号：**任务号和代码托管平台上的议题号都写成 `#数字`。** 「#24」可能是任务 24，也可能是
议题 24，规则分不开。卡片标题因此写全：「任务 #24 · 群 ×××」，让人一眼知道点开的是哪一种；
任务不存在的号不会被认成链接，这挡掉了大部分情况（现在的任务号已经到四位数）。

未验证的，开工前要验：在 agent 的全屏界面里 `#数字` 点不点得中；一屏有上百个 `#数字` 时悬停高亮
卡不卡（每个匹配要查一次任务表）；提到某个任务的消息很多、而且有些只在磁盘上时，卡片出来要多久。

### 15.3 这一节曾经更大，为什么砍掉

这一节的前三稿依次是：交付单加按人的审核速度限流、结果单加判据前置、汇报工具加「要你确认」的队列
——连同收据、盲审复核、风险等级一整套机器把关。全部删了，没有挪到「后期」。

用户的话是：「复杂了，这不是流程，我刚说的痛点在于没法快速看，至于我看不看，不用限制。对总管来说，
我只要回复他就好了，甚至有些不用回复，比如总管报告完成的内容。我看不看，都不影响。」

意思是：**用户要的是看得快，不是被安排去看。** 一旦为「看」设计了表单、队列、通过与打回，
看就成了一项会积压的工作，而积压正是要消掉的东西。以后有人想给这里加登记工具、待确认的列表、
验收的闸，先回来读这一段。
