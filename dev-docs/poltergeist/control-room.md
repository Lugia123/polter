## 1. 定位

**群不是项目。** 项目与 agent 无关：它是布局、目录、历史。群与 agent 强相关：它是「一摊活」，有人在管、
有人在干、有话要说。两者不合并；群只记一个工作目录，不依赖项目，也不改项目。（用户定）

**总控台是 Polter 的主力窗口：只看这一个界面，就知道哪一摊活在等你，并且能当场处理，不必关心开了多少
tab 和分屏。** 它取代现在的「终端群聊」页成为入口；群聊、任务、统计都留着，变成它里面的页签。

要解决的事只有一件：同时开着几个总管、很多群以后，用户又回到了一个个 tab 去看谁在等他。下面每个决定都
用这一条来衡量。

三条已定的约束（用户定）：

1. **第一维度是群**，不是终端，不是会话。群跨重启保留；总管是「现在谁在管这个群」。
2. **纯原生**。不做 TUI，不做两平台共用的网页。mac 与 Windows 各写一套界面；状态、排序、文件记录、
   用量累计全部在核心算好，界面只画。性能是验收判据（§13.2）。
3. **冷启动不要求起名**，重开后**一键开总管接手**（§6）。

### 1.1 这条路走过一次，这次哪里不一样

mac 上做过一个原生的群聊窗口，用户用过后否掉了，窗口、C 接口、菜单全部删除，回到了终端里的 TUI
（`dev-docs/poltergeist/chatui.md:171-208`）。那次记下的账是：四条不满里只有一条是渲染方式造成的
（比例字体、代码对不齐），另外三条是数据不够（看不出谁在说、几点说的、群里有几个人）。

这次重新做原生，理由是用户定的「最高频的界面，性能优先」。但那四条不能再犯一遍，所以本文把它们写成
约束而不是留给实现去碰：

- **数据先于界面。** 第一期先交付核心的快照与排序函数，带测试；界面在它之上只画。上次是界面做完才发现
  数据不够。
- **凡是终端里的内容，就用终端画。** 总管的屏幕、它最后一轮说的话里的代码，不在原生控件里用比例字体
  重排。第 ③ 档直接显示真终端（§7）；消息正文用终端的等宽字体与同一套回退字体。
- **C 接口这次是必要的。** 上次的结论是「TUI 走 socket 就够，不必加导出」。原生界面没有这条路：
  群与任务数据在 `156fa1785` 上没有任何给宿主的导出，只有 TUI 每 500 ms 经 socket 轮询
  （`src/cli/chat.zig:56,187`）。§5.4 给出要加的导出，并限制它的面。

## 2. 名字

**推荐：中文「总控台」，英文 Control Room。**（待用户定）

- 避开 macOS 自带的 Mission Control，也避开各家都在用的 dashboard（那个词暗示「只能看」）。
- 「总」对上产品里已有的「总管」；「台」是一个你坐在那儿操作的地方，不是一张报表。

备选：

| 名字 | 好处 | 问题 |
|---|---|---|
| 值班台 / Watch Desk | 直说「谁在等我」这件事 | 听起来只有监看，没有「在这里把事办了」 |
| 指挥台 / Command Deck | 强调下指令 | 和「命令面板」（Command Palette）撞词 |
| 群 / Groups | 最老实，第一维度就是群 | 说不出它是主力窗口，和群聊页签分不开 |

## 3. 用户看到什么

### 3.1 一个窗口，三栏

总控台是一个独立的原生窗口，不是标签页里的东西。可以拖到另一块屏，位置与大小记住。

mac 版布局：

- **左栏是队列**，一张卡一个群。分段固定为：等你、出错、做完未看、在干活、闲着（§4.3 的排序）；
  其下是未归组一栏；最底一行是三个折叠入口：先放着、无人看管、归档。
- **右栏是选中那个群的详情**，页签：终端、群聊、任务、文件、用量、统计。
- **标题栏的「等你 N」** 和左栏「等你」段的数字、Dock 徽标、主窗口上的提示条，是同一个函数的返回值
  （§4.3）。
- 汇报里「需要确认什么」的条目进「等你」，类别是「要你确认」（§4.3、§15.7）。线框图画的是加它之前的样子。
- 界面上凡是出现文件路径的地方，点一下就地预览（§15.6）。

### 3.2 卡片

卡片上从上到下：

1. 群名；右侧是「等了多久」。只有在等用户的卡才显示这个时间，从进入等待的那一刻算起。
2. 一行停因，写出**在等什么**，不只写「在等」：
   - 等审批：工具名 + 输入的开头（取自 hook 的 `note`）。
   - 等回答：它问的原话的开头。
   - 要你确认：汇报里第一条待确认的原话，后面跟「还有几条」。
   - 出错：原因（限流、过载、鉴权、账单、输出超限、进程退出）。
   - 一轮结束、未看：它最后一句话的开头。
   - 在等后台：还挂着后台任务。这不是等用户，归在「在干活」。
   - 疑似卡住：屏幕多久没动、多久没调工具。
3. 可以当场做的动作（第 ① 档，§7.1）。没有可做的动作就不画按钮。
4. worker 一排小点，一点一个 worker，颜色是它自己的状态；末尾是数量。默认不展开。
5. 状态来源过期时，停因那一行后面跟一个灰色的「？」和年龄（§4.2）。

「在干活」和「闲着」两段的卡只有一行：群名 + 状态。正常的东西不占地方，颜色只给需要用户的。

| 页签 | 内容 | 来自 |

### 3.4 Windows 的差异

布局、分段、卡片内容、排序完全相同，都出自核心。差异只在这几处：

- **画法**：Windows 宿主的非终端窗口全是 Win32 + GDI + 标准控件，没有 Direct2D
  （`windows/host/Cargo.toml:72` 只开了 `Win32_Graphics_Gdi`）。总控台照设置窗口的做法：
  纯逻辑放进一个能在 mac 上测的 crate，窗口只负责画。
- **窗口**：Windows 已经是一个进程多个顶层窗口（`windows/host/src/main.rs:1734,1816`），总控台是又一个
  顶层窗口；新窗口目前位置是系统默认，记住位置要新做。
- **快捷键**：mac 的 `⌘` 换成 `Ctrl`，其余键位相同。
- **系统通知**：走 Windows 的通知中心；任务栏按钮上的数字用覆盖图标。
- **权限面板**：Windows 不需要 mac 那些授权提示。

## 4. 数据模型

### 4.1 群要多记的

`156fa1785` 上，群在内存里是 `name / created_by / next_seq / log / members / brief / last_ms`
（`src/poltergeist/Chat.zig:200-227`），而**写回磁盘再读回来的只有两个字段**：`brief` 与 `listed`
（`src/poltergeist/GroupLog.zig:221-238`），群名取自目录名。工作目录、角色、会话编号都没有。

群的记录文件新增这些字段，都是可选的，旧文件读进来等于「都没有」：

| 字段 | 含义 | 谁写 |
|---|---|---|
| `cwd` | 这摊活的工作目录，一个 | 冷启动时用户选的；`group_set_cwd` |
| `steward` | 上一任（或现任）总管：`{ role, cli, session_id, since_ms, ended_ms }` | 核心，在总管入群、收到会话编号、离开时 |
| `auto_named` | 群名是自动取的，还没被改过 | 核心 |
| `seen_ms` | 用户上次看过这个群的时刻（§4.3 的「未看」靠它） | 总控台 |
| `snooze` | 先放着：`{ at_ms, until: next_event \| <时刻> }` | 总控台 |
| `archived_ms` | 归档的时刻；没有就是没归档 | 总控台 |

三点说明：

- **群名仍然是身份**，规则不变：1–48 字节，小写字母、数字、连字符
  （`src/poltergeist/Chat.zig:264-271`）。自动取名必须落在这条规则里（§6.1）。
- **`session_id` 现在只在内存**（`src/poltergeist/Bus.zig:300`），重启即丢。要恢复上一任的会话，
  必须在它每次变化时写进群的记录。
- **`listed: false` 已有含义，不借用。** 归档用新的 `archived_ms`，免得两种「不在列表里」分不开。

**重启后的上限要改。** 现在重启最多放回 24 个群（`max_groups` 32 减去预留，
`src/App.zig:1546-1569`），其余的留在盘上却没有办法再选出来——代码注释自己写了这是欠账。
群成了第一维度以后，这个上限会直接表现为「我的群不见了」。改法：首屏只把**活跃的**群装进内存；
归档与不活跃的群由总控台直接从盘上的记录列出来，点「恢复」才装进内存。

### 4.2 状态模型：机器事实，加一行自报

每个群有一个**关注状态**，由核心从下面几路信号算出。每一路都带来源与年龄；**「过期」与「不知道」是
画出来的状态，不是悄悄退回成「没事」**。

| 路 | 读的是什么 | 现在有没有 | 过期规则 |
|---|---|---|---|
| hook | agent CLI 自己报的状态：`idle / in_turn / ended / failed / awaiting_approval / awaiting_input`，加 `detail`、`note`、`waiting_on_background`（`src/poltergeist/Bus.zig:225-233,290-307`） | 有，但只有 Claude Code，而且只在按角色启动时装 | `hooks` 不是 `live` 就不读；`in_turn` 超过阈值且屏幕静止，降为「疑似卡住」 |
| 屏幕 | 屏幕多久没变（`quiet_ms`） | 有，但**只量被监管的终端**；总管自己没有读数 | 采样失败单列为「读不到」，不当成「没动」 |
| 调用 | 多久没调 Polter 的工具（`call_silent_ms`，默认 15 分钟，`src/poltergeist/Bus.zig:659`） | 有 | 它只是算术，只用来加重「疑似卡住」 |
| 进程 | 子进程退没退；这个终端的 agent 连没连着（`src/poltergeist/Server.zig:659`） | 有，但后者不在 `terminal_list` 里 | 进程没了，否决 hook 留下的任何旧状态 |
| worker | 每个 worker 自己按同一套规则算出的状态；任务面板的开着、卡住数量 | 有（任务）；worker 状态要新算 | 同上 |
| 自报 | 总管自己写的一行：在做什么、卡在哪、下一步（新工具，§5.1） | 无 | 带时间戳；超过阈值显示年龄；状态变了就标「说这话时还在上一个状态」 |

三条规则：

1. **机器事实定类别，自报只填那一行字。** 自报不能把「等审批」「出错」改成别的。
2. **自报只能把关注往上提，不能往下压。** 总管说「我卡住了，要用户定」可以让这张卡进「等你」；
   总管说「一切正常」不能让一张「出错」的卡离开「出错」。往上提错了只是多看一眼，往下压错了是漏掉。
3. **hook 的 `ended` 分不开「做完了」和「在用一段话问你」。** Claude Code 一轮结束时用正文提问，
   hook 报的是 `ended`，不是 `awaiting_input`（后者只对应表单式提问与空闲提示：装的是
   `Notification` 的 `idle_prompt|elicitation_dialog`，`plugins/claude-code/adapter.py:90-97`）。
   所以「一轮结束、未看」这一类的卡必须把它最后一句话露出来，由用户一眼判断；总管也可以用自报把它
   提成「等回答」。

读代码后要补的缺口，都是这个模型成立的前提：

- **总管的屏幕没人量。** 屏幕静止只对被监管的终端采样。总控台要对有群的总管也开采样。
  代价未验证：每秒比一次屏幕指纹，总管数量通常是个位数；验法是开 8 个总管量采样线程的 CPU。
- **hook 状态只有一个时间戳。** `since_ms` 是状态上次变化的时刻（`src/poltergeist/Bus.zig:294-295`），
  不是上次收到事件的时刻。年龄要读后者，需加 `last_event_ms`。
- **进程信号没露出来。** `agent_present` 只在 `terminal_capabilities` 里；总控台的快照要带上它与
  子进程是否已退出。
- **CLI 退出 hook 不报。** 装的六个事件里没有会话结束（`plugins/claude-code/adapter.py:90-97`）。
  所以「agent 退了只剩 shell」只能由进程信号判断，这正是第 4 路存在的理由。

### 4.3 排序与计数：一个函数

所有地方的数字——标题栏的「等你 N」、左栏分段的计数、Dock 徽标、主窗口的提示条、系统通知要不要发——
都出自同一个函数。宿主不许自己数。

```
类别（Kind），按先后：
  1 needs_approval   等审批          hook = awaiting_approval
  2 needs_answer     等回答          hook = awaiting_input；或自报提上来的
  3 needs_confirm    要你确认        这个群有汇报里的确认条目还没答复（§15.7）
  4 failed           出错            hook = failed；或 agent 进程退出且不是用户关的
  5 suspect_stuck    疑似卡住        hook = in_turn 且屏幕静止 ≥ T1 且无工具调用 ≥ T2；
                                     或 hook 约定要来却没来
  6 done_unseen      一轮结束未看    hook = ended 且没有后台任务挂着 且 since_ms > seen_ms
  7 quiet_unknown    静止，原因不明  没有 hook，屏幕静止 ≥ T1
  8 working          在干活          hook = in_turn；或 ended 且有后台任务挂着；或屏幕在动
  9 idle             闲着            其余，且有总管在
 10 unattended       无人看管        群里没有任何活着的终端

attention(群) -> { kind, since_ms, what, source, age_ms }
  取这个群的总管的类别；
  这个群有未答复的确认条目，而总管的类别排在 3 之后时，取 3，since_ms 是最早那条的时刻；
  worker 的 needs_approval / failed 超过 60 秒没被总管处理，冒到群上，what 写明是哪个 worker；
  snooze 生效期间，kind 记为 snoozed，不进下面的 needs_me。

needs_me(群) = attention(群).kind ∈ { 1, 2, 3, 4, 5, 6, 7 }

排序键 = ( kind 升序, since_ms 升序 )          -- 同一类里，等得最久的在最上
等你 N = | { attention(g) 所指的终端 : needs_me(g) } |   -- 按终端去重，见 §4.4
                                               -- 类别 3 所指的是这个群本身：总管不在了，条目仍然等着
```

为什么是这个顺序：

- 1–2 是「不处理它就不会动」，3 是「它说做完了一部分，等你一句话」，4 是出了错，5 是「可能已经不会
  动了」，6–7 是「它停了，看一眼才知道要不要管」，8–9 不需要用户。「要你确认」排在出错前面，
  是因为它是一个明确问出来的问题，答它只要几秒；排在等审批、等回答后面，是因为那两样正挡着一个
  活着的 agent。调研里五家产品各自收敛到同一个顺序；反例是默认按项目分组，活跃的会话被埋进历史里。
- **组内按等了多久**，而不是按最近有动静。计时从进入这个类别算起，总管再追问不重置——否则越催越靠后。
  用户一回复，它离开这个类别，自然沉下去。
- **行的身份稳定。** 卡片的快捷键是群的编号，不是它在列表里的位置；排序变化只在窗口不在前台、或用户
  超过 2 秒没有动键盘鼠标时才生效，其余时候新来的卡只在段内末尾出现并闪一下。通知一来就把列表重排，
  用户会点错，别家已经为此挨过骂。

阈值 `T1`、`T2` 沿用现有配置的默认值（屏幕静止 3 分钟、无工具调用 15 分钟），不另起一套。

### 4.4 一个总管管几个群

关注状态属于终端，卡片属于群。一个总管管三个群时，它在等审批这件事只有一件：

- **计数按终端去重**，「等你」是 1，不是 3。
- 三张卡排在一起；停因与动作只画在它最近说过话的那个群的卡上，另外两张写「同一个总管，见 ×××」。
- 对其中任何一张操作，三张一起变。

### 4.5 活跃、先放着、无人看管、归档

- **首屏只放活的**：群里有活着的终端。
- **先放着**（snooze）：用户说「知道了，先别提醒」。卡片挪到底部折叠入口里，不计入「等你」。
  回来的条件二选一：它的状态再变一次（默认），或到某个时刻。**先放着不是归档**：它一定会回来。
- **无人看管**：群还没归档，但没有任何活着的终端——重启之后的群都是这样。折叠在底部，每一行带
  「开一个总管」（§6.2）。超过 7 天没动静的，自动落到归档视图里（阈值待用户定）。
- **归档**：用户明确归档。不删任何东西，只是从首屏拿走、不占内存。群里还有活终端时不让归档，
  和销毁群同一条判据。

### 4.6 未归组

两类终端单列一栏，用同一个排序函数：

- 是总管但还没建群的；
- 不属于任何群、也没被监管的独立 agent（有 hook 的，或者有 agent 连着的）。

这一栏存在的理由：用户要的是「不用管开了多少 tab」，如果只有进了群的才上总控台，那么一个手敲出来的
agent 在等审批，用户仍然得去翻 tab。

## 5. 工具与接口

### 5.1 新增的 MCP 工具

| 工具 | 参数 | 谁能调 | 拒绝码 |
|---|---|---|---|
| `status_report` | `doing`（必填，一行）、`blocked_on`、`next`、`needs_user: bool`、`group` | 任何在群里的终端，只能报自己 | `NotAMember`、`TooLong`（每项 200 字节）、`RateLimited`（每终端每 10 秒一次） |
| `group_set_cwd` | `group`、`cwd`（绝对路径） | 群的现任总管 | `NotYours`、`NoSuchGroup`、`BadPath` |
| `report_post` | 完成了什么、需要确认什么、涉及哪些任务、涉及哪些文件（§15.4） | 群里的任何终端 | 见 §15.4 |
| `task_describe` | `task`、`what`、`criteria[]`（§15.5） | 群的现任总管 | `NotYours`、`NoSuchTask`、`TooLong`、`TooMany` |
| `group_usage` | `group` | 群的成员 | `NotAMember`；拿不到数的 CLI 在结果里逐个写明 `unavailable` 与原因 |

`status_report` 的三条约束：

- 它**不是**任务进度。任务面板管「这件事做到哪了」，它管「我这个终端此刻在干什么」。
- 文字原样显示，程序不解析。唯一被程序读的是 `needs_user`。
- 返回值里带上「机器此刻看到你是什么状态」，让总管知道自己说的和测到的差在哪。

### 5.2 改动的 MCP 工具

- **`role_launch` 加 `group` 与 `resume`。** 现在的参数是 `key / cli / cwd / place`
  （`src/poltergeist/rpc.zig:540-550`）。`group`：开出来的终端认领身份时直接进这个群；
  `resume`：会话编号，交给适配器换成那家 CLI 的续接参数。新拒绝码：`GroupHasSteward`（群有活着的总管，
  而调用者不是用户）、`ResumeUnsupported`（这家 CLI 不支持续接，或没有适配器）。
- **`terminal_answer_prompt` 加 `expect_since_ms`。** 现在它是盲发键：按 `choice-1` 次下箭头再回车，
  不看 hook 状态，也不读屏幕（`src/poltergeist/rpc.zig:6813-6851`）。提示换了，它照发，并报成功。
  加上这个参数后：目标终端的 hook 状态必须是 `awaiting_approval` 且 `since_ms` 等于它，否则拒绝
  `PromptGone`。不带参数时行为不变，免得破坏现有调用者。
- **`terminal_list` 的每一行带上 `agent_present`、子进程是否已退出、`last_event_ms`。**
- **`group_list` 带上 §4.1 的新字段与 `attention`。**

### 5.3 归属：接手一个别人建的群

这是读代码后与设想冲突最大的一处。

现状：群的归属在建群时写一次，之后不变。六个操作要求调用者是建群的总管，否则 `NotYours`
（`src/poltergeist/rpc.zig:5643-5662`，调用点在 `:6254`、`:7040`、`:7053`、`:7059`、`:7089`、`:7296`），
其中包括 `group_add`——**新总管连把自己加进去都不行**。上一任的终端关掉或卸任都不动归属，
群就锁在一个已经不存在的终端上。只有重启之后，群以「无主」回来（归属记成用户，
`src/poltergeist/Chat.zig:326`），任何总管才能接。

所以「一键开一个总管接手这个群」在同一次运行里今天走不通。改法：

1. **归属跟着活人走。** 持有归属的终端关闭或卸任时，归属退回「无主」。这一条本身就是修一个缺陷。
2. **用户可以移交。** 新增一个只有用户（总控台）能发起的操作 `group_hand_over(group, to)`：
   把归属交给另一个终端。agent 不能调——被监管的终端是最容易被注入一句话的地方，
   不能让一句话就把群抢走，这和 `become_supervisor` 拒绝被监管终端是同一个理由
   （`src/poltergeist/rpc.zig:7004-7008`）。
3. **群有活着的总管时，一键开总管要先问。** 提示「这个群现在由 ××× 在管，换成新的吗」；确认后
   原总管保留成员身份、失去归属，并收到一条通知。不确认就不开。

顺带暴露的一个已有缺口：`task_edit / task_assign / task_close / task_cancel` 不查群的归属，
任何总管都能动别的总管群里的任务。一个总管时没人注意，几个总管并存时就是真问题。建议第一期一起补上
归属检查（会改变现有行为，列入 §11）。

### 5.4 核心给宿主的接口

现状：核心到宿主只有两种通道。**拉**：一族把 JSON 写进缓冲区的导出，宿主自己轮询
（`src/apprt/embedded.zig:2067,2100`）；**推**：只有按终端的监管标记动作
（`include/ghostty.h:1368`）。没有「数据变了，来取」的机制，群与任务数据没有任何导出。

新增，面尽量小：

| 导出 | 作用 |
|---|---|
| `ghostty_app_control_snapshot` | 整个总控台的快照：每个群的 §4.1 字段、`attention`、worker 小点、`needs_me`、`rev` |
| `ghostty_app_control_group` | 一个群的详情：成员、任务、最后一轮的话、文件、用量 |
| `ghostty_app_control_messages` | 一个群的消息，按序号分页 |
| `ghostty_app_control_act` | 用户在总控台上的动作：批准、拒绝、回一句、先放着、归档、已看、移交、开总管 |
| 动作 `CONTROL_ROOM_CHANGED` | 快照变了。合并发送，每秒不超过 4 次，带 `rev` |

三条约束：

- **宿主只在收到 `CONTROL_ROOM_CHANGED` 时取快照，没有定时器。** 现有 TUI 每 500 ms 轮询一次；
  原生窗口什么都没变时应当一次都不醒（§13.2）。
- **用户的动作只走 `ghostty_app_control_act`。** 宿主已有的 `ghostty_surface_text` 一类通用入口
  走的是「用户本人在那个终端里打字」的路，不过 Polter 的任何守卫，也不记账。总控台的「批准」
  「回一句」如果走它，就绕开了 `PromptGone`、`DraftInLine` 这些检查。
- **快照里全是算好的东西。** 排序、分段、计数、「等了多久」的起点、要显示的那一行字，都在里面。
  宿主里出现任何对状态的判断，都算缺陷（§13.1 第一期的地板里有一道检查）。

总控台窗口是「用户的手」，和现在的群聊页一样：它发出的请求以用户身份到达
（现有做法见 `src/App.zig:2299-2302`）。这个身份由宿主在创建窗口时登记，不是窗口自己声称的。

## 6. 冷启动与恢复

### 6.1 冷启动：新的一摊活

1. 用户点「+ 新的一摊活」（或快捷键）。
2. 弹出一个很小的面板：**工作目录**（默认上次用的那个，可以换）、**角色**（默认上次用的总管角色）、
   **一句要做什么**（可空）。没有「群名」这一栏。（用户定）
3. 核心取群名：目录名转成合法的名字（转小写；不在 `[a-z0-9-]` 里的字符换成连字符；首尾与连续的
   连字符收掉；截到 48 字节）。重名加序号 `-2`、`-3`。转完是空的（比如目录名全是中文）就退回编号
   `g-<n>`。标记 `auto_named`。
4. 核心建群：写入 `cwd`；那句话写成简介的初稿。
5. 核心按 §6.3 开一个总管并绑到这个群。卡片立刻出现在「在干活」里，写着「正在启动」。
6. agent 连上以后，那句话作为第一句发给它（走 `terminal_send` 的同一条路）。
7. 总管弄清要做什么以后，用 `group_rename` 改名、用 `group_set_brief` 写简介；`auto_named` 清掉。
   启动提示里写明这一步。在它改名之前，卡片上的名字后面带一个「暂名」的标记。

**现有的路保留**：普通终端里的 agent 自己 `become_supervisor` 再 `group_create`。群一建，总控台自动
出现它的卡片，不需要它另外做什么。这种群没有 `cwd`，卡片上提示「没有记工作目录」，总管可以用
`group_set_cwd` 补上；核心也可以在建群时把建群终端的当前目录填进去作默认值（待用户定）。

### 6.2 恢复：重开以后

重启后群从盘上回来，成员是空的。这是有意的：终端的编号每次启动都重新生成，「屏幕上哪个终端是昨晚
那个」是一个判断，Polter 不替人做（`src/App.zig:1534-1569`、`src/poltergeist/Chat.zig:314-339`）。
总控台不改这一点，只把「重新找人来管」做成一步：

1. 重启后，昨天的群都在「无人看管」里。每一行显示：群名、简介的第一行、工作目录、上一任是谁
   （角色与 CLI）、上次说话的时间、还开着几个任务。
2. 用户点「开一个总管」。有两个按钮：
   - **接着上次的会话**：只在上一任的 CLI 支持续接、而且记着会话编号时出现。
   - **新会话**：总是有。
3. 核心按 §6.3 开终端：目录是群的 `cwd`，角色是 `steward.role`。
4. 它起来就已经是总管、已经在这个群里、已经持有归属，不需要用户再告诉它用哪个群。（用户定）
5. 启动提示里写明：你接手的是哪个群、它的简介、开着的任务有哪些、上一任的会话记录可以用
   `session_recall` 查。新会话的第一件事是读这些，而不是建一个新群。
6. worker 不自动重开。总管读完面板自己决定要谁；这和「不自动重起」的现有立场一致。

### 6.3 启动即绑定：现在有什么、缺什么

- **启动即总管：已经有。** 角色带总管标记（`src/poltergeist/persona.zig:179`）时，核心先替这个终端
  存一份待认领的身份，agent 的第一条请求到达时认领并成为总管
  （`src/poltergeist/PersonaStore.zig:584-598`）。它第一次问「我是谁」就已经是总管。
- **启动即绑群：没有。** 角色定义和启动请求里都没有群；启动链路里没有任何入群或建群。现在只靠启动
  提示让它自己去建。要加的：待认领的身份里带上群名；认领时把终端加进群、移交归属（§5.3）、
  写 `steward`。
- **认领有 60 秒的期限**，过期只打一行日志（`src/poltergeist/PersonaStore.zig:587-590`）。绑群以后
  这个沉默不能留：过期时卡片要写「总管没连上」，并给「再试一次」。
- **启动行不带参数。** 核心往终端里打的是一行固定的启动命令（`src/App.zig:2647`）。群和会话编号
  不经这一行传，免得出现在屏幕与历史里；它们走待认领的身份和适配器的请求。
- **续接会话：没有一等支持。** 启动请求里没有会话字段；会话编号只在内存。要加的：把编号写进群的
  记录（§4.1）；启动请求带 `resume`；适配器把它换成那家 CLI 的参数。目前只有 Claude Code 有适配器，
  其余几家的按钮就是不出现——不显示成灰的，免得用户以为是出了错。

## 7. 三档介入

界面能缩短的只有「每次应答要多久」。三档从轻到重；每一档解决上一档解决不了的那部分。

### 7.1 第 ① 档：卡片上直接处理

卡片上只放**不需要看上下文就能安全做**的动作：

| 状态 | 动作 | 怎么送 |
|---|---|---|
| 等审批 | 批准一次、拒绝 | 见下 |
| 等回答（有选项） | 选项 1…n | 带守卫的选择 |
| 等回答（自由文本）、一轮结束 | 回一句 | `terminal_send` 的同一条路 |
| 出错 | 重试（发一句「继续」）、看原因 | 同上 |
| 任何 | 先放着、已看 | 只改总控台自己的状态 |

**批准与拒绝怎么送，是这一档的关键，也是与设想冲突的一处。** 设想是直接复用
`terminal_answer_prompt`。但它是数着格子盲发键的：提示换了一个、选项顺序不同、提示已经没了，
它都照发并报成功。把它放到一个一键的按钮后面，等于把「数错了」的后果从一个会回头读屏幕的 agent
手里，交到一个不看屏幕的人手里。

所以第 ① 档只做两个**不靠数格子**的动作：

- **批准一次** = 回车（接受默认高亮的那一项）。
- **拒绝** = Esc。

并且都带守卫：按钮按下时带上卡片画出来那一刻的 `since_ms`；核心核对目标终端的 hook 状态仍是
`awaiting_approval` 且 `since_ms` 没变，否则不发任何键，回 `PromptGone`，卡片当场刷新。
「总是允许」「允许并记住」这类靠位置的选项不放在卡片上，进第 ② 档。

未验证，第一期开工前要先验：

- Esc 在 Claude Code 的授权提示上等于拒绝，而且不会顺手打断整轮。验法：在测试实例里造一个授权提示，
  发 Esc，读 hook 的下一个事件与屏幕。
- 默认高亮是否总是「批准一次」。验法同上，覆盖 Bash、写文件、联网三种提示。
- 更干净的做法是让授权的 hook 自己把决定带回去：Claude Code 的这个 hook 可以返回允许或拒绝，
  这样完全不发键。但 hook 要等用户的决定，等多久会超时、等的时候终端上显示什么，都没有读数。
  列为调查项；验得通就替换发键的做法，验不通就留着发键。

「回一句」沿用 `terminal_send` 现有的守卫：那个终端 10 秒内有人打过字就拒绝，输入行里有没提交的
字就拒绝。拒绝时卡片上说明原因，并给「进终端」。**回执要分两种**：字打进去了，和 agent 已经开始
下一轮了（hook 报 `in_turn`）。只有后一种才把卡片从「等你」里拿走。

### 7.2 第 ② 档：预览并回话

选中一张卡，右栏的「终端」页签显示：

1. **它在等什么**，完整的：工具名与完整输入、它问的原话。
2. **它最后一轮说的话**，取自 hook 带来的最后一条消息（现有的 `terminal_turn`），不是刮屏幕。
   这是结构化的、不随 CLI 改版而坏的那一路，所以排在屏幕之前。
3. **屏幕的最后若干行**，纯文本，等宽，每秒最多刷新两次。来源是现有的读屏接口
   （`src/apprt/embedded.zig:2557`，源码要求调用方节流）。它没有颜色、没有属性，全屏界面的结构
   会丢——所以它是辅助，不是主体。没有 hook 的 CLI 只有这一路，预览上写明「这家 CLI 没有接 hook，
   下面是屏幕的文字」。
4. 一个输入框，和全部动作（包括靠位置的选项，带同样的 `since_ms` 守卫）。

为什么不在这一档就上真终端：预览要在用户上下移动卡片时立刻跟着换，每换一张就搬一次终端，
两边的终端都会被改尺寸、重排一次。预览只读文字，换卡片没有代价。

### 7.3 第 ③ 档：真终端进来

三个方案，读了两个平台的代码以后的判断：

| 方案 | mac | Windows | 代价 |
|---|---|---|---|
| **真镜像**：同一个终端画在两处，两处都能输入 | 要改渲染器 | 明显更难 | 高，而且有做不干净的地方 |
| **借过来**：把视图挪进总控台，用完还回去 | 有先例 | 整个 tab 有先例，单个窗格要新写 | 中 |
| **跳转往返**：跳到它所在的 tab，一个键回来 | 现成 | 现成 | 几乎没有；但离开了总控台 |

事实依据：

- **一个终端只有一个渲染器，画到创建时给定的那一个视图上**（`src/Surface.zig:89`）。mac 的渲染器
  自己建图层并设到视图上（`src/renderer/Metal.zig:114-117`）；Windows 每个窗格是一个子窗口加一个
  OpenGL 上下文。两边都没有把画好的帧交给第二个视图的接口（`src/renderer/OpenGL.zig:563`）。
- **真镜像做不干净的地方**：两处大小不同时，终端只有一个网格尺寸，另一处只能缩放或留边；视图不可见时
  渲染会停；两处都能输入时焦点、输入法、鼠标坐标都要分两份。Windows 上还要在渲染线程里对第二个
  窗口再提交一次。
- **借过来有现成的搬法**：mac 上分屏拖放本来就能把同一个视图从一个窗口的树搬到另一个窗口的树
  （`macos/Sources/Features/Terminal/BaseTerminalController.swift:1017,1053`）；Windows 上
  「把标签页移到新窗口」不重建窗格，是把它们换一个父窗口（`windows/host/src/tabs.rs:4262`）。
- **单个窗格的搬动 Windows 没有**；两边的分屏树叶子都还是单个视图
  （`macos/Sources/Features/Splits/SplitTree.swift:15-17`、`windows/split-tree/src/lib.rs:188-191`）。

**推荐：借过来，而且借的是整个 tab，不是一个窗格。**（待用户定）

- 用户要管的是「总管加它那一组 worker」，而现有规则就是 worker 开在总管自己的 tab 里。借整个 tab，
  右栏看到的就是这一摊活的全貌；只借总管那一格，worker 还得另外去找。
- 整个 tab 换窗口，两个平台都有先例；单个窗格离开 tab，Windows 要新写。
- 被借走的 tab 在原窗口留一个占位，写「在总控台里，点这里收回」。关掉总控台或选别的卡，自动还回去。
- 代价要说清：借过来和还回去各改一次尺寸，里面的程序各重排一次。所以它是用户**明确要进去**
  （`⌘⏎`）时才做的事，不是选中卡片就做——选中卡片只到第 ② 档。

**分期上先做跳转往返**：第一期的「进终端」就是跳到那个 tab，并在那个 tab 上留一个「回总控台」的键。
它几乎没有成本，而且在借过来做完之前，三档是完整的。借过来放到第三期。

不做真镜像。理由是上面那几处做不干净的地方，以及 Windows 上的代价；它换来的只是「不搬动」，
而借整个 tab 已经让用户不必离开总控台。

**值得用户知道的另一条路**：调研里与 Polter 形态最接近的几家，做法是让侧栏直接取代标签栏——
所有 tab 都住在这一个窗口里，侧栏按「谁在等我」排，点一行就是切到那个 tab。那样就没有「借」这回事。
没有推荐它，是因为它要动 mac 上「一个 tab 一个系统窗口」这个基础，范围比 0.10 大；
但如果借整个 tab 做下来顺，下一版自然会走到那里。

## 8. 文件与用量

### 8.1 文件

设想是：写文件的 hook 经过 Polter，可以直接记「这个群动过哪些文件」。读代码的结论是**现在没有经过**：
装的六个事件里没有工具调用前后的那两个，核心遇到它们会直接拒绝
（`src/poltergeist/agent_event.zig:440-441`）。Polter 现在唯一见到文件路径的时刻，是需要授权的写入——
路径的开头进了 `note`；不需要授权的写入完全看不到。

所以分两步：

1. **加一个工具调用之后的 hook，只匹配写文件的那几个工具。** 核心只取路径，记成
   `{ 路径, 哪个终端, 时刻, 新建还是修改 }`，按群累计，同一路径只留最后一次。
   代价未验证：每写一个文件多起一个进程。验法：让 agent 连写 200 个文件，量这一轮多花的时间；
   超过 5% 就把这个 hook 改成批量上报。
2. **在那之前，文件由汇报的人列出。** 汇报（§15.4）里的文件清单就是「这些是要给你看的」；动过的文件
   可能上百个，要看的只有几个。路径在群的 `cwd` 之外的照收但不能一键打开，免得一句被注入的话让用户
   去打开别处的文件。写文件的 hook 接上以后做对账：列了却没动过的、动过却没列的。

「文件」页签：最上是汇报里列过的文件，其次（hook 接上以后）是动过的文件，最下是工作目录的入口。
点一个文件是就地预览（§15.6）：看它现在的内容，不做 diff。目录树与完整的浏览不在这里做——
那是 0.10 的文件窗格 E，用户已经定了它是 TUI；预览顶上有进 E 的入口。

没有 hook 的 CLI：这一页只有汇报里列过的文件与目录入口，并写明「这家 CLI 没有接 hook，看不到它动过哪些文件」，
不显示成一张空表。

### 8.2 用量

现状：**核心里没有任何 token 或费用的量**，统计页签的输入里也没有 agent 一侧的数据；hook 带来的
会话记录路径没有存，也没有任何代码读 agent 的会话记录。

设想是从 agent 的会话记录里加总。**这是按机制推的，未验证**，所以它是用量这一期开工前的第一件事：

- 要验的：Claude Code 的会话记录里每一条助手消息是否带输入、输出、缓存读写的 token 数；续接会话与
  上下文压缩之后会不会重复计；子 agent 的用量记在哪。
- 验法：跑一段已知的会话，把自己加出来的数和那家 CLI 自己的用量命令报的数对比，三段会话的误差都在
  2% 以内才算可用；带一个故意漏算缓存的对照，证明这把尺子量得出差别。
- 验不通时的退路：用 CLI 的状态栏接口——那里有它自己算好的累计 token 与时长——代价是要在启动时
  替它配一个状态栏脚本，和 hook 是同一种配法。

显示：

- 「用量」页签：按会话列出输入、输出、缓存、时长；按天累计；总管与每个 worker 分开。
- 卡片上不放数字。只有一种情况例外：**因为限流或额度停下**是一种明说的停因，出现在卡片的停因那一行。
  并行时额度比注意力更早撞墙，它应当是状态，不是统计页里事后才看到的数字。
- **不显示金额。** 订阅用户没有按量的价格，按列表价估一个数会误导。只显示 token 与占额度窗口的比例
  （拿得到时）。待用户定。
- 拿不到数的 CLI：那一行写「这家 CLI 的用量拿不到」和原因，不显示 0。0 和「不知道」是两件事。

## 9. 通知

- **在场抑制先做。** 总控台窗口在前台且那张卡看得见时，不发系统通知，不出声，只在卡片上动。
  用户正在那个终端里时也不发。拆到第二块屏以后，「在前台」按每个窗口各自算，不按应用算。
- **分级。** 只有「等审批」「等回答」「出错」配打断；「一轮结束未看」「静止原因不明」只亮计数。
- **逐级加响，不是一律响。** 进入「等你」先只亮计数；过了 2 分钟没人理，出一声并发系统通知；
  之后不再重复，除非状态又变了。
- **同一个总管的事合成一条。** 它管三个群，只通知一次；它在等用户时，它下面 worker 的次级状态
  不另发。
- **先放着之后不通知**，直到它回来。

### 10.2 五个坑

| 坑 | 怎么防 |
|---|---|
| 靠刮屏幕文字判状态 | 屏幕这一路只输出「静止了多久」，不匹配任何文字。类别只由 hook 与进程信号决定。没有 hook 的 CLI 得到的是「静止，原因不明」，不是猜出来的「等输入」 |
| 拿不可靠的状态触发自动动作 | 总控台**自己不做任何自动动作**：不替人批准，不自动催，不自动重开。用户点的动作带 `since_ms` 守卫。重启后不重放状态变化，卡片从当前读数算起 |
| 自报通道断了，和「没事」长得一样 | 每路信号带来源与年龄；hook 约定要来却没来是「疑似卡住」而不是「闲着」；进程没了否决旧状态；采样失败单列。卡片上的「？」就是为这个 |
| 就地回复的三种错（乱序覆盖、把排队当等人、答错了对象） | 快照带 `rev`，宿主丢弃比手里旧的；动作带 `since_ms`，对不上就 `PromptGone`；回执分「字进去了」和「开始下一轮了」 |
| 总览自己乱动，或把等人的藏起来 | 行的身份与快捷键跟群走；重排只在用户没在操作时生效；首屏默认就是按状态排的，不需要用户去找这个视图；群聊页签不兼任「谁在等我」的入口 |

### 12.2 单独的调查项：终端状态协议

Claude Code 的文档里有一节：终端如果实现了 OSC 7501 程序状态协议，就能拿到每个会话是在干活、
在等用户还是做完了，agent 一侧不用配置。这对 Polter 是一路不依赖 hook 的信号，而且对手敲出来的
`claude` 也有效。但协议的规范文本、哪些终端已经实现，都没有找到；已知的限制是在 tmux 里和后台会话里
不报。**不作为本期依赖**；单独立一个调查任务，找到规范再评估。

### 12.3 风险

- **厂商自己在做多会话的界面。** Claude Code 已经有按状态分组的会话总览和项目面板，别的 CLI 也在做。
  Polter 的位置是它们做不了的那一块：跨厂商、跨 CLI，以及「一摊活」这个比会话大的单位——一个总管、
  一组 worker、一个任务面板、一段群聊。总控台如果做成「又一个会话列表」，会被厂商自己的东西替掉；
  做成「一摊活的队列」不会。第一维度是群，护的就是这一条。
- **两套原生界面的维护成本。** 这是用户定了的代价。控制它的办法只有一个：让界面真的只画。
  快照里是算好的字符串、算好的顺序、算好的计数；两边各自的代码里没有业务判断。§13.1 每一期的地板里
  都有一条专门守这个。上次那个原生窗口约 200 行 Swift；这次每个平台会是它的十倍以上。
- **非 Claude 的 CLI 质量差一档。** 只有 Claude Code 有 hook。别的 CLI 在总控台里只能得到「在动」
  「静止，原因不明」「进程没了」。这不是能在总控台里补的，要靠 0.10 的 H（其它 CLI 的 hooks）。
  总控台做出来以后，H 的价值比原来排的位置高。
- **只有按角色启动的才有 hook。** 手敲的 `claude` 没有。未归组一栏里它们会显示成「静止，原因不明」。
  这是诚实的，但用户会觉得「它明明在等我」。把状态协议那一路验通，是补这个洞最便宜的办法。
- **`ended` 的含义分不开**（§4.2 第 3 条）。把「一轮结束未看」算进「等你」，会让数字比真正需要处理的
  多；不算进去会漏。推荐算进去，并让用户能一键「已看」。
- **做了总览以后，用户会开更多。** 界面解决的是「找到谁在等我」与「快速应答」，解决不了审查只能
  一个一个来。总控台不应当暗示相反的东西：不做「同时在跑 N 个」的炫耀式数字。

### 13.2 性能判据

性能是验收的一部分（用户定）。下面的门槛是**建议值**，没有量过现有界面作参照；第一期的第一件事是
在两个平台上量一遍现有群聊页，把这张表定下来（§11 第 11 项）。读数取自被测的那个产物，报告里写明
是哪个提交、哪种构建。

| 读数 | 怎么量 | 建议门槛 |
|---|---|---|
| 什么都没变时的开销 | 窗口开着 60 秒，没有任何状态变化，数宿主为它醒了几次 | 0 次定时唤醒；CPU 低于 0.5% |
| 从事件到画面 | hook 事件到达核心的日志时刻，到卡片重画完成的时刻 | 95% 的情况低于 100 ms |
| 算快照 | 32 个群、128 个终端，算一次 | 发布构建下低于 1 ms |
| 按键到动作 | 按下批准，到核心收到动作 | 低于 50 ms |
| 开窗 | 从快捷键到第一帧画完整 | 低于 150 ms |
| 滚动 | 200 张卡的队列连续滚动 | 不掉帧（按显示器刷新率） |
| 内存 | 窗口开着比不开多出的常驻内存 | 低于 30 MB |

第一行是这张表里最要紧的：现在的群聊页每 500 ms 轮询一次，不管有没有事。原生窗口如果也这么做，
「纯原生是为了性能」这句话就不成立。地板：在宿主里加一个定时取快照的定时器，这一行的检查必须红。

## 15. 验收：汇报完成了什么、要你确认什么

**验收的单位是结果，不是内容。**（用户定，2026-10-11）用户的原话：

> 现在我基本都不看你改了什么了，只看结果。就是变成了结果导向，而不是内容导向。

> 我认为比较好的方式，还是汇报完成了什么 / 需要确认什么，涉及哪些任务，哪些文件，用户可以快速查看
> 任务内容，以及最新的文件（先不做 diff）。

所以这一节的主体很小：**一次汇报有四样东西——完成了什么、需要确认什么、涉及哪些任务、涉及哪些文件。**
任务一步点开、读得懂；文件一步看到最新的样子；要确认的那几条进「等你」，当场答复。
第一、二期只做这些（§15.1–§15.7）。

这一节的前两稿建立在别的前提上，被用户否掉了。作废的东西记在这里，免得以后被当成改进捡回来：

- **按人的审核速度限流**作为默认行为：作废。用户判断的是结果，不是按行读代码；按读代码的速度限制
  派活，限的是一个已经不存在的瓶颈。保留成默认关的选项（§15.12）。
- **读代码的占比**：整项删除。
- **每个任务一张的重表单**（交付单、结果单）：作废。汇报是总管或 worker 向用户说的一次话，
  一次可以带多个任务、多个文件。
- **差异（diff）的界面**：本期不做，也不在这里设计。以后要不要做、做成什么样，以后再说。

人不看内容以后，内容层面的把关只能落在机器和 AI 上：收据、判法、盲审复核、风险等级。这些设计
**保留在文中，但整体后移**（§15.8–§15.13，标「后期」），**第一、二期不依赖它们**——不让它们挡住
前面的东西先落地。

依据是调研记录（任务 #1307）。引用的数字都带来源，保留它标的证据类别与「复核 / 未复核」；
支持和反对这一转向的证据都留在文中（§15.14），不只留支持的。

### 15.1 两条主线，各走一遍

这一节以用户的两个真实用法为主线。后面每个小节都是在把这两遍走查里的某一步做出来。

**用法一：先看任务。** 用户的原话：

> 你告诉完成了什么什么功能，测试完成了哪些，涉及那几个任务。这种情况，我会优先看看任务，知道是
> 什么功能或者任务做好了。

走查（从看到汇报，到知道「是什么做好了」，**一步**）：

| 步 | 用户看到的 | 用户做的 |
|---|---|---|
| 0 | 总控台某个群的卡片上多了一行「新汇报」；右栏「汇报」页签最上面是它：谁说的、完成了什么、下面一排任务——每个是**号加标题**，不只是号 | — |
| 1 | — | 点其中一个任务 |
| 到位 | 旁边出一个浮层，从上到下四段：**这是什么**（任务说明）；**现在怎样**（状态、进度、谁做的）；**当初说好做成什么样**（判据）；**最近的汇报里关于它说了什么**。再往下折叠着的才是过程（派给过谁、什么时候改过进度） | 读；按 Esc 关掉，或上下键换到这次汇报的下一个任务 |

- 任务号是汇报的第一入口，所以它排在「完成了什么」的正下方，而且**一步点开**，不换页。
- 浮层先回答「这是什么功能、现在什么状态、谁做的、当初说好做成什么样」，其次才是过程。
- **它要让一个没看过程的人读懂。** 任务面板今天只有一行标题，这不够。所以要有任务说明，
  它放在哪、怎么不碰面板的红线，见 §15.5。

**用法二：快速看文件。** 用户的原话：

> 你告诉我有什么什么文件，在什么目录，我要看下，每次我都还要在 finder 里找目录，点开文件，
> 不能直接看，很麻烦，这种情况需要能快速看到文件。

走查（从看到一个路径，到看见文件内容，**一步**，三个地方都一样）：

| 路径出现在 | 用户做的 | 用户看到的 |
|---|---|---|
| 汇报的文件清单里 | 点它 | 就地出一个预览：文件现在的内容。顶上是完整路径和三个按钮：在访达（资源管理器）中显示、用默认程序打开、在文件窗格里打开 |
| 群聊消息里 | 点它 | 同上 |
| 终端屏幕上（agent 打印出来的） | 按住 ⌘（Windows 是 Ctrl）点它——和今天点链接是同一个手势 | 同上 |

- **凡是出现文件路径的地方，都能一步看到内容。** 不经过访达，不找目录。
- 路径是一个**目录**：预览里是这个目录的列表，点一项就预览那一项。
- 类型的最小集：文本 / Markdown / 代码、图片、PDF。其余类型，预览里只有文件信息和「在访达中显示」。
- 空格再按一次或 Esc 关掉；预览不抢走终端的输入位置。
- **第三行不依赖总控台**，可以很早单独交付（§15.6）。

### 15.2 现在的状态机，和能挂的位置

读代码的结果（行号取自 `156fa1785`）：

- **任务只有三个状态**：开着、关了、取消了，代码注释写明「不会有第四个」
  （`src/poltergeist/Tasks.zig:57-70`）。进度是另一维，四个值：排着、在做、卡住、做完
  （`src/poltergeist/Tasks.zig:80-94`）。「做完」是 worker 认为完成，「关」是总管核过之后的话。
  所以**「做完待验收」已经存在，就是「开着 + 做完」**，不需要新状态。
- **`task_progress` 只有任务号和进度两个参数**（`src/poltergeist/rpc.zig:573`、`:7531-7535`）。
  只有任务的负责人能动，任务关了以后不能动（`src/poltergeist/Tasks.zig:358-368`）。
- **`task_close` 什么都不查**：不查进度是不是「做完」，连任务是不是还开着都不查——对一个已取消的
  任务调用它，会把它改成「关了」（`src/poltergeist/Tasks.zig:336-339`，
  `src/poltergeist/rpc.zig:7461-7464`）。它要求调用者是总管，但不查是不是这个群的总管（§5.3）。
- **`task_assign` 的顺序是「先告诉 worker，再写下来」**（`src/poltergeist/rpc.zig:7343`），并且有
  一个现成的拒绝先例 `NoAgentThere`（`src/poltergeist/rpc.zig:7383-7390`）。任何新的拒绝都要放在
  告诉 worker 之前。
- **用户自己关不了任务。** 用户身份只被豁免了销毁群这一项（`src/poltergeist/rpc.zig:1066-1072`）。
  结果导向以后，「通过」这句话有一部分只能由用户说，而这条路今天不存在。
- **核心不认识 git。** 监管这一层没有任何取提交号、认工作树的代码。

与设计有关的三处事实：

1. **任务说明、判据、汇报都不能做成任务面板上的字段。** 面板有一条写成闸的红线：它存的是「谁在做哪件事、
   做完没有」，明确不存「需求描述、验收细节、附件、评论」（`dev-docs/poltergeist/tasks.md:54-66`）。
   所以它们是**另一种记录**，按任务号挂上去；面板一个字段都不加，三个状态也不变。
2. **「做完」经常不报。** 代码注释里记着：71 个任务只产生了 15 次「做完」的报告
   （`src/poltergeist/rpc.zig:7395-7396`）。只靠 worker 报会漏，§15.7 留了一个机器信号作提示。
3. **证据不能由 agent 自己经手。** 核心不认识 git；工作树的指纹让 agent 报，就又成了自述。
   截图、读数同理。§15.8 让工具来采。

### 15.3 汇报：四样东西

| | 是什么 | 形状 |
|---|---|---|
| 完成了什么 | 一段话，说做成了什么结果 | 文字；可以附截图、读数、一个可以点开试的入口（一条命令、一个地址）。附的东西不是必填 |
| 需要确认什么 | 要用户表态的条目，每条是**一个明确的问题**或**一个待验收的结果** | 若干条，每条一句；可以带选项；可以指向一个任务 |
| 涉及哪些任务 | 任务号的列表 | 一步点开，读得懂（§15.5） |
| 涉及哪些文件 | 路径的列表，每个可带一句说明 | 一步看到最新内容（§15.6） |

几条定性的话：

- **它是一次汇报，不是一张表。** 谁汇报：总管，或者 worker。向谁：用户。一次汇报可以带多个任务、
  多个文件，也可以一个都不带（只说一件事、问一个问题）。
- **只有「需要确认什么」会进「等你」**（§15.7）。其余三样是给用户看的，不要求他做任何事。
  一次没有要确认的汇报，只在汇报列表里多一行，不亮任何数字。
- **文件由汇报的人列出。** 现在 Polter 看不到 agent 写了哪些文件（§8.1）。等写文件的 hook 有了，
  再做对账——列了却没动过的、动过却没列的——那是后期，第一、二期没有。
- **没有 diff。** 文件点开是它现在的样子。

为什么是这个形状：这是用户实际的做法。别家产品也在往「交结果」走——有的让 agent 交「可以合并的
改动加上视频、截图、日志」【宣传，Cursor 2026-02-24，已核】；有的让 agent 复现缺陷、录一段坏的、
修好、再录一段好的，人「可以审但不必审」【宣传，OpenAI 2026-02-11，核的是存档副本】。
反对的证据在 §15.14；其中有两条直接约束这个形状，所以先写在这里：

- **汇报是自述，自述会错。** 单人数据里 516 个「完成」声明有 37% 是「测试过了之后又改了代码」
  【测量·单人，Lencevicius 2026-09，未复核】。第一、二期对此没有任何机器层面的对策（那是后期的
  收据），所以界面上不把「完成了什么」画成已经核实过的东西：它就是「××× 说」。
- **「没验什么」值得有一句。** 调研的判断是，这类汇报成立的条件之一是说出没验的部分。它不在用户
  说的四样里，所以不加第五栏；做法是工具有一个可选的字段，写了就显示在「完成了什么」下面一行。
  要不要改成必填，见 §11。

附的东西有两条现实的限制：

- **Polter 现在没有录屏**，只有截图工具，以及 0.10 截图第三轮里计划的前后对比、测量与步骤记录
  （[v0.10.md](v0.10.md) 的 F2、F4d）。所以先支持截图、读数和入口。
- **截图抓的是屏幕上看得见的像素。** 被遮住的窗格、后台的 tab 抓不到；要截界面，被测的东西得在
  前台，这会打扰正在用机器的人——本仓已经为此被叫停过一次。所以截图是「可以附」，不是「应当附」。

### 15.4 汇报的工具：`report_post`

一个新的 MCP 工具。

| 参数 | 含义 | 约束 |
|---|---|---|
| `group` | 汇报属于哪个群 | 调用者必须是这个群的成员 |
| `done` | 完成了什么 | 必填，一段文字，上限 2000 字节 |
| `confirm[]` | 需要确认什么，每条 `{ text, kind: question \| accept, task?, options? }` | 最多 10 条，每条 300 字节；`accept` 是「这个结果请你验收」，`question` 是「这件事请你定」；`options` 最多 4 个，给了就在界面上画成按钮 |
| `tasks[]` | 涉及哪些任务，任务号 | 最多 20 个 |
| `files[]` | 涉及哪些文件，每个 `{ path, note? }` | 最多 50 个 |
| `attach[]` | 可选：截图的编号、读数、可以点开试的入口 | 不必填 |
| `unverified` | 可选：没验什么 | 一段文字 |

**谁能调**：群里的任何终端——总管，或 worker。汇报上记着是谁说的、当时它是什么身份。总管的汇报
排在群的汇报列表里；worker 的汇报也在，标明是 worker 说的。worker 的 `confirm` 默认先到总管那里
（进总管那张卡的「一轮结束未看」），总管转给用户才进用户的「等你」——否则四个 worker 各问一句，
用户又被淹了。要不要让 worker 的确认直接到用户，见 §11。

**怎么关联任务号**：`tasks[]` 与 `confirm[].task` 里的每个号都要是**这个群的**任务。

- 号不存在：整次汇报拒绝 `NoSuchTask`，消息里点名是哪个号。
- 是别的群的任务：拒绝 `TaskNotInGroup`。
- 不要求任务是「做完」的：汇报可以说到一半的进展。
- 汇报不改任务的任何状态。任务面板一个字段都不加（§15.2 第 1 条）；「哪些汇报提到了这个任务」
  是从汇报的记录反查出来的。

**怎么关联文件路径**：相对路径相对群的工作目录（`cwd`，§4.1）解析；绝对路径原样。解析时把符号链接
解开再判断。然后分三种情况，**都不拒绝整次汇报**，而是逐个文件标记，并在返回值里告诉调用者哪些
被标了：

| 情况 | 怎么办 | 为什么 |
|---|---|---|
| 文件在群的工作目录之下，而且存在 | 正常，可以一键点开 | — |
| **路径不存在** | 汇报照收；这一项标「汇报时不存在」，界面上是灰的、点不开；以后文件出现了，标记自动去掉 | 为一个打错的路径拒掉整次汇报，丢的是汇报；而「说改了一个不存在的文件」本身就是用户该看到的信息 |
| **在群的工作目录之外** | 汇报照收；这一项标「在工作目录之外」，界面上只显示成文字路径，**不能一键点开**——要点开得先在一个确认框里看清完整路径 | 汇报的文字来自 agent，agent 的输入可能被注入过。一键打开任意路径，等于让一句话决定用户去看哪个文件 |
| 群没有登记工作目录 | 相对路径标「无法解析」；绝对路径按「在工作目录之外」处理；返回值里提示用 `group_set_cwd` 登记 | 没有可比的目录，就没有「之内」 |

**其它拒绝码**：`NotAMember`、`TooLong`、`TooMany`、`EmptyReport`（`done` 是空的）、
`RateLimited`（每个终端每分钟一次——汇报是攒一批再说的东西，不是进度条）。

**存在哪**：汇报是群的记录的一部分，按群存、跨重启保留，带序号。它和群聊消息分开存：消息是流水，
汇报是用户要回头翻的东西。同时在群聊里留一行「××× 汇报了：<第一句>」，免得群聊页上看不出发生过汇报。

**用户确认以后，agent 怎么知道**：用户的答复打进汇报人的终端（和 `terminal_send` 同一条路、同一套
守卫），格式固定，带上汇报的序号和是第几条；同时记进汇报的记录。汇报人的终端已经不在了，
答复只记录、不投递，并显示在这个群的卡片上，下一任总管接手时能读到（§6.2）。

**它取代了 §5.1 里原来的 `deliverable_mark`**：「这个文件是要给你看的」现在就是汇报里列一个文件。

### 15.5 任务：点开就读得懂

用法一要求任务点开以后，一个没看过程的人读得懂。面板今天存的是一行标题、负责的终端、状态、进度、
分类，别的都不存，而且这是一条写成闸的红线：面板存的是「谁在做哪件事、做完没有」，明确不存
「需求描述、验收细节」；一行标题放不下的东西，属于别的载体（`dev-docs/poltergeist/tasks.md:54-66`）。

**所以任务说明不进面板，放在「别的载体」里**——和汇报同一处：群的记录里，按任务号存一份。

- 新工具 `task_describe(task, what, criteria[])`。`what`：这件事是什么，给一个没看过程的人写的
  一段话（上限 1000 字节）。`criteria`：做成什么样算完，若干条，每条一句（默认最多 5 条）。
- 谁能调：群的总管。拒绝码 `NotYours`、`NoSuchTask`、`TooLong`、`TooMany`。
- 可以改；改过的时间显示在浮层上，旧的版本留在记录里。
- 面板的字段一个都不加；三个状态也不变（§15.2）。浮层把两处的东西拼在一起显示：面板给「谁在做、
  做完没有」，说明记录给「这是什么、做成什么样算完」。实现时要回去在任务面板那一章写明这一点
  ——这次没有动那份文档。

**怎么保证点开的时候它在：**

- 派活的提示里写明：派一个活，先 `task_create`，再 `task_describe`。
- `report_post` 的返回值里点名「这次汇报提到的任务里，哪几个没有说明」——汇报的那一刻是它最要紧
  的时候，也是汇报的人最可能顺手补上的时候。
- 没有说明的任务，浮层第一段写「没有登记说明」，下面直接是提到它的汇报里「完成了什么」那一段。
  不留一个空的浮层。
- 是否改成「没有说明就不能派」，见 §11。推荐不强制：强制会得到一堆把标题抄一遍的说明。

**浮层的内容与顺序**（用法一的「到位」那一格）：

1. 这是什么：`what`。
2. 现在怎样：状态、进度、负责人（名字，不是编号）、多久没动。
3. 当初说好做成什么样：`criteria`，逐条。
4. 最近的汇报里关于它说了什么：最近两次，各一段。
5. 过程（折叠）：任务的流水——建、派、改进度、关。这个数据已经有（任务的历史记录）。

判据要写**看得见的结果**，不是做了什么：「设置窗口里改字号后，标签栏跟着变」是判据；「重构了字号的
读取」不是。第一、二期这一条靠总管的提示词，核心不强制；**判据在这两期只是给人看的文字**，
没有任何东西去跑它、判它、拦它。

**后期（第一、二期不依赖）：给判据加上判法。** 以下是保留的设计。

- **每条判据必须带一个判法**，二选一：
  - **机器判**：一条命令，它的退出码就是答案。交付时由工具去跑，不占人。
  - **人判**：写明要人看什么——一张截图、一段步骤、一个可以点开试的东西、一组前后读数。
  没有判法的判据登记不上去（`CriterionUncheckable`）。核心判断不了一句话是不是「看得见的结果」，
  它能强制的只有这一条：每条判据都说得出怎么判。
- **能机器判的就不留给人。** 这是「不占人」的全部来源。
- **判据同时是复核方盲审用的需求**，只登记一次。
- 冷启动时用户写的那一句话（§6.1）是第一条判据的初稿，由总管改写成可判的形式；总管改完，用户在
  卡片上看得到改成了什么。

两条约束，都来自反面的证据：

- **判法定下以后，做的人改不了。** 机器判的那条命令和它依赖的检查文件，在派活时记下指纹；交付时
  指纹变了，这条判据显示成「判法被改过」，不算通过。理由：测试与需求冲突时，模型有 76% 的情况仍然
  让测试通过【测量·预印本，ImpossibleBench，arXiv 2510.20270，未复核】；主张「审判据不审代码」的人
  自己也承认，同一个 agent 既写代码又写测试只是把问题挪了个地方，判据必须来自需求而不是实现
  【宣传，Jain 2026-03-02，已核】。有用的变量是「判法先于实现、只凭需求写」和「实现方改不了它」
  【测量·评审，ESEM 2026，未复核】。
- **判据要短。** 每个任务不超过若干条（默认 5），每条一句。调研里有一条针对「先审规格」的反对意见：
  没有证据表明它减轻了审核，亲历者的原话是宁愿审代码也不想审那一堆说明文档【经验，Böckeler
  2025-10-15，复核】。判据如果长成文档，就把那个问题原样造了回来。

没有登记判据的任务照常能派。它的证据页上写「派活时没有登记判据」，复核方拿到的
是标题。是否改成不登记就不能派，见 §11。

---

**以下 §15.8–§15.13 是后期的设计，第一、二期不依赖它们。** 留在文中是因为人不看内容以后，内容层面
的把关只能落在这里；后移是因为不能让它们挡住上面四样先落地。这几节里说的「差异」是机器与复核方
读的输入，不是给用户看的界面。

### 15.6 文件：凡是路径，都能一步看到

**现在是什么样**（行号取自 `156fa1785`）：

- 终端里的路径**已经能认出来**。默认的链接规则同时匹配网址和文件路径：以 `/`、`./`、`../`、`~/`
  开头的，以及 `src/config/url.zig` 这种不带前缀的相对路径（`src/config/url.zig:4-5,77-114`）。
- 按住 ⌘（mac）或 Ctrl（其它平台）悬停会高亮，点一下就打开（`src/config/Config.zig:1968-1974`、
  `:4698`）。
- 点了以后：核心取出那段文字；是相对路径就用这个终端的当前目录补成绝对路径，并且**只在文件存在
  时才补**（`src/Surface.zig:2538-2559`）；然后把它作为「打开网址」这个动作交给宿主
  （`src/Surface.zig:5903-5941`）。
- mac 宿主：没有协议头的当成文件路径，展开 `~`，交给系统用默认程序打开
  （`macos/Sources/Ghostty/Ghostty.App.swift:908-950`）。Windows 宿主：先过一道「能不能打开」的规则，
  再交给系统的外壳去打开（`windows/host/src/links.rs:64-102`）。
- 链接规则**现在不能配置**：配置项在，注释写着「目前设不了」（`src/config/Config.zig:1965-1966`）。
- 两个宿主里都没有任何预览的代码。

所以用户说的麻烦有一半不是「认不出路径」，而是**认出来以后做的是「用默认程序打开」**：一个 Markdown
文件弹出一个编辑器，一个目录弹出访达，一个相对路径在没有当前目录信息时什么都不发生。

**要做的：把「点路径」的结果从「用默认程序打开」改成「就地预览」。** 识别、高亮、手势、相对路径的
解析都是现成的，改的只是宿主收到这个动作以后做什么：

- 宿主收到的是一个本地路径（不是网址），而且文件或目录存在 → 出预览。
- 是网址 → 和今天一样。
- 路径不存在，或相对路径解析不出来 → 出一个很小的提示，写明它找的完整路径是什么。**不许什么都不
  发生**——今天就是这样，用户分不清是没点中还是文件不在。
- 原来的行为留一个入口：预览顶上的「用默认程序打开」；另有一个配置项把默认改回去（§11）。
- 终端程序自己声明的链接（OSC 8）指向本地文件的，今天走的是另一条更严的路
  （`macos/Sources/Ghostty/Ghostty.App.swift:913-918`）。它不变，不进预览：那个路径是屏幕上的程序
  给的，不是用户看着点的那段文字。

**预览用什么画：**

| | 文本 / Markdown / 代码 | 图片 | PDF | 目录 | 其它 |
|---|---|---|---|---|---|
| mac | 系统的快速预览（Quick Look） | 同左 | 同左 | 自己画一个列表 | 文件信息 + 在访达中显示 |
| Windows | 自己画：只读、等宽的文本视图 | 系统的图像解码 | 先不做，给「用默认程序打开」 | 自己画一个列表 | 文件信息 + 在资源管理器中显示 |

- **mac 上用快速预览是可行的**（未验证，按系统能力判断，仓里没有先例）：系统提供一个可以嵌进自己
  窗口的预览视图，文本、代码、图片、PDF 都是它自带支持的类型。把它放进一个自己的小面板里，顶上加
  路径和三个按钮；目录的列表是自己画的，因为快速预览对文件夹只显示信息，不显示内容。要验的两点：
  它在一个不抢焦点的面板里能不能正常工作；Markdown 是渲染出来还是按纯文本显示（按纯文本也可以接受）。
- **Windows 没有对应的系统功能。** 资源管理器的预览窗格背后有一套预览处理器，可以宿主进自己的窗口，
  但那是一套组件接口，各类型由谁提供、装没装都不一定（未验证）。所以 Windows 的最小集自己画：
  文本用一个只读的等宽视图（宿主现在全是系统控件加 GDI，这在它的能力之内），图片用系统的解码器；
  PDF 第一版不做预览，直接给「用默认程序打开」，并在预览里说明，不显示成空白。
- **大文件**：文本只读开头的一段（默认 256 KB），顶上写「只显示了开头」。
- **两个平台不一样没有关系。** 预览是轻的：它回答「这个文件长什么样」，够用就行。

**它和文件窗格 E 的关系：预览是轻的，E 是完整的。**

- 预览：一个文件，一眼，关掉。不需要 E 存在。mac 上是系统的画法，Windows 上是最朴素的画法。
- E（v0.10.md §5，TUI，用户定）：目录树、在目录之间切换、语法高亮、git 状态、把路径发给旁边的终端。
- 预览顶上的「在文件窗格里打开」是从轻到重的那一步：E 做出来之前这个按钮不出现。
- 目录的预览（一个列表）和 E 的目录树是同一个需求的轻重两版；E 做出来以后，目录的预览里加一个
  「在文件窗格里打开这个目录」。
- **不做 diff**，预览和 E 的本期范围里都没有。

**三个地方用同一个预览：**

- **终端屏幕上的路径**：上面说的改法。
- **汇报的文件清单**：点一项就是这个预览。路径在群的工作目录之外的，按 §15.4 的规则，不能一键出来。
- **群聊消息里的路径**：消息正文用同一条规则找路径，相对路径相对群的工作目录解析；找到的画成可点的。
  群聊页签在原生重画之前嵌的是终端里的那个界面（§11 第 3 项），那时它就是「终端屏幕上的路径」，
  不用另做。

**它可以很早单独交付。** 「终端里点路径 → 就地预览」不依赖总控台的任何东西：不需要群、汇报、快照。
它改的是两个宿主各自处理一个已有动作的那一段，加一个小面板。所以把它排在**第一期的最前面**，
作为一个单独的小功能先出（任务 R0p）；汇报的文件清单随后直接用它。它也是这一节里用户最快能用上的
一样东西。

未验证的，开工前要验：

| 项 | 怎么验 | 验不通怎么办 |
|---|---|---|
| 中文路径、带空格的路径认不认得出 | 在终端里打印 10 种路径（中文目录、带空格、带括号、`~/`、相对、末尾带标点），逐个 ⌘ 点 | 认不出的记下来；这次不改识别规则，只改点了之后做什么。认不出的那几种在汇报清单和群聊里仍然能点 |
| `文件:行号` 这种写法会不会把行号一起当成路径 | 打印 `src/a.zig:12`、`src/a.zig:12:5`，看点了之后交给宿主的是什么 | 宿主收到后把末尾的 `:数字` 去掉再找文件；去掉的行号用来让预览滚到那一行 |
| agent 的全屏界面里路径点不点得中 | 在 Claude Code 的界面里让它打印一个路径，⌘ 点 | 点不中的话，这条用法在 agent 的终端里要靠汇报清单来满足，并如实写进说明 |

| 预览出来得够不够快 | 量从点下到内容出现 | 超过 150 ms 就先出面板和路径，内容后到 |

### 15.7 界面：汇报列表与就地确认

**汇报列表。** 群的详情里多一个「汇报」页签，排在「终端」之后、「群聊」之前——它是用户打开一个群
最先想看的东西。按时间倒序，一条汇报一块，从上到下：

1. 谁说的、什么时候。
2. **完成了什么**（附的截图是缩略图；写了「没验什么」就在下面一行）。
3. **涉及的任务**：一排，每个是号加标题，点开是 §15.5 的浮层。它紧跟在「完成了什么」下面——
   用法一里这是用户接着要点的东西。
4. **涉及的文件**：一排路径，点开是 §15.6 的预览。标了「不存在」的是灰的；标了「在工作目录之外」
   的只是文字。
5. **需要确认什么**：逐条，带动作。

还有没答复的确认条目的汇报，顶上有一个标记。

**就地确认：「需要确认什么」进「等你」。**

- 有未答复确认条目的群，卡片进「等你」，类别是「要你确认」，排在「等回答」之后、「出错」之前
  （§4.3 已加）。卡片上直接写第一条的原话，后面跟「还有 2 条」。
- 每一条**就地**处理，三种动作：
  - **答复**：有选项就是按钮，没有就是一行输入。用于提问。
  - **通过**：用于待验收的结果。
  - **打回**：带一句话。用于待验收的结果。
- 条目指向了一个任务的，旁边就是那个任务（可点，同一个浮层）；汇报里列了文件的，旁边有「看文件」。
  判断一条确认所需要的东西，都在这一条的手边。
- 处理完一条，它从卡片上消失；一个群的条目都处理完，卡片离开「要你确认」。
- 「通过」对任务的含义，第一、二期是最轻的那种：记下用户通过了，告诉汇报人；**关任务仍然是总管的
  事**。用户直接关任务的路现在没有（§15.2），后期再加。
- 可以「先放着」（§4.5），和别的卡一样。
- **只显示，不拦人。** 等你确认的攒了多少，都不影响派活（§15.12）。
- **会旧。** 一条等了很久的确认，它说的那个结果可能已经被后面的改动盖掉了。条目上显示等了多久；
  涉及的文件在汇报之后改过的，条目上有一个小标记（比较修改时间）。没有限流以后，这是积压最直接的
  后果，第一、二期对它只有显示，没有对策。

「像是做完了，没有报」保留，作为一个只在总管卡片上出现的提示：某个任务标着「在做」，但负责它的
agent 已经一轮结束并静止超过阈值。依据是 §15.2 第 2 条那个读数。它是推出来的，可能错，
所以写成这句话，不写成「做完」，也不进用户的「等你」。

---

**以下 §15.8–§15.13 是后期的设计，第一、二期不依赖它们。** 留在文中是因为人不看内容以后，内容层面
的把关只能落在这里；后移是因为不能让它们挡住前面的东西先落地。这几节里说的「差异」是机器与复核方
读的输入，不是给用户看的界面；「任务的证据页」是后期在 §15.5 那个浮层里加的一段。

### 15.8 机器采的证据：收据与采集

人不看内容，所以任务的证据页上的每一样东西，要么是机器采的，要么明说不是。

**收据**：跑了什么命令、退出码、输出的最后若干行（全文另存，记它的摘要）、在哪个目录、什么时候、
**当时那棵工作树的指纹**。

- 由一个包住命令的小工具产生：`polter +receipt -- <命令>`。工具自己跑、自己取输出、自己算指纹，
  用这个终端自己的身份交给核心。agent 能决定的只有跑哪条命令。
- **指纹要认得出没提交的改动**：当前提交、相对它的全部差异、未被忽略的新文件，合起来算一个摘要。
  只取提交号不够。
- **树一改，收据作废**，显示成「已过期：验过之后树变了」，不算数。单人数据里 516 个「完成」声明
  有 37% 是「测试过了之后又改了代码」【测量·单人，Lencevicius 2026-09，未复核】。
- 机器判的判据（§15.5）就是这样跑的：工具跑那条命令，产生一张收据，判据的结论取它的退出码。
- 不是 git 仓库的目录算不出指纹：照样记，但标「没有绑定到树」，和绑定了的分开显示。

**采集**：「结果」一栏里的截图与读数，由 Polter 自己的工具采，并和收据一样绑到工作树的指纹。
agent 自己递上来的图片可以放进任务的证据页，但标「agent 提供，不是机器采的」。理由不是不信任，而是它
确实出过事：有用户报告 agent 附上的「录屏」是它自己拼出来的文件【未核，论坛帖】——演示本身可以是假的。

收据**不是**什么：它证明「这条命令在这棵树上跑出了这个结果」，不证明这条命令验得对。agent 可以跑
一条什么都不验的命令。收据把它如实记下来，让复核方看得见——它是证据，不是证明。

多个 worker 共用一棵树时，别人一改，所有人的收据都过期。这是如实的。它也说明收据要好用，
worker 得各有各的工作树——依赖 0.10 的 D。

### 15.9 AI 复核：否决优先、盲审、只报不改

人不读内容以后，这是唯一还在读内容的一方，所以分量很重：**必审的范围由风险等级定（§15.10），
不是可选的一步。**

**规则：否决优先。任何一方反对就不能关；全都通过的，按比例抽出来再加一道独立复核。**

「意见有分歧才升级」作废，理由留在这里：

- 它隐含着「一致就放行」。而 AI 当裁判偏向放行：14 个模型当裁判，认出有效输出 96%，认出无效输出
  不到 25%，作者明说少数否决比多数表决好【测量·预印本，arXiv 2510.11822，复核】。
- 换一家厂商买不到完整的独立性：跨模型的组合只拿到「真独立」时可靠性增益的 0.43，同模型低于 0.3
  【测量·预印本，arXiv 2607.02808，复核】；两个模型都错时约六成错成同一个答案【测量·评审，
  ICML 2025；多选题，不是代码；未复核】。
- **两家一致放行时，代码实际有错的概率，没有人测过。** 人不读内容以后，这个没人测过的数就是整套
  做法的底。一致通过只能换来「少加几道」，换不来「不用查」。

**反对了以后怎么办**——人不读代码，所以反对不能以「请你看这段」的形式到人面前：

1. 反对必须带发现；能复现的要带一张收据（一条跑出失败的命令）。
2. 先退回给做的人改，最多两轮。
3. 两轮之后仍有反对，才到用户面前，而且是以**结果层面的一个问题**出现：「复核方说 ××× 会坏，
   证据是这条命令的输出；做的人说 ×××。」用户判断的是这件事要不要紧，不是这段代码对不对。
4. 没有可复现证据的反对（比如「这样写以后不好改」）不拦关任务，记进这个群的欠账（§15.11）。

复核方的三条约束不变：

1. **盲审。** 只给判据和差异，不给汇报里的文字、不给对话。迭代润色过的描述让两条
   AI 审查流水线在 33 个漏洞里漏掉 32 个【测量·预印本，arXiv 2603.18740，未复核】。由工具保证：
   复核方拿到的那一包由核心拼。
2. **只报不改。** **现在没有现成的开关**：角色定义里的工具限制管的是 Polter 自己的工具
   （`src/poltergeist/persona.zig:79-90`），不是 CLI 自带的写文件工具。Claude Code 的适配器已经在往
   启动参数里加禁用项（`plugins/claude-code/adapter.py:581`），给角色加一个「只读」选项走得通
   （未验证：禁用后经 shell 还写不写得了）；别家 CLI 没有适配器，做不到。兜底是让复核方在只读的
   副本里干活。有一个方向上的测量：弱的审强的并动手改，通过率反而下降——71.6% → 89.7% 对
   91.4% → 82.8%【测量·预印本，arXiv 2607.21656，未复核】。
3. **不能审自己。**

**换厂商复核是可选的角色。** 它的价值是找到不同的错，不是更可靠地放行：跨模型与同模型新会话的
总体成绩没有显著差别，但找到的错只重合约四成；「同模型一遍加跨模型一遍」命中 56.7%，「同模型两遍」
42.7%【测量·预印本，单作者，arXiv 2610.01471；设计已复核，两个百分比未复核】。抽中要再加一道时，
有换厂商的角色就优先用它。

### 15.10 风险等级：决定机器要验多严

风险等级不再决定「人要读多少」。它决定的是**关这个任务之前必须有哪些证据**：

| 档 | 关之前必须有 | 谁说「通过」 |
|---|---|---|
| 低 | 机器判的判据全过，收据都有效 | 总管 |
| 中 | 上面的，加仓库的闸全过，加一道盲审且无人反对 | 总管；含人判的判据时是用户 |
| 高 | 上面的，加第二道独立复核（有换厂商的角色就用它），加 §15.11 那几类专门的闸 | 用户，看的是任务的证据页 |

等级由规则算，输入全是机器看得见的：

- **动了哪些路径**：从差异里取。哪些算高风险是一张配置里的表，agent 改不了（改这张表本身是高风险）。
- **改了多少**：行数、文件数。
- **是不是不可逆、是不是对外**：推送、发布、删除、改权限、往外发东西。**这一条现在判不了**——
  工具调用没有经过 Polter（§8.1）。在那个 hook 接上之前只按路径和大小判，任务的证据页上写明
  「没有检查对外动作」。
- **任务的种类**：面板已有的分类。

agent 不能给自己定级，任务的证据页里也没有这一栏。抽出来再加一道复核的比例**变严快、变松慢**：一次被
加的那一道查出问题，这个 worker、这类任务立刻回到每次都加；连续若干次没问题才降一档。
**数字没有任何测量依据**，是可配的默认值（§11）。

### 15.11 从结果上看不出来的，必须靠闸

只看结果，有几类问题人永远看不到——结果是对的，它们也在：

| 看不出来的 | 靠什么 | 现状 |
|---|---|---|
| 泄密（密钥、本机路径、真实邮箱进了提交） | 泄密闸 | 本仓已有；只扫已跟踪的文件，看不见提交的作者字段 |
| 安全（注入、越权、把守卫删了） | 盲审时专门的一项；高风险路径上的第二道复核 | 没有专门的闸 |
| 弄坏了别处 | 不止跑这个任务的判据：仓库的闸全跑，改动涉及目标的构建都过 | 本仓的规矩已有；带过滤的测试不编译没被选中的部分，所以要另有构建来证 |
| 把检查弄没了（删了断言、把守卫改成恒真） | 每道闸先看它红过；判法的指纹（§15.5） | 本仓的规矩已有 |
| 可维护性（重复、死代码、越写越绕） | **没有好的闸** | 见下 |

**可维护性是这张表里最弱的一格，要明说。** 它从结果上看不出来，机器也判不好。能做的只有三件：
复核方把这类发现记进群的欠账而不是拦人（§15.9 第 4 条）；欠账在总控台上看得见（一个数，点开是
列表）；隔一段时间派一个专门清欠账的任务。走在这条路最前面的团队自己写过：他们曾经每周五花
两成时间清理 AI 产生的烂摊子，「不出所料，这撑不住」，后来改成把原则写进仓库加定期清理
【宣传，OpenAI 2026-02-11，核的是存档副本】。

**代价也要明说：只看结果，人对内部的了解会变少。** 调研里的反面意见是，读代码的摩擦原本在同步
人脑子里的模型，拿掉以后「塔不会倒，只是继续长高」【经验，Ronacher 2026-07】。本文不把「去读代码」
当建议——用户已经定了不读。对策做在机器这一层：上面这张表，加上让「系统由哪几块组成、这摊活动了
哪几块」这类结构信息由机器维护并摆在任务的证据页上。一位基本不读代码的实践者给自己这种做法定的条件
正是这一条：他知道组件在哪、系统怎么搭的【经验，Steinberger 2025-12-28，已核】。这个条件在
Polter 里现在没有任何东西帮着维持，是一个开着的口（§15.15）。

### 15.12 可选：按待验收的量限流（默认关）

这一节的第一稿把它当默认行为，用户否掉了：用户判断的是结果，几秒到几分钟一份，不是按行读代码；
按读代码的速度去限制派活，限的是一个已经不存在的瓶颈。所以**默认关，不因为人没看就拒绝派活。**

保留成用户可以自己打开的选项，因为支持它的意见并没有消失，只是对这位用户的工作方式不适用：
高采用团队合并的改动 +98%、审查时间 +91%、单个改动 +154%，公司层面没有显著改善【测量·厂商，
Faros 2025-07，复核】；「输入增长快过吞吐就是累积性故障……要限制输入」【经验，Ronacher
2026-02-13，复核】；「按你真正能审的量，给自己设每天让它生成多少代码的上限」【经验，Zechner
2026-03-25，复核】。结果导向下它仍可能有用的场合是 §15.7 那句「结果会旧」：等你确认的东西攒得太多，
用户想让它停一停。

打开以后的行为：

- 某个群「等你确认」的数量超过上限时，`task_assign` 拒绝 `ReviewBacklogFull`，消息里写现在几个、
  上限几个、最久的是哪个。拒绝放在告诉 worker 之前（§15.2）。
- 总管可以带一个明说的参数越过，越过的事记下来。
- 数的是「到了人面前还没判的」，不是所有「做完未关」的——机器还在查的不算人的积压。
- 另有一个所有群合计的上限。
- 上限的值是可配的默认，**没有测量依据**：调研没有找到一个人能同时监管多少个 agent 的任何测量。

### 15.13 后期的工具

| 工具 | 参数 | 谁能调 | 拒绝码 |
|---|---|---|---|
| `task_describe`（加判法） | `criteria[]` 的每条多一个 `check: { machine: 命令 } \| { human: 要看什么 }` | 群的总管 | 新增 `CriterionUncheckable`、`Frozen`（任务已经有人在做，改判法要明说） |
| `polter +receipt --task <号> -- <命令>` | 命令行工具；收据挂到任务上 | 任何在群里的终端 | 不在群里时照常跑命令，但说明没有记下收据 |
| `review_packet` | `task` | 被指定的复核方 | `SelfReview`、`NotReviewer`；返回判据与差异，不含 worker 写的任何一段 |
| `review_verdict` | `task`、`verdict: pass \| object`、`findings[]`（可带收据） | 被指定的复核方 | `SelfReview`、`NotReviewer`、`ObjectNeedsFinding` |
| `task_return` | `task`、`reason` | 群的总管，或用户 | `NotYours`、`NotOpen`；把进度退回「在做」并告诉 worker |

改动的：

- **`task_close`**：新拒绝码 `NotOpen`（修掉「能关一个已取消的任务」）、`ReceiptStale`、
  `CriteriaUnmet`（机器判的判据没过，或判法被改过）、`EvidenceMissing`（这一档风险要求的证据不齐，
  消息里列出缺哪样）、`ObjectionOpen`、`NeedsUser`（含人判的判据，或高风险）。
- **`task_assign`**：只在 §15.12 的选项打开时才有 `ReviewBacklogFull` 与 `over_backlog`。
- 用户（总控台）可以关任务、把任务退回。

面板的字段一个都不加（§15.2 第 1 条）。实现时要回去改任务面板那一章，写明任务说明、判据、汇报与证据
都是「别的载体」，不是红线的破口——这次没有动那份文档。

### 15.14 边界：支持与反对这一转向的证据

**支持的**

- 产品都在往「交结果」走：视频、截图、日志、可接管的环境（§15.3 引的两家，都是厂商自述）。
- 人读代码本来就不是抓功能错误的可靠手段：一家大公司 570 条审查评论里，缺陷类只占 14%
  【测量·评审，Bacchelli & Bird 2013，未复核】。
- 人加 AI 的组合平均比两者中较好的那个差，给解释、给置信度都不显著（106 项实验的元分析）
  【测量·评审，Vaccaro 2024，复核】。让人去复核 AI 的内容，未必比让机器把关再让人看结果更好。
- 「人必须审每一份」既给不了像样的保证，也跟不上产出【立场论文，不是测量，Monperrus 2026-06，
  只核了摘要】。

**反对的**——这些没有被这一节解决，只是被摆在明处：

- **测试通过不等于可以接受。** 296 个通过基准测试的 AI 改动，由 4 名维护者盲审，约一半不会被合并；
  同一批人写的标准答案也只有约 68% 被批准【测量·机构自发，METR 2026-03-10，复核】。结果对、判据过，
  改动仍可能是维护者不会收的。而且**不是所有的活都有看得见的结果**：重构、库代码、构建脚本，
  「完成了什么」往往只剩「测试过了」，这一条对它们最直接。
- **自述会错**：37% 的「完成」是验过之后又改了；润色过的描述带偏审查（§15.8、§15.9）。汇报整个
  是自述；第一、二期对此没有机器层面的对策（§15.3），后期的复核方看不到它（§15.9）。
- **走得最远的那家自己说了条件**：全新的仓库、内部产品、纠错便宜；原文写明这种做法在低吞吐的环境
  下是不负责任的，并且承认瓶颈变成了人的验收容量【宣传，OpenAI 2026-02-11，核的是存档副本】。
- **宣称长期不读代码而成功的几家，没有找到公开的结果数据**【调研没查到】。其中一家的规则是
  「代码不许由人审」，记录它的人的反应是：模型容易犯人不会犯的错，这怎么可能是明智的做法
  【经验，Willison 2026-02-07，已核】。
- **理解会塌**：见 §15.11 的「塔」。另有亲历者在几次事故后回头手工重写【经验，Horthy 2026-07】。
- **视频不是代码审查的替代品**，只是比一大坨差异更容易入手的入口——这是做这个功能的那家自己的人
  说的【未核，播客的二手摘要】。
- **算术上的上限还在**：能判断的人只有一个。结果导向把每一份的时间从读代码降到看结果，没有把它
  降到零；§15.7 的列表仍然只能一份一份过。

调研里列的五条「看起来对、其实不管用」，在新方向下各自的位置：

1. **「两个 AI 都通过就不给人看」。** 现在的规则是：都通过也不等于查完了，抽中的再加一道。但要承认，
   人不读内容以后，这一条离被违反只有一步——所以 §15.9 把「一致放行的真实错误率没人测过」写成了底。
2. **让另一个模型给实现写测试来验收。** 没有采用。判法是派活时凭需求写的，做的人改不了（§15.5）。
3. **审规格或计划来代替审代码。** 判据前置看起来像它。区别是判据只有几句、每句一个可判的结果；
   一旦长成文档，那条反对意见原样适用（§15.5 的上限就是为此）。
4. **给人看 AI 的解释和置信度。** 确认条目里不显示复核方的置信分数，只显示它反对了没有、
   反对的是什么、证据是哪条命令。
5. **把「每次多少行、每小时多少行」当硬阈值。** 不再相关：人不按行读了。

### 15.15 未验证与没查到的

**调研没查到的**——写在这里，免得被读成「查过了，没问题」：

- **用结果或摘要替代读差异以后，漏出去的缺陷率的对照测量。** 它现在是整个方向的前提，没有人测过。
- 两家不同厂商的审查者一致放行时，代码实际有错的概率。§15.9 的加查比例因此没有依据。
- 长期不读代码的团队的公开结果数据。
- 一个人能同时监管多少个编码 agent 的任何测量。§15.12 的默认值因此没有依据。
- 把「哪条结论由哪条命令支撑」串起来的规范或现成工具。收据与判据的形状是这里自己定的。

**本节自己没验的**，开工前要验：

| 项 | 怎么验 | 验不通怎么办 |
|---|---|---|
| 有多少任务写得出看得见的判据 | 拿最近 50 个任务的记录回放，逐个写判据，数机器判、人判、写不出的各几个 | 写不出的超过三成，判据对这个仓库的价值就有限；要如实告诉用户 |
| 截界面不打扰用户 | 在测试实例上采一轮界面结果，看它抢不抢前台、吃不吃用户的按键 | 抢的话，界面类的结果只能在用户明说可以占用屏幕时采，其余时候任务的证据页写「界面结果没采」 |
| 指纹够不够快、认不认得出「验过之后又改了」 | 在本仓上算 20 次取耗时；改一个被跟踪的文件、加一个新文件必须不同，只动被忽略的文件必须相同 | 超过 1 秒只算被跟踪文件的差异并写明；三格有一格不对就不能叫「绑到树」 |
| 判法的指纹拦不拦得住改检查 | 派活后让 worker 改掉机器判用的那个检查，交付时必须显示「判法被改过」 | 这是地板，不是可选项 |
| 盲审的那一包里确实没有自述 | 在 worker 写的每一段里放一个记号串，取复核包，一个都不许出现 | 这是地板 |
| agent 能不能摆拍一个结果 | 让 agent 在被测对象没改对的情况下交一张「看起来对」的截图，看采集的标注与复核能不能认出来 | 认不出来就在任务的证据页上对界面类结果加一句「画面不证明行为」，并要求配一条机器判的判据 |
| 「像是做完了，没有报」误报多不多 | 拿现有任务记录回放，数它点名的里有几个其实还在做 | 多于三成就只在总管那里提示，不进用户的列表 |

**这一转向带来的、还没有答案的口**：

- **谁来维持「人知道系统怎么搭的」**（§15.11）。没有设计，只有一个被点名的条件。
- **可维护性没有闸**（§15.11）。欠账看得见，不等于有人还。
- **积压的结果会旧**（§15.7）。默认不限流，所以这一条只有显示，没有对策。

**用这些数字要小心**（调研者自己的提醒）：行业报告几乎都出自卖审查工具或卖度量工具的厂商；
多数模型测量落后当前模型一到两代，而且多在竞赛题和植入的错误上，仓库级多文件改动的测量很少。

### 15.16 落到哪一期

**第一、二期只做两条主线要的东西。** 机器把关全部后移。

| 期 | 做什么 | 不做什么 |
|---|---|---|
| 第一期最前（单独交付，任务 R0p） | **终端里点路径 → 就地预览**（§15.6）：两个宿主各改「打开」这个动作的处理，加预览面板；文本、图片，mac 加 PDF；目录出列表；找不到时有提示 | 汇报、群聊里的路径（它们随后用同一个预览） |
| 第一期 | `report_post`（四样、任务号与路径的关联与标记、存储）；「汇报」页签与列表；**点任务**：浮层的五段，`task_describe` 的登记与显示；**点汇报里的文件**：出同一个预览；**就地确认**：进「等你」（新类别「要你确认」）、答复 / 通过 / 打回、答复送回汇报人 | 任何机器把关；diff |
| 第二期 | 群聊消息里的路径可点；「汇报之后改过」的标记；汇报里附截图与读数；「像是做完了，没有报」的提示；worker 的确认经总管转给用户；预览顶上的「在文件窗格里打开」（等 E 的进度） | diff；任何机器把关 |
| 后期（第三期起，顺序再定） | 收据与工作树指纹；判法与机器判的判据；截图与读数的机器采集；`task_close` 的闸与用户直接关任务；盲审复核与否决优先；风险等级；加查比例；群的欠账 | — |
| 更后 | 写文件的 hook 接上以后：汇报文件的对账（列了没动过的、动过没列的）、风险规则里的对外动作；可选的限流（默认关） | — |

第一期包含的就是表里那一行，加上 §13.1 原有的队列、机器状态与卡片上处理。它比原来重，所以把不依赖
总控台的那一样（点路径预览）提到最前单独出，其余的仍然只用核心已有的数据加一份汇报的记录。

各期要加的地板，并入 §13.1 对应的期：

- R0p：把「路径不存在」改成什么都不做，「找不到时有提示并写明完整路径」那条红；让程序自己声明的
  本地文件链接也走预览，「那一类链接的处理不变」红；把网址也送进预览，「网址和今天一样」红。
- 第一期：把「在工作目录之外」的文件标成可以一键点开，「目录之外的路径不能一键打开」红；让别的群的
  任务号通过，`TaskNotInGroup` 红；把没有确认条目的汇报也算进「等你」，「没有要确认的汇报不亮数字」
  红；把用户的答复只记录不投递，「答复送回了汇报人」红；把路径不存在改成拒绝整次汇报，
  「汇报照收、该项标灰」红；把任务说明写进面板的记录，「面板的字段没有变」那道检查红。
- 第二期：把「汇报之后改过」的比较去掉，对应的标记测试红；把 worker 的确认直接放进用户的「等你」，
  「worker 的确认先到总管」红（若 §11 定成直达，这条地板反过来写）。
- 后期：指纹只取提交号时「验过之后改了没提交的文件，收据过期」红；去掉判法的指纹检查时
  「判法被改过」红；`task_close` 接受已取消的任务时对应的测试红；复核包里带上汇报人写的任意一段时
  记号串那条红；否决优先改成多数表决时「一个反对就不能关」红；任务负责人交复核结论时 `SelfReview` 红；
  限流的默认值改成开时「默认不因为人没看就拒绝派活」红。
