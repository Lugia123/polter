## 0. 五件事和它们的关系

| # | 功能 | 一句话 | 依赖 |

| A | 单群聊分屏 | 把一个群聊开成当前 tab 里的一个窗格 | 无 |

## 1. A：单群聊分屏

**要解决的**：现在「终端群聊」是所有群的合集界面。实际干活时用户只盯一个群（当前总管
那一个），想让它就在手边，而不是切到另一个 tab。

- 群聊页本来就是跑在终端里的程序（`polter +chat`，`src/cli/chat.zig`），所以开成分屏
  只是换一个地方启动，不需要新的界面技术。
- 给它加一个「只看一个群」的启动方式：去掉群列表，只留消息和任务面板。
- **建群时不自动打开**（用户定）。入口有两个：
  - **菜单**：tab 的右键菜单与终端的右键菜单里「打开当前群聊」。菜单要能认出该开哪几个群：
    这个 tab 里的终端所在的群（总管终端则是它建的群）。只有一个就直接开，有多个列成子菜单，
    一个都没有时这一项置灰。
  - **让总管开**：用户对总管说一声，总管用工具把某个群的群聊开在自己的 tab 里。需要给
    `terminal_open`（或一个专门的工具）加「开成某个群的群聊窗格」的能力；只许开调用者自己
    在的群。
- 这个窗格和合集页一样算「用户的手」：核心要把它登记成群聊页（`App.addChatSurface`），
  它发的请求才以用户身份到达。⚠️ 登记是宿主做的，分屏路径要和开 tab 的路径走同一处。
- 现有合集界面**不动、不删**。

验收：从总管终端右键打开 → 旁边出现只含该群的窗格；发一条消息对方收到；关掉窗格不影响
群；合集页仍能看到全部群。

## 2. B：层叠

**要解决的**：分屏只有平铺，开到五六个 worker 以后每格都小得没法看。要像 VS Code 的
编辑器组：一个格子里叠多个终端，上面一条子 tab 切换。这样可以摆 1:n（n 全叠在右边一格）
或 1:n:1。

### 2.1 模型

分屏树的叶子从「一个终端」变成「**一组终端 + 当前显示哪一个**」。只有一个成员的组和
现在的叶子等价，不画子 tab 条。1:n、1:n:1 只是这棵树的不同形状，没有新概念。

### 2.2 被叠住的终端必须看得见状态

被叠在后面的终端屏幕不可见，但它仍在跑。**子 tab 条上不显示状态，层叠就会把卡住的
worker 藏起来，和产品的目的正相反。** 用户定的呈现方式：

- **文字只有名字**（角色名或标题）。
- **状态不用文字**：在跑 / 等输入 / 等授权 / 已结束 / 失败（核心已有，`terminal_list` 的
  `agent.state`）用图形表达——颜色点、图标或动效，具体样子在 B2 出图给用户挑。
- **未读标记也不用文字**。它的意思是：这个终端被叠住（或没被看着）的这段时间里屏幕上
  出了新内容，用户还没切过去看过；切过去即清除。和聊天软件的小红点同一个意思。
- **静止时长、分支名放进鼠标悬停提示**，不常驻。

### 2.2.1 平铺的分屏也要有自己的标题区（用户定）

现在平铺的分屏没有各自的标题，要一个个点过去、看 tab 上的名字才知道哪格是谁。和子 tab 条
用**同一套设计**：每个分屏顶上一条标题区，显示名字、状态图形、未读标记，悬停同上。
只有一个成员的格子，标题区就是「只有一个子 tab 的子 tab 条」——一种部件，两个场合。

- 只有一个分屏的 tab 不画标题区（tab 本身已经说了名字），开第二个分屏时才出现。
- 标题区是拖放的把手（§2.3、§3）。

### 2.3 操作

- 新建：在当前组里再开一个（菜单 + 键位动作）。
- 切换：点子 tab；键位「组内上一个 / 下一个」。
- 拖动：子 tab 可以拖到别的组（叠进去）、拖到窗格边缘（切开成新格子）、拖出去成独立 tab。
- 关闭当前成员后显示组里相邻的一个；组空了，格子消失，树照常收拢。

### 2.4 给 agent 的工具

- `terminal_layout` 要能表达层叠（一个格子里列多个终端）。
- `terminal_open` 的位置多一种：「叠到某个终端后面」。
- `terminal_list` 说清楚每个终端在哪个组、是不是当前显示的那个——agent 读屏不受影响
  （读的是终端内容，不是画面），但它需要知道用户此刻看不看得见。
- 总管 skill 补一条：worker 多于 N 个时叠起来。

### 2.5 实现要点

- 子 tab 条是原生界面，mac（Swift）和 Windows（Rust 宿主）各画一遍；外观进同一份外观表，
  和截图界面一样「写一次、两边生成」。
- 项目保存的布局（`dev-docs/poltergeist/tabs.md`）要能存层叠；旧项目文件读进来是「每组
  一个成员」。
- **开工前要量**：mac 上游 Ghostty 的分屏树能不能在叶子上挂多个 surface 而不大改；
  Windows 宿主自己的分屏树改动量。两边各出一份现状说明再定方案。

验收（两平台各一轮）：1:n 与 1:n:1 两种摆法；被叠住的 worker 等授权时子 tab 上看得出来；
存成项目再读回来形状不变；`terminal_layout` 能摆出层叠并回报哪个终端在哪个组。

## 3. C：跨 tab 嫁接

**要解决的**：想把一个 tab 拉进另一个 tab 的分屏里，现在做不到。难点是被拖的 tab 自己
可能有多个分屏。

- **被拖 tab 里的终端一律叠到一起进去，原来的平铺布局不保留**（用户定）。所以这件事
  不需要「嫁接一棵子树」，只需要「把一串终端放进一个组」，比原设想简单：
  - 拖到某个格子**中央** → 这些终端全部叠进那一组，排在原有成员后面。
  - 拖到某个格子的**上/下/左/右** → 在那一侧切出一个新格子，这些终端在新格子里叠成一组。
  - 组内顺序按它们在原 tab 里的阅读顺序（从左到右、从上到下）；原 tab 里聚焦的那个
    成为当前显示的成员。
- 落点提示和 VS Code 的拖放提示一致。
- **反向操作一起做**：把一个窗格、一个组或一棵子树拖出去变成独立 tab。否则拖进去就
  回不来。
- 键盘入口：命令面板「把这个 tab 移到…」，列出目标 tab 和方向。拖放不是唯一入口。
- **跨窗口不做**（用户定）：只做同一个窗口里的 tab 之间。把窗口甲的 tab 拖进窗口乙某个 tab
  的分屏里，本轮不支持；拖过去时不给落点提示。

连带要核对的（都是树变了以后会跟着变的东西）：

- `terminal_list` 的 `window` / `tab` 值。
- 「总管的 worker 开在总管自己的 tab 里」这条规则，在总管被嫁接走以后指的是新 tab。
- 监管标记、护盾、持有（held）跟着终端走，不跟着 tab 走。
- 项目保存的布局。

**开工前要量**：mac 上游是否已有窗格在树内拖动重排（若有，跨 tab 是在其上扩展）；
Windows 宿主现在的 tab 拖动到了哪一步。

验收：把含 3 个分屏的 tab 拖到另一个 tab 某窗格右侧，右侧出现一个新格子、里面叠着这三个
终端，进程没断、agent 仍能按原 id 读写；拖到某个已有的组中央，三个都叠进那一组；再把
其中一个拖出去成为独立 tab。

## 4. D：worktree

**要解决的**：多个 worker 并行改同一个仓库时要各自一棵 git worktree。0.9 这一轮是总管
手拼 `git worktree add`，暴露了三个问题：哪棵树是谁的只在总管脑子里，重启或压缩后要重查；
每个总管拼法不同；做完没人收，构建缓存把磁盘吃满。

**结论：建和收由产品做，什么时候用、怎么合由 skill 教。不做成默认角色**——worktree 是
「在哪干活」，角色是「谁在干」，两个维度独立，绑在一起每个角色都要出两份。

### 4.1 产品层

- `terminal_open` 与 `role_launch` 加 `worktree` 参数（一个名字）。核心在约定位置建树、
  建分支、把终端开在里面，并回报路径、分支、基于哪个提交。
- 记账：这棵树属于哪个终端、哪个任务、基于哪个提交，写进任务面板与会话记录，重启后还在。
- 可见：`terminal_list` 带上树与分支；任务面板显示「改动在哪棵树、领先主线几个提交、
  脏不脏」。
- 收尾：关任务时提示树还在；一个工具回答「合了没有、有没有未提交的」；**删除必须是
  总管明确调用，而且只在干净且已合并时放行**，其余情况拒绝并说明原因。不自动删。
- 人也能用：右键菜单「在新 worktree 里开一个 tab」，走同一条路。
- 每棵树用自己的构建目录——产品能做的只是把树的路径放进终端的环境变量，隔离本身靠
  skill 里的规矩。

### 4.2 skill 层（`supervising`）

- 什么时候用：会改代码且并行的 worker 用；只读调研、测试机操作不用。
- worker 不提交、不碰暂存区，总管统一合。
- 合之前核对 worker 报的读数取自哪个提交；合并后的树总管自己跑全套闸。
- 什么时候删：判据是「还会不会被需要」，不是「任务做完没」。

### 4.3 用户定的三件事

1. **树放哪：可设定。** 默认仓库旁边 `<仓库名>-wt/<名字>`（0.9 这一轮的做法），可以改成
   仓库里。放仓库里时，产品要保证那个目录不会被提交进去（写进该仓库的
   `.git/info/exclude`，不改用户的 `.gitignore`）。配置项进设置窗口。
2. **不做合并工具。** 只做到「显示差异、提示可合」，合并由总管用 git 做。
3. **不是 git 仓库的目录：退化。** 带了 `worktree` 参数也照常在该目录开终端，不建树；
   回报里必须明说「这里不是 git 仓库，没有用 worktree」，不许让调用者以为隔离了。

验收：`role_launch` 带 `worktree` 开出的终端在新树里、分支已建；重启 Polter 后面板上
仍能看到归属；脏树或未合并的树删不掉且说明原因；干净已合并的能删；在非 git 目录里带
`worktree` 开终端，终端照常开出、回报里写明没有用 worktree；把位置改成「仓库里」后新树
建在仓库里且 `git status` 看不到它。

## 5. E：文件窗格

**要解决的**：开发时总要另开一个 VS Code，其实只是看文件。想集成进来：选目录、看目录树、
看文件，多个目录之间快速切换。

**结论：做成 TUI，只做浏览和预览，不做编辑器。**

为什么 TUI：

- 一份代码两个平台都有，和群聊页同一条路。原生要 mac 与 Windows 各写一遍，文件树加
  编辑器是这五件里最大的工作量。
- 它天然是一个窗格：能进分屏、能层叠（B）、能存进项目布局。
- agent 能读它的屏幕、能驱动它。

代价：图片预览要走终端图形协议（**开工前要量**：我们的终端在两个平台上、在这个 TUI
里实际能不能画出来）；文本编辑做不到 VS Code 的水平，自己写编辑器是无底洞。

范围：

- 做：目录树；多个目录快速切换（复用「项目」里存的目录，以及 D 的各棵 worktree）；
  文本预览带语法高亮；图片预览；git 状态与 diff；按文件名搜索。
- 做：「把这个路径发给旁边的终端」「在旁边的终端里打开」。这是集成进来的理由。
- 不做：编辑器。编辑交给 `$EDITOR`（在一个层叠窗格里打开），或一键用外部编辑器打开。

用户定：

1. **不要编辑能力。**
2. **自己写一个小的**，不整个内嵌别人的程序。但开工前（E0）先看一遍 GitHub 上做得好的
   开源终端文件管理器与预览器，把好的部分吸收进来：交互设计可以借鉴，代码只在**协议
   友好**（MIT / Apache-2.0 / BSD 一类，和本仓的许可相容）时才搬，搬了要按其许可署名。
   E0 的产出里列清楚看了哪些、各是什么协议、借了什么。

验收：在一个窗格里打开、切到另一个项目目录与一棵 worktree；预览一个源文件和一张图片；
看到未提交文件的标记并打开 diff；把路径发到旁边的 agent 终端。

## 5.6 F：截图第三轮——专为 AI 设计的截图工具

前两轮的规格在 `screenshot.md`。这一轮的线索只有一条：**普通截图工具的产物是一张给人看
的图；这里的产物是一份 AI 能直接用的上下文，图只是其中一部分。** 已经做到的一半：标注是
文本数据（旁路 `.json`）、agent 能自己截。下面四个方向按价值排序。落地时并进
`screenshot.md` 作为第三轮，旁路文件升 `version`。

### F1 截到的不只是像素（最先做）

AI 从图里认字、猜这是哪个文件哪个页面，又慢又容易错。能直接给的就直接给。

- **截到 Polter 自己的终端时，附上那块屏幕的文字。** 我们白拿，不需要识别，别的截图工具
  做不到。选区只盖住窗格一部分时，给选区内的那些行。
- **本机文字识别。** 选区里的文字随图一起给；用系统自带的能力（mac Vision、Windows 的
  系统 OCR），**不联网**——产品承诺除「检查更新」外不发网络请求，这条不许破。顺带给人
  一个「复制图中文字」。**开工前要量**：两个平台上中文与代码的识别质量、耗时，以及
  Windows Server 上有没有这个系统组件。
- **来源信息**：浏览器窗口带网址；终端窗格带所在目录与 git 分支；应用与标题已有。
  **开工前要量**：不要辅助功能权限能不能拿到网址。
- **界面元素信息**：选区里有哪些按钮、输入框，各自的名字和位置。用户框一个按钮说「没
  对齐」，AI 拿到「名为保存的按钮，位置与大小是多少」，能直接对到代码。
  - mac 上要「辅助功能」权限。**用户定：接受。** 这推翻了 `screenshot.md` §6「第 2 步都不要
    辅助功能权限」那一句，落地时那一节要一起改。用户没给这项权限时其余功能照常，只是
    `.json` 里没有元素信息，并且说明是因为没授权，不写成「选区里没有元素」。

### F1.5 权限一次要全（用户定）

现在首次截图只提示「屏幕录制」，以后用到别的再提示。用户定：**既然首次截图已经要打断
用户去开权限，就把截图需要的权限在这一次全部列出来要完**，不是用到一个要一个。

- 首次截图（或权限不全时）给一个说明面板：列出截图用到的每一项权限、各自是干什么的、
  现在是否已给，逐项带「去打开」。mac 目前是两项：屏幕录制（截图本身）、辅助功能
  （界面元素信息）。Windows 目前一项都不要，不显示这个面板。
- 必需与可选要分开写清楚：屏幕录制不给就截不了；辅助功能不给只是少元素信息。
- 以后截图功能再多用一项权限，就加进这张表，不另起一个提示。
- ⚠️ 已知的坑：adhoc 签名的包重装后，系统设置里勾着的授权其实已经作废，要删掉重加。
  面板的「是否已给」必须问系统的实测结果，不读开关的样子。
- 粘贴给 CLI 时这些怎么送：仍然是「路径一次、文本一次」，文本里加上识别文字与来源；
  太长就只给摘要并指向 `.json`。

### F2 让 agent 自己验证界面改动

0.9 这一轮反复手动做的事——改完界面、截图、看对没对齐——要变成 agent 能闭环的能力。

- **前后对比**：改动前截一张、改动后截一张，工具回答哪些区域变了（矩形列表），并给一张
  标出差异的图。纯函数，可测。
- **测量当数据**：两条边的间距、两个元素是否对齐、某处的颜色值，以数字返回。「界面对齐」
  是本仓的验收判据，现在靠人眼读图；这条让它可以被检查。
  - **只给 agent 用，不做进人用的截图界面**（用户定：人操作的交互不好做，也没有人会用
    的场景）。前后对比同理。
- **agent 指给人看**：agent 在截图上画框标号后弹给用户看，「我说的是这个按钮」。现在只有
  人指给它。不抢焦点，和「保存」的小浮条同一个级别的打扰，点开才放大。
- **agent 请人指**：`screenshot_interactive` 已有；加一句问题一起显示（「请框出你说的错位
  的地方」）。

### F3 发给 AI 之前把好关

截图会离开这台机器，这是「给 AI 用」特有的风险。

- **敏感内容提示**：识别出密钥、令牌、邮箱、手机号一类内容时，完成前提示并一键打码。
  依赖 F1 的文字识别。只提示，不替用户决定；识别不到不等于没有，界面上不许写成「已检查，
  安全」。
- **agent 截图的范围**：现在是一个总开关（`screenshot-agent-access`）。细到「只许截 Polter
  自己的窗口」「只许截指定的应用」。
- **截图记录**：agent 什么时候截了什么，给人一个能查的地方（`by` 已经记在 `.json` 里，
  缺的是界面；放进 F4 的历史视图）。

### F4 用起来更顺

- **截图历史**：最近的截图，能预览、重新标注、再发一次。做成文件窗格（E）里的一个视图，
  不单独做界面。
- **直接送达**：完成时由用户选「发给哪个终端」或「发到哪个群」。⚠️ `screenshot.md` §3.4 定了
  完成时不自动往窗格里送（#1114）——所以这条只能是用户主动选，不是默认。
- **控制图片大小**：模型对过大的图会自己缩小，细节反而丢。按目标模型的上限预先缩放或
  切片，并显示大概占多少上下文。**开工前要量**：各 CLI 实际的上限。
- **步骤记录**：连续操作时每次点击自动截一张并标序号，产出一份「复现步骤」。模型看不了
  视频，这比录屏有用。
- **钉在屏幕上**：把一张截图浮在桌面当参照。给人用的，排最后。

### F 的先后（用户定）

**截图先做，排在 A–E 前面。** F 内部：F1（终端文字 + 文字识别 + 来源 + 元素信息）与 F1.5
（权限一次要全）→ F2（前后对比 + 测量）→ F3（敏感内容提示、范围）→ F4 其余。
只有 F4a（历史视图）要等文件窗格 E，留到 E 之后。

## 5.5 节奏与默认行为（用户定，2026-10-10）

1. **未读标记只在需要人看时亮**：这一轮结束了、在等输入、在等授权、失败了，而当时没在看它。
   普通的持续输出不点亮，只用「在跑」的状态图形表示。切过去即清除。
2. **总管开 worker 的默认位置**：第一个 worker 仍然从总管的 tab 里切一格出来，之后的
   worker 默认叠进那一格——自动就是 1:n。调用者可以明说别的位置。
3. **worktree 不是默认**：总管明确带参数才建；什么时候该用写进 skill。
4. **两个平台一起交付**：每个功能 mac 与 Windows 同时算完成，不出现一边有一边没有。
5. **顺序**：F（截图，F4a 除外）→ A → B（含标题区）+ C → D → E → F4a。
6. **先收尾 0.9 再开分支**：等 README 那边改完并提交，把 0.9.1728 装到本机、用户重启看过
   （截图新版、选角色、删群），有问题在 0.9 上修掉，然后才开 `feature/v0.10`。不着急。
