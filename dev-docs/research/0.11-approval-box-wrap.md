# 审批框在窄分屏里还认不认得出（task 1788）

> 调研，不改产品代码。对象：`Plugin.ScreenSays`，也就是各家 `plugin.json` 的
> `screen_says.awaiting_approval.contains`。它的用法是：在屏幕最底下 16 行
> （`ScreenSays.rows`）里逐字找声明的句子。
> 起因：#1787 发现 agy 的 trust 问句在窄分屏里会折行，于是 `StartupSays` 改成了
> 忽略空白的匹配（`containsWrapped`）。审批框会不会有同样的问题，当时说好另开一单先量。
> 代码基于 a8887eac8；CLI 版本：claude-code 2.1.302、codex 0.163.0、opencode 1.2.10、agy 1.4.2。

## 结论

| CLI | 声明的句子 | 35 列 | 40 列 | 60 列 | 现在的匹配 | 改成 containsWrapped |
|---|---|---|---|---|---|---|
| claude-code | `Do you want to proceed?` | 不折，距底 11 行 | 不折，距底 10 行 | 不折，距底 9 行 | ✅ 认得出 | 不需要 |
| opencode | `Permission required` | 不折（右边的选项被截断），距底 10 行 | 同左 | 同左 | ✅ 认得出 | 不需要 |
| codex | `Would you like to run the following command?` | **折成两行，距底 20 行** | **折成两行，距底 19 行** | 不折，**距底 15 行** | ❌ 35、40 列认不出；60 列刚好在窗口里 | **救不了**：问句已经出了 16 行窗口 |
| agy | `Requesting permission for:` / `Run this command?` / `Allow calling this tool?` | 没测到 | 没测到 | 没测到 | — | — |

「距底 N 行」的数法：从屏幕最后一行非空行往上数，到问句（折行时是问句的第一行）为止，含两端。
`bottomRows(16)` 能看到的范围是 N ≤ 16。

**三类：**
- **会折、而且认不出：codex。** 但折行是次要原因。主要原因是 codex 把问句放在框的最上面，下面依次是 `Environment`、`Reason`、命令和三个选项。列宽一窄，选项和 Reason 都会折高，问句就被挤出了最底下 16 行。60 列时问句距底 15 行，命令只有一行（`touch codex-probe-file`），已经贴着上限；命令多一两行、Reason 长一点，60 列也会出窗口。
- **不会折：claude-code、opencode。** 声明的句子短（19 到 23 个字符），而且就在框的下部，紧挨着选项。
- **没测到：agy。** 见下。

**要不要改成 containsWrapped：** 对这一单量到的三家都不必。
- claude-code 和 opencode 不折。
- codex 的问题出在 16 行窗口，不在折行：忽略空白也找不到一句根本不在窗口里的话。

**codex 这一格目前影响有多大：** 不大。codex 的等批准状态由 hooks（`PermissionRequest`）和标题（`title_says`：`[ ! ] Action Required`）报告，跟屏幕宽度无关。`screen_says` 只在 `terminal_answer_prompt` 盲按时才用，也就是 agent 自己什么都没说的时候（`blindRefusal`）。所以窄分屏里的 codex，遇到这种情况会回 `PromptGone` 或 `PromptUnknown`，而不是按错键。这是保守的方向。
- 要修的话，可选：(a) 扩大 codex 的窗口，比如 manifest 里加一个 `rows` 声明；(b) 声明框里靠下、而且一直在的句子，比如 `Press enter to confirm or esc to`（会折，要配合 containsWrapped）；(c) 不修，写进文档。我倾向 (c)，或者等需要时再做 (b)：这条路径本来就只是兜底。

**agy 要单独看：** 它的插件声明 `hooks_report_approval: false`，屏幕是它报「等批准」的唯一来源，所以它才是最该量的那家。没测成的原因：agy 要 Google 登录，临时 HOME 里没有凭据；用真 HOME 会改到用户的 agy 状态（新的会话记录、信任目录列表），而且会用到真账号的额度。
- 按 `Plugin.zig` 里 agy 1.4.0 / 1.4.2 实录的框推断：三句都只有 17 到 26 个字符，35 列也装得下。`Run this command?` 和 `Allow calling this tool?` 紧挨着选项；第 2 个选项（`Yes, and always allow in this conversation for commands that start with …`）在 35 列会折成 3 行左右，问句距底大约 6 到 8 行，在窗口里。**这是推断，没量过。**
- 建议由 mac 测试员在 poltertest 里补一格：那里装着已经登录的 agy。

## 怎么量的

1. **真 CLI，跑在指定列宽的 pty 里，不是把一份宽屏录制拿到窄屏去重放。** 这几家都是按终端宽度自己排版的 TUI，100 列下录的字节流放进 35 列的终端，得到的是一张没人见过的屏幕。所以每个宽度都单独起一次 CLI，录下它在这个宽度下写出的全部字节，再按同样的宽度重放。
   - 采集器：python 的 `pty.fork` 加 `TIOCSWINSZ`。它按屏幕上出现的文字一步步发键，并代答 TUI 会等的查询：DSR 6n、DA1、OSC 10/11、kitty 键盘协议的 `CSI ? u`。
   - 子进程的环境去掉了本会话的 `CLAUDE*`、`POLTER*`、`GHOSTTY_POLTER*` 这些变量。第一次没去掉时，claude-code 屏幕上出现了 `inherited CLAUDE_CODE_CHIL…`。
2. **替身模型，不花钱，也不碰用户的配置和账号：**
   - claude-code：`CLAUDE_CONFIG_DIR` 和 `HOME` 都指向临时目录，里面预先写好 onboarding 完成、API key 已认可、cwd 已信任；`ANTHROPIC_BASE_URL` 指向本地的替身 `/v1/messages`（SSE），它对 `RUNCMD` 回一个 `Bash` 的 tool_use，命令是 `touch claude-probe-file`。
   - codex：临时 `HOME` 和 `CODEX_HOME`，provider 是本地的替身 Responses API。0.163 已经不支持 `wire_api = "chat"`，也不支持 `approval_policy = "untrusted"`（都在启动时报错），所以用的是 `on-request` 加 `read-only`，由替身在 `exec_command` 的参数里申请 `sandbox_permissions: require_escalated`。
   - opencode：和 #1777 一样，临时 HOME 加 `@ai-sdk/openai-compatible` 的替身，并且 `permission.bash = ask`。
3. **读屏：** 先用 pyte 读最底下 16 行，再拿各家声明的句子去比，逐字比一次、去掉空白再比一次。之后在 Ghostty 自己的 Terminal 里用同样的字节流和列宽重放复核（见下一节）。

## 原样屏幕（codex，pyte）

35 列（`|` 标出 16 行窗口的上沿；问句在窗口外）：

```
    Would you like to run the
    following command?

    Environment: local
|
    Reason: Probe: needs to write a
    file

    $ touch codex-probe-file


  › 1. Yes, proceed (y)
    2. Yes, and don't ask again for
       commands that start with
       `touch codex-probe-file` (p)
    3. No, and tell Codex what to do
       differently (esc)

    Press enter to confirm or esc to
    cancel
```

## 没量的

- agy，见上。
- 各家其它种类的框：codex 的改文件（`Would you like to make the following edits?`，43 个字符，比运行命令那句还长）、权限申请、MCP 工具；claude-code 的 MCP 工具框和改文件框；opencode 的 edit。我推断它们的版式和量到的同类框一样，没逐个触发。
- 多行命令、很长的 Reason、更矮的终端（这次是 30 行）。这些只会让问句离底部更远。
