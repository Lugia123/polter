### A3. 交接设计（草案）

#### 1. 怎么检测快用尽

- **CC，mac 和 Linux**：
  - `+statusline` 已经在读 stdin，再多取一个字段 `context_window.used_percentage`，按终端存一份（和额度并排）。没有 usage 时这个值是 null，要按「不知道」处理，不能当 0。这是 AGENTS.md 第 5 条说的两种状态要分开。
  - 成本：小。
- **CC，Windows**：没有 statusLine，改用 hook 输入里的 `transcript_path`：在 Stop hook 时读 transcript 末条 assistant 的 usage，除以窗口大小。
  - 窗口大小从哪来：`modelUsage.contextWindow` 只在 `-p` 的输出里有。**推断**：交互会话只能按模型名查表，或者干脆只报绝对 token 数。
  - 成本：中。
- **Codex**：rollout 的 `token_count` 里 `last_token_usage.input_tokens / model_context_window`。Polter 读 Codex rollout 的路子已经有了（memory 里那条「Windows 上活 codex 的 rollout 要共享读」）。成本：小到中。
- **OpenCode**：只读库 `message.data.tokens`；或者 #1777 接插件之后，由插件在 `session.idle` 时上报。成本：跟着 #1777 走。
- **agy**：statusLine 的字段。成本：小，但要实测字段名。
- **阈值建议**：
  - 70%：在总管的标签和总控台上标出来。
  - 85%：给总管打一句话，叫它写交接。
  - 由 CLI 自己的自动压缩兜底。
  - 这些是配置项，默认值待定。

#### 2. 交接时写什么

记录里**已经有**的，不用写：群的 brief、任务面板、群消息、各终端的转录。

**只存在总管脑子里的**才要写下来：

- 每个 worker 被告知了什么，还欠什么；
- 待用户决定的事；
- 正在等谁、等什么；
- 下一步打算；
- 哪些判断还没核实。

**落在哪**：建议做一个专门的「交接条」，跟 brief 分开：

- 新增一个工具 `group_handoff(text)`，或者 `group_set_brief` 加一个 `handoff` 字段。
- 理由是 brief 描述群「是什么」，交接条描述「此刻进行到哪」。生命周期不同，混在一起，下一次改 brief 就会把交接冲掉。这条是 AGENTS.md 第 5 条的判据。
- 写入时带时间，读出时附上「几分钟前写的」。

#### 3. 压缩还是换人

**默认先压缩**，同一个会话：

- 压缩之前：PreCompact hook 的 stdout 写一句「摘要要保留：群名、自己是总管、未决事项、交接条的位置」。
- 压缩之后：SessionStart(compact) 的 `additionalContext` 注入一句「你是群 X 的总管；先 `group_list` 读 brief 和交接条，`task_list`、`terminal_list` 对一遍再动手」。
- **这两步都只是在 adapter 里加两个 hook，成本小。**

**换一个新总管**，以下任一条成立就换：

- 同一个会话已经压缩了 N 次。每次压缩都有信息损失，摘要会叠着摘要。N 待定，建议 2–3 次。
- 用户要求换。
- CLI 没有压缩。

换人的做法照现成的接回方法：`polter +launch <总管角色> <cli> --group=<群>`，**不带 `--resume`**；启动语里点名交接条。

**旧总管怎么退**：

- 写完交接条以后，旧总管 `stand_down`（下班），新总管再 `become_supervisor`。
- 顺序不能反：同一个群同一时间只许有一个总管，这是现有约束。

#### 4. CLI 不支持压缩、或者不能注入时

| 情形 | 做法 |
|---|---|
| agy（有 `/compact <msg>`，没有 hook） | Polter 等它空闲时代它敲 `/compact 先读 group_list 和交接条，再接着做`。用现成的 `terminal_send`，但要先读屏，确认没有审批框（memory：脚本给 agent CLI 发回车前先读屏） |
| Codex（能压缩，不能在压缩前加料） | `compact_prompt` 是全局配置，Polter 不能改用户配置，所以只靠 SessionStart(compact) 的 `additionalContext` |
| 完全不能压缩、也没有 hook 的 CLI | 只能换人 |

### A4. 优先级建议

1. **P0（小）**：
   - CC 的 adapter 加 PreCompact 和 SessionStart(compact) 两个 hook；
   - supervising.md 补一节「你自己的上下文快满了」；
   - `+statusline` 多取 `context_window.used_percentage`。
   - 做完这一组，**压缩以后不再忘记自己是谁**。
2. **P0（中）**：交接条（工具加落盘），加上总控台上的百分比显示。
3. **P1**：
   - 换人流程，包括 `stand_down` 和启动语；
   - Codex 和 agy 的检测与代敲 `/compact`；
   - Windows 上 CC 走 transcript 的检测。

## B. Claude Code agent teams 的分屏后端（P0#5）

### B1. CC 怎么选后端、调用什么

**开启**：

- 设 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`，或带 `--agent-teams`。
- `teammateMode` 可选 `auto`、`tmux`、`iterm2`、`in-process`，**默认是 in-process**（cc.txt 偏移约 33752529：`var CKn="in-process"`）。
- `-p` 模式下永远走 in-process。
- 文档的「Limitations」一节写明 **Ghostty 不支持分屏模式**：https://code.claude.com/docs/en/agent-teams 。

**后端探测**（函数 `F0n`）：

1. 有 `$TMUX`：选 tmux。只看这个变量非空，不验证真假。
2. 否则如果在 iTerm2 里（`TERM_PROGRAM=iTerm.app`，或者有 `ITERM_SESSION_ID`）且 `it2` 能用：选 iTerm2。
3. 否则如果 `tmux -V` 能跑：新开一个外部 tmux 服务器 `-L claude-swarm-<pid>`。
4. 都不行，并且是 `auto`：回到 in-process。

⇒ **Polter 只要伪造 `$TMUX`、`$TMUX_PANE`，再设 `teammateMode=tmux` 或 `auto`，CC 就会对 PATH 上的 `tmux` 发下面这些命令。**

**tmux 调用**（TmuxBackend，cc.txt 偏移约 49101500–49109200；`split-window … -l 70% …` 那一段在 49107118，我复核过）：

- 每条都带 `-S <$TMUX 第一个逗号前的部分>`，都检查退出码；pane id 取的是 stdout trim 之后的值。
- 第 1 步：`display-message -p '#{pane_id}'`。有 `TMUX_PANE` 时不调这条。
- 第 2 步：`display-message -t $TMUX_PANE -p '#{window_id}'`。
- 第 3 步：`list-panes -t <win> -F '#{pane_id}'`。
- 第 4 步，新建 pane：
  - 第一个 teammate：`split-window -d -t <leader> -h -l 70% -P -F '#{pane_id}' -- cat`；
  - 之后的：`split-window -d -t <中间那个> (-v|-h) -P -F '#{pane_id}' -- cat`；
  - **stdout 必须正好是新 pane 的 id。**
- 第 5 步，装饰：`set-option -p/-w …`、`select-pane -T <名字>`，只看退出码。
- 第 6 步，pane 多于 2 个时重排：`select-layout -t <win> main-vertical`，再 `resize-pane -t <leader> -x 30%`。
- 第 7 步，起 teammate：`set-option -p remain-on-exit failed`，然后 `respawn-pane -k -t P -- "cd '<cwd>' && env CLAUDECODE=1 CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 … '<claude>' --agent-id … --team-name …"`。命令是**一整串，要交给 sh 执行**。
- 第 8 步，收尾：`kill-pane -t P`。

**团队通信不经过终端**：

- teammate 之间靠 `~/.claude/teams/*/inboxes/*.json` 通信。
- **不用 send-keys，也不用 capture-pane**：send-keys 只出现在一段 `if(!1)` 的死代码里。

**pane id 的格式**：CC 校验协议帧里 pane id 的正则是 `^(%[0-9]{1,10}|<uuid>)`（cc.txt 偏移 10397780，复核过）。所以 shim 给出的 id 要是 `%` 加 1–10 位数字。

**伪造 `$TMUX` 对 leader 本身的副作用**：

- 颜色会降到 256 色，设 `CLAUDE_CODE_TMUX_TRUECOLOR=1` 可以绕开（字符串存在，已复核）。
- OSC 会再包一层 `ESC P tmux; … ESC \` 发出。
  - Ghostty 的 `src/terminal/dcs.zig` 只认 `1000p`（tmux 控制模式），**不认 `tmux;` 透传**。
  - 推断：OSC 52 剪贴板不受影响，因为它裸发一份、包着再发一份；只发包装形式的 OSC 会丢，要实测。

**iTerm2 后端**用的是 `it2` CLI（Python API）：`session split -v -s <id>`、`session run`、`session close -f`。Polter 用不上，不做。

### B2. cmux 怎么做的

**怎么注入**：

- `cmux claude-teams` 在 PATH 前面放一个 bash 写的 `tmux`（`CLI/CMUXCLI+TmuxCompatLaunchContext.swift:215`）。
- 有 `CMUX_CLAUDE_TEAMS_CMUX_BIN` 时执行 `exec cmux __tmux-compat "$@"`；没有就把自己剔出 PATH，交给真的 tmux。

**伪造的环境变量**（`CLI/cmux.swift:26817-26870`）：

- `TMUX=/tmp/cmux-claude-teams/<ws>,<win>,<hash>`；
- `TMUX_PANE=%<哈希>`；
- `TERM=screen-256color`，并 unset `TERM_PROGRAM`。

**子命令映射**（`cmux.swift:29663-30450`），都走 cmux 自己的 socket：

| tmux 子命令 | cmux 做法 |
|---|---|
| split-window | `surface.split`，按 `-F` 打印 id，然后 equalize |
| respawn-pane | `surface.respawn` |
| kill-pane | `surface.close` |
| list-panes / display-message | `pane.list` 后渲染格式串 |
| select-layout | 只做 equalize |
| set-option 等 | 直接返回 0 |

- 约 30 个子命令，额外兼容 send-keys/capture-pane，供其它插件用。
- 它会无视 `-t`，统一钉在 leader 上排成「左 leader、右一列」，状态存在 `~/.cmuxterm/tmux-compat-store.json`。

**两个值得注意的地方**：

- cmux 的 `TMUX_PANE` 是一长串哈希，**推断**会撞上面那条 1–10 位的正则。
- 没搜到 WezTerm、Zellij 有现成的 shim；只有一张功能请求 https://github.com/anthropics/claude-code/issues/31901 。

### B3. Polter 的 shim：最小集合、映射、成本

**放在哪、怎么注入**：

- shim 是一个 `tmux` 脚本，放在 Polter 自己的目录，例如 `~/.local/state/polter/tmux-shim/`，并前置到 PATH。
- 只在 `POLTER_TMUX_SHIM=1` 时拦截，否则剔掉自己、交给真 tmux。
- **只在 Polter 用角色启动 CC、且角色开了 teams 时**设 `TMUX`、`TMUX_PANE`、`POLTER_TMUX_SHIM`、`CLAUDE_CODE_TMUX_TRUECOLOR`，再通过 `--settings` 设 `teammateMode`。这和现在 adapter 用 `--settings` 设 statusLine 是同一条路（`adapter.py:801`）。
- **不要全局伪造 `$TMUX`**：所有读 `$TMUX` 的程序（vim、shell 提示符）都会被骗。
- 坑：CC 可能用 shell 快照替换 PATH（cmux 的注释这么说），要实测 PATH 前置能不能活下来。

**怎么跟 Polter 通信**：新增 `polter +tmux <argv…>`。

- `polter` 就是本仓产出的可执行文件（`src/build/exe_name.zig:25`），`+launch`、`+statusline`、`+mcp` 都是它的动作。
- 走现有 socket 调内部工具。shim 本身只有一行 `exec polter +tmux "$@"`。
- 推断：每次调用起一个 `+mcp` 做 JSON-RPC 也行，但慢、而且解析分散，不推荐。

**最小子命令集**：

| 子命令 | CC 要什么 | 映射到 Polter | 难点 | 成本 |
|---|---|---|---|---|
| 全局 `-S`/`-L`、`-V` | `-V` 只看退出码 | 剥掉；`-V` 打印 `tmux 3.4` | 无 | 小 |
| `display-message -p [-t] '#{pane_id}'`/`'#{window_id}'` | 输出 `%n`/`@n` | `terminal_list` 加一张 `%n`↔terminal id 的表 | 只实现这两个格式变量 | 小 |
| `list-panes -t W -F '#{pane_id}'` | 每行一个，**第一行必须是 leader** | `terminal_list` 过滤出本 tab | 顺序要稳定 | 小 |
| `split-window -d … -P -F '#{pane_id}' -- cat` | stdout 是新 pane 的 id | `terminal_layout` 会返回它做出的 pane；而普通分屏「不告诉你做了哪个」（`src/cli/mcp.zig:49-50`） | 要么每次都用 layout 重排整个 tab，要么新增「分屏并返回 id」的内部调用；`-d` 不能抢焦点；不要真的跑 `cat` | 中 |
| `respawn-pane -k -t P -- "<cmd>"` | 只看退出码 | 在新 pane 里起这串命令 | 最干净的是分屏时直接把命令当 pane 的 command（不过 shell 这一步）；退一步就等 shell 就绪后 `terminal_send` `exec sh -c '<cmd>'`，要处理转义和就绪时机 | 中 |
| `kill-pane -t P` | 只看退出码 | `terminal_action close_surface` 指向那个 pane。只禁止对自己执行（`src/poltergeist/actions.zig:112-114`），对别的终端可以 | 无 | 小 |
| `select-layout main-vertical` + `resize-pane -x 30%` | 只看退出码 | `terminal_layout`：左 30% 是 leader，右边一列 | layout 会不会重建已有 pane、打断正在跑的 teammate，要实测 | 中 |
| `set-option …`、`select-pane -T`、`show…` | 退出码 | 返回 0；`show` 返回 1 也行；`-T` 可以选做成 pane 标题 | 无 | 小 |

- 不需要实现：send-keys、capture-pane、new-session、has-session、new-window。它们只在外部会话模式和死代码里用。
- **总成本：中。** 估计 shim 加 `+tmux` 约 300–600 行，外加一个「分屏并返回 id、可以直接带 command」的内部入口（推断）。
- **Windows**：CC 的 tmux 后端在 Windows 上能不能走到，没有核。推断：先只做 mac。
- **要先实测的风险，按顺序**：
  1. 包成 `tmux;` 的 OSC 会丢；
  2. PATH 能不能在 shell 快照里活下来；
  3. layout 重排会不会打断已有的 teammate；
  4. teammate pane 要不要被 Polter 当成受监督的终端（`set_watch`、群）。第 4 条是产品决定，待用户定。

### B4. 优先级建议

- **价值**：CC 官方文档明写 Ghostty 不支持分屏，Polter 补上就是差异点；teammates 在 Polter 里还能直接被总管读屏。
- **限制**：agent teams 本身还是实验特性，默认是 in-process。
- **建议**：放在 A 的 P0（小）之后；先做一个只支持 mac、只覆盖上表的版本，并把「OSC 包装」那条风险先实测一遍再定。

   - **机制**：
     - 每次读 pty 后调一次 `Transcript.note`（`src/termio/Termio.zig:1168-1183`），**持着 `renderer_state.mutex`**（在 `processOutputLocked` 里，`:1086`）。

   - **估算（推断）**：
     - 空闲和 TUI 重画时几乎为 0：重画不产生滚出的行。
     - 最坏的是 `cat` 大文件：每秒滚出几十万行时，每行一次 JSON 编码加一次 pwrite 系统调用（量级是微秒），**每 250ms 一次、持锁做完**，期间渲染和输入都在等这把锁。
     - 按每行 2–5µs、每秒 50 万行算，每秒有 1–2.5 秒的工作量，会成为吞吐瓶颈，并带来周期性的卡顿。这个量级要实测，可能高估也可能低估。
     - 能缓解的办法（未实施）：把一批行攒成一次 `writev`/一次 pwrite；或者把编码和写盘挪到锁外。
   - **怎么测**：
     - 在 poltertest 实例里，配置 `poltergeist-terminal-log = true/false` 各跑 3 次：`time cat <1GB 固定文本>`，并用 `time seq 1 20000000`；
     - 同时用 `sample <pid>` 看 `Transcript.flush`/`pwrite` 的占比；
     - 再测一项交互延迟：输出期间按键回显的延迟。
     - 判据是两组的中位数之差，加上 sample 里转录的占比。
